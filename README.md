# ShitPM

## 🔥 一句话需求丢进去，全套评审材料自己长出来

**PRD、设计文档、可点击原型——一次全给你。**

你只管把业务讲人话，剩下的交给 AI。

## 😭 这几个瞬间，产品经理狠狠共情了

- 业务方甩来一句"做个报修系统"，你盯着空白文档坐了三天，光标一动没动。
- PRD 写完了，研发一句"这没写清楚"，你当场哑火。
- Design 改了一个字段，PRD 忘了改，原型也忘了改，评审会现场三份文档互相打架。
- 想让 AI 帮忙？它甩你一坨模板腔流水账，改它的稿比自己写还累。
- 原型另外找人画，评审会上才发现——页面少了一半。

**够了。这些事不该是你的日常。**

## 💡 ShitPM 不是模板，是一整条流水线

划重点：**它不是又一个 PRD 模板。**

它是一套让 AI 在**同一份产品事实基线**上帮你干活的工作流。

你跟 AI 聊需求 → 它产出对齐稿、设计基线、PRD、HTML 原型。

**所有下游文档都长在同一份你确认过的 Design 上。不会各说各话。**

## 🗺️ 流程长这样（真的就三步）

```text
                    [Align]  ← 必经，形成需求事实
                       │
                       ▼
                 [材料准备/复用]
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
       [简单模式]                 [完整模式]
          │                         │
  最小闭环分析 → 写作自审      A → B → C → 设计写作自审
          │                         │
          └────────────┬────────────┘
                       ▼
              [页面/区块/字段/操作]
                       │
               [用户确认 Design]  ← 你点头，才往下走
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
           [PRD]             [Prototype]
       （并列下游，想先要哪个要哪个）

旁路技能（按需喊）：Design Review、Fix、Prototype Mark
```

**三步走完：聊需求 → 确认 Design → 收文档。**

### 🎚️ 两种模式，按需求复杂度挑

| 对比项 | 简单模式 | 完整模式 |
| --- | --- | --- |
| 目标 | 搞定当前需求的最小产品闭环 | 完整分析 + 一致性挑战 |
| 内部分析 | 只分析真正需要的目标、范围、主路径、规则、状态、权限、页面、字段、异常、验收 | A 层需求理解 → B 层业务建模 → C 层产品承接 + 跨层挑战 |
| 最终文档 | 只留本次需求相关章节 | 保留完整方案结论，不暴露中间过程 |
| 页面表达 | 有页面就完整定义 | 系统覆盖页面/区块/字段/操作及角色、状态、场景差异 |

没指定？**AI 只问你一次，不自作主张升级降级。**

## 🎬 实战演示：三个场景，看完就会

### 场景一：从零做一个新功能

> 老板："小区要做报修系统，业主小程序报修，物业派单给维修工。"

**你只需要说这几句话：**

1. **"启动辅助器"** → AI 扫描项目状态，列出能干的活，顺带告诉你该用哪档模型
2. **"开始设计"** → Design 内部先做完 Align；没指定模式会问你一次。报修系统多角色 + 派单状态流转 + 权限，**闭眼选完整模式**。然后 A/B/C 基线、跨层挑战、写作，一路跑到 `output/design/design.md`
3. **"确认 Design"** → 你看完没问题，一句话搞定。AI 自动执行确认写入。
4. **"开始写 PRD"** / **"开始原型"** → 两个互不依赖，先要哪个要哪个，只要一个也行
5. **"PRD review"** → 想要第二意见就喊，不喊也没人逼你

**⏱️ 全程 60-90 分钟，一整套能上评审会的材料到手。**

### 场景二：改一个字段，全链路自动同步

> 评审会上研发发难："资产名称限制 50 还是 100？"

Design 里写 50，业务方要 100。这是**高影响修改**，必须回写 Design。

**你的操作：一句"同步修复"。**

AI 自动判断这是设计层修改 → 先改 `design.md` → 再按实际存在的下游同步 PRD 字段落点和原型输入框限制 → **旧确认哈希对不上，自动失效** → 提示你重新确认。

改按钮颜色、文案措辞这种**纯表现层**？AI 只动对应下游，不惊动 Design，也不用你重新确认。**分寸拿捏得死死的。**

### 场景三：AI 写的 PRD 居然不是流水账？

**因为 ShitPM 把"首次生成责任"直接压在 AI 头上。**

它不会先甩一版垃圾稿给你看。**正式写入前**必须自己过三关：

- 🔎 **语义对照** —— 列出 Design 的模块、页面、字段、状态、权限，逐项核对，一个字都不许超纲
- ✍️ **风格自检** —— 跑 `prd-style-lint.py`，专杀"点击按钮→填写表单→提交"这种动作流水账
- 🧩 **一致性校验** —— 跑 `prd-consistency-check.py`，PRD 字段和 Design 字段对不上直接拦

**三关全过才准写入。**

Design 里标"待确认"的高影响问题，PRD 不许偷偷拍板，必须原样暴露在正文和 `decision-notes.md` 里。

**结论：你不用去改 AI 的稿。它写之前自己就改好了。**

```powershell
python scripts/python/shitpm-host.py install --host codex
python scripts/python/shitpm-host.py install --host trae-cn
python scripts/python/shitpm-host.py install --host claude-code
python scripts/python/shitpm-host.py install --host workbuddy
```

**升级？** `git pull` 完事，自动生效——安装建的是 junction，指向仓库本体，代码一更新立刻同步。只有新增 skill 或改 host 配置目录才需要重跑 install。

**想验一下装没装好：**

```powershell
python scripts/python/shitpm-host.py verify --host <你的 host>
```

**不想用了：**

```powershell
python scripts/python/shitpm-host.py remove --host <你的 host>
```

细节看 [USAGE.md](USAGE.md)。

## 🔬 硬核区：背后是怎么做到的（选读）

> 只想用的可以直接关掉了，下面是给想扒原理的人看的。

### Design 是唯一产品事实源

字段、权限、状态、页面、区块、操作的产品语义，**只在确认后的 `output/design/design.md` 里定义**。

PRD 是研发评审视图，Prototype 是可视化视图。两者只能承接 Design，**没资格独立改写高影响语义**。

### Design 内部是依赖图，不是固定三段式

编排器根据材料版本、模式、产物、输入哈希、上游依赖，实时返回 `ready_actions[]`：

- **简单模式**：材料准备/复用 → 最小闭环分析 → 写作与生成内自审 → 确定性检查 → Design 索引
- **完整模式**：材料准备/复用 → A 层 → B 层 → C 层 → 设计写作与自审 → 三类成品检查并行 → 有限局部修复 → Design 索引
- 同批没硬依赖的动作**可以并行**；有效上游**不因下游失败重跑**
- `ready_actions[]` 是执行接口，不是产品事实——动作卡、运行状态、缓存**一律不许写进 Design 正文**

### 页面 → 区块 → 字段/操作，结构死死的

Design 不是研发规格表。正式页面定义长这样：

```markdown
### 页面：填写周报

- 页面目的：成员填写、暂存和提交本周周报。
- 适用角色：普通成员。
- 进入条件：用户已登录并属于有效团队。
- 数据范围：仅当前成员自己的周报。

#### 区块：基本信息

- 区块目的：展示周报归属周期和当前状态。

##### 字段：所属周

- 业务含义：本次周报归属的统计周期。
- 字段来源：系统根据当前日期生成。
- 展示条件：始终展示。
- 输入与编辑：只读，不可修改。
- 取值与默认：默认当前周。
- 交互方式：只读文本。
- 校验与反馈：无法确定当前周时禁止提交，并提示用户刷新后重试。

##### 操作：提交

- 适用角色：普通成员。
- 展示与可用条件：周报为草稿且必填内容完整。
- 二次确认：提交前询问是否确认。
- 成功结果：提交成功并记录提交时间。
- 数据与状态变化：周报从草稿变为已提交。
- 失败与恢复：保持草稿和当前输入，允许重新提交。
- 后续去向：返回周报列表并展示成功提示。
```

宽表可以做页面清单、权限速览、状态速览，**但替代不了正式定义**。产品正文不写数据库字段、接口结构、技术类型、缓存或编排实现。

### 首次生成责任，压在 AI 身上

首次正式写入前，生成 Skill 必须完成当前模式适用的分析 + 生成内自审 + 确定性检查。

完整模式按需求理解、业务建模、产品承接、跨层一致性、问题发现**五个维度**审查；简单模式只查最小闭环，**不为了凑量表生成废话**。

Review 是独立第二意见——不自动改 Design、不自动确认、不自动推进。高影响未决事项必须在 Design 正文显式标"待确认"，**不许藏进决策记录，也不许甩锅给下游**。

### 模型等级建议

每个动作开始前，AI 会按复杂度给建议：

- 🪶 **轻量模型**：业务简单、输入完整、关系明确、照模板展开
- 🧠 **深度推理模型**：方案权衡、跨模块关系、状态权限设计、复杂业务背景
- 🤷 **判断不了**：默认深度推理，**优先保住首次产物质量**

### Fix 双分支传播

| 修改类型 | 走哪条 | Design 确认失效吗 |
|---------|--------|--------------------|
| 字段 / 权限 / 状态 / 模块边界 / 跨系统责任 | 回写 Design → 同步下游 | ✅ 是，重新确认 |
| 纯文案 / 措辞 / 格式 / 视觉表达 | 只改对应下游 | ❌ 否 |

**判断不了影响范围？按高影响处理，先回写 Design。宁可多走一步。**

### 已经甩掉的历史包袱

主流程**不依赖** metadata、`status.json`、`stage-prep.py`：

- 新项目不用生成 metadata
- PRD 和 Prototype 直接读 `design.md`，不读 `.workflow/metadata/design/`
- Review 没 metadata 照样跑
- 旧项目留的 metadata 只做兼容诊断，**不算质量证明**

`stage-prep.py` 已标记旧版兼容，只给老项目参考，**不再是新流程的硬门禁**。
