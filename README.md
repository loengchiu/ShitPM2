# ShitPM

**一句话需求进去，完整 PRD + 设计文档 + 可交互原型出来。**

你只负责讲清楚业务，AI 帮你把想法变成可以直接拿去评审的全套文档。

---

## 你是不是也遇到过这些问题？

| 痛点 | 后果 |
|------|------|
| 业务方给了一句话需求，不知道从哪开始写 PRD | 拖了三天还在"理解需求" |
| 好不容易写完 PRD，研发说"没写清楚" | 来回返工，评审变辩论 |
| 改了 Design，PRD 和 Prototype 旧版本需要重新生成 | 文档之间互相矛盾 |
| 想用 AI 帮忙写，但输出总是"模板腔"、流水账 | 花更多时间改 AI 的稿子 |
| 原型要另外找人画，跟 PRD 对不上 | 评审会上才发现页面少了一半 |

**ShitPM 就是为了解决这些问题而生的。**

它不是又一个文档模板，而是一套**让 AI 在统一的产品事实基线上帮你写文档的工作流**。你跟 AI 聊需求，它帮你产出对齐稿、设计基线、PRD、HTML 原型——所有下游文档都基于同一份确认过的 Design，不会各说各话。

---

## 你能得到什么

完成一轮流程后，你的项目文件夹里会多出这些东西：

| 产物 | 是什么 | 给谁看 |
|------|--------|--------|
| 对齐稿 | 确认目标、范围、角色、边界的对话记录（可选） | 你自己、业务方 |
| 设计基线 | 模块、页面、字段、规则、权限的完整定义——**唯一产品事实源** | 你自己、UI 设计师 |
| PRD 文档 | 研发可直接评审的详细需求说明 | 研发、测试 |
| HTML 原型 | 可点击的页面原型，展示主流程和状态变化 | 评审会上所有人 |
| 标注原型 | 带关键点标记和备注弹窗的原型，展示规则和交互逻辑 | 研发、测试 |
| 审查报告 | 独立挑战结论，区分确定性问题、产品风险和待用户决策项 | 你自己 |

**最关键是：** PRD 和 Prototype 都直接来自同一份用户确认过的 Design。改了 Design 里的字段定义，PRD 和 Prototype 的旧确认自动失效，必须重新生成——不会出现"设计里有 8 个字段，PRD 里写了 6 个"这种事。

## ShitPM 流程长什么样

不再是"8 步线性走完"。ShitPM 是一棵以 Design 为根的树：用户从可用动作里按需挑，AI 不会强制推下一步。

```
                    [Align]  ← 可选，目标/范围/边界整理
                       │（如存在，作为 Design 的输入参考）
                       ▼
                   [Design]  ← 必须做，唯一产品事实基线
                       │
                       │  用户明确确认（写入 confirmation，仅记哈希）
                       ▼
              ┌────────┴────────┐
              ▼                 ▼
           [PRD]            [Prototype]  ← 双下游并列
        （任意顺序，             （任意顺序，
          可只选其一）             可只选其一）
              │                 │
              ▼                 ▼
        [PRD Review]    [Prototype Review]  ← 按需独立调用，不是门禁

  旁路动作（任何时候按需调用）：
    [Design Review]   独立挑战 Design 基线质量
    [Fix]             双分支传播：高影响回写 Design 并使旧确认失效；表现层只改下游
    [Prototype Mark]  给原型加标记和备注弹窗
```

**核心规则：**

| 规则 | 含义 |
|------|------|
| Align 可选 | 空项目可以直接进 Design，不强求先对齐 |
| Design 是唯一事实源 | 字段、权限、状态的完整定义只在 Design 里；PRD 和 Prototype 只能镜像，不能独立改写语义 |
| Design 必须用户确认 | 用户明确确认后才写入 `.workflow/confirmations/design.json`，只记版本哈希，不复制产品事实 |
| 双下游并列 | PRD 和 Prototype 都是 Design 的直接下游，任意顺序、任意子集，互不为前置 |
| Review 按需 | Review 是独立挑战和第二意见，不是门禁，不自动推进阶段，不自动修改产物 |
| Fix 双分支 | 高影响修改回写 Design 并使旧确认失效；纯表现层修改可以只改对应下游 |
| 模型等级建议 | 每个动作开始前 AI 会建议用哪种模型（轻量/深度推理）和推理深度 |

**Design 有两种模式，由你选：** `spm-design` 不替你决定用哪种。

- **简单模式**：只完成最小业务闭环——目标、范围、主路径、关键规则、必要状态/权限、功能/数据、异常和验收，不生成无关空章节、干系人地图或虚构状态机。适合需求清楚、范围小的项目。
- **完整模式**：在简单模式之上，额外承担完整分析——需求理解、业务建模（含业务模型一致性挑战）、系统需求与跨层一致性挑战。适合复杂业务或需要拿去严肃评审的项目。

> 需求理解、业务建模、系统需求这三层分析是 Design 生成时的**内部分析责任**，不是最终 `design.md` 的目录。无论哪种模式，你拿到的都是一份按业务闭环组织、适合人读的设计文档；中间分析过程不写进产物。

**每次启动后**，AI 会列出当前所有可用动作（`available_actions`），每个动作附带模型等级建议，你挑哪个就跑哪个。

## 实际使用示例

### 示例 1：从零开始做一个新功能

> 老板说："我们小区要做一个报修系统，业主能在小程序上报修，物业能派单给维修工。"

你的操作：

1. **启动：** 对 AI 说"启动辅助器"。AI 扫描项目状态，列出可用动作（Align、Design），并给出模型建议（比如 Design 建议深度推理模型）
2. **跳过 Align 直接 Design：** 需求已经够清楚，对 AI 说"开始设计"。如果没指定模式，AI 会问一次"本次用简单模式还是完整模式"——报修系统涉及多角色、派单状态流转和权限，建议选**完整模式**。选定后 AI 通读背景，完成 Design → PRD/Prototype 的语义对照和自检后写入 `output/design/design.md`，同时生成 `decision-notes.md`（记录设计决策、偏离、权衡、待确认，仅作审计）
3. **确认 Design：** 你看完设计没问题，直接对 AI 说"确认 Design"（或"这个 design 没问题了"）。AI 执行 `confirm-design` 动作，底层运行 `python scripts/python/design-confirmation.py --project-root . confirm` 写入确认。喜欢终端的话也可以自己手敲这条命令。
4. **并列生成 PRD 和 Prototype：**
   - 对 AI 说"开始写 PRD"——AI 校验 Design 确认有效，按 Design 展开成研发可评审的需求文档
   - 对 AI 说"开始原型"——AI 同样直接读 Design，生成可在浏览器打开的 HTML 原型
   - 两个动作互不依赖，可以先做哪个就先做哪个，也可以只做其中一个
5. **按需 Review：** 想要第二意见就说"PRD review"或"原型 review"。Review 不会强制你改，只输出问题清单

整个过程大概 30-60 分钟，你就能拿到一份**可以直接拿去评审会的全套文档**。

### 示例 2：改了一个字段，全链路同步（Fix 双分支传播）

> 评审会上研发说："资产名称这个字段，长度限制是 50 还是 100？"

你发现 Design 里写的是 50，但业务方说需要 100。这是**高影响修改**（涉及字段定义），必须回写 Design：

1. 对 AI 说"同步修复"，告诉它"资产名称字段长度改为 100"
2. AI 按传播矩阵判断这是设计层修改，先改 `output/design/design.md`，再按实际存在的下游分支同步更新 PRD 字段定义表和原型输入框限制
3. Design 一改，**旧确认自动失效**（哈希不一致）。AI 输出修复摘要，提示你重新确认 Design：
   ```
   python scripts/python/design-confirmation.py --project-root . confirm
   ```
4. 你重新确认后，按需重新生成受影响的下游

如果改的只是原型里某个按钮的颜色或文案措辞（**纯表现层**），AI 只改对应下游文件，不触发 Design 失效，也不用重新确认。

### 示例 3：AI 写的 PRD 不像流水账（首次生成责任 + 自检）

ShitPM 把"首次生成责任"压在生成 Skill 自己身上。AI 写 PRD 时不会先甩一版流水账给你看，而是在**首次正式写入前**完成：

1. **语义对照**：列出 Design 里的模块、页面、字段、状态、权限清单，逐项对照确认 PRD 表达不超出 Design 范围
2. **风格自检**：运行 `prd-style-lint.py` 扫"点击按钮→填写表单→提交"这种动作流水账写法
3. **一致性校验**：运行 `prd-consistency-check.py` 检查 PRD 字段和 Design 字段是否对齐

只有自检通过才正式写入 `output/prd/prd.md`。Design 里标"待确认"的高影响问题，PRD 不会静默拍板，必须原样暴露在 PRD 正文和 `output/prd/decision-notes.md` 里。

**你不需要手动去改 AI 的稿子**，它会在首次写入前自己改好。

## 怎么开始用

### 第一步：准备环境

你需要两样东西：

1. **Codex / Trae-CN / Claude Code / WorkBuddy 桌面应用**（你的 AI 助手运行环境，四选一即可）
2. **ShitPM 仓库**（包含 skills、scripts、templates 等）

不需要装任何开发工具，不需要写任何代码。Python 3.10+ 是脚本运行所需。

### 第二步：安装到你的 AI 助手

在 ShitPM 仓库根目录运行（任选一种 host）：

```powershell
python scripts/python/shitpm-host.py install --host codex
python scripts/python/shitpm-host.py install --host trae-cn
python scripts/python/shitpm-host.py install --host claude-code
python scripts/python/shitpm-host.py install --host workbuddy
```

这会在 host 的配置目录下建立 skills 映射和全局规则。

**升级：** `git pull` 拉最新代码后自动生效。安装建立的是 junction（指向仓库目录），仓库更新后 junction 自动指向新代码，无需重装。仅在新增 skill 或修改 host 配置目录时才需要重跑 `install`。

**校验：** 想确认安装是否正常：

```powershell
python scripts/python/shitpm-host.py verify --host <你的 host>
```

**卸载：** 不想用了：

```powershell
python scripts/python/shitpm-host.py remove --host <你的 host>
```

安装、升级、校验、卸载的详细说明见 [USAGE.md](USAGE.md)。

### 第三步：在你的项目里启动

切到你的项目文件夹（用来存放所有文档的地方），对 AI 说：

> "启动辅助器"

AI 会扫描 `output/` 下已有产物，列出当前所有可用动作和 Design 确认状态，并为每个动作附带模型等级建议。**新项目不会创建 `status.json`**，等你首次产出 Design 时才创建。

### 第四步：跟着 AI 走

每完成一个动作，AI 会刷新可用动作列表。你只需要：

- **跟 AI 聊你的需求**（Align 阶段，可选）
- **看 AI 生成的 Design，确认没问题就对它说"确认 Design"**
- **从 PRD 和 Prototype 里挑你想先生成的**（任意顺序、可只选其一）
- **想要第二意见就调用 Review**（按需，不是必须）
- **改了字段/权限/状态就让 AI 同步修复**（Fix 双分支传播）

不需要记住任何命令顺序。AI 会全程列出可用动作，你挑哪个就跑哪个。

## 一句话指令速查

你只需要记住这些自然语言指令，直接对 AI 说就行：

| 你说 | AI 做什么 |
|------|-----------|
| "启动辅助器" | 扫描当前状态，列出所有可用动作和模型建议 |
| "开始对齐" | 多轮对话整理目标/范围/边界（可选，可跳过） |
| "开始设计" | 生成 Design 基线和 decision-notes；先选简单/完整模式（未指定会问一次），**不自动确认** |
| "确认 Design" | 对 AI 说"确认 Design"即可，AI 执行 confirm 动作写入确认（也可自己手敲 `design-confirmation.py confirm`） |
| "设计 review" | 独立挑战 Design 质量，输出问题清单（不自动改） |
| "开始写 PRD" | 校验 Design 确认有效后，按 Design 展开成 PRD |
| "PRD review" | 独立挑战 PRD 质量（不自动改） |
| "开始原型" | 校验 Design 确认有效后，按 Design 生成 HTML 原型 |
| "原型 review" | 独立挑战原型完整性（不自动改） |
| "开始标注" | 给原型加标记和备注弹窗，方便研发看规则 |
| "同步修复" | 改了一处，按传播矩阵同步所有相关文档；Design 改动让旧确认失效 |

## 这套东西适合谁

**非常适合：**
- 手上有一堆零散需求，需要快速整理成可评审文档的产品经理
- 想用 AI 帮忙写 PRD，但试过几次发现 AI 写的东西"看着像那么回事，实际没法用"的团队
- 一份需求要出设计文档 + PRD + 原型，希望这三样东西保持一致的项目组
- 只想要 PRD 不想要原型、或只想要原型不想要 PRD 的项目（ShitPM 支持只生成其中一个）

**不太适合：**
- 需求已经非常清晰、只需要做微调的项目（直接改文档可能更快）
- 不使用 Codex / Trae-CN / Claude Code / WorkBuddy 作为 AI 协作工具的场景

## 背后原理（可选阅读）

> 以下是给想了解技术细节的人准备的，不影响使用。

### Design 是唯一事实源

字段、权限、状态的完整定义只在 `output/design/design.md` 里。PRD 是研发评审视图，Prototype 是可视化视图，两者都只能镜像 Design 的语义，不能独立改写。这样保证三份文档永远一致。

### Design 确认机制

用户明确确认 Design 后，系统在 `.workflow/confirmations/design.json` 里**只记录版本哈希**，不复制产品事实。一旦 Design 被修改，哈希自动不一致，旧确认失效，PRD 和 Prototype 都拒绝生成——必须用户重新确认才能继续。这避免了"确认过的内容悄悄变了没人知道"。

### 双下游并列

PRD 和 Prototype 都是 Design 的直接下游，互不为前置：

- 可以先生成 PRD，再生成 Prototype
- 可以先生成 Prototype，再生成 PRD
- 可以只生成 PRD，不生成 Prototype
- 可以只生成 Prototype，不生成 PRD

不存在"必须先有 PRD 才能做 Prototype"这种线性约束。

### 首次生成责任

生成 Skill 在**首次正式写入前**必须完成 Design 到下游的语义对照和自检。这意味着：

- PRD 不会先甩一版流水账给你看再让你改
- Prototype 不会先做一个错页面给你看再让你指出哪里错了
- 自检脚本（`prd-style-lint.py`、`prd-consistency-check.py`）在写入前就跑过

### V2 的 Design 质量标准

V2 把"Design 质量"作为首要目标，而不只是"能跑通流程"。完整模式产出的 `design.md` 要覆盖需求理解、业务建模、系统需求三层完整分析。

评审时按五个维度分别评级（L0 失效 → L3 完整可交付），总分不能抵消单个维度的严重缺口：

- **覆盖度**：适用事实、边界、异常、验收是否都到位；
- **关系解释**：关键对象、角色、状态、权限、数据之间是否互相解释、没有断链；
- **待确认暴露**：高影响未决事项是否显式标在 `design.md`，没有静默拍板或藏进 决策记录；
- **产品闭环**：是否形成了端到端可评审的业务闭环；
- **事实纪律**：没有引入 Design 未授权的高影响事实，没有用内部机制（稳定 ID、缓存、Worker）污染产物。

质量门槛和分级细则见 `references/design-quality-rubric.md`；生成前的分析责任协议见 `references/design-analysis-protocol.md`。

### 模型等级建议

每个动作开始前，AI 会基于任务复杂度给出模型建议：

- **轻量模型**：业务简单、输入完整、关系明确、主要按模板展开
- **深度推理模型**：涉及方案权衡、跨模块关系、状态权限设计、复杂业务背景
- **无法判断时**：默认深度推理模型，优先保护首次产物质量

实际建议会作为运行时输出展示给你，不只是背景说明。

### Fix 双分支传播

修改的影响范围决定走哪条分支：

| 修改类型 | 走哪条 | Design 确认是否失效 |
|---------|--------|--------------------|
| 字段/权限/状态/模块边界/跨系统责任 | 回写 Design → 同步下游 | 是，需重新确认 |
| 纯文案/措辞/格式/视觉表达 | 只改对应下游 | 否 |

无法判断影响范围时，按高影响处理，先回写 Design。

### 不再依赖 metadata 和 stage-prep.py

ShitPM 主流程**不依赖** metadata、`status.json`、`stage-prep.py`：

- 新项目无需生成 metadata
- PRD 和 Prototype 直接读 `design.md`，不读 `.workflow/metadata/design/`
- Review 不要求 metadata 存在也能执行
- 旧项目保留的 metadata 仅用于兼容诊断，不构成质量证明

`stage-prep.py`、`verify-against-metadata.py` 等脚本标记为旧版兼容，仅供旧项目兼容参考，不作为新流程硬门禁。
