---

> 本文件是 fix skill 的执行依据。
> ShitPM：Design 是唯一产品事实体系（多文件集合）；Fix 按用户指令连续完成 Design 修改与实际受影响下游的同步，无确认停顿。
> `output/verification/` 是 Design 的第三个下游。规则语义变化必须同步验证包，未更新不算 Fix 完成。

## 一、常见错误

| 级别 | 场景 | 识别信号 | 为什么错 | 首选修复 | 仍失败处理 |
|---|---|---|---|---|---|
| 失败处理 | 无法判断归属层 | 用户指令模糊，可能是需求问题也可能是设计问题 | 归属层判断错，传播方向就错，可能在错误层制造事实 | 按事实闭包定位：问题位置到正式 Design 文件 | 停在具体业务问题，输出当前判断和缺失信息，不直接改下游 |
| 失败处理 | 传播遗漏 | 改了 Design 但忘了同步实际存在的 PRD / Prototype | 下游仍承接旧事实，评审时口径不一 | 按设计集清单和 provenance 计算受影响下游并同步 | 运行 prd-consistency-check.py / prototype-consistency-check.py 检查一致性 |
| 失败处理 | 逆向定源 | PRD 直接改了 design 的语义 | 下游反向覆盖破坏唯一事实体系，后续每层继承错误事实 | 识别到语义变更后，先回写正式 Design 文件 | 若已误改 PRD，恢复 PRD 改动，先修 Design |
| 失败处理 | fix 改了不该改的内容 | 表现层问题被误判为语义问题 | 表现问题按语义传播会无谓触发下游同步 | 重新归类：表现问题只改 prototype，语义问题才回 Design | 若已误改，按传播方向表反向恢复 |
| 失败处理 | 上游缺失导致下游无法修复 | Design 中缺少字段定义 | 下游没有事实可承接，硬补会造出 Design 未授权字段 | 先在 Design 对应文件补字段定义 | 若字段来源不明，标记未决并询问具体业务问题 |
| 失败处理 | 多版本并存 | fix 覆盖后旧版本未清理 | 评审和下游无法确定哪份是当前真相 | 确认每阶段只有一份当前稿 | 删除 output/ 下的旧版本文件 |
| 失败处理 | 把下游内容提升为事实源 | PRD 或 Prototype 反向覆盖 Design | 未经确认的意见反向覆盖唯一事实体系 | 拒绝下游反向覆盖；以下游反馈为由先回写 Design | 若已误改，恢复 Design 原文，按传播方向重新同步 |
| 反模式 | **跳过影响分析直接改下游** | 出现该做法 | 可能遗漏受影响阶段，或改错归属层 | 必须先从问题位置定位事实归属 | — |
| 反模式 | **fix 时整篇重写** | 出现该做法 | 破坏当前真相原则，引入不必要的变更 | 只改必要内容，覆盖式更新 | — |
| 反模式 | **PRD 直接改 design 语义** | 出现该做法 | 违反逆向定源禁令 | 先停，说明问题，由用户确认后回写 Design | — |
| 反模式 | **修改 Design 后停止等待重新确认** | 出现该做法 | 旧确认机制已删除；用户指令明确时 fix 应连续完成 | 按用户指令连续修改 Design 和所有受影响的现有下游 | — |
| 反模式 | **自动创建不存在的下游** | 出现该做法 | 只有实际存在的下游才同步 | 只同步实际存在的 PRD / Prototype 模块 | — |
| 反模式 | **自动确认或要求确认哈希** | 出现该做法 | 确认动作已从运行路径删除 | 高影响未知只询问具体业务问题 | — |

## 二、传播方向

ShitPM 新时序：定位问题类型到找到正式事实归属到修改 Design到计算受影响下游到同步所有实际存在且受影响的 PRD / Prototype 模块到运行针对性检查到更新下游依据。用户指令明确时一次 fix 连续完成，无确认停顿。

| 修改发起层 | 事实源 | Fix 阶段传播方向 | 下游处理 |
|---|---|---|---|
| 对齐 | 设计（align 仅作输入参考） | align 到目标 Design 文件（回写事实源） | 同步实际存在且受影响的现有下游 |
| 设计（高影响） | 设计 | 修改唯一事实归属，同步受影响下游 | 同步实际存在且受影响的 PRD / Prototype 模块 |
| 设计（纯组织变化） | 设计 | 只更新 ID/路径/指纹依据，不改语义 | 下游保持 current，不重新生成 |
| PRD 发现设计有误 | 设计 | 先回写 Design，再同步 PRD | 只同步 PRD（Prototype 是否受影响按依据判断） |
| 原型语义反馈 | 设计 | 先回写 Design，再同步 Prototype | 只同步 Prototype（PRD 是否受影响按依据判断） |
| 原型表现反馈 | 原型 | 只改原型，不回写 Design | 无下游处理 |
| 纯格式/措辞/排版 | 对应下游 | 只改对应下游，不回写 Design | 无下游处理 |
| Design 未变、下游错误 | 下游 | 只修错误下游 | 不修改 Design 和另一份下游 |
| 外部未知修改 | Design | 当前任务触达时标记相关下游 affected | 不自动改写下游 |
| 设计规则语义变化 | 设计 | 修改 Design 后同步 `output/verification/` 受影响验证包，再同步 PRD / Prototype | 受影响条目标记 `stale`，同步 PRD `4.x.9` 引用的规则 ID |

## 三、传播原则

1. 只改必要内容，不整篇重写
2. 覆盖式更新（当前真相原则），不制造多版本并存
3. 不允许逆向定源（PRD/Prototype 不能直接改 design 的语义）
4. 若无法判断归属层，先停在澄清，不得直接改下游
5. 无法判断影响范围时，按高影响变化处理
6. **只同步实际存在的下游**：只有 PRD 只同步 PRD；只有 Prototype 只同步 Prototype；两者都存在同步所有实际受影响模块；两者都不存在只修 Design
7. **不自动创建下游**：PRD 或 Prototype 不存在时不创建
8. **Design 修改走事务**：单文件用 design-set.py stage-single/commit-single；多文件用 begin/commit；中断用 recover
9. 纯组织变化（文件移动/拆分/排版）更新指纹和依据，下游保持 current
10. **Align 不是事实源**：目标/范围/建设方式的事实源是 Design 集合；align.md 仅作为输入参考
11. 高影响未知只询问具体业务问题（如"库存不足时是否允许部分扣减"），不询问确认 Design
12. **验证包是 Design 下游**：规则语义变化必须更新 `output/verification/` 中受影响的验证包，未更新不算 Fix 完成；纯组织变化（文件移动、拆分、排版、措辞）不产生 `stale`
13. **`stale` 必须可读**：标记时说明是规则本身变了还是预期来源变了；`stale` 条目在重新验证前不得作为有效证据
14. **不伪造独立来源**：不得用 `ai_inference` 预期来源冒充 `contract`、`historical_data`、`independent_calculation`、`system_behavior` 或 `human_confirmation`
15. **改名称不引入新约束**：修改页面名、区块名、按钮文案、字段名或状态名时，只做同名收敛、简化或按当前有效材料口径校正，不把适用条件、实现形态、方案代号或判定规则并入名称；需要表达条件的写入属性行、条件列或正文。命名规则见 [设计写法参考](../references/design-writing.md) 命名规范

## 四、Design 变化后的处理流程

ShitPM：不再有"确认 Design"或哈希确认。下游依据（provenance）记录每个业务模块实际读取的 Design 文件 ID 和指纹。

0. **在 Design 集合内部做影响面枚举**（修改对象是 Design 语义变化时必做，先于任何写操作）：约束化、类别差集、三维影响表、回读四步见
   [业务闭环规则](../references/design-business-closure.md) 的 Fix propagation 定义。要点：
   - 把每个问题改写成**业务约束**，不是"把某一句改成某一句"；
   - **先做约束类别差集**：把约束归入类别（角色与可见性、状态与迁移、动作与前置条件、数据范围、规则与来源、异常与恢复、结果与去向等），对照关系维度清单确认是否有整类约束从未进入过核对面；类别缺口与同类下的实例缺口分别记录；
   - 建立"**业务约束 × 承载面 × 对象（含细分类型）**"三维影响表；承载面清单与"承载面不等于文件"的枚举要点见 [业务闭环规则](../references/design-business-closure.md) 3.4，本文件不重复枚举，避免两处漂移；
   - 检查整页、整列属性或整组字段是否缺失；搜索字面变体、统称下的细分类型、同类型对象和兄弟页面，但**只修改确认受影响的位置**；
   - 修改后**逐位置回读**，并检查新句与既有规则的冲突。

1. **用户明确说明改什么、改成什么**：
   - 定位唯一事实归属，修改对应 Design 文件（单文件或多文件事务）
   - 计算受影响下游，同步所有实际存在且受影响的 PRD / Prototype 模块；规则语义变化时同步 `output/verification/` 中受影响的验证包
   - 运行针对性检查，更新下游依据（status=current, check_status=passed, 清空 affected_by）

2. **Design 没变、下游不一致**：
   - 只修错误下游，不修改 Design 和另一份下游

3. **外部未知修改（非当前任务造成）**：
   - 当前任务触达时用 design-set.py check-inputs 检查，标记相关下游 affected
   - 不自动传播、不自动改写下游

4. **纯组织变化（文件移动、拆分、排版、措辞）**：
   - 更新设计集清单中的 ID、路径、指纹和依据
   - 下游保持 current，不重新生成

5. **针对性检查失败时**：
   - 保留 affected 或 incomplete 状态，不得伪装通过
   - 修复后重新检查，通过后更新依据并消除受影响状态

## 五、修复完成后的 review 建议

fix 完成覆盖后，必须输出：

~~~text
建议进入 [阶段] review，检查对象：[对象列表]
已同步下游：[PRD/Prototype 模块列表]（如适用）
已同步验证包：[业务闭环名]（如适用）
~~~

不自动执行 review，由用户手动确认后触发。

**宣称与实际对照**：在后续 Review 中逐问题输出"上一轮宣称修改位置 ↔ 当前正文实际内容"。修复声明与正文不一致是覆盖失败的强信号，不得用"已修改"概括。
