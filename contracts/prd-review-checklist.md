# PRD Review 检查项

> 本文件只定义 PRD 专项审查责任。通用结论、问题分级、输出格式、独立性和停止规则见 `review-checklist.md`。
> Review 只输出第二意见，不修改 PRD、Design 或决策记录，不自动推进。
> 先审最后一个业务模块，再向前审查。每个模块先做读者任务试读，再查 Design 一致性。

## 1. 读者任务试读

Review 不按章节名称逐项打勾，而是给真实读者任务。任务试读期间只读当前 PRD 模块，不查 Design、Prototype、旧 PRD 或其他模块。

### 1.1 后端任务

每个对象单元出 2 至 3 个任务，覆盖：

- 对象从哪个业务事件开始，在哪个状态或结果结束。
- 触发某次状态迁移需要什么角色、条件、输入和写入对象。
- 失败、并发、重复提交或外部数据变化后，对象保留什么，下一次由谁处理。

完成条件：不看对象单元以外的章节，也能说出起点、推进、写入、失败保留和终态。

### 1.2 前端任务

每个页面出 2 至 3 个任务，覆盖：

- 当前角色在什么前提进入页面，要完成什么判断。
- 某次操作允许的状态、输入、校验、成功反馈和失败保留。
- 操作后哪些字段、状态、列表或按钮刷新，页面去向是什么。

完成条件：不查 Prototype，也能确定区块、字段、操作、反馈和结果去向。

### 1.3 测试任务

每个对象出 2 至 3 个任务，覆盖正常场景、权限或状态边界、金额或时间边界。

完成条件：验收场景能直接取得输入、预期输出和精度，不写规则 ID，也不需要打开验证包。

### 1.4 跨对象任务

存在跨对象异常时，给出部分成功、并发或恢复任务。

完成条件：能确定受影响对象、失败时共同保持的状态、恢复责任和最终结果。

### 1.5 试读记录

每个任务记录：

- 使用的题目。
- 访问过的标题顺序。
- 相邻标题切换次数。
- 是否答错。
- 是否提出追问。
- 被迫猜测的条件。
- 答案是否能唯一落到实现或测试。

任务无答案、答案依赖未声明假设、必须追问或出现两种合理解释时，记 P1；只增加重复阅读但不改变事实时，记 P2。

## 2. 单一归属抽查

每个对象至少抽三条事实：

1. 一条状态迁移。
2. 一条公式、阈值或口径。
3. 一条失败、异常或并发处理。

在当前模块全文检索每条事实，记录所有出现位置。允许一处完整定义，其他位置只能出现对象名、状态名、入口、页面反馈或结果去向。

以下任一情况记 P1：

- 两个位置都写完整规则且口径相同，形成重复维护。
- 两个位置口径不同。
- 页面功能重新解释对象规则或计算过程。
- 共用规则和对象规则保存同一公式、阈值或例子。
- 同一组数值在对象规则和验收场景重复出现。

## 3. 结构与读者价值

| 检查项 | 判定 | 默认级别 |
|---|---|---:|
| 模块结构完整 | 模块概览、对象单元、共用规则、页面功能、跨对象异常按实际适用建立，标题可定位 | P1 |
| 空章节 | 没有内容的共用规则、待确认、跨对象异常仍保留标题 | P1 |
| 对象槽位 | 对象单元未按适用性使用业务过程、状态迁移、对象规则、异常与边界、验收场景、待确认六个稳定槽位，或另起同义章节 | P1 |
| 表格边界 | 只出现状态迁移表、字段表、角色能力矩阵和验收场景表 | P2 |
| 验收场景 | 四列为场景、输入、预期输出、精度或判定；无规则 ID、验证包位置或追溯说明 | P1 |
| 页面标注 | 页面或区块标题带“所属对象”“只读承接”等内部标注 | P2 |
| 过程说明 | 正文出现“本节不重复”“本试点”“后续补验证”“对应规则 ID”“见待确认事项”等作者说明 | P2 |
| 重复数值 | 同一组输入和预期在多个位置重复 | P2 |
| 空泛内容 | 出现“待补充”“待定”“按配置”“按规则处理”等掩盖未知的表述 | P1 |
| 事实来源 | PRD 依赖 Design、Prototype、旧 PRD 或验证包才能理解 | P1 |

每个结构问题必须附具体标题或段落，不接受“整体不清”这类概括。

## 4. 内容完整性

### 4.1 模块和对象

- 功能概述只写模块对象、起点、角色和最终结果。
- 对象关系能说明对象之间的真实关系、生命周期边界和跨对象结果。
- 页面清单只写页面名称、终端、任务和结果去向，不复述后续区块。
- 业务过程连续写起点、生成、提交、审核、确认、退回、失败恢复、终态和重新打开条件。
- 状态迁移表覆盖角色、条件、下一状态和失败保留。
- 对象规则写公式、口径、快照、重算、优先级和刷新范围。
- 异常与边界写并发、重复提交、部分失败、外部失败、边界和恢复。
- 待确认写问题、方案、后果和当前保守行为。

缺少会让后端产生两种以上合理实现的事实，记 P1。

### 4.2 页面功能

- 页面名称采用 Design 原名。
- 页面任务说明进入前提、核心判断和结果去向。
- 区块写影响操作判断的字段和展示条件。
- 动作写角色、允许状态、输入、校验、写入对象、成功反馈、失败保留和下一去向。
- 字段表只承载字段属性，不压入公式、主流程和异常恢复。
- 状态变化后需要刷新的字段、状态标签、按钮、列表和页面去向可判断。

前端需要自行补页面行为、权限、失败结果或下一去向时，记 P1。

### 4.3 数据与验收

- 指标、统计、金额、周期结算写清业务含义、来源、组织范围、时间边界、纳入排除、公式、精度、尾差、刷新和异常兜底。
- 名称相同的指标保持同一口径。
- 验收场景的输入和预期可直接复算。
- 复杂计算至少有一个正常例和一个边界例。
- 作者可用 `output/verification/` 核对预期，但 PRD 不写规则 ID。验证包缺失不自动构成 PRD 缺陷；PRD 缺少可执行预期才构成缺陷。
- 两种以上计算结果都合理时，记 P1；不影响业务结果的纯展示格式差异记 P2。

### 4.4 Design 一致性

Review 在任务试读完成后读取该模块实际 Design 依据，逐项检查：

- 目标、范围、系统边界和排除项未改变。
- 页面、字段、角色、权限、状态、枚举和流程未新增或改写。
- Design 的高影响待确认事项仍保留为未决。
- 变更传播到对象规则、页面操作、状态、权限和验收场景后口径一致。
- Design 自身错误使 PRD 无法成立时，输出上游同步建议，不代写 Design。

未授权新增或冲突记 P1，并写 `affected_objects` 或 `needs_upstream_sync`。

## 5. 确定性检查

按顺序运行：

~~~text
python $BUNDLE/scripts/python/prd-style-lint.py output/prd/prd.md
python $BUNDLE/scripts/python/prd-consistency-check.py --project-root . --module <模块名>
~~~

处理要求：

- lint 返回 1 时修复；warning 和 info 逐项判断。
- consistency 的 `deterministic_conflict` 返回 1 时阻断。
- `possible_omission` 和 `needs_semantic_judgment` 逐条给结论，不默认通过。
- 无法提取或无法判断时写“未评估”。
- 脚本通过不代替任务试读，脚本失败也不替代原文定位。

流程图的触发、`.drawio`、PNG、嵌入路径和图中事实另做确定性核对。命中流程图条件却没有图，或图中事实与正文不一致，记 P1。

## 6. 输出

按公共契约写入 `.workflow/reviews/prd-review-N.md`。至少包含：

- 审查模块和 Design 依据。
- 每个读者任务的题目、访问标题、切换次数、答错、追问和猜测。
- 每个对象的单一归属抽查记录。
- 文本问题、确定性检查结果和 Design 一致性问题。
- 每条问题的位置、影响、建议和 P0/P1/P2。
- 未评估范围。

Review 结论不改变 Design 修改状态，不自动推进阶段，也不能替代研发试读或宣布 PRD 零缺陷。
