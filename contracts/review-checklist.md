# Review 公共执行契约

> 本文件只定义所有 Review 共用的执行、阻塞、判定和输出契约；具体 Design、PRD、Prototype 检查项分别见三个专项检查清单。

## 常见错误

| 级别 | 场景 | 识别信号 | 为什么错 | 首选修复 | 仍失败处理 |
|---|---|---|---|---|---|
| 失败处理 | 预检查报告目标不可读 | 路径编码不一致（大小写/中文路径）或文件确实缺失 | 预检查是 Review 启动前提，目标不可读时继续审查等于对不存在的内容下结论 | 检查文件名大小写，修正路径 | 直接检查目标文件路径、编码和可读性 |
| 失败处理 | 检查项数过多导致审查者疲劳 | 一次性输出全部检查项 | 全部检查项平铺会让重点被淹没，后半段审查质量下降 | 先输出 P0/P1 检查项，P2 可选输出 | 若 P0 已阻塞，明确标注不再展开 P2 |
| 失败处理 | 字段名模糊匹配误判 | design 与 PRD 字段名不完全一致 | 按 PRD 自造名称判定会造成假冲突或漏判真实差异 | 以 Design 正式文件原文字段名为准，修正 PRD | 若无法判断，标记 [待确认] 回退 PM |
| 失败处理 | 非页面落点字段占比异常高 | 过多字段被归入例外表 | 例外表异常膨胀说明页面落点可能缺失，字段被错误隐藏 | 逐一检查是否有字段实际应分配到页面 | 若确认为合理内部字段，在例外表注明原因 |
| 失败处理 | Review 结论三档无法区分 | 既有 P0 又有 P1 | 三档不互斥时结论失去可执行性，PM 无法判断是否放行 | 按 §四 "统一判定与输出契约"的三档门槛判定，不以 max(severity) 简化定级 | 若 P0 可快速修复（少于 5 分钟），建议修复后重新给出审查结论 |
| 失败处理 | PRD 字段定义表缺少 design 中的实体 | PRD 只覆盖部分实体 | PRD 未承接 Design 实体，研发会漏做功能或自行补事实 | 按所属业务对象或业务阶段就近补充准确落点 | 若实体已废弃，先从 design 中移除再同步 |
| 失败处理 | 把下游内容误当事实源 | PRD 或 Prototype 与 Design 冲突时 | 以下游为准会让唯一事实基线失效，冲突被固化进产物 | 以 Design 集合为唯一事实体系；下游必须让位 | 若需提升下游意见，先经 spm-fix 回写 Design |
| 反模式 | **把预检查当门禁** | 出现该做法 | ShitPM：预检查仅在目标文件不存在/不可读/无法解析时阻止执行；章节缺失、内容不足是 Review 审查问题，不是阻塞 | 缺章节、结构不足应作为 Review 结论输出，不阻止 Review 开始 | — |
| 反模式 | **把审查者写成生成者** | 出现该做法 | 审查者职责是判断质量，不是代写正文 | 只输出审查结论和 `issues`，不输出修改后的文档 | — |
| 反模式 | **用建议代替审查结论** | 出现该做法 | 建议关注不阻塞下游，PM 可能忽略 | 正式审查结论只用三档：通过 / 有问题需修改 / 阻塞 | — |
| 反模式 | **只查结构不查语义** | 出现该做法 | 章节完整不等于内容正确 | 结构检查可用确定性脚本或人工核对，语义检查必须由人审完成 | — |
| 反模式 | **一次性输出全部检查项** | 出现该做法 | PM 看不完，重点被淹没 | 先输出 P0/P1，P2 可选输出 | — |
| 反模式 | **review 通过后自动推进阶段** | 出现该做法 | 违反 review 不自动推进原则 | 通过后输出建议，由 PM 手动触发下一步 | — |
| 反模式 | **忽略 alias 假阳性** | 出现该做法 | 章节名使用别名时可能出现结构识别偏差 | 人工核对章节是否真实存在 | — |
| 反模式 | **把 metadata 当成 Review 前置** | 出现该做法 | ShitPM 不要求 metadata 存在 | 即使无 metadata 也可执行 Review，结构完整性由人工或现有确定性检查判断 | — |
| 反模式 | **把下游内容提升为事实源** | 出现该做法 | Design 是唯一事实源 | 下游冲突按 Design 修正下游，或经 Fix 回写 Design | — |
| 反模式 | **承担计划内补全** | 出现该做法 | Review 是独立挑战，不补生成 | 计划内缺口由对应生成 Skill 负责；Review 只输出问题 | — |
| 反模式 | **把一致性校验当门禁** | 出现该做法 | ShitPM：一致性校验是 Review 审查问题，不是阻塞门禁 | 一致性问题作为审查结论依据，不阻止 Review 进行 | — |
## CHECKPOINT - review 开始前

先确认目标文件存在、可读且可解析；缺章节、结构不足、metadata 缺失和正文质量问题应作为 Review 审查问题返回，不阻止 Review 开始。
Review 不要求 metadata 存在，不要求先通过其他 Review。
## CHECKPOINT - review 结束前

输出审查结论后，检查：
1. 是否有 P0 未修 -> 审查结论必须为“阻塞”
2. 是否需要回上游 -> 输出 needs_upstream_sync: true + affected_objects
3. 是否区分了确定性问题、产品风险和待用户决策问题

> ShitPM：`next_recommended` 可选输出，不再线性推进；审查者可不填或填 `null`，PM 根据 `available_actions` 自行决定下一步。

---
## 四、统一判定与输出契约

### 审查结论门槛

- **通过**：零 P0、零 P1。
- **有问题需修改**：零 P0，且有 1 个 P1。
- **阻塞**：存在 P0 或至少 2 个 P1。
- P2 写入 `issues`，但不计入审查结论；P0 优先停止展开低优先级 P2。

### 结果结构

审查结果只输出人读 `.md` 文件，不生成机读 JSON：

- `.workflow/reviews/design-review-N.md`
- `.workflow/reviews/prd-review-N.md`
- `.workflow/reviews/prototype-review-N.md`

每条审查问题至少包含编号、严重级别（P0/P1/P2）、描述，可附位置和建议；正文必须包含审查结论（通过 / 有问题需修改 / 阻塞）、主要问题、三类问题分布（structure / content / consistency）、`needs_upstream_sync`、`affected_objects` 和下一步建议。P2 记录但不计入审查结论。

### 共同禁止事项

- 不运行 `stage-prep.py` 生成 metadata，不把 metadata 当 Review 前置。
- 不自动调用 `spm-fix`，只输出 `needs_upstream_sync` 建议。
- 不自动推进阶段，不把 Review 通过当成 Design confirmation。
- 输入缺失、不可读或无法解析才硬阻塞；章节缺失、内容不足、一致性问题和质量问题必须作为审查问题返回。
