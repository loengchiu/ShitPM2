# Review 检查项清单

> 本文件是 reviewer skill 的执行依据，不是 writer 的写作指导。
> 检查项引用规约 §3.4 和 §7.2。

## 失败模式速查表

| 场景 | 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|---|
| precheck 阻塞但产物实际存在 | 路径编码不一致（大小写/中文路径） | 检查文件名大小写，修正路径 | 手动运行 review-precheck.py 查看 blocking_issues 详情 |
| 检查项数过多导致 reviewer 疲劳 | 一次性输出全部检查项 | 先跑 Phase A 结构完整性，通过后再跑 Phase B | 若 Phase A 已有 P0，不进入 Phase B |
| 字段名模糊匹配误判 | design 与 PRD 字段名不完全一致 | 以 design.md 原文字段名为准，修正 PRD | 若无法判断，标记 [待确认] 回退 PM |
| 非页面落点字段占比异常高 | 过多字段被归入例外表 | 逐一检查是否有字段实际应分配到页面 | 若确认为合理内部字段，在例外表注明原因 |
| review 结论三档无法区分 | 既有 P0 又有 P1 | verdict = max(severity)，P0 -> 阻塞 | 若 P0 可快速修（<5min），建议修后再出 verdict |
| stable ID 泄漏到正文 | design.md / prd.md 出现 FIELD-design-001 | 全文搜索并删除 ID 引用 | 确认 stage-prep.py 未将 ID 写入正文模板 |
| metadata 与正文数量不一致 | 字段数/页面数/模块数对比偏差 | 运行 stage-prep.py --stage design 重新生成 | 若重新生成仍不一致，检查 design.md 表格格式 |
| PRD 数据字典缺少 design 中的实体 | PRD 只覆盖部分实体 | 按 design 实体清单逐个补入 PRD 数据字典 | 若实体已废弃，先从 design 中移除再同步 |

## 反例黑名单（不要做的事）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | **跳过 precheck 直接人审** | 产物不存在或章节缺失时人审无意义 | 必须先跑 review-precheck.py，can_start_review=true 才开始 |
| 2 | **把 reviewer 写成 writer** | reviewer 职责是判断质量，不是代写正文 | 只输出 verdict + issues，不输出修改后的文档 |
| 3 | **用建议代替 verdict** | 建议关注不阻塞下游，PM 可能忽略 | 正式 verdict 只用三档：通过 / 有问题需修改 / 阻塞 |
| 4 | **只查结构不查语义** | 章节完整不等于内容正确 | 结构检查用 precheck，语义检查用人审，两者缺一不可 |
| 5 | **一次性输出全部检查项** | PM 看不完，重点被淹没 | 先输出 P0/P1，P2 可选输出 |
| 6 | **review 通过后自动推进阶段** | 违反 review 不自动推进原则 | 通过后输出建议进入下一阶段，由 PM 手动触发 |
| 7 | **忽略 alias 假阳性** | 章节名用别名时 precheck 可能误报缺失 | 检查 alias_missed_count，>0 时人工确认 |
| 8 | **metadata 不存在就判定阻塞** | design 阶段 metadata 在 review 通过后才生成 | design review 用 --no-metadata 模式，第三段再生成 |

## CHECKPOINT - review 开始前

运行 review-precheck.py --stage <stage> 并确认 can_start_review: true。
若 blocking_issues 非空，先回上游补结构，不进入人审。

## CHECKPOINT - review 结束前

输出 verdict 后，检查：
1. 是否有 P0 未修 -> verdict 必须为 阻塞
2. 是否需要回上游 -> 输出 needs_upstream_sync: true + affected_objects
3. PM 是否能看到下一步建议 -> 输出 next_recommended

## 一、design review 检查项

### Phase A：人读质量（review 时检查）

#### 结构完整性

1. 核心章节是否全部存在（角色定义、模块定义、页面清单、字段定义、规则与状态定义、权限定义）
2. 辅助章节是否存在（可选，不强制）
3. 关键表格仍为结构化格式（字段定义、页面落点、状态流转、权限矩阵使用 Markdown 表格，列名符合模板约定）

#### 内容质量

4. 字段定义属性是否齐全（9 属性：名称、类型、长度、必填、默认值、枚举值、格式、业务来源、说明）
5. 权限定义是否覆盖到字段级
6. 权限是否按“页面 > 角色 > 字段权限例外”组织
7. 状态定义是否覆盖完整
8. 是否存在“页面与字段落点”章节，且按页面组织字段落点

#### 一致性（不依赖 metadata）

9. 数据字典中的每个业务字段是否在“页面与字段落点”中出现至少一次
10. “页面与字段落点”中是否引用了数据字典未定义的字段
11. 纯内部字段是否进入“非页面落点字段”例外表并写明原因，而不是静默遗漏
12. “非页面落点字段”中是否混入了本应落页面的可见/可编辑/可筛选字段
13. 页面清单中的页面是否全部出现在“页面与字段落点”中
14. 不新增 align 未确认的范围
15. 状态定义是否包含流转速览 + 状态明细表（进入/退出条件）+ 逐条迁移规则（触发角色、前置条件、是否可逆）
16. 涉及多角色或 3+ 步骤的业务流程是否按阶段展开，关键分支是否写具体判断条件，异常路径是否覆盖

### Phase B：metadata 一致性（stage-prep.py 生成后自动校验）

> 以下检查项由 design review 第三段自动执行，不需要人工判断。

17. metadata/design 与 design.md 字段/页面/模块数量一致
18. page-fields 覆盖率：所有页面清单中的页面是否出现在 page-fields.json
19. non-page-fields 覆盖率：非页面落点字段是否合理（不超过总字段 40%）
20. 字段约束一致性（prd 生成阶段已用 verify-against-metadata.py 基于 fields.json 自检，review 时抽查）
21. 稳定 ID 是否正确生成（6 种前缀）
22. design.md 正文中无稳定 ID 泄漏

## 二、PRD review 检查项

### 坏味道检查（引用规约 §7.2）

1. 是否为标签式正文（`**页面目标：**`、`**关键动作：**`、`**状态变化：**`、`**异常提示：**`）
2. 是否为动作流水账（只按点击顺序描述动作过程）
3. 是否为纯表格式页面正文
4. 是否过多加粗
5. 是否有模板腔（"用于承载""用于支撑""需支持""同常规"）
6. 是否有模糊表述（"按配置"、"按规范"、"同常规"、"待补充"、"详见原型"、"待定"、"按业务规则"）
7. 是否出现原因腔（"方便用户理解""避免用户误判""符合操作习惯"）

### 三层覆盖检查

8. 每个页面是否覆盖界面元素与展示规则
9. 每个页面是否覆盖交互逻辑与状态流转
10. 每个页面是否覆盖异常处理与边界场景

### 写作质量检查

11. Markdown 标题层级是否稳定，中文编号前缀是否仅增强结构感且未跳级
12. 详细需求说明是否按模块 → 页面 → 动作组织，而不是按页面平铺整章
13. 模块开头是否先用 1-2 句话说明模块职责和涉及页面
14. 页面内部是否按用户动作组织（动词短语），并使用 `（1）/（2）/（3）` 等顺序标识形成动作分块，非 UI 区域盘点
15. 页面开头可用一段交代区域职责，但后文不得退回按区域逐项说明
16. 每个动作是否覆盖触发、过程、结果、异常四类信息，但不套用固定四段格式
17. 简单动作是否一段话带过，复杂动作是否按复杂度展开
18. 有顺序的流程是否用 `1. 2. 3.`，并列规则是否用 `·`
19. 业务流程是否只写整体业务对象流转、角色处理、关键分支和结果约束，并在需要时提供整体流程图，未混入页面跳转、按钮点击、抽屉/弹窗开合等页面操作细节
20. 列表、表单、详情中的字段描述是否只保留当前动作需要的关键字段、展示方式和规则，未把数据字典完整字段清单原样搬进页面正文
21. 动作开头是否优先写业务判断、关键状态和用户首先关心的信息，而不是先写排序、分页、默认加载等低优先级通用规则
22. 所有数值是否写死具体数字，无占位符（"按配置""N 条"等）
23. 静态内容是否用双引号标明，动态内容是否说明数据来源
24. 超长文本场景是否写清截断/换行/滚动/悬停查看全文的处理方式
25. 按钮是否写清可点击/不可点击条件、点击反馈、成功变化、失败提示
26. 表单是否写清输入限制、校验时机（实时/失焦/提交时）和错误提示文案
27. 列表是否写清加载方式、加载中提示、无数据/失败/完毕状态
28. 弹窗是否写清触发/关闭方式、遮罩层行为、多弹窗优先级
29. 异常是否写清网络异常、权限不足、关键功能失效时的降级处理
30. 标题下内容是否连续完整，无空栏目、无占位段
31. 是否未使用伪缩进字符、手敲空格模拟首行缩进、空行制造视觉层级
32. 表格是否只用于数据字典、权限矩阵、状态映射、枚举定义
33. 是否禁用模板腔和模糊表述

### 一致性检查

34. PRD 字段列表与 design.md 字段定义是否一致
35. PRD 权限口径与 design.md 权限定义是否一致
36. PRD 状态机与 design.md 状态定义是否一致
37. 页面编号是否重复
38. 是否存在动作复用（不同页面的动作描述完全照抄）
39. 是否跨节代写（一个页面的规则在另一个页面描述）

### 结构检查

40. 核心章节是否完整（详细需求说明、权限汇总、数据字典、状态机）
41. 数据字典是否使用轻量格式（默认字段、类型、必填、说明；额外属性仅在确实影响实现时写入说明）
42. 数据字典是否按实体分组，且额外属性没有无差别平铺为固定大宽表
43. 状态机是否按核心业务对象组织，包含状态集合、迁移、触发动作和限制条件
44. 验收标准汇总、风险与待确认是否仅在存在真实约束时出现；不存在时不保留空章节
45. 权限汇总是否包含页面级、按钮级权限；如存在字段权限例外，是否已写入详细需求说明对应动作

### 一致性校验（机读交叉校验）

> PRD 生成阶段已用 `verify-against-metadata.py` 自检幻觉字段和约束一致性。以下检查项在 review 时抽查确认，重点关注 verify 脚本无法覆盖的语义层面一致性。

46. 功能覆盖：design 页面清单中每个页面是否有对应章节
47. 字段覆盖：design 字段定义中每个字段是否在数据字典或页面章节中体现
48. 字段落地：数据字典每个业务字段是否在详细需求说明、权限汇总、状态流转、验收标准或风险待确认中有明确落点
49. 字段一致性：同一字段在不同页面的展示格式和校验规则是否一致
50. 权限一致性：权限汇总与各页面按钮可见性/可操作性是否匹配
51. 状态一致性：状态机与各页面状态筛选/展示是否一致
52. 变更传播：本轮若修改了字段、页面动作、状态、权限、规则阈值或验收项，相关章节是否已同步更新

### 幻觉检测

53. PRD 中出现但 design.md 中不存在的字段/页面为幻觉，必须修正（prd 生成阶段已用 verify-against-metadata.py 自检）
54. 状态机是否包含流转速览 + 状态明细表 + 逐条迁移规则，密度是否足以让研发直接写代码
55. 业务流程是否按阶段展开、关键分支是否写具体判断条件和字段值、异常路径是否覆盖降级策略
56. 存在跨页面流转或状态变更的模块，是否在详细需求说明中用自然语言明确说明了流转边界和关键结果

### 门禁规则

57. 一致性校验为必做门禁，不是建议
58. 功能/页面/字段/字段落地/模糊表述有任何缺口，不得通过 review
59. 仅表达不足：留在当前稿件修正
60. 问题来自上游（design 缺失或错误）：停止，回退到 design 修复

### 角色视角自审

生成完毕后从三个视角审读：

- **开发视角**：能否直接写代码（字段定义是否完整、接口行为是否隐含在描述中、边界是否明确）
- **测试视角**：能否直接写用例（触发条件是否清楚、预期结果是否可验证、异常路径是否覆盖）
- **设计视角**：能否直接画原型（页面结构是否清楚、交互反馈是否明确）

上游事实源缺失不得脑补，标记 `[待确认]` 或回退上游。
