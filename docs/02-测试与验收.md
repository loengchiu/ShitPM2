# 新辅助器测试与验收

> 本文档是 `01-新辅助器实现总规约.md` 的配套验收文件。
>
> 规约定义"做什么、怎么做"；本文档定义"做到没有、怎么验"。
>
> 一切验收场景均从规约已定规则推导，不新增流程、不新增阶段、不改主链路。

---

## 0. 文档定位

本文档用于：

1. 实现阶段的逐项自验
2. 第一轮交付前的整体验收
3. review 阶段的判定参考

本文档不用于：

1. 写作指导（那是 skill 和 reference 的职责）
2. 门禁前置（那是 stage-context 的职责）
3. 项目管理

---

## 1. 测试原则

与规约 §1 设计原则对齐：

1. **阶段隔离**：每个阶段的验收独立进行，不跨阶段混合判定
2. **当前真相**：只验证当前产物状态，不验证历史版本
3. **人机分离**：人读产物和机读产物分别验收
4. **质量后置**：前置 gate 验收只查结构性问题；质量验收后置到 lint + reviewer
5. **脚本确定性**：脚本验收只查确定性输出；AI 生成产物的质量由 reviewer 验收

## 2. 验收场景总表

| 阶段 | 人读产物验收 | 机读产物验收 | 脚本验收 | 质量验收 |
|------|-------------|-------------|---------|---------|
| 启动 | — | status.json 读取 | stage-context.py | — |
| 对齐 | align.md 结构 | .workflow/metadata/align + align-notes.json | stage-context.py (gate) + stage-prep.py (anchor) | — |
| 设计 | design.md 核心章节 | .workflow/metadata/design 全量 | stage-context.py (gate) + anchor-build.py | design-review |

| 同步修复 | 覆盖后当前稿 | 覆盖后机读物 | anchor-verify.py | fix → review 建议 |

## 3. 启动阶段验收

### 3.1 测试对象

- `skills/start/SKILL.md`
- `scripts/python/stage-context.py`
- `.workflow/status.json`

### 3.2 输入 fixture

准备一个最小测试项目目录：

```text
test-project/
  .workflow/
    status.json
    metadata/
      align/
      design/
      prd/
      prototype/
    runtime/
    reviews/
  output/
    align/
    design/
    prd/
    prototype/
```

`status.json` 最小内容：

```json
{
  "current_stage": "align",
  "artifacts": {},
  "metadata_paths": {},
  "latest_reviews": {},
  "align_notes": {},
  "next_recommended": "align"
}
```

### 3.3 验收场景

#### S-3.1 新项目启动

- **输入**：空项目目录（只有 `.workflow/status.json`）
- **执行**：运行 `stage-context.py`
- **预期输出**：
  - `current_stage` = `"align"`（或 `"not_started"`）
  - `next_recommended` = `"align"`
  - 各产物路径为空或 null
- **pass 标准**：输出 JSON 包含 §5.3 定义的全部 6 类字段

#### S-3.2 对齐完成后启动

- **输入**：`output/align/align.md` 存在，`.workflow/metadata/align/` 有内容
- **执行**：运行 `stage-context.py`
- **预期输出**：
  - `current_stage` = `"design"`（对齐已完成，下一步是设计）
  - `artifacts.align` 指向 `output/align/align.md`
  - `metadata_paths.align` 指向 `.workflow/metadata/align/`
  - `align_notes` 包含 `can_enter_design` 字段值
- **pass 标准**：能正确识别对齐已完成，建议进入设计

#### S-3.3 串项目检测

- **输入**：status.json 中 `current_stage` 为 `"prd"`，但 `output/design/design.md` 不存在
- **执行**：运行 `stage-context.py`
- **预期输出**：报错或警告，指出上游产物缺失
- **pass 标准**：不得建议直接进入 PRD

#### S-3.4 review 结果读取

- **输入**：`.workflow/reviews/design-review.json` 存在，verdict = `"有问题需修改"`
- **执行**：运行 `stage-context.py`
- **预期输出**：`latest_reviews.design` 包含该 review 结果摘要
- **pass 标准**：review 状态正确反映在启动输出中

#### S-3.5 对齐阶段判断记录读取

- **输入**：`runtime/align/align-notes.json` 存在
- **执行**：运行 `stage-context.py`
- **预期输出**：输出中包含 `align_notes` 字段，值来自 `align-notes.json`
- **pass 标准**：能正确读取并透传，不修改内容

#### S-3.6 对齐阶段判断记录不存在

- **输入**：`runtime/align/align-notes.json` 不存在
- **执行**：运行 `stage-context.py`
- **预期输出**：`align_notes` 字段为空对象或 null，不报错
- **pass 标准**：不影响启动流程

## 4. 对齐阶段验收

### 4.1 测试对象

- `skills/align/SKILL.md`
- `scripts/python/stage-context.py`（对齐阶段准入）
- `scripts/python/stage-prep.py`（对齐 anchor 生成）
- `output/align/align.md`
- `.workflow/metadata/align/`（index.json / entities.json / relations.json）
- `.workflow/runtime/align/align-notes.json`

### 4.2 验收场景

#### S-4.1 对齐产物结构

- **输入**：完成一轮对齐对话
- **检查 `align.md`**：
  - 包含目标、范围、边界、建设方式
  - 包含建设类型初判（`iteration` / `new_build` / `hybrid` 三选一）
  - 包含待确认问题（如有）
  - 不包含页面字段细节
  - 不包含 PRD 正文
  - 不包含原型表达
- **pass 标准**：全部命中

#### S-4.2 align-notes.json 字段完整

- **检查文件**：`runtime/align/align-notes.json`
- **必须包含字段**：
  - `blocking_gaps`
  - `needs_ask_back`
  - `ask_back_reason`
  - `can_enter_design`
  - `judgement_note`
  - `last_updated_at`
- **不得包含**：页面清单、字段清单、长篇业务事实、可由 metadata/align 表达的索引信息
- **pass 标准**：6 个字段齐全，无越界内容

#### S-4.3 metadata/align 字段映射

- **检查文件**：`.workflow/metadata/align/index.json`
- **必须包含**：`request_summary`、`solution_shape`、`business_stage`、`context_gaps`
- **检查文件**：`.workflow/metadata/align/entities.json`
- **必须包含**：`system_or_page_clues`、`material_paths`、已确认角色/场景/关键对象的轻量索引
- **检查文件**：`.workflow/metadata/align/relations.json`
- **必须包含**：来源关系、承接关系、线索到对象的映射关系
- **pass 标准**：三个文件均存在且字段齐全

#### S-4.4 ask-back 纪律

- **模拟场景**：对齐过程中发现 context_gaps
- **检查行为**：
  - 只为真实阻塞追问
  - 一次只追一个问题
  - 先查资料，查不出再问 PM
  - 最后一行收口为唯一问题
- **pass 标准**：SKILL.md 中包含上述 4 条硬规则

#### S-4.5 stage-context.py 对齐准入

- **输入**：`status.json` 的 `current_stage` = `"align"`，上游无缺失
- **执行**：运行 `stage-context.py`
- **预期输出**：
  - 正确识别当前阶段为 `align`
  - `next_recommended` = `"align"`
  - 收集最小读取集合路径
- **pass 标准**：准入判断正确，输出包含 §5.3 定义的全部字段

#### S-4.6 can_enter_design 准入判断

- **输入**：`align-notes.json` 中 `needs_ask_back` = `true`
- **执行**：运行 `stage-context.py`
- **预期输出**：
  - `next_recommended` 不建议进入 `design`
  - 提示对齐尚未完成
- **pass 标准**：不得允许在 `needs_ask_back = true` 时进入设计

#### S-4.7 stage-prep.py 对齐 anchor 生成

- **输入**：对齐阶段已完成，`output/align/align.md` 存在
- **执行**：运行 `stage-prep.py --stage align`
- **预期输出**：
  - 从 `align.md` 抽取内容生成 `.workflow/metadata/align/`（index.json / entities.json / relations.json）
  - 生成 `.workflow/runtime/align/stage-context.json`
  - 不修改 `align.md` 正文
- **pass 标准**：机读镜像正确生成，与人读稿一致

## 5. 设计阶段验收

### 5.1 测试对象

- `skills/design/SKILL.md`
- `scripts/python/stage-context.py`（设计阶段准入）
- `scripts/python/stage-prep.py`（metadata 生成）
- `scripts/python/anchor-build.py`（design metadata 生成）
- `output/design/design.md`
- `.workflow/metadata/design/`（8 个 JSON 文件）

### 5.2 验收场景

#### S-5.1 design.md 核心章节完整性

- **检查 `design.md`**，核心章节必须全部存在：
  1. 角色定义
  2. 模块定义
  3. 页面清单
  4. 字段定义
  5. 规则与状态定义
  6. 权限定义
- **辅助章节可选**：文档概述、范围与建设方式、核心业务流程
- **pass 标准**：6 个核心章节全部存在

#### S-5.2 字段定义完整性

- **检查 design.md 的字段定义章节**：
  - 每个字段有完整属性（名称、类型、长度、必填、默认值、枚举值、格式、业务来源、说明）
  - 字段定义章节不写字段级权限表
- **pass 标准**：所有已定义字段属性齐全

#### S-5.3 权限定义组织方式

- **检查 design.md 的权限定义章节**：
  - 按"页面 > 角色 > 字段权限例外"组织
  - 先写默认权限规则，再写例外字段
  - 不把所有字段逐个平铺成巨大权限表
  - 包含字段级权限
- **pass 标准**：组织方式符合规定

#### S-5.4 design 是唯一事实源

- **检查 design.md 包含**：
  - 字段完整定义（完整属性）
  - 权限完整定义（完整口径）
  - 状态完整定义（完整口径）
- **pass 标准**：三类内容均在 design 中有完整定义，不依赖下游补充

#### S-5.5 metadata/design 字段齐全

- **检查以下 JSON 文件均存在且有内容**：
  - `index.json`：总索引
  - `entities.json`：实体列表
  - `relations.json`：关系列表
  - `modules.json`：模块定义
  - `pages.json`：页面清单
  - `fields.json`：字段定义
  - `rules.json`：规则定义
  - `states.json`：状态定义
  - `permissions.json`：权限定义
- **pass 标准**：9 个文件均存在

#### S-5.6 稳定 ID 首次生成

- **检查 `.workflow/metadata/design/` 中的 JSON**：
  - 包含 `MODULE-*`、`PAGE-*`、`FIELD-*`、`RULE-*`、`FLOW-*`、`REL-*` 前缀的稳定 ID
  - 稳定 ID 只存在于机读物，不在 design.md 正文中
- **pass 标准**：6 种前缀的 ID 均存在，正文无 ID 泄漏

#### S-5.7 人读与机读一致性

- **交叉检查**：design.md 正文中的字段/页面/规则数量 与 `.workflow/metadata/design/` 中的 JSON 记录数量一致
- **pass 标准**：100% 映射一致，机读物不新增正文中不存在的业务事实

#### S-5.8 design gate 检查

- **输入**：`align.md` 存在但 `.workflow/metadata/align/` 不完整
- **执行**：运行 `stage-context.py`
- **预期输出**：准入不通过，提示上游机读物缺失
- **pass 标准**：不得在上游机读物缺失时允许进入设计

#### S-5.9 不新增 align 未确认范围

- **检查**：design.md 中的模块/页面/字段/规则均能在 align.md 中找到对应来源
- **pass 标准**：无凭空新增的范围

- **检查 `prd.md`**，核心章节必须全部存在：
  1. 详细需求说明
  2. 权限汇总
  3. 数据字典
  4. 状态机

#### S-6.2 数据字典 9 列

- **检查 prd.md 的数据字典章节**：
  - 按实体分组
  - 使用统一 9 列：字段、类型、长度、必填、默认值、枚举值、格式、业务来源、说明
  - 不带内部稳定 ID、relations、anchors、source refs

#### S-6.3 权限汇总完整性

- **检查 prd.md 的权限汇总章节**：
  - 包含页面级权限
  - 包含按钮级权限
  - 包含字段级权限
  - 不带机读映射字段
- **pass 标准**：三类权限均覆盖

#### S-6.4 状态机完整性

- **检查 prd.md 的状态机章节**：
  - 按核心业务对象组织
  - 包含状态集合、迁移、触发动作和限制条件
  - 不带机读映射字段
- **pass 标准**：状态机结构完整

#### S-6.5 页面正文三层覆盖

- **逐页检查 prd.md 的详细需求说明**：
  - 每个页面必须覆盖：
    1. 界面元素与展示规则
    2. 交互逻辑与状态流转
    3. 异常处理与边界场景
  - 页面正文必须把状态如何流转、权限如何影响当前页面写清楚
- **pass 标准**：每个页面三层均覆盖

#### S-6.6 PRD 不独立新增 design 内容

- **交叉检查**：prd.md 中的字段、权限、状态定义均能在 design.md 中找到对应来源
- **pass 标准**：PRD 不得独立新增 design 中不存在的字段、权限或状态定义

#### S-6.7 PRD 镜像一致性

- **检查**：PRD 数据字典的字段列表 与 design.md 字段定义完全一致
- **检查**：PRD 权限汇总的权限口径 与 design.md 权限定义一致
- **检查**：PRD 状态机的状态口径 与 design.md 状态定义一致
- **pass 标准**：三类内容镜像一致，PRD 不改写 design 语义

#### S-6.8 prd-style-lint.py 检查

- **执行**：`prd-style-lint.py output/prd/prd.md`
- **必须检出的问题类型**：
  1. 标签式正文（`**关键动作：**` 等模式）
  2. 动作流水账特征（只按点击顺序描述，缺展示规则/状态/异常）
  3. 表格主导（页面主要信息依赖表格承载）
  4. 重复页面编号
  5. 跨节引用
  6. 机读字段泄漏（稳定 ID 出现在正文）
  7. AI 痕迹
  8. 占位符（"待补充"、"按配置"等）
- **pass 标准**：lint 对上述 8 类问题均有检出能力（用构造的坏样本验证）

#### S-6.9 metadata/prd anchor 完整

- **检查以下 JSON 文件均存在且有内容**：
  - `index.json`：总索引
  - `entities.json`：实体列表
  - `relations.json`：关系列表
  - `page-anchor.json`：页面锚点
  - `rule-anchor.json`：规则锚点
  - `field-anchor.json`：字段锚点
- **pass 标准**：6 个文件均存在

#### S-6.10 prd-writing.profile.json 可读

- **检查**：`references/prd-writing.profile.json` 存在且为有效 JSON
- **检查**：包含正文颗粒度、表格使用边界、禁止表达、覆盖要求等配置项
- **pass 标准**：文件存在、JSON 合法、配置项完整

- **检查**：如 prd.md 已存在，则原型也读取了 prd.md 中的详细需求说明、状态机、权限汇总、数据字典

- **pass 标准**：原型只做展示，不做业务规则定义

#### S-7.4 metadata/prototype 完整

- **检查以下文件存在**：
  - `index.json`：总索引
  - `page-map.json`：页面映射
- **pass 标准**：2 个文件均存在

#### S-7.5 prototype-feedback 归类格式

- **输入**：一份包含表现问题和语义问题的 `prototype-feedback.md`
- **检查 AI 输出**：
  - 输出固定格式归类结果（§4.5 定义的格式）
  - 分为"表现问题"和"语义问题"两类

  - 若某一类为空，保留标题并写"无"

  - 同步更新 metadata/design

  - 不得把语义问题只留在 prototype 闭环
- **pass 标准**：语义问题正确传播到 design

#### S-7.7 表现问题不传播

- **输入**：归类结果中只包含表现问题
- **检查行为**：
  - 只修改 prototype
  - 同步更新 metadata/prototype
  - 不回写 design
- **pass 标准**：表现问题不污染 design

#### S-7.8 未归类禁止修改

## 8. 同步修复验收

### 8.1 测试对象

### 8.2 验收场景

#### S-8.1 从对齐阶段发起修复

- **检查行为**：
  1. 判定事实源在设计
  2. 受影响阶段：PRD（数据字典、详细需求说明）、原型（如存在）
  3. 先更新 design.md 和 metadata/design
  4. 再更新 prd.md 和 metadata/prd
  5. 再更新 prototype 和 metadata/prototype（如存在）
- **pass 标准**：只改必要内容，不整篇重写

#### S-8.3 从 PRD 发现问题回 design

- **输入**：PRD review 发现 design 中字段定义有误
- **检查行为**：
  1. 判定事实源在设计
  2. 先回写 design.md
  3. 同步更新 metadata/design
  4. 再更新 prd.md
- **pass 标准**：不允许逆向定源（PRD 不能直接改 design 的语义，必须通过 fix 流程）

#### S-8.4 归属层无法判断时停止

- **输入**：用户修改指令模糊，无法判断是需求问题还是设计问题
- **检查行为**：先停在澄清，不得直接改下游
- **pass 标准**：SKILL.md 中包含此停止条件

#### S-8.5 修复完成后输出 review 建议

- **输入**：fix 完成对设计阶段的覆盖
- **检查行为**：
  1. 自动判断受影响最深阶段（设计）
  2. 输出：`建议进入 设计 review，检查对象：[对象列表]`
  3. 不自动执行 review
- **pass 标准**：输出格式正确，不自动推进

#### S-8.6 anchor-verify.py 修复后校验

- **输入**：fix 完成覆盖后
- **执行**：`anchor-verify.py --stage design`
- **预期输出**：验证 metadata/design 中的 anchor 与 design.md 一致
- **pass 标准**：修复后 anchor 完整，无断链

#### S-8.7 不制造多版本并存

- **检查**：fix 覆盖后，每个阶段只有一份当前稿
- **pass 标准**：无旧版本残留

#### S-8.8 不回避影响分析

- **检查**：fix 执行前必须完成影响分析（最小判断清单 6 步）
- **pass 标准**：不得跳过影响分析直接硬改下游

## 9. Review 验收

### 9.2 review 通用验收

  1. `通过`
  2. `有问题需修改`
  3. `阻塞，不能继续`
- **pass 标准**：verdict 值在三档之内

#### S-9.2 review 结果双输出

- **检查每个 review 输出两份结果**：
  1. 机读 JSON：`.workflow/reviews/<stage>-review.json`
  2. 人读摘要：简短 Markdown
- **机读 JSON 最小字段**：`stage`、`verdict`、`issues`、`issue_layer`、`affected_objects`、`needs_upstream_sync`、`next_recommended`
- **人读摘要最小骨架**：结论、主要问题、是否需要回上游、下一步建议
- **pass 标准**：两份输出均存在且字段完整

#### S-9.3 review 不自动推进阶段

- **检查**：review 通过后，status.json 的 `current_stage` 不自动变更
- **pass 标准**：通过后仍由 PM 手动进入下一阶段

#### S-9.4 两段式 review 流程

- **检查 review 执行顺序**：
  1. 先跑外置 metadata 的 lint / anchor 校验（生成 review-precheck.json）
  2. 再做人读正文质量审查
- **pass 标准**：SKILL.md 中明确两段式顺序

### 9.3 design review 专项验收

#### S-9.5 design review 检查项

- **reviewer 必须能判断**：
  1. 核心章节是否完整（角色定义、模块定义、页面清单、字段定义、规则与状态定义、权限定义）
  2. 字段定义属性是否齐全
  3. 权限定义是否覆盖到字段级
  4. 状态定义是否覆盖完整
  5. metadata/design 与 design.md 是否一致
  6. 稳定 ID 是否正确生成
- **pass 标准**：上述 6 项均可判定

### 9.4 PRD review 专项验收

#### S-9.6 PRD review 检查项

- **reviewer 必须能判断**：
  1. 是否命中 §7.2 定义的坏味道
  2. 页面是否缺展示规则
  3. 页面是否缺状态变化
  4. 页面是否缺异常边界
  5. 页面编号是否重复
  6. 是否跨节代写
  7. 是否存在动作复用
  8. 核心章节是否完整（详细需求说明、权限汇总、数据字典、状态机）
  9. 数据字典是否使用 9 列格式
  10. PRD 与 design 的字段/权限/状态是否镜像一致
- **pass 标准**：上述 10 项均可判定

### 9.5 prototype review 专项验收

#### S-9.7 prototype review 检查项

- **reviewer 必须能判断**：
  1. 原型是否展示了 design 中定义的页面结构
  2. 状态表达是否覆盖核心状态
  3. 交互主路径是否覆盖
  4. 权限表现是否覆盖
  5. metadata/prototype 与原型是否一致
- **pass 标准**：上述 5 项均可判定

### 9.6 review-precheck 验收

#### S-9.8 review-precheck.json 生成

- **执行**：`review-precheck.py --stage prd`

  - `deterministic_checks`
  - `blocking_issues`
  - `warnings`
  - `can_start_review`
  - `recommended_focus`
- **pass 标准**：8 个字段均存在

#### S-9.9 review-precheck 阻塞项

- **执行**：`review-precheck.py --stage prd`
- **预期输出**：
  - `can_start_review` = `false`（或 `true` 但 `blocking_issues` 非空）
