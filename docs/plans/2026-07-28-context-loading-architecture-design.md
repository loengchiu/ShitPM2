# ShitPM Design / PRD 上下文装载架构设计

> 状态：已确认并实施（当前工作区未提交 Git）
> 日期：2026-07-28
> 适用范围：`spm-design`、`spm-prd` 及其内部生成、自检和可选 Sub-agent 编排
> 实施约束：用户确认本设计后才允许修改 Skill、reference、contract、script 和测试；本文件本身不改变当前运行行为。

## 1. 背景与问题

ShitPM V2 已经建立了完整的 Design 分析责任、写作规则、质量标准和 PRD 承接要求，但当前运行方式主要依赖 Agent 在一次任务中全文读取多份规则文件，再连续完成分析、挑战、写作、检查和修复。

这种方式的主要风险不是硬上下文窗口立即溢出，而是有效上下文密度下降：同一产品契约在不同文件重复表达，分析规则、写作规则、正反例和评分标准同时占据注意力，旧工具输出和旧草稿持续留在对话记录中。随着业务材料和产物变大，模型需要在大量相似指令、事实和中间状态之间持续判断优先级，容易出现遗漏、误用和跨层不一致。

### 1.1 当前静态装载基线

按当前仓库文件统计：

| 阶段 | 静态资源口径 | 文件数 | 行数 | 字符数 |
| --- | --- | ---: | ---: | ---: |
| Design | `spm-design` Skill、Design 模板、六份 Design reference、决策记录模板 | 9 | 1,019 | 24,905 |
| PRD | `spm-prd` Skill、PRD 模板、规则、名词、版本、场景清单、profile、决策记录模板，不含示例 | 8 | 641 | 16,932 |
| PRD 示例增量 | `prd-writing-examples.md` 全文 | 1 | 261 | 6,567 |

以上尚未包含系统指令、项目 `AGENTS.md`、Bundle `AGENTS.md`、用户输入、Align、已有 Design、Prototype、工具输出、中间分析和最终产物。

字符数只是确定性统计代理，不等同于模型 token。实施时应在可获得目标模型 tokenizer 的环境中同时记录 token；没有 tokenizer 时继续使用字符数、行数和文件数作为稳定回归指标。

### 1.2 当前前提中的两个事实

1. PRD 当前并不是每次都读取完整示例。`spm-prd` 已规定只在高复杂动作、规则无法决定组织方式、自检命中失败模式或用户明确要求时读取 `prd-writing-examples.md`。问题在于一旦命中，仍会读取整个示例文件，而不是相关章节。
2. Design 当前确实要求完整读取六份 reference。部分文件承担不同职责，但产品契约、模式边界、首次生成责任和 Review 边界存在多处重复表达。

### 1.3 根因

当前问题分为四类：

1. **规则重复**：相同语义在 `AGENTS.md`、Skill、分析协议、写作规则和质量标准中重复出现。
2. **阶段混装**：分析、挑战、写作、成品审查和正式 Review 规则未在运行时充分隔离。
3. **条件内容全量装载**：状态、流程、文件、批量、并发、跨系统和示例等专项内容未按适用性精确加载。
4. **对话充当工作内存**：多个推理阶段在同一持续增长的上下文中完成，旧草稿和旧检查结果继续干扰后续判断。

## 2. 设计目标

### G1：降低无关上下文

每次推理只加载当前阶段、当前模式和当前适用场景需要的规则，避免为了保证不遗漏而全文加载所有 reference。

### G2：保持 Design 深度推理质量

完整模式仍必须完成 A、B、B3、C 和跨层一致性挑战。上下文优化不能以减少分析责任、弱化挑战或把缺口推给 Review 为代价。

### G3：保持唯一事实源边界

内部适用性清单、分析交接文件、上下文包、Sub-agent 输出和缓存只用于执行、导航和审计，不成为 PRD 或 Prototype 的产品事实源。用户确认后的 `output/design/design.md` 仍是唯一产品事实基线。

### G4：规则可追溯且不漂移

运行时上下文必须从现有权威规则的明确章节确定性生成，不能依赖模型临场总结形成第二份不可验证规则。

### G5：可量化验证

能够回答每次运行实际加载了哪些文件、哪些章节、多少字符或 token、为什么加载，以及相对于基线减少了多少。

### G6：小任务保持简单

简单 Design 和小型 PRD 不引入不必要的多 Agent、复杂缓存或模块流水线。优化机制不能让简单任务的失败点和维护成本增加。

## 3. 非目标

本设计不改变：

- 简单模式和完整模式由用户选择的规则；
- Design 的 Product Definition 与 Design Baseline 双重职责；
- Design、PRD、Prototype 的事实源和上下游关系；
- `spm-design-review`、`spm-prd-review` 的按需独立第二意见定位；
- PRD 的页面组织和写作风格；
- Prototype 的 HTML + Vue + Tailwind + daisyUI + 本地 lib 架构；
- confirmation、artifact guard、lint 和 consistency check 的既有产品边界；
- 通过换用更长上下文模型掩盖规则重复；
- 以增加 Schema、缓存、Sub-agent 或脚本数量作为产品完成证明。

## 4. 设计原则

### 4.1 一个规则只有一个权威来源

`SKILL.md` 负责阶段编排、输入顺序、门禁、停止条件和写入顺序；`references/` 负责分析方法、写作规则和场景语义；`templates/` 负责输出骨架；`contracts/` 负责跨阶段公共契约；JSON profile 和 schema 只承载程序实际消费的确定性约束。

运行时包可以组合权威来源的章节，但不得复制后独立维护。

### 4.2 核心责任短而完整，专项规则按需展开

始终加载的核心内容必须覆盖所有不可遗漏的责任，但只保留责任声明和停止边界。具体推导方法、写法、正反例和专项闭环在确定适用后再加载。

### 4.3 适用性判断与规则细节分离

Agent 必须先判断状态、权限、生命周期、文件、批量、并发、跨系统等维度是否适用，再读取对应规则细节。不能因为没有加载专项规则而跳过“是否适用”的判断。

### 4.4 使用结构化选择，不使用普通相似度检索决定强制规则

规范性规则不能由向量相似度排名决定是否加载。加载依据必须是明确的阶段、模式、适用性键和稳定章节标记。语义检索可以帮助查找示例或补充材料，但不能决定强制责任是否存在。

### 4.5 使用干净推理阶段，不携带完整历史记录

分析、写作和成品审查通过显式交接产物衔接。每一阶段建立新的最小上下文，不依赖前一阶段完整对话记录。

### 4.6 主 Agent 对全局业务模型负责

Sub-agent 可以读取材料、提出挑战或草拟独立模块，但不能各自定义角色、状态、规则和边界后直接合并为最终 Design。跨层一致性必须由一个主 Agent 统一负责。

## 5. 目标架构

### 5.1 五类运行时上下文

| 类型 | 作用 | 是否始终加载 | 典型内容 |
| --- | --- | --- | --- |
| Core | 建立阶段职责和不可越界边界 | 是 | 事实源、模式、停止条件、输出、首次生成责任 |
| Mode | 承载当前模式的分析责任 | 二选一 | Simple 最小闭环或 Full ABC + 跨层挑战 |
| Card | 承载适用场景的详细规则 | 按需 | 状态、流程、权限、生命周期、文件、并发、跨系统 |
| Writing | 承载成品组织和表达规则 | 写作阶段 | 模板、字段表、页面落点、PRD 动作写法 |
| Verification | 承载成品审查和失败模式 | 审查阶段 | 质量标准、场景检查清单、已知失败模式 |

示例不属于强制规则，作为独立的 Example 资源按章节加载。

### 5.2 上下文来源与运行时视图

现有 reference 继续作为权威来源。新增 `contracts/context-loading.manifest.json`，描述：

- 阶段和推理阶段；
- 模式；
- 场景卡键；
- 权威来源文件；
- 稳定章节标记；
- 加载顺序；
- 互斥和依赖关系；
- 预期用途；
- 是否允许传给 Sub-agent。

Markdown 权威来源增加稳定段落标记，例如：

```markdown
<!-- context:design-analysis-full:start -->
...
<!-- context:design-analysis-full:end -->
```

构建脚本根据 manifest 提取原文，不让模型总结规则。生成的上下文包保留来源路径、章节键和内容哈希，便于验证来源和发现漂移。

### 5.3 运行时文件位置

运行时文件只存放在当前项目内部：

```text
.workflow/runtime/context/
  design/
    run.json
    applicability.json
    packs/
      001-core.md
      002-mode.md
      003-card-state.md
      004-card-cross-system.md
      005-writing.md
      006-verification.md
    handoff/
      analysis.json
      challenge.json
  prd/
    run.json
    applicability.json
    packs/
    handoff/
      coverage.json
      module-plan.json
```

这些文件具有以下约束：

- 只用于执行、导航、校验和审计；
- 不参与 Design confirmation；
- 不成为下游事实源；
- 不写入最终 Design、PRD 或 Prototype；
- 可以删除并根据权威来源重建；
- 未获得用户确认前，本设计不创建上述结构。

## 6. Design 运行流程

### 6.1 D0：预检和模式确定

读取：

- 项目状态；
- Align 或用户原始材料清单；
- 现有 Design，如存在；
- Core 上下文。

执行：

- 判断首次生成或修改；
- 获取用户指定的简单模式或完整模式；
- 用户未指定时仍只询问一次；
- 检查必要资源和输入是否可读。

本阶段不加载完整写作规则、质量评分和示例。

### 6.2 D1：需求分析和适用性判断

加载：

- Core；
- 当前 Mode；
- 用户输入或 Align；
- 一份短而完整的适用性检查表。

输出内部 `analysis.json`，至少包含：

- 输入材料清单和来源指针；
- 已确认事实及其来源；
- 可直接推导但需要保留推导依据的结论；
- 来源冲突；
- 高影响待确认；
- 角色、业务对象、主流程和关键动作目录；
- 场景适用性键和理由；
- 跨模块全局不变量。

适用性键至少覆盖：

```text
state_machine
multi_role_flow
data_scope
field_permission
uniqueness
lifecycle
time_boundary
file
import_export
batch
repeat_submit
concurrency
cross_system
product_quality
```

`analysis.json` 不是新的事实源。凡是进入最终 Design 的事实，必须能够追溯到用户输入、Align、现有 Design 或明确待确认项。

### 6.3 D2：场景卡装载与业务挑战

加载器根据 D1 的适用性结果装载对应 Card。规则如下：

- `applicable`：加载完整 Card；
- `not_applicable`：不加载 Card，但保留不适用理由；
- `unknown`：高影响场景按保守策略加载 Card，并在 Design 中形成待确认或停止；
- 适用性键缺失：视为流程错误，不继续正式写作。

业务挑战读取输入证据、`analysis.json`、当前 Mode 和适用 Card，输出 `challenge.json`：

- 发现的问题；
- 受影响对象；
- 证据位置；
- 是否可以根据已确认事实修正；
- 是否必须转为待确认；
- 是否阻止写作。

挑战可以由主 Agent 在干净上下文中执行，也可以由独立 Sub-agent 执行。无论由谁执行，都属于首次生成内部责任，不等同于 `spm-design-review`。

### 6.4 D3：Design 写作

写作上下文只加载：

- 原始输入或可验证证据包；
- 修正后的 `analysis.json`；
- 已解决或已分类的 `challenge.json`；
- 适用 Card；
- Design Writing；
- Design 模板；
- 决策记录模板。

不加载：

- 独立 Review 评分细节；
- 无关场景卡；
- 完整历史工具输出；
- 旧草稿的全部版本；
- 与当前场景无关的正反例。

主 Agent 统一生成 `output/design/design.md` 和 `output/design/decision-notes.md`。Sub-agent 不直接写最终 Design。

### 6.5 D4：生成内成品审查

使用新的干净上下文，加载：

- Design 草稿；
- 原始输入或证据包；
- Core；
- Verification 中的“生成成品自审”部分；
- 适用 Card 的闭环检查；
- 已知失败模式。

输出内部缺陷列表，不输出正式 Review 评分和 verdict。发现可修复问题时返回 D3；发现高影响未决事实时写入 Design 待确认或停止请求用户决定。

### 6.6 D5：确定性检查和交付

运行现有适用检查器。检查器只阻断可可靠证明的结构、引用、完整性和执行错误。业务合理性、隐含语义和高影响判断仍由 D1 至 D4 负责。

全部通过后才交付 Design 和决策记录；不自动确认、不自动执行 `spm-design-review`、不自动推进 PRD 或 Prototype。

## 7. PRD 运行流程

### 7.1 P0：事实源和确认门

检查 Design 存在、可读且确认有效。Design 是唯一产品事实源；Prototype 只用于发现冲突，不得覆盖 Design。

Prototype 冲突检查不得默认全文加载整个 HTML 目录。应先由脚本提取页面名、动作名、可见字段和路由等结构信息；只有发现疑似冲突时才读取对应片段。

### 7.2 P1：全局承接规划

加载：

- PRD Core；
- 完整 Design；
- PRD 模板；
- PRD 写作规则中的结构和边界部分。

输出内部：

- 模块和页面目录；
- 全局名词；
- 共享角色、状态和规则；
- Design → PRD 承接矩阵；
- 字段归宿；
- 模块依赖；
- 高复杂动作和场景适用性。

本阶段不加载完整示例。

### 7.3 P2：按模块写作

小型 PRD 由主 Agent 一次生成。大型 PRD 可以按业务模块分批，但不能按页面机械分页，也不能让模块各自重定义共享规则。

每个模块上下文只包含：

- PRD Core；
- 全局不变量；
- 对应 Design 模块；
- 相关字段、状态、角色和规则；
- 对应场景 Card；
- 必要的写作规则章节。

高复杂动作需要示例时，只加载 `prd-writing-examples.md` 的对应章节，而不是全文。

### 7.4 P3：全局整合

主 Agent 统一处理：

- 版本记录；
- 名词说明；
- 模块编号；
- 共享规则；
- 跨模块动作；
- 全字段承接；
- 状态和权限一致性；
- 验收汇总；
- 决策记录。

模块草稿只能写入 `.workflow/runtime/context/prd/handoff/`，不能由 Sub-agent 直接合并或覆盖 `output/prd/prd.md`。

### 7.5 P4：生成内成品审查和检查

使用干净上下文加载 Design、PRD 草稿、场景检查清单和适用 Verification 内容，检查遗漏和越界。然后依次执行现有 style lint、consistency check 和 artifact guard。

生成内成品审查不等同于 `spm-prd-review`，不输出正式 Review verdict，不自动修复 Design 缺失的高影响事实。

## 8. Sub-agent 设计

### 8.1 默认策略

简单 Design 和小型 PRD 默认不使用 Sub-agent。只有满足明确条件时才启用，避免为并行而并行。

### 8.2 允许的角色

| 角色 | 触发条件 | 输入 | 输出 | 禁止事项 |
| --- | --- | --- | --- | --- |
| Material Reader | 输入材料多且可按来源独立阅读 | 单份或一组材料、事实提取契约 | 带来源的事实、冲突、缺失 | 不做最终产品决策 |
| Design Challenger | 完整模式或高复杂 Design | 原始证据、Design 草稿、挑战清单 | 缺陷和证据 | 不直接修改 Design，不输出 Review verdict |
| PRD Module Writer | Design 超过 10 页或 50 个字段，且模块边界清楚 | 全局不变量、模块 Design、PRD 写作包 | 模块草稿 | 不修改共享规则，不写最终 PRD |
| Module Verifier | 大型 PRD 可并行检查独立模块 | Design 模块、PRD 模块、检查清单 | 缺失和冲突 | 不静默补充 Design 事实 |

### 8.3 不允许的拆分

不把 Design 按 A、B、B3、C 分给不同 Agent 后直接拼接；不把角色、状态、页面、权限分别交给不同 Agent 独立定义；不让所有 Sub-agent 重复读取全部规则；不以多数投票替代业务证据和用户确认。

### 8.4 主 Agent 责任

主 Agent 始终负责：

- 全局业务模型；
- 来源冲突处理；
- 高影响待确认；
- 跨层一致性；
- 最终写入；
- Sub-agent 结果采纳或拒绝的理由；
- 确定性检查失败后的修复或停止。

## 9. 装载器设计

### 9.1 候选脚本

确认实施后新增：

```text
scripts/python/context-pack.py
scripts/python/context-budget.py
scripts/python/test-context-loading.py
contracts/context-loading.manifest.json
```

职责：

- `context-pack.py`：解析 manifest、提取稳定章节、组合上下文包、记录来源哈希；
- `context-budget.py`：对运行包和业务输入做保守体量测量，提供中英文混合 token 启发式估算和可选阈值检查；不替主 Agent 选择模式、模块或默认上限。
- `test-context-loading.py`：验证标记完整、路径可读、场景键闭合、无重复装载和无未授权来源。

是否合并进现有 `stage-context.py` 在实施时再决定。默认先保持职责分离，避免把阶段导航脚本改造成大型编排器。

### 9.2 运行记录

`run.json` 至少记录：

```json
{
  "stage": "design",
  "mode": "full",
  "pass": "writing",
  "sources": [],
  "packs": [],
  "characters": 0,
  "tokens": null,
  "source_hashes": {},
  "generated_at": ""
}
```

运行记录只用于执行和审计，不进入产品产物，不作为事实输入。

### 9.3 失败策略

- manifest 缺失、格式错误或来源路径不可读：停止，不凭模型记忆继续；
- 章节标记缺失或重叠：停止，不读取不确定范围；
- 权威来源哈希变化：重新构建上下文包；
- 适用性键未知：高影响场景保守加载并形成待确认；
- 上下文预算超限：若调用方显式提供阈值则失败或告警；优先移除无关规则和旧历史，再考虑材料分组或 PRD 模块化。预算估算是保守启发式，不替代目标模型 tokenizer；
- Sub-agent 输出缺来源：拒绝采纳；
- Sub-agent 结论冲突：由主 Agent 回到原始证据判断，不能静默选择多数意见。

## 10. 与现有契约的关系

### 10.1 不冲突的部分

`output/shitpm-v2-prd.md` 和 `output/shitpm-v2-implementation-design.md` 已明确内部可以采用单次、多遍、缓存、Sub-agent 或其他编排方式，只要不把实现机制当作产品目标、不污染最终产物、不降低首次生成责任。因此本设计不需要修改批准产品基线。

### 10.2 需要确认后替代的旧执行规则

`references-optimization-plan.md` 当前规定：

- Design 六份 reference 不继续按章节拆分；
- `spm-design` 完整读取 analysis、methodology、writing、state、flow 和 quality rubric 的生成自审部分。

本设计确认后，将仅替代该文件中的以下内容：

- Design 六份 reference 的运行时全文装载策略；
- Skill 与脚本读取策略中 Design、PRD 的最小集合定义；
- PRD 示例从文件级条件加载改为章节级条件加载。

现有 reference 的权威职责和内容不因本设计自动失效。是否需要物理拆文件由实施阶段根据稳定章节标记的可维护性决定，默认优先不拆文件，只生成运行时章节视图。

### 10.3 PRD 大型任务边界

当前 `spm-prd` 禁止分页流水线、逐页 Checkpoint 和 page-fields 索引等能力补偿机制。本设计允许的仅是按清晰业务模块产生内部草稿，不允许按页机械切分，不改变 Design 唯一事实源，也不依赖内部索引成为产品事实源。

实施时必须把该边界写清，避免“模块化内部草拟”演变成第二套 PRD 事实模型。

- 质量下降时回退装载策略，不以 token 降低掩盖产物退化。

## 12. 验收标准

### 12.1 装载效率

以下以字符数作为确定性验收代理，token 作为环境允许时的补充指标：

| 场景 | 当前静态基线 | 目标 |
| --- | ---: | ---: |
| 简单 Design | 24,905 | 不高于当前基线的 45% |
| 完整 Design 分析或写作单次推理 | 24,905 | 不高于当前基线的 70%，且 Verification 不与 Writing 同次加载 |
| 普通 PRD | 16,932 | 不高于当前基线的 65% |
| PRD 示例 | 6,567 | 仅加载命中章节，不全文加载 |

这些指标只约束静态规则装载，不包含用户业务材料和产物正文。若质量对照失败，即使达到上下文指标也不能验收。

### 12.2 产品质量

- 完整模式仍完成 A、B、B3、C 和跨层挑战；
- 简单模式仍完成最小闭环；
- 已知失败样例中的状态孤岛、规则遗漏、自确认、异常断链和范围冲突仍能被发现；
- Design 继续是 PRD 和 Prototype 的唯一产品事实源；
- PRD 不新增 Design 未确认的高影响事实；
- 决策记录继续只用于审计；
- 生成内成品审查不变成正式 Review；
- 最终产物不出现运行包、metadata、内部路径或 Sub-agent 记录。

### 12.3 工程质量

- 每个运行时段落可以追溯到唯一权威来源和内容哈希；
- manifest、章节标记和运行包有确定性测试；
- 规则源变化后旧运行包能够被识别为陈旧；
- 不存在无法解释的关键词业务阻断；
- 不保留人工维护的第二份规则摘要；
- 不要求 Sub-agent 才能完成普通任务；
- `git diff --check` 和现有回归测试通过。

## 13. 方案权衡

### 13.1 采用“编译式章节装载”，不采用普通 RAG

原因：强制规则需要可证明的完整性和来源，不能依赖相似度召回。代价是需要维护 manifest 和稳定章节标记，但这种复杂度可以通过确定性测试控制。

### 13.2 采用多遍干净上下文，不采用单次超长任务

原因：分析、写作和审查需要不同注意力目标。代价是需要内部交接文件和来源追溯；通过规定交接文件不是事实源，降低中间总结漂移风险。

### 13.3 主 Agent 保持全局所有权

原因：Design 的核心质量来自跨流程、对象、状态、规则、角色和系统承接的一致性。代价是主 Agent 仍然承担最终综合压力，但可以把材料阅读和独立挑战交给 Sub-agent。

### 13.4 默认不物理拆分现有 reference

原因：当前 reference 已经完成职责整理，立即拆文件会扩大改动和链接维护成本。优先使用稳定章节标记生成运行时视图；只有某个章节长期独立演进且边界稳定时，再考虑物理拆分。

### 13.5 不把 Prompt Caching 或自动压缩作为质量方案

Prompt Caching 只能优化重复前缀的成本和延迟；自动压缩可能丢失规范性细节。两者可以作为运行优化，但不能代替分层装载、来源追溯和独立成品审查。

## 14. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 适用性判断漏项 | 专项规则未加载，Design 缺失 | Core 保留完整适用性键；缺键阻断；`unknown` 保守加载 |
| 交接文件变成第二事实源 | 下游注入原始输入不存在的事实 | 所有事实保留来源；最终写作读取证据；一致性检查禁止无来源结论 |
| 多遍推理产生结论漂移 | 分析、写作和审查对事实理解不同 | 使用全局不变量和来源哈希；主 Agent统一裁决 |
| Sub-agent 模块漂移 | 角色、状态、字段和规则不一致 | 只处理独立材料或模块；共享规则只由主 Agent维护 |
| manifest 维护成本 | 规则更新后运行包失效 | 自动完整性检查、来源哈希和陈旧检测 |
| 为降低上下文而过度切分 | 全局一致性变差 | 静态预算不是唯一验收；质量回归优先于 token 指标 |
| 旧计划和新策略并存 | 执行者不知道采用哪个基线 | 确认后明确标注替代范围并更新旧计划状态 |
