# Design 确定性编排低成本测试方案

## 1. 文档目的

本文为 `docs/plans/2026-07-29-design-orchestration-context-governance.md` 定义可执行、低成本、分层的测试方案。

测试首先证明编排是否正确，再用少量在线模型调用验证宿主集成，最后才用真实项目验证外部有效性。日常回归不再依赖完整真实项目冷启动，也不以反复运行十五分钟以上的真实流程作为主要证据。

本文只设计测试体系，不修改 Skill、脚本、契约、模板和运行时实现，不执行真实模型调用。

## 2. 需要纠正的测试前提

### 2.1 真实项目不是日常回归样例

真实项目适合验证最终效果，但不适合定位编排错误，原因是：

- 输入规模大，单次失败成本高；
- 模型输出存在波动，同一缺陷不一定稳定复现；
- 模型负载、网络和工具等待会污染耗时；
- 失败后很难立即区分是编排、上下文、模型质量还是宿主调度问题；
- 为验证一个局部失效规则而重跑整条真实链路，测试粒度与故障粒度不匹配。

因此，真实项目只能是发布级验收，不是每次改动后的常规测试。

### 2.2 墙钟时间不能单独证明编排提速

“总耗时从十五分钟降到多少”可以反映用户体验，但不能单独证明根因已修复。模型服务负载变化可能让正确编排偶尔更慢，也可能让错误编排偶尔更快。

编排测试的硬证据应优先是：

1. 动作轨迹是否正确；
2. 模型调用次数是否符合预算；
3. 材料事实提取是否被错误重复执行；
4. 相同输入文件是否重复进入不同或同一任务；
5. 下游失败是否错误导致上游重跑；
6. 上下文输入清单是否越过动作授权边界；
7. 输入、输出和依赖哈希是否能够解释每次复用或失效。

墙钟时间作为趋势指标记录，不作为普通回归的唯一硬失败条件。

### 2.3 “生成了隔离动作”不等于“已经实现上下文隔离”

Python 编排器最多能返回：

```json
{
  "type": "run_isolated_agent"
}
```

这只能证明控制平面要求宿主创建隔离执行实例，不能证明宿主实际没有继承父对话历史。上下文隔离必须由宿主执行记录或会话日志提供证据，不能只靠任务说明中的文字要求。

## 3. 测试目标

### 3.1 编排正确性

- `next` 每次只返回一个动作；
- 动作顺序由产物依赖和哈希决定，不由主代理临时规划；
- 不允许跳过依赖、重复接受同一动作或接受不匹配的输出；
- 中断后从第一个无效依赖恢复；
- 下游失败不使已验证的上游重新执行；
- 用户回答只使声明依赖该回答的动作失效；
- 自动修复有次数和指纹边界，不形成无限循环。

### 3.2 上下文治理

- 主对话不读取原始材料、完整规则正文和完整阶段产物；
- 每个隔离执行动作只接收任务所需文件；
- 同一文件正文不在同一任务中重复装载；
- Design 三个核心动作不依赖父对话历史；
- 任务说明可审计地记录输入文件、输入哈希、规则包引用和预期输出；
- 没有宿主证据时，不把“上下文隔离”标记为自动测试通过。

### 3.3 复用与局部失效

- 材料未变化时不重新提取事实；
- 单个来源变化时只重建对应事实及其下游；
- 规则包按内容哈希跨项目复用；
- 仅检查脚本变化时只重跑确定性检查；
- 已验证的合法旧产物可以被新编排器恢复；
- 上游哈希陈旧、结构损坏或依赖不匹配时拒绝错误复用。

### 3.4 成本约束

- 日常自动回归零模型调用；
- 材料缓存命中的在线合成冒烟最多执行三次 Design 核心模型调用；
- 材料冷启动在线冒烟与 Design 主路径分开计数；
- 真实项目只在发布级节点运行；
- 不用连续三次或五次真实项目冷启动来证明性能。

### 3.5 产品质量边界

提速不能以减少完整模式责任为代价。测试必须同时守住：

- 完整模式 ABC 分析责任未被删除；
- 独立业务模型挑战仍发生在 Design 正式写入前；
- Design 分析产物足以支持新写作实例恢复统一业务模型；
- 写作任务仍执行生成内自查；
- 用户确认后的 `output/design/design.md` 仍是下游唯一产品事实基线；
- 运行时中间产物不成为 PRD 或 Prototype 的产品事实输入。

## 4. 非目标

本文不负责：

- 证明所有业务设计都正确；
- 用程序替代用户对高影响产品决策的确认；
- 把模型输出文本逐字固定；
- 为测试方便重新引入 Hook；
- 建立常驻后台服务；
- 强制模型在固定秒数内完成；
- 把现有大型真实项目复制为公开固定样例；
- 重写现有 Design 质量回归体系。

## 5. 总体测试结构

采用五层结构，越靠前成本越低、执行越频繁、定位越精确。

| 层级 | 名称 | 模型调用 | 主要目的 | 执行频率 |
|---|---|---:|---|---|
| 第一层 | 确定性单元与契约测试 | 0 | 验证状态机、依赖、哈希、任务说明和预算 | 每次相关改动 |
| 第二层 | 无模型全链路回放 | 0 | 验证完整动作图、恢复、失败注入和调用计数 | 每次相关改动 |
| 第三层 | 录制结果重放 | 0 | 验证历史合法产物、运行事件和版本兼容 | 每次相关改动或发布前 |
| 第四层 | 小型合成项目在线冒烟 | 3 次核心调用为主 | 验证真实宿主隔离调用和阶段交接 | 编排或上下文边界变化时 |
| 第五层 | 真实项目发布验收 | 按实际记录 | 验证真实规模下的外部有效性 | 首次落地、重大变更、发布候选 |

第一、二、三层组成默认回归套件。第四层不进入每次提交的默认测试。第五层不能替代前四层。

## 6. 第一层：确定性单元与契约测试

### 6.1 运行方式

- 使用临时项目目录；
- 不访问模型；
- 不依赖固定用户工作区；
- 每个用例只构造最小输入和产物；
- 失败信息必须指出动作、依赖、期望哈希和实际哈希；
- 整层目标耗时控制在约一分钟内。

一分钟是工程目标。若测试机偶发超过一分钟但功能断言全部通过，只记录趋势，不立即判定产品失败；若耗时持续上升，则单独调查测试自身是否重复扫描大目录。

### 6.2 状态机与唯一下一动作

| 编号 | 场景 | 准备 | 期望 |
|---|---|---|---|
| O-001 | 新运行且模式未指定 | 只有 `request.md` | 返回一次询问模式动作，不生成分析任务 |
| O-002 | 模式已回答 | 写入 `user-decisions.json` | 不再重复询问模式 |
| O-003 | 材料未准备 | 缺少有效材料资产 | 只返回材料检查或准备动作 |
| O-004 | 材料有效 | `manifest.json`、`source-index.json`、`facts.json` 有效 | 返回 Design 分析动作 |
| O-005 | 分析完成 | 有效 `design-model.json` 与 `applicability.json` | 返回业务模型挑战动作 |
| O-006 | 挑战完成 | 有效 `design-challenge.json` | 返回写作与生成内自查动作 |
| O-007 | Design 草稿完成 | `design.md`、`decision-notes.md` 有效 | 返回确定性检查动作 |
| O-008 | 全部检查通过 | 所有依赖有效 | 返回完成，不再返回模型动作 |
| O-009 | 动作未接受时重复调用 `next` | 保持状态不变 | 返回同一个 `action_id`，不得创建新动作 |
| O-010 | 接受未知动作 | 使用不存在的 `action_id` | 明确拒绝，状态不前进 |
| O-011 | 接受已完成动作 | 重复 `accept` | 幂等返回或明确拒绝，不重复计数、不重复失效 |
| O-012 | 越级提交输出 | 分析未完成却提交挑战产物 | 拒绝接受，不跳过分析动作 |

### 6.3 运行输入快照

| 编号 | 场景 | 期望 |
|---|---|---|
| I-001 | 相同用户需求重复初始化 | `request.md` 内容哈希稳定，不重复附加聊天历史 |
| I-002 | 需求正文变化 | 运行输入版本变化，依赖旧输入的 Design 产物失效 |
| I-003 | Align 不存在 | 允许直接进入 Design，不把 Align 设为硬前置 |
| I-004 | Align 新增或变化 | 仅依赖 Align 的 Design 分析及下游失效 |
| I-005 | 用户回答写入 | 使用独立问题 ID 和答案哈希，不改写历史回答 |
| I-006 | 不相关用户回答变化 | 不使未声明依赖该问题的动作失效 |
| I-007 | 阻断问题未回答 | 返回等待用户动作，不启动写作 |
| I-008 | 输入快照结构损坏 | 明确失败，不根据残缺文件猜测状态 |

### 6.4 材料复用与局部失效

复用现有 `test-context-runtime.py` 已覆盖的首次生成、未变化复用、新增、修改、删除和版本门禁，并补充编排层断言。

| 编号 | 场景 | 期望 |
|---|---|---|
| M-001 | 来源集合和内容未变化 | 复用全部材料资产，材料事实提取次数为 0 |
| M-002 | 单个来源修改 | 只重建该来源事实，生成新的 `material_revision` |
| M-003 | 新增来源 | 只提取新增来源，旧来源事实保持 |
| M-004 | 删除来源 | 移除对应事实，不重读其余来源 |
| M-005 | 文件时间变化但内容哈希未变 | 不重新提取事实 |
| M-006 | 来源顺序变化但集合和内容相同 | 材料版本稳定，不误判全部失效 |
| M-007 | `facts.json` 缺少来源引用 | 材料资产门禁失败 |
| M-008 | `facts.json` 声明旧材料版本 | 拒绝 Design 分析恢复 |
| M-009 | 只执行确定性哈希扫描 | 不把原始材料正文计入模型输入 |
| M-010 | 需要定点补读 | 任务只列出 `source_id`、路径、行范围和原因，不授权全目录扫描 |

### 6.5 产物依赖与恢复

| 编号 | 变更或故障 | 必须失效 | 必须保留 |
|---|---|---|---|
| R-001 | `design-model.json` 内容变化 | 挑战、写作、检查 | 材料事实资产 |
| R-002 | `design-challenge.json` 内容变化 | 写作、检查 | Design 分析产物、材料事实资产 |
| R-003 | `design.md` 内容变化 | 确定性检查 | 分析、挑战 |
| R-004 | 检查脚本版本变化 | 确定性检查 | 三次核心模型产物 |
| R-005 | 写作规则包变化 | 写作、检查 | 材料、分析；挑战是否保留由显式依赖决定 |
| R-006 | 挑战规则包变化 | 挑战、写作、检查 | 材料、分析 |
| R-007 | 分析规则包变化 | 分析及全部下游 | 材料事实资产 |
| R-008 | 运行记录丢失但产物和依赖有效 | 从文件重建状态，不从头执行 |
| R-009 | 产物存在但上游哈希陈旧 | 从第一个陈旧产物恢复，不误报完成 |
| R-010 | 产物 JSON 结构损坏 | 该产物及下游失效，上游保留 |
| R-011 | 中断发生在任一动作之后 | 新会话返回第一个未完成或无效动作 |
| R-012 | 下游动作执行失败 | 重试当前动作或进入失败状态，不重跑有效上游 |

### 6.6 规则包内容寻址缓存

| 编号 | 场景 | 期望 |
|---|---|---|
| P-001 | 两个项目选择相同规则 | 引用同一个内容哈希规则包 |
| P-002 | 规则源未变化 | 不重新生成相同规则正文 |
| P-003 | 规则源变化 | 生成新哈希路径，旧运行仍可按旧哈希审计 |
| P-004 | 缓存正文被篡改 | 哈希校验失败并重新编译，不盲目复用 |
| P-005 | 项目运行目录 | 只保存规则包引用、哈希和选择信息，不保存重复静态正文 |
| P-006 | 不同规则选择 | 不因文件名相同而错误命中缓存 |
| P-007 | 缓存缺失 | 可从规则源确定性重建，项目状态不被错误标记为完成 |

### 6.7 阶段任务说明契约

每个任务说明必须可被程序检查，而不是只靠人工阅读。

必需字段至少包括：

```text
action_id
role
objective
input_files
input_hashes
rule_pack_ref
allowed_evidence_ranges
expected_outputs
output_schema
completion_check
forbidden_inputs
```

用例：

| 编号 | 场景 | 期望 |
|---|---|---|
| T-001 | 输入白名单完整 | 任务说明通过结构检查 |
| T-002 | 缺少输入哈希 | 拒绝启动隔离执行 |
| T-003 | 输出路径不在当前动作允许范围 | 拒绝启动或拒绝接受 |
| T-004 | 分析任务包含挑战产物 | 任务说明门禁失败 |
| T-005 | 挑战任务包含完整父对话导出 | 任务说明门禁失败 |
| T-006 | 写作任务包含原始材料目录通配读取 | 任务说明门禁失败 |
| T-007 | 同一文件在输入清单重复出现 | 去重后生成，或直接拒绝重复项 |
| T-008 | 规则包只给路径不记录哈希 | 拒绝启动，避免规则漂移无法审计 |
| T-009 | 缺少输出结构要求 | 拒绝启动，避免无法确定性验收 |
| T-010 | 定点证据越过授权行范围 | 标记越权，不把结果接受为合法输出 |

### 6.8 自动修复边界

| 编号 | 场景 | 期望 |
|---|---|---|
| F-001 | 确定性检查首次失败 | 生成只含失败定位和相关片段的局部修复任务 |
| F-002 | 修复后检查通过 | 完成，不重跑分析和挑战 |
| F-003 | 相同检查指纹再次失败 | 不无限自动修复，转为明确失败或等待人工处理 |
| F-004 | 检查失败指纹变化 | 在配置的总次数上限内允许新的局部修复 |
| F-005 | 修复任务请求全量原始材料 | 任务说明门禁失败 |
| F-006 | 修复修改了无关 Design 区域 | 通过差异范围或输出声明标记异常，进入人工审查 |

第一版不要求程序理解所有 Markdown 语义变化，但必须至少限制修复输入、修复次数和重复失败指纹。

## 7. 第二层：无模型全链路回放

### 7.1 伪造宿主

建立只执行文件复制和事件记录的伪造宿主，不调用任何模型。它接收编排器动作，并从固定样例中写入对应产物：

```text
材料事实提取器 -> facts.json
Design 分析者 -> design-model.json + applicability.json
业务模型挑战者 -> design-challenge.json
Design 写作者 -> design.md + decision-notes.md
```

伪造宿主不得自行判断下一步，只能执行 `next` 返回的动作，然后调用 `accept`。这样可以验证控制权是否真正位于编排器，而不是测试代码里又写了一套隐藏流程。

### 7.2 标准动作轨迹

材料已经缓存时，完整模式的预期轨迹为：

```text
读取运行输入快照
检查材料资产并命中复用
运行 Design 分析
校验 Design 分析产物
运行业务模型挑战
校验挑战产物
运行写作与生成内自查
校验 Design 和 decision-notes
运行确定性检查
完成
```

模型动作计数必须是：

```json
{
  "material_fact_extraction": 0,
  "design_analysis": 1,
  "business_model_challenge": 1,
  "design_writing": 1,
  "independent_final_review": 0,
  "core_design_calls": 3
}
```

“校验”是本地程序动作，不计为模型调用。局部修复只有在检查失败时出现，不能计入正常主路径。

### 7.3 回放用例

| 编号 | 场景 | 关键断言 |
|---|---|---|
| E-001 | 缓存命中的正常完整模式 | 三次核心代理动作，无第四次独立成品审查 |
| E-002 | 材料首次准备 | 先发生材料事实提取，再进入三次 Design 核心动作 |
| E-003 | 分析输出结构失败 | 停在分析动作，不启动挑战 |
| E-004 | 挑战输出结构失败 | 只重试挑战，不重跑材料和分析 |
| E-005 | 写作输出结构失败 | 只重试写作，不重跑挑战及其上游 |
| E-006 | 确定性检查失败一次 | 进入局部修复，修复后重新检查 |
| E-007 | 相同检查连续失败 | 到达边界后停止，不形成循环 |
| E-008 | 每个动作后模拟进程退出 | 新进程从正确动作继续 |
| E-009 | 删除 `run.json` 后恢复 | 根据有效产物和依赖恢复 |
| E-010 | 篡改旧产物哈希 | 从第一个失效依赖恢复 |
| E-011 | 回答阻断问题 | 只重跑依赖该答案的动作 |
| E-012 | 不显式输入 `$spm-design` 但已正确路由 | 与显式调用产生相同编排轨迹 |
| E-013 | 伪造宿主试图执行非当前动作 | 编排器拒绝接受 |
| E-014 | 两个动作并发接受 | 只允许当前动作成功，防止状态竞争 |
| E-015 | 重复运行已完成项目 | 直接返回完成，核心模型动作数为 0 |

### 7.4 失败注入点

每个以下边界至少注入一次失败：

- 动作创建后、宿主执行前；
- 输出写入一半时；
- 输出写完但尚未 `accept` 时；
- `accept` 后、下一次 `next` 前；
- 检查结果写入后、完成状态写入前；
- 用户答案文件写入一半时；
- 规则包缓存命中后、任务说明生成前。

目标不是为所有磁盘故障建立复杂事务系统，而是确认部分文件不会被误判为有效完成状态。

## 8. 第三层：录制结果重放

### 8.1 作用

录制结果重放保存一次经过确认的合成项目阶段产物和运行事件，以后测试新编排器时不重新调用模型。

它主要回答：

- 新版本还能否接受旧版本生成的合法产物；
- 依赖哈希、任务说明和动作事件是否可恢复；
- 动作轨迹是否因代码改动发生非预期变化；
- 指标统计是否把本地检查误计为模型调用；
- 旧运行版本是否被明确迁移或明确拒绝，而不是静默误读。

### 8.2 录制内容

```text
request.md
input-manifest.json
user-decisions.json
materials/manifest.json
materials/source-index.json
materials/facts.json
design-model.json
applicability.json
design-challenge.json
design.md
decision-notes.md
action-trace.json
host-events.jsonl
metrics.json
expected-status.json
```

录制样例必须来自合成项目，不得包含真实项目敏感信息、用户聊天全文或主对话导出。

### 8.3 兼容策略

- 每份录制结果声明 `schema_version`、编排器版本和规则包哈希；
- 当前版本支持时，必须重放通过；
- 不支持时，必须返回明确迁移提示或版本错误；
- 不允许为了让测试通过而忽略未知字段或错误哈希；
- 文本产物可以变化，但动作和依赖契约变化必须经过显式更新。

## 9. 第四层：小型合成项目在线冒烟

### 9.1 为什么需要在线冒烟

前三层能证明程序编排，却不能证明宿主真的创建了隔离执行实例，也不能证明模型能消费任务说明并产出符合门禁的结果。因此需要一个体量小、事实密度高、可重复运行的合成项目。

### 9.2 合成项目规模

建议总输入控制在约 5～15 KB，拆成 3～5 个短材料文件。项目必须包含：

- 两个业务角色；
- 两种不同数据范围；
- 一个有状态实体；
- 一条主流程；
- 至少一条异常路径；
- 一个跨系统责任边界；
- 一处材料冲突；
- 一个必须询问用户的高影响缺口；
- 一个明确不适用的场景；
- 一个需要写入 `decision-notes.md` 的权衡。

推荐主题为“小型设备借还管理”，避免复用现有大型库存样例造成输入过大。建议材料：

```text
01-background.md
02-roles-and-scope.md
03-process-and-state.md
04-external-system.md
05-conflict-note.md
```

### 9.3 合成项目事实骨架

合成事实应足够具体，使动作是否漏读或重新推理能够被发现：

- 员工只能查看和申请自己所属部门可借设备；
- 资产管理员可以处理本组织全部申请；
- 设备状态至少包含可借、预占、借出、逾期、维修；
- 审批通过后由库存系统完成最终锁定；
- 审批系统与库存系统对“审批通过是否等于预占成功”存在冲突描述；
- 逾期后是否禁止再次申请属于高影响未决问题；
- 不涉及付费结算，结算规则应判断为不适用；
- “先审批再锁库存”和“先锁库存再审批”必须记录方案权衡。

这套事实不是产品标准，只是为了让角色、权限、状态、异常、跨系统责任、冲突和待确认都能在很小输入中被覆盖。

### 9.4 在线冒烟拆分

为控制成本，在线冒烟拆为两个独立测试：

#### A. Design 主路径冒烟

- 预置并校验材料事实资产；
- 只运行 Design 分析、业务模型挑战、写作与生成内自查；
- 核心模型调用必须恰好为 3；
- 不运行第四次独立成品审查；
- 验证三次调用使用不同执行实例；
- 验证写作实例不需要重新读取全部原始材料。

#### B. 项目级材料准备冒烟

- 从 3～5 个短材料文件冷启动；
- 验证材料事实提取能够生成带来源引用的 `facts.json`；
- 随后不继续跑完整 Design，避免一次测试同时承担两个目标；
- 第二次以相同材料运行时，材料事实提取调用次数必须为 0。

只有发布候选时，才把 B 后接 A 做一次完整合成冷启动。此时总调用数应按“材料事实提取调用 + 三次 Design 核心调用”分别报告，不能把材料提取混入“三次核心调用”后声称超预算。

### 9.5 入口路由冒烟

“不显式输入 `$spm-design`”与“显式输入 `$spm-design`”是否会进入同一 Skill，属于宿主路由能力，不是 Python 编排器能够独立证明的内容。

发布前用两个全新任务做一次低成本入口检查：

1. 任务一显式输入 `$spm-design` 和同一份短需求；
2. 任务二只输入“开始做完整模式 Design”和同一份短需求；
3. 两个任务都只运行到编排器返回第一个业务动作，不继续生成完整 Design；
4. 对比实际 Skill 标识、模式、运行输入快照哈希和首个动作类型；
5. 若自然语言任务未路由到 `spm-design`，报告为宿主路由问题，不能归因于 Design 编排器；
6. 若已经路由成功但后续轨迹不同，才属于 Skill 入口或编排适配问题。

该检查不需要消费三次 Design 核心模型调用，也不能用“自然语言任务最后碰巧生成了 Design”代替路由证据。

### 9.6 在线质量断言

不对全文做逐字比较，改为检查可观察责任：

- `design-model.json` 包含角色、数据范围、流程、状态、权限、跨系统责任、不变量、权衡、待确认和来源引用；
- `design-challenge.json` 至少识别预置的材料冲突或说明其裁决；
- 未回答高影响问题时，不得静默写入最终事实；
- `design.md` 能覆盖主流程和异常路径；
- `decision-notes.md` 按设计决策、偏离、权衡、待确认四类记录；
- 不适用场景被明确判断，而不是机械生成无关章节；
- 确定性检查通过；
- 输出不包含内部路径、调试字段或模型工作过程。

## 10. 第五层：真实项目发布验收

### 10.1 触发条件

只在以下情况运行：

1. 新编排器首次完成；
2. 宿主隔离执行协议发生重大变化；
3. 产物依赖或失效契约发生重大变化；
4. 发布候选版本准备交付。

普通文档调整、错误信息调整、局部确定性检查修改，不触发真实项目全流程。

### 10.2 每个发布候选的运行上限

默认最多保留：

- 一次真实项目冷启动；
- 一次相同材料版本的恢复或复用运行。

如果冷启动暴露问题，先用最小合成样例复现并修复，再决定是否重新运行真实项目。不能在没有定位的情况下连续重跑真实项目碰运气。

### 10.3 真实项目需要记录的证据

- 项目标识和材料版本，不记录敏感正文；
- 运行开始和结束时间；
- 每个动作开始和结束时间；
- 动作轨迹；
- 每类模型调用次数；
- 每个动作的输入文件哈希和估算 token；
- 材料事实提取是否复用；
- 是否发生定点补读；
- 是否发生失败、重试和局部修复；
- 主对话是否读取完整阶段产物；
- 每个隔离执行实例的宿主证据；
- 最终 Design 质量验收结果。

真实项目总耗时要与旧运行对比，但必须同时解释调用次数和输入体量，不能只比较一个总分钟数。

## 11. 上下文隔离与读取边界的可测性

### 11.1 宿主必须提供的执行记录

每次隔离执行至少记录：

```json
{
  "action_id": "design-analysis-001",
  "execution_instance_id": "...",
  "parent_task_id": "...",
  "inherit_history": false,
  "task_hash": "...",
  "declared_input_files": [],
  "observed_read_files": [],
  "written_files": [],
  "started_at": "...",
  "finished_at": "..."
}
```

其中：

- `declared_input_files` 来自编排器任务说明；
- `observed_read_files` 必须来自宿主工具调用日志或等价审计数据，不能由模型自行声明；
- `inherit_history` 必须由宿主提供，不能由任务提示自证；
- `task_hash` 用于证明宿主执行的是编排器生成的任务说明。

### 11.2 当前能够自动证明的内容

即使宿主暂时不提供完整读取日志，程序仍能自动证明：

- 编排器只声明了哪些输入；
- 任务说明是否包含禁止输入；
- 规则包和输入哈希是否正确；
- 产物是否写入允许位置；
- 动作是否按顺序执行；
- 模型调用计数是否符合动作轨迹。

### 11.3 当前不能自动证明的内容

若宿主不提供执行元数据和实际读取日志，则不能自动证明：

- 隔离执行实例没有继承父对话；
- 执行实例没有自行遍历项目目录；
- 主对话没有通过其他工具读回完整中间产物；
- 模型没有读取任务说明以外的宿主注入内容。

这些项目必须标记为“人工会话日志验收”，不能在测试报告中伪装为自动通过。

### 11.4 分阶段增强方案

第一版：

- 保存任务说明、动作事件和宿主可取得的调用记录；
- 在线冒烟后人工审查一次会话日志；
- 报告中区分“程序断言”“宿主声明”“人工审计”。

后续如果宿主读取日志不足：

- 为每个动作建立只包含授权文件的临时任务工作区；
- 隔离执行只能看到该工作区；
- 输出通过受控复制回项目；
- 以文件系统可见性缩小越权读取面。

临时任务工作区是后续增强，不是第一版编排器落地的前置条件。测试方案不引入 Hook。

## 12. 指标与预算

### 12.1 必须记录的动作指标

| 指标 | 用途 |
|---|---|
| `action_type` | 区分材料、分析、挑战、写作、检查、修复和等待 |
| `reused` | 判断是否命中复用 |
| `input_files` 与哈希 | 发现重复输入和错误失效 |
| `estimated_input_tokens` | 观察上下文规模变化 |
| `estimated_output_tokens` | 观察阶段产物规模 |
| `model_call_count` | 编排成本硬证据 |
| `tool_call_count` | 发现重复读取和无效探索 |
| `retry_count` | 发现不稳定动作 |
| `targeted_evidence_read` | 区分定点补读和全量重读 |
| `execution_instance_id` | 验证不同动作使用独立实例 |
| `elapsed_ms` | 趋势和用户体验观察 |

### 12.2 硬预算

| 测试类型 | 模型调用预算 | 失败条件 |
|---|---:|---|
| 第一层 | 0 | 发生任何模型调用 |
| 第二层 | 0 | 发生任何模型调用 |
| 第三层 | 0 | 发生任何模型调用 |
| 第四层 A | 恰好 3 次 Design 核心调用 | 少于或多于 3 次，或出现独立成品审查 |
| 第四层 B 首次 | 只允许材料事实提取调用 | 同时触发 Design 核心调用 |
| 第四层 B 复用 | 0 | 再次触发材料事实提取 |
| 第五层缓存命中 | 默认 3 次 Design 核心调用 | 无解释地增加核心调用 |

如果某个变化来源需要并行分片提取，材料提取调用数可大于 1，但必须按变化来源或片段解释，不能与 Design 核心调用混为一项。

### 12.3 上下文预算

上下文预算先作为异常检测，不设固定业务上限。每次比较以下指标：

- 同一动作的输入文件数量；
- 同一动作的估算输入 token；
- 同一文件哈希在一个动作中出现次数；
- 原始材料和 `facts.json` 是否同时全量装载；
- 父对话历史是否被宿主声明继承；
- 写作动作是否因交接不足而重新请求全量材料；
- 检查失败后是否重新执行上游模型动作。

固定合成项目可建立版本基线。若输入 token 比已确认基线增加超过约 20%，测试先报警并输出新增文件和哈希差异，不直接认定业务失败；确认是无授权输入后再升级为硬失败。

### 12.4 时间预算

建议目标：

- 第一至第三层合计约 60 秒内；
- 第四层记录每个动作耗时，不设置严格秒级失败阈值；
- 第五层与旧基线比较总耗时和分阶段耗时。

时间目标必须与执行环境一同记录。模型服务波动导致的单次超时不应掩盖动作数和输入体量已经正确的事实，但连续多个版本恶化必须调查。

## 13. 测试报告格式

每次回归输出机器可读 JSON 和简短中文摘要。

机器可读结果示意：

```json
{
  "suite": "design-orchestration",
  "model_calls": 0,
  "passed": 42,
  "failed": 0,
  "duration_ms": 1234,
```


- 创建最小临时项目构造器；
- 覆盖 `next`、`accept`、`answer`、`status`；
- 覆盖哈希、失效、恢复和修复边界；
- 确保失败能够定位到具体依赖。

验收：第一层全部通过，模型调用数为 0。

### 第二步：建立伪造宿主和动作轨迹回放

- 伪造宿主只复制固定产物；
- 编排器保持唯一控制权；
- 增加中断点和失败注入；
- 固定正常完整模式的预期动作轨迹。

验收：缓存命中路径恰好出现三次核心代理动作，没有第四次独立成品审查。

### 第三步：冻结合成录制结果

- 使用小型合成项目；
- 保存阶段产物、事件和指标；
- 加入版本和哈希；
- 建立兼容或明确拒绝策略。

验收：不调用模型即可完整重放并恢复状态。

### 第四步：接入宿主审计证据

- 记录执行实例 ID、父任务 ID、历史继承标记和任务哈希；
- 尽可能记录实际读取文件；
- 报告区分程序断言、宿主声明和人工审计。

验收：不能取得的证据明确显示为缺失，不被计为通过。

### 第五步：执行一次小型在线冒烟

先运行 Design 主路径，再单独运行材料冷启动与复用。发现问题时回到前三层构造最小复现，不直接连续重跑在线模型。

### 第六步：发布候选真实项目验收

只在前五步通过后执行一次真实冷启动和一次复用运行。

## 18. 完成标准

测试体系实施完成需要同时满足：

1. 日常编排回归不调用模型；
2. 正常完整模式动作轨迹被固定并可重放；
3. 材料缓存命中时，Design 主路径恰好三次核心模型调用；
4. 默认路径不存在第四次独立成品审查；
5. 任一动作中断后能够从第一个无效依赖恢复；
6. 下游失败不重跑有效上游；
7. 材料增删改只造成声明范围内的失效；
8. 规则包按内容哈希复用；
9. 任务说明输入白名单、输出约束和哈希可被程序检查；
10. 自动修复存在重复指纹和次数边界；
11. 宿主无法提供的隔离证据被明确标记，不虚报自动通过；
12. 小型在线冒烟和真实项目验收与日常回归分离；
13. 现有 Design 质量、防幻觉和资源完整性测试继续保留；
14. 不引入 Hook，不改变 Align 可选、Design 唯一事实源和双下游边界。

## 19. 待确认决策

测试实施前需要确认以下决策：

1. 接受五层测试结构，日常默认只运行前三层零模型测试；
2. 接受“小型设备借还管理”作为新的编排合成项目；
3. 接受材料冷启动冒烟与 Design 三次核心调用冒烟分开执行；
4. 接受没有宿主读取日志时，将“未越权读取”标为人工会话日志验收，而不是自动通过；
5. 接受真实项目只用于首次落地、重大编排变化和发布候选，不作为每次提交回归；
6. 接受第一版先记录宿主证据，临时任务工作区作为后续增强而非前置实现。
