# 材料摄取与 Design 编排优化讨论稿

日期：2026-07-29
状态：讨论中，未批准实施

## 1. 本轮需要纠正的判断

上一版方案把材料索引、事实提取、运行时检查放进 Design 的 D0。这个位置不对：如果这些步骤只是叠加在原有 Design 读取链之前，而没有真正替代原始材料读取，就会把 Design 变成更长的串行流水线，导致运行更慢。

因此，本轮不再把“Design 前先做更多准备”当作优化目标，而是调整材料责任归属：

> 原始材料摄取、文件索引、来源哈希和基础事实整理应在进入 Design 前完成一次；Design 只消费已经存在的材料包，不负责建立材料包。

## 2. 已确认事实与待验证点

### 已确认

- 真实运行中工具调用不是主要耗时来源；主要耗时来自模型上下文膨胀。
- Design 阶段不应重复读取原始材料、建立索引和反复整理事实。
- 上一版实现增加了额外串行步骤，且没有证据证明旧读取链已被完全替换，因此变慢是合理结果。
- Hook 不属于本轮方案。

### 仍需确认

- Align 当前是可选模块，是否继续保持可选。
- 材料索引是 Align 产物的一部分，还是项目级内部材料资产。
- 用户在跳过 Align、直接进入 Design 时，谁负责第一次材料摄取。
- Align 是否允许重跑；重跑时是增量更新还是全量重建。

## 3. 三种编排方案

### 方案 A：Align 负责一次性材料摄取，Design 只读取（推荐的短期方案）

```text
Align 启动
  -> 一次读取原始材料
  -> 生成材料索引和来源清单
  -> 生成基础事实包
  -> 可选生成 align.md

Design 启动
  -> 读取已存在的材料索引/事实包
  -> 直接完成业务建模和 Design 写作
```

优点：改动最小，符合“材料先整理、Design 后建模”的直觉；Design 的输入稳定、可审计。

风险：当前 Align 是可选的。如果用户跳过 Align 直接进入 Design，必须定义一个明确的补偿路径，否则会破坏现有“无 Align 也能进入 Design”的契约。

### 方案 B：把 Align 改成 Design 的硬前置

```text
原始材料 -> Align -> Design
```

优点：编排最简单，不需要 Design 兜底。

缺点：会改变当前产品契约；用户只提供清晰需求时也被迫经过 Align；无法证明一定更快，因为会增加一次阶段交互。除非用户明确接受流程改变，否则不推荐。

### 方案 C：项目级材料摄取，Align 和 Design 都只消费（长期方案）

```text
项目接收材料
  -> 项目级材料摄取：一次性建立索引、来源清单、基础事实包
  -> Align：可选整理目标、范围、不确定点
  -> Design：直接读取材料包和 Align 结果
```

优点：既保留 Align 可选，又避免把材料摄取绑定到 Design；PRD、Review、Fix 也可以复用同一个材料包。

缺点：需要引入一个新的项目级运行概念，编排改动较大；必须定义材料更新、失效、重建和用户确认边界。

## 4. 推荐方向

建议采用“**项目级材料摄取的责任模型 + Align 触发的短期落地方式**”：

- 概念上引入项目级材料摄取；
- 第一阶段由 Align 触发和承载；
- Align 仍然不是业务上的硬前置；
- 如果用户直接进入 Design，宿主只执行一次确定性的材料摄取，不执行完整 Align 对话；
- Design 不建立索引、不做原始材料全文扫描、不重复生成基础事实包；
- Design 只读取已经存在的材料包和必要的 Align 结果。

这样可以同时满足两个目标：

1. 不破坏“Align 可选”；
2. 不让 Design 承担材料摄取工作。

## 5. 运行时资产边界

建议不要把材料索引塞进 `output/align/align.md`，也不要把 `align-notes.json` 直接当作全部事实源。应区分：

```text
.workflow/runtime/materials/manifest.json       # 文件、哈希、更新时间
.workflow/runtime/materials/source-index.json   # 主题、行范围、关键词
.workflow/runtime/materials/facts.json          # 带来源的基础事实、冲突、缺失
output/align/align.md                            # 人读的需求整理稿，可选
.workflow/runtime/align/align-notes.json         # Align 内部整理记录
```

其中：

- `manifest.json` 是材料版本清单；
- `source-index.json` 是定位结构，不是业务事实；
- `facts.json` 是材料层事实，不是 Design 决策；
- `align.md` 是需求整理结果，不应承载所有原始材料；
- `design.md` 仍然是确认后的产品事实基线。

## 6. Design 应该读取什么

Design 启动时只读取：

```text
.workflow/runtime/materials/manifest.json
.workflow/runtime/materials/facts.json
output/align/align.md                       # 存在时读取
用户本轮明确补充的内容
Design 分析规则和适用场景卡
```

Design 不应该做：

- 原始目录全文扫描；
- 重建材料索引；
- 重新提取同一批基础事实；
- 为了校验 handoff 再启动一个模型阶段；
- 把完整历史对话重新带入新的 Design pass。

必要的原文核验只能是按 `facts.json` 的来源路径和行范围定点读取，而且应当是例外，不是默认路径。

## 7. 为什么上一版会变慢

上一版实际形成的风险链是：

```text
Design 开始
  -> 建索引
  -> 检查索引
  -> Material Reader
  -> 主 Agent 建模
  -> Challenger
  -> context-pack
  -> 主 Agent 写作
  -> verification
```

如果旧的原始材料读取仍然存在，实际就会变成：

```text
旧读取链 + 新索引链 + 新 handoff 链 + 新检查链
```

这不是上下文优化，而是串行步骤叠加。下一轮必须先确认编排调用图，再决定删掉哪些旧步骤，不能继续往 Design 前面增加准备步骤。

## 8. 讨论时需要先定的决策

1. 是否接受“项目级材料摄取”这个概念？
2. Align 是否继续保持业务流程上的可选？建议保持。
3. 直接进入 Design 时，是否允许宿主自动执行一次无交互的材料摄取？建议允许。
4. 材料事实包是否只做基础事实，不承担角色、状态、权限、流程和方案决策？建议是。
5. 材料发生变化时，是否按文件哈希增量重建，并使旧 facts 失效？建议是。
6. 在没有原始文件、只有用户本轮文字需求时，是否允许直接生成最小材料包？建议允许，但应标记来源为本轮用户输入。

## 9. 本文之后的实施前置条件

在上述决策确认前，不修改 Skill、契约、脚本或 manifest。

确认后再执行：

1. 先画出当前真实编排调用图，标明每个模型调用、文件读取和上下文传递；
2. 删除 Design 内重复的材料摄取步骤；
3. 决定材料摄取的触发时机和失效规则；
4. 设计最小材料资产 Schema；
5. 用同一真实样例对比旧链路和新链路的模型调用次数、输入 token 和机器耗时。
