# 项目级材料摄取设计稿

日期：2026-07-29
状态：已确认，实施中

## 1. 设计目标

减少同一批材料被重复读取造成的低效率和上下文爆炸。项目级材料摄取只是实现手段，不是目标本身；关键是确保同一个材料版本只进行一次原始材料的模型级读取和基础事实整理，后续 Design、PRD、Review 和 Fix 复用同一版本的材料资产。

必须同时区分两类时间：

- 阶段时间：Design 本身需要多长时间；
- 端到端时间：从用户开始整理材料到 Design 完成需要多长时间。

材料摄取迁移后，Design 阶段时间应明显下降；端到端时间只有在材料资产被复用、旧的重复读取链被删除时才会下降。

## 2. 核心原则

1. 同一个材料版本只允许一次原始材料的模型级读取；确定性文件扫描可以幂等执行，但不得把全文重新注入模型上下文。
2. 文件未变化时，不重新建立索引，不重新提取基础事实，也不重新把原始材料全文交给任何后续阶段。
3. Design、PRD、Review 和 Fix 只能消费已存在的材料资产，不能各自创建或修复一份新的材料事实副本。
4. Align 仍然是业务整理模块，不改成 Design 的硬前置。
5. 用户直接进入 Design 时，宿主可以执行一次无交互的项目级材料摄取，但该过程不属于 Design 模型上下文。
6. 材料事实不等于产品决策；角色、流程、状态、权限、模块边界和方案权衡仍由 Design 负责。
7. 材料资产版本变化时，旧事实包必须失效，不能静默复用。

## 3. 责任分层

### 项目级材料摄取

负责：

- 收集用户明确提供的文件、目录、文字和链接引用；
- 计算来源哈希；
- 建立文件和章节索引；
- 记录文件版本、行范围和定位信息；
- 提取带来源的基础事实、冲突、缺失信息和不可直接推导项；
- 生成材料资产版本。

不负责：

- 定义产品流程；
- 决定角色、权限和状态；
- 选择系统方案；
- 生成 Design、PRD 或 Prototype。

### Align

负责：

- 在已有材料资产基础上整理目标、范围、背景、建设方式和不确定点；
- 记录用户确认和未决问题；
- 生成可供 Design 读取的人读整理稿。

不负责：

- 重新全文扫描已有材料；
- 重复建立索引；
- 替代 Design 完成业务建模。

### Design

负责：

- 读取材料资产和 Align 结果；
- 完成产品定义和 Design 基线；
- 统一定义流程、角色、权限、状态、模块、数据范围、跨系统责任、异常路径和方案权衡；
- 对材料冲突做业务裁决；
- 将高影响未决事实写入 Design 的待确认部分。

不负责：

- 建立项目级材料索引；
- 重复提取基础事实；
- 在缺少材料资产时自行偷偷补建材料资产。

## 4. 材料资产目录

建议使用独立于阶段上下文的目录：

```text
.workflow/runtime/materials/
├── manifest.json
├── source-index.json
├── facts.json
└── runs/
    └── <run-id>.json
```

### manifest.json

记录项目当前材料版本：

```json
{
  "version": 1,
  "material_revision": "<stable revision id>",
  "sources": [
    {
      "source_id": "source-001",
      "path": "materials/业务说明.md",
      "sha256": "<hash>",
      "characters": 0,
      "lines": 0,
      "updated_at": "<timestamp>"
    }
  ],
  "generated_at": "<timestamp>"
}
```

### source-index.json

只做定位，不做产品决策：

- `source_id`；
- 标题和主题；
- 起止行号；
- 关键词；
- 对应来源哈希。

### facts.json

只记录材料层事实：

```json
{
  "version": 1,
  "material_revision": "<same as manifest>",
  "confirmed_facts": [],
  "source_conflicts": [],
  "missing_information": [],
  "non_derivable_items": []
}
```

每条记录必须包含：

- 事实陈述；
- `source_id`；
- 行范围；
- 来源哈希；
- 是否需要用户确认。

`facts.json` 不是 Design 唯一事实源，也不能绕过用户确认直接变成产品决策。

## 5. 一次读取和上下文边界

材料资产必须把“原文读取”和“后续业务建模”分开：

```text
原始材料
  -> 一次材料级模型读取
  -> facts.json（压缩事实 + 来源行范围）

Design / PRD / Review / Fix
  -> 只读取 facts.json
  -> 只有发生冲突或高影响疑点时，按来源行范围定点读取
```

每个后续阶段都禁止默认携带：

- 完整原始材料；
- 前一阶段完整对话；
- 其他阶段的完整输出；
- 已经被 facts.json 覆盖的重复证据。

因此，材料资产复用的验收重点不是“索引文件是否存在”，而是“后续模型调用是否再次收到同一份原始材料”。

## 6. 触发时机

### 5.1 首次进入 Align

```text
检查材料资产
  ├─ 已存在且版本有效：直接读取
  ├─ 不存在：执行一次项目级材料摄取
  └─ 存在但来源变化：增量重建变化来源并生成新 revision
```

Align 只读取材料资产，不再自行全文扫描原始文件。

### 5.2 直接进入 Design

```text
检查材料资产
  ├─ 已存在且版本有效：Design 直接读取
  ├─ 不存在但用户提供了文件：宿主执行一次无交互材料摄取
  ├─ 不存在且只有本轮文字需求：建立“本轮用户输入”材料源
  └─ 材料版本失效：先完成材料摄取，再启动 Design
```

无交互材料摄取只负责建立材料资产，不执行 Align 的追问和范围整理。

### 5.3 后续 Design 修改

只要材料 revision 未变化：

- 不重新扫描原始文件；
- 不重新建立索引；
- 不重新生成 facts；
- 只读取已有材料资产和当前 Design。

## 7. 失效与增量重建

### 文件未变化

通过 `path + sha256` 判断。材料 revision 不变，所有下游可复用材料资产。

### 文件新增或修改

只重新处理新增或修改的来源：

1. 更新 `manifest.json`；
2. 重建对应来源的索引片段；
3. 重新提取受影响来源的事实；
4. 合并其他未变化来源的事实；
5. 生成新的 `material_revision`；
6. 将旧 facts 标记为过期；
7. 要求 Design 判断是否影响已有业务模型。

### 文件删除

不得静默忽略。必须：

- 从 manifest 标记为删除；
- 使引用该来源的事实失效；
- 标记受影响的 Design 事实为待重新确认；
- 禁止直接沿用旧的确认结果。

## 8. Design 的最小输入

材料版本有效时，Design 只读取：

```text
.workflow/runtime/materials/manifest.json
.workflow/runtime/materials/facts.json
output/align/align.md（如存在）
用户本轮新增文字
Design 分析上下文包
适用场景卡
```

只有发现事实冲突、来源不足或高影响疑点时，才按 `source_id + line_start + line_end` 定点读取原文。

## 9. 当前上一版方案需要删除或迁移的内容

等本设计确认后再执行，当前不改代码：

- 从 Design D0 删除材料索引建立；
- 从 Design D0 删除材料事实提取；
- 从 Design 主链删除重复全文读取；
- 将材料索引输出目录从 `.workflow/runtime/context/design/` 迁移到 `.workflow/runtime/materials/`；
- 将材料事实从 Design handoff 改成项目级材料资产；
- 保留 Design handoff 仅用于业务模型和挑战结果；
- `context-pack` 只负责编译规范性规则，不再承担材料摄取；
- 将指标拆分为“材料摄取耗时”和“Design 模型运行耗时”。

## 10. 验收指标

至少使用同一固定输入运行三次，分别记录：

- 材料摄取耗时；
- Align 模型耗时；
- Design 模型耗时；
- Design 输入 token；
- 原始材料全文读取次数；
- 材料资产复用次数；
- 后续模型调用收到重复原文的次数；
- 上下文压缩次数；
- 端到端总耗时。

验收目标：

- 材料未变化时，Design 不触发材料摄取；
- 每个材料版本的原始材料模型级读取次数不超过 1 次；
- 后续 Design 修改不重新生成 facts；
- Design 主模型单次输入尽量不超过 50,000 token；
- Design 阶段 P50 不超过 10 分钟，P90 不超过 12 分钟；
- 不以增加压缩次数作为性能优化手段。
