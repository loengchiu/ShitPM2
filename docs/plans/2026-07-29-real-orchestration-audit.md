状态：讨论稿，未实施代码改动

## 1. 审计范围与结论

本审计只回答一个问题：为什么完整模式 Design 在真实项目中运行时间长、上下文不断膨胀，以及项目级材料摄取应该删除什么、保留什么。


项目工作目录：

```text

```

先纠正两个容易混淆的判断：

1. **不是完全没有启用子代理。** 日志中确实出现了 2 次 `spawn_agent`：一次材料事实提取员，一次 Design 挑战员。但它们分别在约 03:24 和 03:37 才启动，发生在主 Agent 已经完成多轮原始材料读取、Design 重写和多次上下文压缩之后。因此，子代理没有承担前期主要工作，也没有把主 Agent 从长对话中隔离出来。
2. **主要瓶颈不是本地文件读取。** 日志中 207 次工具调用带有可解析的 `Wall time`，累计约 99.9 秒；相比持续数十分钟的模型推理和多轮长上下文调用，本地扫描不是主耗时。文件读取仍然是上下文膨胀的入口，但不是操作系统读盘慢。

核心结论：

> 当前编排不是“材料读取慢”，而是“同一个主 Agent 在一个长会话里反复读取材料、反复读取 Design、反复读取规则，并把每轮结果继续留在上下文中”。项目级材料摄取如果只是新增索引、事实包和检查步骤，而不删除旧读取链，反而会更慢。

## 2. 真实运行的硬证据

## 3. 真实调用时序

### 3.1 启动与 Align：第一次读取链

```text
主 Agent
  ├─ 读取记忆和项目规则
  ├─ 一次性读取多个阶段 Skill
  ├─ 扫描项目、V1 和工作流目录
  ├─ 读取 V1 主 PRD 的标题和前 260 行
  ├─ 再读取 V1 主 PRD 的 1-1040 行分段内容
  ├─ 再按三级标题重新读取 V1 主 PRD 各段摘要
  ├─ 再用关键词检索 V1 主 PRD
  ├─ 读取 FeatureList、项目状态、brief、source-index
  └─ 写入 Align
```

对应日志中的关键位置：

- 第 30 行：V1 标题和前 260 行；
- 第 37 行：V1 主 PRD 1-1040 行分段读取；
- 第 53 行：按三级标题重新读取 V1 片段；
- 第 58 行：关键词检索 V1；
- 第 64、69 行：再次读取多个历史材料。

这里已经出现第一个重复读取问题：同一份 V1 主 PRD 在一次 Align 前置工作中同时使用了“前段全文、分段全文、标题摘要、关键词检索”四种读取方式。对确定性程序来说这些操作很快，但对模型来说，每次工具输出都会成为当前会话的新上下文。

### 3.2 第一次 Design：主 Agent 持续建模和反复回读

Align 完成后，Design 仍然由同一个主 Agent 连续执行。日志显示它没有拿到一个稳定、短小、版本化的材料事实包，而是继续在当前长会话中：

```text
主 Agent
  ├─ 重新读取 spm-design Skill、状态和规则
  ├─ 生成或修改 output/design/design.md
  ├─ 多次读取 design.md 的局部区间
  ├─ 读取 Design 检查脚本和状态机规则
  ├─ 回到 V1 主 PRD核对业主五项能力
  ├─ 再修改 Design
  └─ 继续读取 Design 局部区间并修正文档结构
```

日志中约 41 次命令引用 `output/design/design.md` 进行区间读取、标题扫描、全文读取或生成后检查；这不等于 41 次完整全文读取，但足以说明 Design 生成和验证没有形成“模型一次写入、程序一次验证”的边界，而是主 Agent 自己反复读回自己的产物。

特别关键的是：

- 第 589、594、599 行（约 02:31:33～02:31:51）再次检索和大段读取 V1 主 PRD；
- 第 650、655 行（约 02:34:09～02:34:18）再次按完整业务区间读取 V1 主 PRD，覆盖车辆、车流、车位、两客一危、分析等主要章节；
- 这些读取发生在 Design 已经生成、又进入纠偏的阶段，而不是首次材料发现阶段。

因此，Design 的实际输入不是“Align 结果 + 规则”，而是“历史材料 + 当前 Design + 规则 + 之前所有工具输出 + 用户确认过程”。

### 3.3 上下文压缩后：旧链路没有消失

日志出现 5 次上下文压缩：

```text

```

压缩后主 Agent 获得新的交接摘要，但后续仍然继续读取：

- `spm-design/SKILL.md`；
- `output/design/design.md`；
- V1 主 PRD及 FeatureList；
- 需求卡、brief 和其他历史材料；
- 新生成的 `source-index`、`material-facts`、`design-model`、`design-challenge`。

其中第 1165、1170、1175 行（约 03:25:07～03:25:27）在接近后半程时再次读取 V1 主 PRD、V2 normalized 文件和 DOCX；第 1180、1185、1190 行继续读取 brief、FeatureList 和需求卡。此时原始材料并没有发生版本变化，却再次进入主 Agent 上下文。

这证明：上下文压缩只是把旧内容替换成摘要，不能阻止编排在下一轮重新把同一材料读回来。

### 3.4 子代理和新材料链：启动太晚，而且是叠加关系

真实运行后半程才出现新的材料交接链：

```text
原始材料
  -> source-index
  -> 材料事实提取子代理
  -> material-facts.json
  -> 主 Agent读取并修正事实包
  -> design-model.json
  -> Design挑战子代理
  -> design-challenge.json
  -> 主 Agent写作和验证
```

对应时间：

- 约 03:24:49：启动材料事实提取子代理；
- 约 03:32:56：材料事实提取完成；
- 约 03:37:39：启动 Design 挑战子代理；
- 约 03:45：主 Agent生成写作上下文包；
- 约 03:58:58：主 Agent生成验证上下文包并运行多个检查。

问题不在于这条链本身没有价值，而在于它没有替换前面的旧链路。实际效果接近：

```text
旧材料全文读取链
  + 新索引链
  + 新事实提取链
  + 新挑战链
  + 新上下文检查链
```

这正是“加了编排后更慢”的直接原因。

## 4. 重复读取和上下文重复传递点

### P0：主 Agent长会话承载全部阶段

从 Align 到 Design 纠偏、事实提取、挑战、写作、验证，核心决策仍在同一个主会话中连续完成。即使子代理被调用，主 Agent的原始上下文和历史工具输出仍未被切断。

**后果：**

- 用户确认、旧版分析、旧 Design、修改过程和验证过程全部成为后续输入的一部分；
- 每次工具调用都在增加对话历史，而不是只增加当前任务所需的材料；
- 压缩后仍需通过新的读取调用恢复关键内容，造成“压缩—重读—再压缩”循环。

### P0：同一材料在 Align和Design分别全文读取

V1主PRD至少在以下三个阶段重新被读取：

1. Align前置扫描；
2. Design纠偏时按完整业务区间回读；
3. 上下文压缩后的新一轮 Design 重建时再次回读。

原始材料没有变化，但模型级读取没有复用结果。

### P1：规则和模板重复装载

`spm-design/SKILL.md` 在日志中至少被 13 次相关命令读取或检索，`spm-align/SKILL.md` 至少 3 次；初始阶段还将多个阶段 Skill 一次性全文读取。压缩后重新读规则是可以理解的，但当前没有短版规则包或稳定边界，导致每次恢复都将长规则和业务材料一起带回。

### P1：Design 自己的产物反复回读

`output/design/design.md` 被约 82 次命令引用，其中约 41 次是局部区间读取、标题扫描或全文读取。部分读取是必要验证，问题在于：

- 写作、结构修正、字段补写、状态机修正和验证没有分开；
- 主 Agent不断读回整个 Design 的大区间来决定下一处修改；
- 生成与验证没有使用独立的短交接结构。

### P1：事实包生成后仍保留历史原文路径

`material-facts.json` 生成后，主 Agent仍然可以继续读取 V1原文。事实包没有成为默认事实入口，也没有形成“只有冲突才定点回读”的硬边界。

### P1：确定性检查输出和模型分析混在同一主会话

`context-pack`、`stage-prep`、`review-precheck`、`state-machine-check` 等检查的输出被连续注入主 Agent会话。检查结果本应是短的机器结论；当前编排同时读取脚本源码、规则全文和大量产物区间，使“验证”变成新的长上下文阶段。

## 5. 当前编排的真实职责错位

| 责任 | 当前实际位置 | 问题 |
|---|---|---|
| 原始材料发现 | Align前置和Design多轮读取 | 没有项目级一次性资产，阶段重复发现 |
| 文件清单与索引 | Design后半程临时建立 | 建立太晚，且与旧读取链并存 |
| 材料基础事实 | 主 Agent边读边提取，后半程才由子代理提取 | 事实提取不是一次性责任 |
| 产品定义 | 主 Agent | 责任正确，但被原始材料和历史会话淹没 |
| 业务建模挑战 | 后半程才由子代理执行 | 挑战没有前置到 Design 写作前的稳定边界 |
| 文档写作 | 主 Agent多轮修改 | 写作与建模、验证交织，导致反复回读 |
| 确定性验证 | 脚本和主 Agent共同执行 | 工具输出过长，且主 Agent承担不必要的规则解释 |

## 6. 目标编排：一次摄取，阶段复用

### 6.1 材料版本首次出现时

```text
项目接收材料
  ├─ 确定性扫描：文件清单、哈希、行数、标题、主题索引
  └─ 一次模型级材料事实整理
       └─ .workflow/runtime/materials/facts.json
```

材料事实整理只产生：

- 可验证事实；
- 来源文件和行范围；
- 冲突；
- 缺失信息；
- 不能直接推导的事项。

它不决定产品流程、角色、权限、状态、模块或方案。

### 6.2 Align（可选）

```text
manifest.json + facts.json + 用户本轮文字
  -> output/align/align.md
```

Align 不读取原始材料全文。只有用户明确提出“核对原文”或事实包中出现高影响冲突时，才按来源定位读取小范围证据。

### 6.3 Design

```text
facts.json + align.md（如存在）+ 用户本轮确认 + 设计规则短包
  -> Design模型/结构化交接
  -> output/design/design.md
```

Design 默认禁止读取：

- 原始材料全文；
- 完整历史对话；
- 其他阶段完整输出；
- 已被事实包覆盖的证据。

Design 可以读取原文的唯一例外是：事实冲突、高影响疑点或用户要求核验，并且必须按 `source_id + line_start + line_end` 定点读取。

### 6.4 Design挑战和验证

```text
Design挑战：design-model.json + facts.json + 适用规则
Design写作：design-model.json + challenge.json + 写作规则
Design验证：design.md + 机器检查结果
```

挑战、写作、验证使用独立短会话或独立上下文包。它们不能把前一阶段完整对话作为输入。

## 7. 必须删除、必须保留、暂不动

### 必须删除或迁移

1. Design 内对原始材料的默认全文扫描；
2. Design 内重新建立项目材料索引的逻辑；
3. Align和Design各自生成基础事实副本的逻辑；
4. `material-facts.json` 生成后仍默认回读整份原始材料的路径；
5. 写作和验证阶段携带完整历史对话的路径；
6. 将多个阶段 Skill、模板、脚本源码一次性全文注入主 Agent的做法。

### 必须保留

1. 确定性文件哈希和版本失效检查；
2. 带来源定位的事实、冲突和缺失记录；
3. Design对角色、流程、权限、状态、模块边界、异常路径和方案权衡的完整责任；
4. 用户确认和高影响未决事实处理；
5. 独立的 Design挑战和机器验证；
6. Align可选，不改成硬前置。

### 暂不动

1. 不通过增加压缩次数来解决问题；
2. 不通过单纯增加子代理数量来解决问题；
3. 不引入 Hook；
4. 不在本轮直接重写 PRD、Prototype或下游链路；
5. 不把材料事实包升级成产品唯一事实源；Design确认后的 `output/design/design.md` 仍是产品事实基线。

## 8. 验收指标

### 必须满足

- 同一个材料版本的原始材料模型级读取次数 ≤ 1；
- 材料版本未变化时，不重新生成事实包；
- `facts.json` 生成后，Design、PRD、Review、Fix的默认模型输入中原始材料全文出现次数 = 0；
- 发生冲突时，只允许按来源定位读取必要行范围；
- Design写作、挑战、验证不携带完整历史对话；
- 子代理承担明确的隔离任务，不作为主 Agent长会话的附加工具调用。

### 性能指标

首轮先比较旧链路与新链路，不先承诺绝对秒数。至少记录：

- 原始材料模型读取次数；
- 各阶段模型输入 token；
- 全链路累计输入 token；
- 上下文压缩次数；
- 主 Agent和子代理各自耗时；
- 本地工具耗时；
- Design阶段端到端耗时。

建议目标：

- Design正常路径输入不超过模型窗口的 35%～50%；
- Design单次阶段交接包控制在可审计的固定上限内；
- 在材料不变的重复运行中，跳过材料事实提取；
- 新链路累计输入 token相对该真实样例下降 50%以上，再讨论进一步优化。

## 9. 当前待确认事项

本稿只提出编排边界，不实施代码。实施前需要确认：

1. 是否接受“项目级材料摄取”作为项目级责任，而不是 Align 或 Design 的内部步骤；
2. 是否接受“同一材料版本只做一次模型级事实读取”；
3. 是否接受 Design 默认不读原始材料全文，只在冲突时定点回读；
4. 是否接受挑战、写作、验证使用短交接，而不是复用完整历史对话；
5. 是否接受先删除旧读取链，再接入材料资产，不允许新旧链路并存。

在以上决策确认前，不修改 `skills/`、`contracts/`、`scripts/`、`schemas/` 或运行时文件。
