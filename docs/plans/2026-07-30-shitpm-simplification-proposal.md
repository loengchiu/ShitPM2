# ShitPM 简化重构提案（修订版）

日期：2026-07-30  
状态：讨论稿，未动本提案所描述的简化重构代码  
适用范围：ShitPM 仓库（skills / scripts / contracts / references）

---

## 一、先给结论

这份提案的**方向基本正确，但原方案的删除范围过大，且把若干推测写成了事实**。

建议采用以下目标：

> 保留确定性门禁、事实落盘、缓存、哈希、断点恢复和结构检查；删除大部分细粒度分析编排；把 A、B、C 改为层级级分析；把三个生成后检查合并为一次独立综合审查；规则包、上下文指标和材料索引保留，但改成轻量审计与观测机制；先做新旧路径对比，再逐步淘汰旧路径。

本提案不建议一次性删除大量脚本，也不建议在没有在线质量对比前直接断言“粗粒度调用质量不下降”。

---

## 二、当前事实、推测与待验证事项

### 2.1 已由仓库和历史记录确认的事实

1. 当前 Python 脚本约 13,278 行，其中非测试脚本约 9,375 行；当前 `SKILL.md` 合计约 1,144 行。非测试脚本约为 Skill 文档的 8 倍。
2. 当前完整模式任务图在 3 个材料文件时包含 38 个任务节点，其中 34 个是隔离代理动作，4 个是确定性命令动作。材料数量变化时，材料事实提取动作数量也会变化。
3. 34 个隔离代理动作由以下部分组成：3 个材料事实提取、23 个 A/B/C 分析、4 个基线或挑战汇总、1 个 Design 写作、3 个生成后检查。这里是编排器声明的隔离动作数量，不等同于已经被真实宿主执行的模型调用数量。
4. 当前完整模式确实有 3 个独立生成后检查：产品经理可读性、Park 覆盖、下游充分性。
5. 当前 `source-index.py` 优先按标题和章节建立材料片段；没有标题时才使用 80 行分片。材料索引被子代理上下文契约用于定位来源和限制读取范围。
6. 当前 `next/accept`、输入哈希、输出收据和 Design 结构门禁已经存在，Design 写作结果会在接受前检查新格式。
7. 当前 Design 写作者接受门禁主要检查成品存在性、结构和部分交接物；还没有明确要求 Design 写作者接受时重新核对所有 A/B/C 基线的存在性和新鲜哈希。
8. 历轮报告显示，问题来源不只包括程序 Bug，也包括 Skill、契约、文档、安装器和接线不一致。
9. 现有宿主无法完整提供每次模型请求的真实输入、子代理实际文件访问和隐藏上下文继承审计，因此目前无法仅凭仓库测试证明上下文压缩的唯一根因。
10. 最近一次真实项目运行记录显示，预定的完整编排没有按计划执行：主代理在前期多轮读取原始材料并发生多次上下文压缩，子代理没有在前期承担主要分析，直到较晚阶段才启动。该记录可以证明“实际执行偏离了预定编排”，但不能单独证明某一个具体节点数量是唯一根因。

### 2.2 高概率但尚未完全证明的判断

1. 细粒度任务越多，主代理需要处理的动作卡、回执和状态交互通常越多，主代理上下文膨胀风险越高。
2. 子代理长篇分析在被主代理接收后，可能成为上下文膨胀的重要来源；当前规则主要通过约定和输出文件解决，宿主级硬拦截尚不完整。
3. A/B/C 层级级调用可能比当前 23 个细分分析更高效，但是否保持同等业务质量，必须通过在线对比验证。
4. 规则包哈希、上下文指标和 token 估算不能直接减少上下文，但它们可以帮助发现重复读取、输入过大和重构是否有效。

### 2.3 不能直接当成事实的判断

以下说法在没有新的在线证据前不得写成结论：

- 子代理一定不会触发自身上下文压缩；
- 31 个节点一定是主代理上下文膨胀的最大来源；
- 当前模型一次完成整个 A 层已经证明质量不下降；
- 所有历史问题都是程序层 Bug；
- 80 行材料分片可以直接删除；
- 删除所有 token、规则包和运行指标机制不会损失审计能力。

## 三、重构原则

### 3.1 程序只负责模型不稳定的确定性工作

程序继续负责：

- 材料版本和文件哈希；
- 材料索引、来源定位和缓存；
- 事实、基线和审查结果落盘；
- 输入输出新鲜度检查；
- 结构、字段、页面、操作和交接物检查；
- 断点恢复和局部重试；
- 最终产物的出口门禁。

程序不再负责：

- 把一个业务层人为拆成大量细小语义任务；
- 用正则猜测自然语言的复杂业务含义；
- 通过大量动作卡替模型安排分析顺序；
- 把 token 估算伪装成上下文治理本身。

### 3.2 上下文治理优先减少“重复装载”和“长文本回传”

优先级应当是：

1. 材料只索引一次；
2. 材料事实只提取一次；
3. 每个层级只读取它需要的事实和上游基线；
4. 分析正文只写文件，主对话只接收短回执；
5. 主代理需要事实时从文件重读，不依赖历史对话；
6. 用输入哈希和文件收据保证重读的是当前版本。

### 3.3 不是“程序越少越好”，而是“程序做更适合程序做的事”

结构完整性、哈希、版本、依赖和出口门禁适合程序；业务判断、冲突解释、方案权衡和产品表达适合模型。重构不能因为反对过度编排，就把程序应该守住的出口也删除。

## 四、推荐目标架构

### 4.1 目标流程

```text
材料索引（确定性命令）
    ↓
材料事实提取（按材料并行，按体量动态决定是否合并）
    ↓
A 层：用户、目标、场景、范围、成功标准
    ↓
B 层：业务流程、对象、规则、状态、权限、数据范围
    ↓
C 层：页面、字段、操作、异常、验收
    ↓
Design 写作：汇总 A/B/C，生成 design.md
    ↓
一次独立综合审查：可读性、覆盖度、下游可承接性
    ↓
必要时局部修复
```

### 4.2 模型调用目标不要写死

不建议把目标固定成 6—7 次，因为材料数量和体量不同。

建议目标为：

- 材料事实提取：按材料并行；
- A 层：1 次；
- B 层：1 次；
- C 层：1 次；
- Design 写作：1 次；
- 独立综合审查：1 次；
- 必要时只重跑修复动作。

对于 3 个材料文件，预期约为 8 个隔离代理动作；如果材料已经形成一个质量足够高的事实包，可以合并材料事实提取，降到约 6 个。这里是目标范围，不是未经验证的承诺。

### 4.3 为什么不把 A/B/C 合成一个大调用

A、B、C 仍然保留为三个层级，原因是：

- A 负责理解用户和业务目标；
- B 负责业务规则、流程、状态和权限；
- C 负责页面、字段、操作和验收；
- 三层分别形成可复用的事实基线；
- 任一层失败时可以只重跑该层及其下游。

真正要删除的是层内的细碎任务，不是删除 A/B/C 的业务边界。

### 4.4 生成后检查合并为一次独立综合审查

不建议把检查全部并入 Design 写作提示词，因为写作者自查容易重复自己的遗漏。

推荐生成一个综合审查结果，至少覆盖：

- 产品经理是否能读懂；
- 关键角色、场景和闭环是否覆盖；
- 页面、区块、字段和操作是否完整；
- 状态、权限、数据范围和异常是否一致；
- PRD 和 Prototype 是否可以直接承接；
- 是否存在高影响未决问题。

综合审查通过后才能建立最终 Design 索引；失败时只生成局部修复动作，不重新运行 A/B/C。

## 五、各现有机制的处理方式

| 机制 | 处理建议 | 原因 |
|---|---|---|
| 材料索引 | 保留并轻量化 | 它负责版本、来源定位和读取边界，不能删除 |
| 材料事实缓存 | 保留 | 避免重复读取同一材料 |
| 80 行兜底分片 | 保留但改为自适应 | 无标题长材料仍需要分片，不能直接删除 |
| `next/accept` | 保留并收缩到层级关卡 | 当前宿主执行纪律不稳定，不能只靠 Skill 自觉 |
| 输入哈希和输出收据 | 保留 | 这是断点恢复和防陈旧结果的基础 |
| Design 结构门禁 | 保留并加强 | 防止字段、页面、操作在写作时丢失 |
| 规则包 | 保留哈希审计，取消重复构建 | 每次运行或每个阶段生成一次即可 |
| token 估算 | 保留为观测和超限保护 | 不能治疗膨胀，但能发现输入过大 |
| 运行指标 | 保留为诊断 | 没有指标无法验证重构是否真的提速 |
| 三个生成后检查 | 合并为一次独立综合审查 | 减少调用，同时保留独立审查能力 |
| PRD 语义正则 | 新格式收缩为结构化比较 | 自然语言正则容易产生假阳性 |
| 旧格式兼容 | 读取兼容，生成废弃 | 避免破坏历史项目，同时防止新项目继续产生旧格式 |

### 5.1 为什么仍然保留 `next/accept`

最近一次真实项目运行已经提供了反例：即使 Skill 和任务图写明了应当先做材料摄取、再由子代理承担分析，实际运行中仍出现主代理前期反复读取原始材料、子代理较晚启动、上下文多次压缩的情况。这个实证只能证明“不能只靠 Skill 文本要求主代理自觉遵守顺序”，不能证明所有问题都由任务数量造成。

因此，重构后仍保留 `next/accept`，但把它从大量细粒度任务节点收缩为少量层级关卡：

- `next` 只返回当前可以执行的层级动作及其输入文件；
- `accept` 检查该层级的输出、输入哈希、结构和上游依赖；
- 未通过 `accept` 时不能进入下一层；
- Skill 负责说明怎么做，`next/accept` 负责约束是否可以继续。

这不是为了增加流程，而是为了防止“文档要求的顺序”和“实际执行的顺序”再次分离。

### 5.2 旁路观测层：保留，但不参与主流程门禁

规则包哈希、`token_estimate.py`、`context-budget.py`、`context-run.py`、`context-pack.py` 以及运行指标暂不删除，但统一降级为**旁路观测层**，不再作为新编排的强依赖，也不直接决定 `next/accept` 是否通过。

具体约束：

- `token_estimate.py` 的结果是估算值，不得当作宿主真实 token；
- `context-budget.py` 默认只报告，不因估算误差阻断主流程；
- `context-run.py` 继续记录运行情况，但运行记录缺失不能伪造成功，也不能单独阻断核心编排；
- `context-pack.py` 保留兼容能力，但新编排不以它作为唯一材料读取通道；
- 所有观测数据标明 `estimated`、计算方法、工具版本，以及是否来自宿主真实数据；
- 观测数据异常不应改变核心编排结果；只有当观测层错误导致接受陈旧结果、跳过必要门禁或污染产品事实时，才升级为高优先级问题，普通估算偏差按低优先级处理。

规则包哈希的覆盖边界必须明确：它只覆盖规则包的生成、版本和声明引用，不覆盖子代理绕过规则包后直接读取原始 `references/*.md` 的行为。当前宿主没有可靠的文件级读取审计，因此规则包哈希只能证明规则版本一致性和变更情况，不能被表述为完整的实际读取审计。后续只有在宿主提供文件级读取记录后，才能补足这部分审计。

## 六、必须补强的出口门禁

### 6.1 Design 写作接受前核对上游基线

`design-editor` 或其他 Design 写作动作接受前，必须确认：

- A baseline 存在且通过交接检查；
- B baseline 存在且通过交接检查；
- C baseline 存在且通过交接检查；
- Design brief 和冲突记录存在且版本正确；
- 所有上游基线的输入哈希仍与当前运行一致；
- Design 写作动作使用的输入文件哈希与当前文件一致。

这项检查不能只写在 Skill 中，必须接入 `accept`。

### 6.2 输出存在不等于输出合格

当前部分输出检查只验证：

- 文件存在；
- JSON 可以解析；
- 输入哈希没有变化。

重构后应增加最小结构要求，例如：

- `schema_version` 正确；
- `task_id` 正确；
- `status` 正确；
- `coverage` 非空或明确声明不适用；
- `source_refs` 存在；
- 冲突、问题和未决项具有固定结构。

程序不判断业务结论是否正确，但要防止模型只写一个空壳文件就通过门禁。

### 6.3 子代理回执控制

在宿主无法硬限制完整输出之前，先在动作契约中明确：

- 分析正文必须写入声明的输出文件；
- 回执只返回完成状态、结论摘要和文件路径；
- 不返回完整分析正文；
- 主代理不得把专项正文复制回长期对话；
- 需要事实时重新读取文件。

这仍不是宿主级审计，但比只写口头建议更明确。后续如宿主提供输出拦截能力，再增加硬限制。

## 七、实施顺序

### 第一阶段：先测量，不删代码

新增或补充合成项目测试，记录：

- 每个动作的输入文件和估算 token；
- 每个动作输出文件大小；
- 主代理收到的动作卡和回执大小；
- 预期隔离代理动作数；
- 实际模型调用数（宿主能提供时）；
- 总耗时；
- Design 的字段、操作、角色、状态和异常覆盖情况。

先建立旧流程基线，不能只凭体感判断新流程更快。

### 第二阶段：增加层级级新路径

不要先删除旧任务图，新增一个实验模式，例如：

- `full-layered`：A/B/C 层级编排；
- `full`：保留现有路径，作为对照。

两条路径使用相同的：

- 材料索引；
- 材料事实；
- Design 模板；
- Design 结构门禁；
- 输出格式。

### 第三阶段：合并生成后检查

先把三个检查合并为一个独立综合审查，不直接删除审查能力。

验收重点：

- 是否减少模型调用；
- 是否减少主代理回执体量；
- 是否仍能发现字段遗漏、权限遗漏和状态遗漏；
- 是否能生成局部修复动作。

### 第四阶段：收缩规则包和指标机制

只有确认它们没有被其他流程依赖后，才做以下调整：

- 每次运行生成一次规则清单；
- 每个阶段复用规则清单；
- token 检查默认只记录，不把估算值误称为真实模型 token；
- 指标文件保留，但不阻断正常运行，除非超过明确安全上限；
- 规则包哈希保留为版本审计，不宣称覆盖子代理的全部实际文件读取；
- 观测层的普通数据错误不阻断主流程，避免把估算工具的维护问题重新变成编排问题。

### 第五阶段：收缩 PRD 检查器

新格式路径保留：

- 页面、字段、操作是否存在；
- 字段属性是否一致；
- 状态和操作是否一致；
- Design 是否定义了下游使用的内容。

删除或隔离：

- 对自然语言规则的模糊枚举推断；
- 对旧格式混合列的强语义判断。

旧格式检查建议改为兼容警告，后续再宣布废弃。

### 第六阶段：再决定是否删除旧任务图

满足以下条件后，才考虑删除旧路径：

- 层级路径连续多次通过合成项目测试；
- 真实项目质量不低于旧路径；
- 字段和操作遗漏率没有上升；
- 总耗时和主代理上下文明显下降；
- 断点恢复和局部修复没有退化；
- 产品经理确认 Design 可读性和确认效率没有下降。

## 八、验收标准

### 8.1 性能和上下文

- 核心隔离代理动作显著少于当前完整模式；
- 材料只索引一次，未发生无意义重复读取；
- 主代理回执不包含专项分析正文；
- 如宿主提供可靠的上下文压缩记录，则记录压缩次数及压缩前后的输入规模，并比较新旧流程；
- 如宿主不提供压缩记录，不把“压缩次数下降”写成硬验收条件，改用以下间接指标判断主代理负载是否下降：动作卡总字符数、回执总字符数、主代理处理轮次数、子代理正文回传字数、模型调用次数和总耗时；
- 间接指标只能证明对话负载或运行成本变化，不能证明上下文压缩次数本身下降；
- 总耗时不高于旧流程，目标是在质量不下降的前提下明显下降。

### 8.2 质量

- 页面清单和正式页面双向一致；
- 字段逐项列出，不出现合并字段；
- 操作逐项列出，不把操作混入字段；
- 角色、权限、数据范围、状态和异常完整；
- Design 能被产品经理直接阅读和确认；
- PRD 和 Prototype 可以直接承接，不自行补充高影响事实。

### 8.3 确定性和恢复

- 任一层失败只重跑该层及下游；
- 材料未变化时不重复生成材料事实；
- 输入变化时陈旧结果不能被接受；
- 缺少上游基线时 Design 写作不能通过；
- Design 结构不合格时不进入后续审查和完成报告；
- 状态文件丢失时可以根据收据和输入哈希恢复或明确提示迁移。

## 九、执行方式

本提案的实施必须采用“先测量、再做新路径、最后决定是否淘汰旧路径”的顺序，不允许一开始就删除旧任务图或直接用真实项目反复试错。

### 9.1 执行前准备

1. 使用合成项目或固定脱敏材料建立旧流程基线；
2. 确认当前测试和仓库状态，保留现有测试结果；
3. 不修改真实项目的 `output/design/design.md`，不手工修改材料清单或事实缓存来绕过门禁；
4. 不执行 Git commit 或 push；
5. 先确认宿主能提供哪些记录：模型调用数、耗时、动作卡、回执、子代理启动状态和可用的 token 数据。拿不到的指标必须标记为“不可测”，不能伪造。

### 9.2 实施顺序

#### 第一步：建立旧流程基线

在固定材料、固定模式和固定规则版本下运行旧路径，记录：

- 是否完成；
- 模型调用次数（宿主能提供时）；
- 主代理动作卡总字符数；
- 主代理回执总字符数；
- 子代理正文回传字数；
- 材料原文模型级读取次数；
- 总耗时和各阶段耗时；
- 页面、字段、操作、角色、权限、状态和异常覆盖；
- 是否发生上下文压缩；若无宿主记录，标记为不可测；
- 失败位置、重试次数和断点恢复结果。

#### 第二步：实现或验证层级级实验路径

保留旧路径，新增实验路径，例如 `full-layered`。实验路径至少包含：

1. 一次材料索引和材料事实整理；
2. A、B、C 三个层级分析，可并行的层级并行执行；
3. 一个 Design 写作动作；
4. 一个独立综合审查动作；
5. `next/accept` 层级关卡；
6. 输入输出哈希、结构门禁和断点恢复。

实验路径的输入材料、Design 模板、输出结构和验收标准必须与旧路径一致，避免通过降低要求制造“变快”。

#### 第三步：做合成项目对比

至少使用三类固定样例：

- 只有展示页面和字段的简单样例；
- 包含角色、权限、状态和页面操作的业务样例；
- 包含冲突、缺失材料和异常分支的复杂样例。

每类样例至少执行旧路径和实验路径各若干次，记录平均值和最差值。若某条路径只跑一次，不得据此宣布质量或性能结论。

#### 第四步：通过合成项目门槛后，再做一次真实项目对照

真实项目只用于最终对照，不用于定位基础编排问题。应选择同一项目、同一材料版本，分别运行旧路径和实验路径；不得修改真实项目输入来配合实验路径。若两条路径产物存在差异，先做质量对照和根因分析，再决定是否扩大测试。

#### 第五步：决定是否收缩旧路径

只有当实验路径在质量、性能、断点恢复和产品经理可读性方面都达到验收标准，才可以把旧路径标记为待淘汰。未经连续对比验证，不删除旧任务图。

### 9.3 新会话执行时的硬性限制

- 不要直接进入新的真实项目；
- 不要先删除旧脚本、旧任务节点或兼容逻辑；
- 不要跳过 `next/accept`；
- 不要把规则包哈希当作文件读取审计；
- 不要把 token 估算当作宿主真实 token；
- 不要因为观测指标缺失就伪造通过；
- 不要修改真实项目产物来绕过材料或新鲜度门禁。

## 十、验收方式

验收分为“能不能跑”“跑得是否更轻”“结果是否合格”三层，必须按顺序判断。

### 10.1 第一层：流程可运行

必须全部满足：

- 合成项目能够从材料索引进入事实整理、A/B/C、Design 写作和综合审查；
- `next/accept` 能阻止缺少上游基线、输入哈希过期或结构不合格的输出继续向下；
- 任一层失败后可以只重跑该层及下游，不必从头读取全部材料；
- 材料未变化时不重复生成材料事实；
- 观测层数据损坏不会改变核心编排结果；
- 不能通过空文件、陈旧文件或手工修改 manifest 绕过门禁。

### 10.2 第二层：运行负载和性能

新旧路径必须使用同一材料版本、同一模式和同一验收规则比较。至少比较：

- 模型调用次数；
- 主代理动作卡总字符数；
- 主代理回执总字符数；
- 子代理正文回传字数；
- 材料原文模型级读取次数；
- 总耗时；
- 各阶段耗时；
- 宿主能提供时的输入 token、缓存输入 token、输出 token 和压缩记录。

通过条件建议为：在 Design 质量不下降、字段和操作遗漏率不升高的前提下，实验路径的主代理动作卡和回执总字符数明显下降，材料原文模型级读取次数不增加，总耗时不高于旧路径；若性能没有改善，不得以“调用节点更少”代替结论。

### 10.3 第三层：Design 质量

由产品经理按同一份检查清单确认，至少检查：

- 页面清单与正式页面双向一致；
- 每个字段独占一行，字段属性完整；
- 页面操作单独列出，不混入字段；
- 角色、权限、数据范围、状态和异常完整；
- 设计中的未决事项、冲突和假设有明确标记；
- Design 可直接阅读和确认，不需要产品经理先理解编排实现；
- PRD 和 Prototype 可以直接承接，不自行补充高影响事实。

建议至少记录以下差异，而不只写“通过/不通过”：

- 字段遗漏数；
- 字段属性不一致数；
- 操作遗漏数；
- 状态或状态流转遗漏数；
- 权限和数据范围遗漏数；
- 异常和失败反馈遗漏数；
- 产品经理发现并需要返工的问题数。

### 10.4 验收结论规则

- 只满足第一层：说明流程可运行，不能说明变快或质量达标；
- 满足第一、二层：说明运行负载或性能改善，仍不能说明业务质量等价；
- 只有三层全部满足，才允许把实验路径作为默认路径；
- 旧路径只有在实验路径连续通过合成项目和真实项目对照后，才进入淘汰评估；
- 宿主无法提供的指标必须写明“不可测”，不能用估算值冒充真实值。

## 十一、其他 AI 讨论时需要重点确认的问题

1. A/B/C 各自一次调用，是否足以覆盖原有责任清单？需要哪些最小输出字段？
2. 材料事实提取应按材料并行，还是按总材料体量动态合并？
3. 综合审查是否覆盖产品经理可读性、Park 覆盖和下游承接三类责任？
4. 是否保留 `next/accept`，但把任务从细粒度节点收缩为层级关卡？本提案建议保留。
5. 规则包是否改为“每次运行一次、每阶段复用”的轻量哈希清单？本提案建议保留哈希审计，不删除。
6. 旧格式是否只保留读取兼容，不再生成和强语义校验？本提案建议这样处理。
7. 新旧流程比较时，是否把字段遗漏率、操作遗漏率、状态遗漏率和产品经理确认时间作为质量指标，而不是只看耗时？
