> 日期：2026-07-31  
> 状态：待执行  
> 适用对象：实施 PRD 优化的 AI、后续复核者、产品经理  
> 验收对象：模板、规则、Skill、Review、既有脚本适配、用户说明和真实样本结果。

## 1. 验收结论口径

本轮验收不能用“新版 PRD 行数超过 Design”作为通过条件。

行数只能说明文本长度，不能证明以下事项：

- Design 的事实是否全部被准确承接；
- 同一业务闭环是否被放在一起；
- 字段、状态、权限和异常是否有明确落点；
- PRD 是否新增了 Design 未授权事实；
- 人类是否能独立读懂一个模块；
- 流程图是否与正文一致。

本轮以“规则一致、工具可用、样本正确、人读可用”为通过标准。

最终只有同时满足以下四层验收，才能判定完成：

1. **规则层通过**：模板、写作规则、Skill、示例和 Review 口径一致；
2. **工具层通过**：上下文装载和既有确定性脚本适配新结构，相关回归通过；
3. **样本层通过**：简单样本与智慧停车区真实复杂样本均能生成符合新结构的候选 PRD；
4. **语义层通过**：候选 PRD 对 Design 无高影响遗漏、无事实冲突、无未授权新增，且业务模块可独立阅读。

任何一层未通过，都不能用其他层的通过代替。

## 3. 第一层：规则与结构一致性验收

## 3.1 PRD 模板验收

检查文件：`templates/prd.md`

### 必须满足

- 保留 `context:prd-template:start` 和 `context:prd-template:end`；
- 顶层结构体现：
  - 文档信息；
  - 产品定义与范围；
  - 系统全景与共享规则；
  - 业务闭环模块；
  - 待确认事项索引；
- 业务模块骨架能容纳：
  - 目标与边界；
  - 业务对象；
  - 角色、权限与数据范围；
  - 流程；
  - 状态与规则；
  - 按业务阶段展开的功能；
  - 字段；
  - 外部协作、异常与恢复；
  - 模块验收；
  - 模块待确认事项；
- 明确说明并非每个项目都要机械保留空章节；
- 页面能够在系统映射和业务阶段中定位。

### 不得存在

- 把“模块 → 小模块 → 页面 → 动作”作为唯一固定结构；
- 强制所有字段集中到大模块末尾；
- 强制七列字段表；
- 强制状态机固定放在小模块末尾；
- Mermaid 代码块；
- 文末统一“验收标准汇总”；
- 文末统一“风险与待确认”；
- 智慧停车区等特定项目内容。

### 判定

任何一项“不得存在”的旧强制规则仍保留，模板验收不通过。

## 3.2 PRD 写作规则验收

检查文件：`references/prd-writing-rules.md`

### marker 完整性

以下 marker 必须各存在且成对闭合：

- `prd-writing-structure`；
- `prd-writing-action`；
- `prd-core-boundary`。

### 内容完整性

规则必须明确回答：

1. 为什么按业务闭环而不是菜单或页面目录组织；
2. 系统级共享规则与模块内规则如何划分；
3. 同一闭环的管理端和移动端如何归位；
4. 页面如何定位但不成为唯一组织轴；
5. 动作如何以业务条件、处理结果和影响表达；
6. 字段如何按对象级定义和使用处补充两层表达；
7. 业务状态、展示状态和操作过程状态如何区分；
8. 权限如何表达角色、数据范围、允许状态和敏感动作；
9. 异常如何表达触发、可见结果、业务影响和恢复；
10. 验收如何放入所属模块并能实际判断；
11. 待确认事项何时阻断、何时可保守表达；
12. 查询、统计、下钻、导出如何说明口径；
13. 表单保存与提交、配置生效和历史影响如何说明；
14. 外部系统的数据责任边界如何说明；
15. 提示文案、默认值和数字何时可以给具体值；
16. draw.io 源文件与 SVG 如何交付；
17. 最终如何逐项回读 Design，检查遗漏和擅自增加。

### 反向检查

规则不得再要求：

- 无依据补具体数字；
- 无依据补默认排序、分页数量或导出上限；
- 所有提示都写成逐字固定文案；
- 所有表单默认拥有草稿、自动保存或离开提醒；
- 所有外部系统默认具有重试、补偿或降级；
- 使用统一七列字段表证明字段完整；
- 使用 Mermaid 作为正式流程图。

## 5. 第三层：简单样本验收

## 5.1 样本目的

复杂样本容易掩盖模板本身的问题。必须先用一个小型业务验证新模板不是只适用于智慧停车区。

## 5.2 推荐简单样本

可使用“访客预约与入园”类最小闭环，Design 至少包含：

- 访客提交预约；
- 被访人审核；
- 访客到达后核验；
- 预约完成或失效；
- 一个管理端页面；
- 一个移动端页面；
- 一个业务对象；
- 3—5 个业务状态；
- 一项外部协作或异常；
- 少量已确认字段；
- 一项高影响待确认。

样本只能使用 Design 中已写明的事实，不得在验收 PRD 中自行补造短信次数、分页数量、超时时间、字段长度或默认排序。

## 5.3 简单样本通过标准

- 顶层是系统总览和业务闭环，不是按端拆分；
- 管理端审核和移动端预约处于同一业务模块；
- 状态定义只设一个权威位置；
- 字段在业务对象或使用处可定位；
- 有流程时产出 `.drawio` 和 SVG；
- 模块包含异常、恢复、验收和待确认；
- 单独阅读模块能理解完整闭环；
- 文风脚本无错误级问题；
- 一致性脚本无 `deterministic_conflict`；
- 人读回读无 Design 遗漏和未授权新增。

若简单样本无法自然套用新模板，说明模板过度绑定复杂项目，验收不通过。

- 相关角色、数据范围、状态、异常与验收。

### B. 车流、车位与视频监测

应连贯承接：

- 车流实时监控；
- 车位类型、数量、占用率与未知数据；
- 监控点位绑定；
- 外部视频展示与失败状态；
- 刷新、空态和设备异常；
- 相关权限、字段和验收。

### C. 滞留监测与现场处置

应连贯承接：

- 滞留阈值配置；
- 阈值启用与通知开关；
- 滞留记录生成；
- 移动端通知；
- 保安核实；
- 信息更新；
- 提前离场与正常结束两个终态；
- 处理记录留存；
- 管理端详情与处理结果；
- 模块验收和待确认。

移动端“滞留通知”和相关“我的处理记录”必须位于或明确服务于本闭环，不能因为端不同被拆到独立移动端大模块。

### D. 两客一危核查与告警处置

应连贯承接：

- 自建库比对；
- 比对成功、失败和无匹配；
- 核查任务；
- 移动端现场核查；
- 缺失字段补录；
- 违规、超时和异常状态告警；
- 告警级别；
- 处理、上报、关闭；
- 配置、推送方式、台账和统计；
- 对应角色、权限、字段、状态、异常、恢复和验收。

移动端“待核查任务”“两客一危核查任务”和相关“我的处理记录”必须进入本闭环。

### E. 多级组织汇总分析

应连贯承接：

- 服务区、区域中心和服务中心的数据范围；
- 汇总指标；
- 时间和组织口径；
- 下钻到车辆级明细；
- 上级只看不处理、不配置、不上报；
- 导出与权限；
- 空数据和统计异常；
- 模块验收。

### 闭环判定

若同一闭环的状态、字段、移动端动作、异常或验收仍被放到远离主体的统一章节，导致读者必须频繁跨章查找，则结构验收不通过。

## 6.4 模块独立可读验收

对每个业务模块执行“隔离阅读”：只阅读该模块正文和系统共享规则，不查看其他业务模块。

每个模块必须能回答：

1. 该模块解决什么问题，不负责什么；
2. 谁使用，能看什么数据，能执行什么动作；
3. 从什么事件或入口开始；
4. 涉及哪些业务对象；
5. 正常流程如何结束；
6. 有哪些业务状态及允许转换；
7. 每个关键动作的前置条件、输入、结果和影响是什么；
8. 外部系统失败、空数据、重复提交、提前离场等情况如何处理；
9. 失败后用户看到什么，业务能否继续，如何恢复；
10. 如何验收；
11. 有哪些未确认事项。

缺少任一核心问题且必须跨多个模块才能补齐，判为失败。

## 6.5 Design 事实承接验收

按 Design 顺序逐项回读以下事实类型：

- 产品目标与成功标准；
- 范围内、范围外；
- 角色；
- 数据范围；
- 业务对象与关系；
- 核心流程；
- 业务状态和状态转换；
- 业务规则；
- 外部系统与责任边界；
- 21 个页面；
- 页面区块；
- 字段及已确认属性；
- 页面操作；
- 权限；
- 统计口径；
- 通用交互；
- 异常与恢复；
- 非功能要求；
- 验收标准；
- 待确认事项。

每项事实必须满足以下之一：

- 在 PRD 中有准确、可定位的权威定义；
- 确实不属于 PRD 展开范围，且 Design 或规则明确允许省略；
- 作为待确认事项清楚保留。

不得以“参见前文”“同上”“按相关规则处理”等模糊引用代替承接。

## 6.6 未授权新增验收

反向从候选 PRD 回读 Design，重点检查：

- 新增角色或扩大权限；
- 新增页面或页面区块；
- 新增业务状态或允许转换；
- 新增字段、枚举或校验；
- 新增默认值；
- 新增排序、分页、导出上限；
- 新增自动保存、草稿、撤回、批量操作；
- 新增超时、重试、补偿、降级；
- 新增固定提示逐字文案；
- 新增外部系统责任；
- 把 Design 待确认事项静默写成确定规则。

若新增内容会改变流程、权限、数据范围、状态、系统边界、页面或验收，直接失败并回上游确认。

普通自然语言解释只要不引入新行为，不算未授权新增。

## 6.7 字段验收

字段可以分散在不同业务对象或阶段，但必须满足：

- Design 中每个业务字段可定位；
- 已确认的类型、长度、格式、枚举、范围、精度、默认值、来源和说明没有丢失；
- 未确认属性没有被补造；
- 系统内部字段说明用途；
- 同一字段只设一个权威定义；
- 使用处补充不与对象级定义冲突；
- 未知、空值、零值和“不适用”表达清楚；
- 字段权限和编辑时点就近说明。

不要求所有字段进入一张表，也不要求固定七列。

## 6.8 状态与权限验收

### 状态

- 业务状态有明确含义、进入条件、允许动作和下一状态；
- 页面加载中、提交中、失败等过程状态不混入业务状态机；
- 空态、离线、数据异常等展示状态不冒充业务状态；
- 滞留“已离场”和“已结束”保持两个不同终态；
- 两客一危比对、核查和告警状态没有被合并成一个含糊状态。

### 权限

- 服务区管理员只能处理本服务区业务；
- 保安移动端只能处理任务范围；
- 区域中心和服务中心按管辖范围查看和下钻；
- 上级角色不出现处理、配置和上报动作；
- 敏感动作明确允许角色、允许状态和数据范围；
- 页面可见、字段可见、字段可编辑和动作可执行没有混淆。

## 6.9 异常与恢复验收

每个高影响异常至少说明：

- 触发条件；
- 用户可见结果；
- 对当前业务的影响；
- 数据是否保留；
- 是否可重试或继续；
- 恢复条件；
- 是否需要人工处理。

智慧停车区至少检查：

- 入口或出口数据匹配失败；
- AI 车位摄像头异常；
- 外部视频拉流失败或设备离线；
- 自建库比对超时或失败；
- 车辆在滞留核实前提前离场；
- 无车位数据时不能显示为 0；
- 重复提交或状态已变化时的处理；
- 汇总数据为空或部分来源异常。

## 6.10 验收标准与待确认事项验收

### 模块验收

- 与所属业务模块放在一起；
- 使用自然语言说明前置、动作和可观察结果；
- 能判断通过或失败；
- 覆盖正常、权限、异常和边界；
- 不使用“功能正常”“权限有效”等空泛结论。

### 待确认事项

- 在受影响模块就近说明；
- 文末索引只列编号、事项和所在模块，不重复定义；
- 高影响未知未被静默拍板；
- Design 已有待确认事项没有因改写而消失；
- 已确认事项不继续伪装成待确认。

## 6.11 “我的处理记录”专项验收

“我的处理记录”同时可能承接滞留和两客一危处理结果，容易被重复定义。

通过标准：

- 只存在一个权威页面定义；
- 明确其数据范围和记录类型；
- 滞留闭环和两客一危闭环可以就近引用其用途，但不能复制出两套互相漂移的字段与规则；
- 页面入口、筛选、详情和权限与 Design 一致；
- 不因避免重复而使用“同上”或无法定位的模糊引用。

## 7. 第五层：draw.io 交付验收

## 7.1 需要画图的判断

以下场景通常需要 draw.io：

- 跨角色闭环；
- 跨端协作；
- 多状态分支；
- 外部系统参与；
- 正常流程与异常恢复交织；
- 仅用文字难以快速理解先后关系。

简单查询、单步保存或无分支展示页面不应为了“有图”而强行画图。

## 7.2 文件要求

每张正式流程图必须同时存在：

- 可编辑源文件：`.drawio`；
- 正文展示文件：`.svg`。

文件建议放在 PRD 同级或 PRD 资产目录中，命名能对应业务模块，例如：

- `vehicle-entry-exit-flow.drawio`；
- `vehicle-entry-exit-flow.svg`；
- `retention-handling-flow.drawio`；
- `retention-handling-flow.svg`。

不要求固定英文文件名，但源文件与 SVG 必须一一对应。

## 7.3 导出验证

使用本机 draw.io 验证源文件可打开并能重新导出：

```powershell
& 'C:\Program Files\draw.io\draw.io.exe' --export --format svg --output '<临时输出.svg>' '<源文件.drawio>'
```

### 通过标准

- 命令能够生成非空 SVG；
- SVG 可由浏览器打开；
- 中文文字不丢失；
- 节点和连线没有严重遮挡；
- 泳道角色与正文角色一致；
- 状态名、动作名和异常分支与正文一致；
- 图中没有正文未定义的新流程；
- 正文引用的是实际存在的 SVG；
- 不存在 Mermaid 正式流程图残留。

draw.io 启动时若出现不影响导出的本机凭据提示，以实际是否成功生成 SVG 为准，并在结果中如实说明。

## 8. 第六层：脚本对候选样本的验收

在候选项目根目录运行：

```powershell
python D:\work\ShitPM\scripts\python\prd-style-lint.py output\prd\prd.md
python D:\work\ShitPM\scripts\python\prd-consistency-check.py --project-root .
```

### 文风脚本

- 错误级问题必须为 0；
- 警告需逐项阅读，确认是真问题还是合理内容；
- 不得通过删除必要字段、状态或异常描述来消除“表格主导”告警；
- 应优先增加自然语言解释或调整表达，而不是绕过规则。

### 一致性脚本

- 不得有 `deterministic_conflict`；
- `possible_omission` 必须逐项人工回读；
- `needs_semantic_judgment` 必须逐项人工判断；
- 脚本返回 0 不能代替语义验收；
- 若脚本因新结构稳定误报，应修正提取逻辑和现有测试，而不是在 PRD 中恢复旧章节来迎合脚本。

## 9. 验收失败分级

### P0：不能交付

- 覆盖或修改真实项目原 PRD/Design；
- Design confirmation 被绕过；
- 候选 PRD 改变核心系统边界；
- 大量 Design 内容缺失；
- 引入新角色、权限、状态或核心流程；
- draw.io 文件损坏或无法打开；
- 新结构使主流程无法运行。

### P1：必须修正后再验收

- 某个业务闭环不完整；
- 管理端和移动端仍被错误拆散；
- 页面或字段无准确落点；
- 状态、权限、异常或恢复存在高影响缺口；
- Review 仍以旧结构误判；
- 上下文 marker 装载失败；
- 相关自动化回归失败；
- 候选存在确定性 Design 冲突；
- 模块无法独立阅读；
- 图文冲突。

### P2：可记录但不阻塞

- 个别自然语言仍可更简洁；
- 不影响理解的标题命名差异；
- SVG 视觉细节可优化但不遮挡内容；
- 低影响待确认事项的措辞可以更清楚；
- 某些合法表格收到低风险文风警告。

P2 不得掩盖 P0/P1。
