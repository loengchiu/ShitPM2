# PRD 优化迭代执行方案

> 日期：2026-07-31  
> 状态：待执行  
> 用途：指导后续 AI 在 ShitPM 仓库内实施 PRD 结构与写作优化  
> 本文只定义实施范围、顺序和边界，不直接修改正式模板、Skill、规则、脚本或测试。

## 1. 结论先行

本轮优化不能只修改 `templates/prd.md`。

PRD 的最终形态同时受模板、写作规则、生成 Skill、上下文装载、示例、Review 清单、现有检查脚本和用户说明影响。若只改模板，将出现以下后果：

1. `spm-prd` 仍按“模块 → 小模块 → 页面 → 动作”组织正文，新模板无法真正生效；
2. 写作规则仍要求字段集中、状态后置、Mermaid、文末验收汇总和风险汇总，生成结果会回到旧结构；
3. 示例继续向 AI 示范旧写法，容易覆盖新规则；
4. PRD Review 会把符合新结构的 PRD 误判为缺章节、缺统一字段表或页面未独立成章；
5. `prd-style-lint.py` 和 `prd-consistency-check.py` 会因依赖旧章节与旧字段表而误报或漏检；
6. README、USAGE 和 Prototype 辅助说明会继续向使用者传达过时做法。

因此，推荐采用“先统一内容规则，再同步生成与审查行为，最后适配既有确定性检查”的顺序，一次完成同一语义链路的最小必要修改。

## 2. 已确认的设计基线

实施必须同时读取并遵守以下两份已确认文档：

1. `D:\work\ShitPM\docs\plans\2026-07-31-prd-structure-design.md`
2. `D:\work\ShitPM\docs\plans\2026-07-31-prd-writing-design.md`

两份基线共同确定：

- PRD 按业务闭环组织，而不是照搬 Design 的菜单模块或页面目录；
- PRD 由“系统级总览 + 多个可独立阅读的业务模块”组成；
- 同一闭环中的管理端、移动端、状态、字段、权限、异常、恢复、验收和待确认事项尽量放在一起；
- 字段按业务对象或子业务就近定义，不再强制集中到大模块末尾的一张七列表；
- 业务状态、页面展示状态和操作过程状态分开表达；
- 有必要画图的业务流程使用 draw.io 源文件，并导出 SVG 就近插入正文；
- 不使用 Mermaid 作为正式流程图交付格式；
- PRD 必须完整承接 Design，但不能以行数、表格数量、章节数量或承接矩阵代替语义回读；
- Design 未确认的高影响事实不得静默补造；
- 自检与生成合并，发现遗漏后直接修正文档，不新增独立证明流程。

## 3. 本轮成功标准

实施完成后，应同时满足以下结果：

1. 新生成的 PRD 能按业务闭环组织，并完整承接确认版 Design；
2. 单独阅读任一业务模块时，可以理解该闭环的角色、入口、数据、状态、动作、异常、恢复、权限和验收；
3. 管理端与移动端页面按业务关系归位，不再机械拆成独立“移动端模块”；
4. 字段定义与使用场景相邻，字段事实不因分散表达而丢失；
5. Review 使用相同结构与事实边界，不再按旧模板误判；
6. 现有确定性脚本能够识别新结构中明确可解析的页面和字段，不把语义判断伪装成机器结论；
7. 现有上下文装载机制继续工作，不新增 pack、marker、门禁或回执；
8. 简单样本与“智慧停车区”复杂真实样本均通过验收；
9. 不覆盖真实项目原 PRD，不执行 Git commit，不执行 Git push。

## 5. 实施原则

### 5.1 事实源不变

确认版 `output/design/design.md` 仍是 PRD 的产品事实源。模板、示例和规则只能改变表达与组织方式，不能新增产品事实。

### 5.2 先消除规则冲突，再调整脚本

先让模板、写作规则、Skill、示例和 Review 对“正确 PRD 长什么样”达成一致，再适配脚本。否则脚本会围绕尚未稳定的结构反复修改。

### 5.3 AI 判断与程序检查分工

- AI 负责：业务闭环、语义承接、状态合理性、权限一致性、异常完整性、模块独立可读和高影响未知判断；
- 程序负责：文件读取、marker 装载、明确页面名和字段名提取、明显属性冲突、固定禁用表达及退出码；
- 程序不得根据标题数量、字段表列数或章节位置判断 PRD 是否完整。

### 5.4 允许结构灵活，但落点必须明确

不同项目可以有不同数量的业务模块和业务阶段。模板提供组织原则和建议骨架，不要求所有项目机械保留空章节。

页面、字段、状态、权限、异常、验收和待确认事项可以采用不同表达形式，但必须有明确、可定位且不互相冲突的权威定义。

### 5.5 最小修改

只修改与本轮 PRD 结构和写作优化直接相关的内容。不顺手重构脚本、不统一全仓库文风、不调整无关 Skill，也不迁移现有检查逻辑到新框架。

## 6. 分阶段执行方案

## 阶段一：建立实施基线

### 目标

在修改前确认设计基线、当前行为和回归命令，避免边改边重新解释目标。

### 操作

1. 读取两份 PRD 设计基线全文；
2. 读取本执行方案和对应验收方案；
3. 记录当前 Git 状态，但不暂存、不提交；
4. 运行受影响测试，记录修改前基线；
5. 核对 `context-loading.manifest.json` 中现有 PRD marker 与 pack 关系；
6. 核对真实样本文件存在且保持只读。

### 完成标准

- 能明确说出必须修改、条件修改和明确不改的文件；
- 能明确说明为什么不能只改模板；
- 已知现有测试是否原本通过；
- 未修改任何真实项目文件。

## 阶段二：统一模板与写作规则

### 2.1 修改 `templates/prd.md`

#### 目标

把模板从“固定菜单层级”改为“系统总览 + 业务闭环模块”。

#### 必须体现

1. 文档信息；
2. 产品定义与范围；
3. 系统全景与共享规则；
4. 若干业务闭环模块；
5. 待确认事项索引，仅作定位，不重复定义事项；
6. 每个业务模块建议包含：
   - 模块目标与业务边界；
   - 业务对象及关系；
   - 角色、数据范围与权限；
   - 业务流程；
   - 状态与业务规则；
   - 按业务阶段展开的功能需求；
   - 数据与字段定义；
   - 外部协作、异常与恢复；
   - 模块验收标准；
   - 模块待确认事项。

#### 必须删除或替换

- 固定“详细需求说明”总章；
- 固定“模块 → 小模块 → 页面 → 动作”说明；
- 固定大模块末尾七列字段表；
- 固定小模块末尾状态机；
- Mermaid 示例；
- 文末独立“验收标准汇总”；
- 文末独立“风险与待确认”。

#### 必须保留

```md
<!-- context:prd-template:start -->
<!-- context:prd-template:end -->
```

模板应以注释解释“如何组织”，不要内置智慧停车区等特定项目名称。

### 2.2 修改 `references/prd-writing-rules.md`

#### 目标

将两份设计基线转化为正式写作规则，成为 PRD 生成和 Review 共用的文字依据。

#### 必须改写

- 正文组织：按业务闭环，不照抄菜单或 Design 章节；
- 动作表达：以业务动作和结果为中心，不写操作流水账；
- 字段表达：对象级定义 + 使用处补充，不强制统一七列表；
- 状态表达：业务状态、展示状态、操作过程状态分开；
- 流程图：draw.io 源文件 + SVG，不使用 Mermaid；
- 验收：放所属业务模块；
- 待确认：就近说明，文末仅保留索引；
- 数字和默认值：只有 Design 已确认或有明确依据时才写具体值；
- 普通提示：规定语义即可，不强制补造逐字文案；
- 查询、统计、下钻、导出、表单配置和外部系统：按设计基线中的适用规则表达；
- 最终自检：从 Design 逐项语义回读，既检查遗漏，也检查擅自增加。

#### 必须保留的 marker

- `prd-writing-structure`；
- `prd-writing-action`；
- `prd-core-boundary`。

marker 内的内容必须能够独立成立，不能把关键规则放在 marker 外导致上下文包读不到。

## 阶段三：同步生成行为、场景与示例

### 3.1 修改 `skills/spm-prd/SKILL.md`

#### 保留

- Design confirmation 前置要求；
- 普通 PRD 只使用 `writing`；
- 超大型 PRD 才允许使用 `module`；
- 不依赖 Prototype；
- 不新增 plan、integration、verification 等 pass；
- 不生成承接矩阵、覆盖率报告或验证回执；
- 正式展示前直接回读真实 PRD 并修正。

#### 更新

- 生成正文时先识别业务闭环及边界；
- 系统级共享规则只定义一次；
- 管理端和移动端按同一业务闭环组织；
- 页面是承接载体，不是全文唯一组织轴；
- 字段按对象和使用场景就近定义；
- 状态、权限、异常、恢复、验收、待确认事项归入所属模块；
- 有必要画流程时生成 `.drawio` 并导出 SVG；
- 自检改为业务闭环、事实承接、模块独立可读、图文一致和无未授权新增。

Skill 保持精简。详细写法继续放 `references/`，不要把两份设计基线全文复制进 Skill。

### 3.2 修改 `references/prd-scene-checklist.md`

重点修正会诱导补造的检查项：

- 字段长度、格式、默认值只有 Design 已确认或业务必须且有依据时写；
- 草稿、自动保存、离开未保存提醒不能作为所有表单的默认要求；
- 查询默认排序、分页数量、导出上限不能无依据补充；
- 外部系统超时、重试、补偿策略按 Design 事实和业务影响表达，不能默认发明；
- 配置需说明生效范围、生效时点、历史数据影响和失败结果，但未知高影响项必须回到 Design；
- 保存与提交、空值与零值、未知与无数据必须清楚区分。

保留 `prd-verification-scenes` marker。

### 3.3 修改 `references/prd-writing-examples.md`

示例至少覆盖：

1. 系统全景与页面落点表；
2. 一个完整业务闭环模块；

4. 业务阶段下的页面与动作表达；
5. 对象级字段定义与使用处字段补充；
6. 业务状态和页面展示状态分开；
7. 外部系统成功、失败与恢复；
8. 配置生效范围与历史影响；
9. 模块验收；
10. 模块待确认事项和文末索引；
11. draw.io 图片引用方式；
12. 错误示例：流水账、跨章“同上”、无依据数字、统一移动端模块、文末堆风险。

- `prd-example-page-fields`；

## 阶段四：同步 Review 口径

### 4.1 修改 `contracts/prd-review-checklist.md`

优先改写或合并旧检查项，不机械增加数量。

必须消除以下旧判断：

- 必须按模块 → 小模块 → 页面 → 动作；
- Design 每个页面都必须对应独立 PRD 章节；
- 所有字段必须进入统一字段定义表；
- 必须有文末验收汇总和风险汇总；
- 必须补默认分页、排序、上限等未确认参数。

必须覆盖以下新判断：

- PRD 是否按业务闭环组织且模块边界合理；
- 同一闭环的管理端、移动端、字段、状态、权限、异常、验收是否被拆散；
- 页面是否有准确落点，而不是是否独立成章；
- 字段事实是否在对象定义或使用位置准确承接；
- 业务状态是否与展示/过程状态混淆；
- draw.io 源文件、SVG 和正文是否一致；
- 模块是否可独立阅读；
- Design 事实是否无遗漏且无未授权新增；
- 高影响未知是否被静默拍板。

### 4.2 修改 `skills/spm-prd-review/SKILL.md`

只更新审查内容，不改变 Review 职责和输出方式：

## 9. 风险及处理

### 风险一：模板变了，规则仍冲突

处理：先完成模板和正式写作规则的成对修改，再进入 Skill 与脚本阶段。

### 风险二：为了“完整承接”引入承接矩阵或检查器

处理：拒绝新增。完整承接由生成时逐项 Design 回读、现有确定性检查和真实样本验收共同保证。

### 风险三：脚本试图判断业务闭环是否合理

处理：删除或避免此类逻辑。脚本只处理明确可解析事实，业务闭环由 AI 阅读判断。

### 风险四：新规则鼓励 AI 补造通用参数

处理：所有数字、默认值、排序、分页、超时、重试、文案逐字值都必须有 Design 或明确依据；否则保守表达或列为待确认。

### 风险五：示例比规则更有诱导力

处理：规则修改后必须同步示例，特别删除固定分页、固定长度、倒计时和 Mermaid 示例中的无依据参数。

### 风险六：真实项目被覆盖

处理：真实项目路径只读使用，候选产物生成到仓库临时目录。

### 风险七：修改范围膨胀

处理：条件文件只在测试真实失败时修改；不改无关 Design、Prototype 或 Fix 流程。

## 11. 停止条件

出现以下任一情况时，应停止拍板并向用户说明：

- 两份设计基线之间出现实质冲突；
- 必须改变 Design confirmation、Review 判定门槛或 Prototype 事实源才能继续；
- 新结构要求改变现有公开命令或新增程序检查器；
- 真实样本暴露出会改变核心流程、权限、状态或系统边界的未知事实；
- 需要覆盖真实项目原 PRD；
- 需要 Git commit 或 Git push。

普通文案、示例措辞或低影响标题差异不构成停止条件，执行 AI 应按设计基线自行完成。
