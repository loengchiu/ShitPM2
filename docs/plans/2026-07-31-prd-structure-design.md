# PRD 结构设计基线

> 日期：2026-07-31  
> 状态：结构已确认，写法已另行确认并落盘  
> 依据样本：智慧停车区 `design.md` 与 `prd.md` 真实产物对照  
> 本文只记录已确认的 PRD 结构，不是正式 PRD 模板，不包含具体项目需求正文。

## 1. 背景与问题判断

智慧停车区样本中，Design 共 1114 行、约 3.38 万字符，PRD 共 883 行、约 2.60 万字符，两者都包含 21 个页面。页面数量没有减少，但 PRD 内容减少约 23%，同时出现了业务事实压缩和分散的问题。

行数少不能单独证明承接失败。真正的判断标准是：Design 中每一条产品事实是否在 PRD 中拥有明确、准确、便于查找的落点，且没有发生语义丢失。

当前 PRD 的主要结构问题不是篇幅不足，而是组织主线不合理：

1. 正文按菜单模块和使用端组织，管理端与移动端被拆开，同一个业务闭环无法连续阅读。
2. 多段核心业务闭环被压缩成一段整体说明和一张总图，关键分支、状态、责任人和异常没有得到充分展开。
3. 字段集中在大模块末尾，具体业务动作与字段定义距离过远。
4. 验收标准、异常、非功能要求和待确认事项集中在文末，导致同一模块的信息分散在多个章节。
5. 页面虽然全部存在，但页面背后的业务对象、状态、规则、外部协作和异常恢复没有形成完整的模块阅读链路。

因此，PRD 不能继续以“全局概述—菜单模块—独立移动端模块—验收汇总—风险汇总”为主体结构，应改为“少量系统级总览 + 按业务闭环组织的自包含模块”。

## 2. 结构目标

新结构同时满足以下目标：

1. 完整承接确认版 Design 的全部有效产品事实，不以压缩篇幅为目标。
2. 同一个业务闭环的目标、角色、流程、状态、页面、字段、异常、验收和待确认事项尽量放在一起。
3. 管理端和移动端按业务归属组织，不按使用端强行拆成独立业务模块。
4. 让产品、研发和测试可以连续阅读一个模块，并直接完成模块评审。
5. 全局规则只定义一次，模块内完整说明业务事实和例外，避免重复与跨章节拼接。
6. 流程使用可编辑的 draw.io 源文件，并在 PRD 中就近展示清晰预览。

“完整承接”不等于逐句复制 Design，也不要求 PRD 行数机械地多于 Design。允许调整章节顺序、合并重复表达和将抽象规则放入实际使用场景，但不得删除影响产品、研发或测试理解的事实。

## 3. PRD 顶层结构

### 3.1 文档信息

只记录文档管理信息：

- 文档版本；
- 文档状态；
- Design 基线；
- 修订记录。

本章不承载产品事实。

### 3.2 产品定义与范围

完整承接：

- 产品定位；
- 解决的问题；
- 产品目标；
- 成功判断；
- 本期范围；
- 明确不做；
- 系统边界；
- 保守边界。

“本期范围”“明确不做”和“待进一步确认的保守边界”必须分开表达，不合并成一个过长自然段。

### 3.3 系统全景与共享规则

本章帮助读者建立全局认知，只承载真正跨模块的内容：

- 名词说明；
- 三级组织与角色职责；
- 系统级数据权限基线；
- 业务模块全景；
- 业务模块、菜单、页面和使用端映射；
- 外部系统关系概览；
- 系统整体业务流程；
- 跨模块共享的时间、导出、审计和脱敏规则；
- 系统级性能、安全和兼容要求；
- 真正跨模块的共用页面。

系统级总览只负责建立认知，不能代替各业务模块的详细流程、规则和异常说明。

### 3.4 车辆进出与停车记录

完整承接车辆进场、停车记录、车辆详情、离场匹配、识别异常、数据异常、离场异常和档案归档。

### 3.5 车流、车位与视频监测

完整承接车流实时监控、车位占用情况、监控点绑定、外部视频展示、实时刷新和相关数据异常。

### 3.6 滞留监测与现场处置

完整承接滞留阈值配置、滞留时长计算、滞留通知、移动端现场核实、车辆提前离场、处理记录和历史查询。

### 3.7 两客一危核查与告警处置

完整承接集团自建库比对、待核查任务、移动端现场核查、人工补录、核查台账、违规识别、告警处理、严重或紧急告警上报、告警配置和统计分析。

### 3.8 多级组织汇总分析

完整承接服务区、区域中心和服务中心的业务汇总、车辆级下钻、查询、导出及上级只读限制。

### 3.9 待确认事项索引

文末只保留待确认事项索引，记录：

- 问题；
- 所属模块；
- 当前保守表达；
- 影响范围；
- 确认状态。

详细背景、当前处理方式和业务影响仍放在所属模块，本章不重复完整内容。

## 4. 业务模块边界

PRD 正文固定采用五个业务模块：

1. 车辆进出与停车记录；
2. 车流、车位与视频监测；
3. 滞留监测与现场处置；
4. 两客一危核查与告警处置；
5. 多级组织汇总分析。

模块边界按业务闭环确定，不按菜单层级或管理端、移动端划分。菜单归属和使用端仍然保留，但只作为页面属性和系统映射关系。

“移动端小程序”不再作为独立业务模块：

- 滞留通知与现场核实归入“滞留监测与现场处置”；
- 待核查任务和两客一危核查归入“两客一危核查与告警处置”；
- 管理端与移动端只要参与同一个业务阶段，就在同一处连续说明。

“我的处理记录”同时包含滞留处理和两客一危核查记录，属于真正跨模块的共用页面。该页面整体定义一次，放在系统级共用页面中，并说明两类记录分别来自对应业务模块。不得为了结构整齐而虚构两个 Design 中不存在的新页面。

## 5. 每个业务模块的内部结构

每个模块按照以下顺序组织。简单模块可以合并没有独立价值的小节，但不能省略适用的产品事实；复杂模块可以继续按业务阶段拆分。

### 5.1 模块目标与业务边界

说明：

- 模块解决什么问题；
- 业务从哪里开始、在哪里结束；
- 包含哪些管理端和移动端页面；
- 与前后模块如何衔接。

### 5.2 业务对象及关系

在模块开头自然说明核心业务对象、对象职责和关键关系。跨模块关联应明确指向相关模块，不单独建立全文业务对象大章来分散阅读。

### 5.3 角色、数据范围与权限

说明：

- 哪些角色参与；
- 各角色承担什么责任；
- 各角色可以查看哪些数据；
- 谁可以处理、配置、修改或上报；
- 哪些字段和敏感操作存在特殊限制。

系统级默认权限不在每个动作中重复，但模块例外必须直接写清。

### 5.4 业务流程

只要存在跨页面、跨角色、跨系统或业务状态变化，就使用 draw.io 表达完整闭环，包括：

- 起点和终点；
- 系统自动动作；
- 人工操作；
- 关键判断分支；
- 外部系统参与；
- 异常出口；
- 状态变化。

复杂模块可以先提供一张主流程图，再按子业务提供局部流程图。不得把整个系统的所有细节塞进一张巨图。

### 5.5 状态与业务规则

紧跟流程说明：

- 状态含义；
- 进入条件；
- 允许操作；
- 下一状态；
- 终态；
- 提前结束条件；
- 计算规则；
- 判定规则；
- 触发与去重规则。

状态流转使用 draw.io 展示，状态表用于补充精确的操作人、进入条件、下一状态和限制，两者不互相替代。

### 5.6 按业务阶段展开功能需求

模块内部采用“业务阶段为主、页面为辅”的结构：

1. 先确定业务阶段；
2. 再列出该阶段涉及的管理端和移动端页面；
3. 页面内按用户动作展开；
4. 同一阶段的字段、状态、异常和后续责任人就近说明。

页面仍保留明确名称和编号，但不再主导模块划分。

例如，“两客一危核查与告警处置”可以按以下业务阶段展开：

1. 车辆识别与自建库比对；
2. 现场核查与信息补录；
3. 核查台账；
4. 告警识别与处置；
5. 严重、紧急告警上报；
6. 告警配置；
7. 统计分析。

### 5.7 数据与字段定义

字段按业务对象或子业务就近放置：

- 车辆停车记录字段放在车辆记录相关子业务；
- 滞留记录字段放在滞留处置相关子业务；
- 核查任务和核查结果字段放在现场核查相关子业务；
- 告警、处理和上报字段放在告警处置相关子业务；
- 配置字段放在配置相关子业务。

同一个字段只完整定义一次。页面动作只说明本动作实际涉及的字段、展示方式、输入规则和关键校验，不重复整张字段表。

不再在大模块末尾集中堆放跨多个子业务的超长字段定义表，也不按页面重复复制相同字段。

### 5.8 外部协作、异常与恢复

异常优先写在真正发生的动作附近：

- 进出摄像头异常归入车辆进出相关动作；
- AI 车位摄像头异常归入车位监测相关动作；
- 自建库超时和比对失败归入两客一危比对相关动作；
- 视频拉流失败和设备离线归入视频监测相关动作；
- 提交失败、上报失败和车辆提前离场归入对应处理动作。

只有影响整个模块的异常，才在模块末尾进行模块级汇总。不得再建立全文统一的异常大表代替模块说明。

### 5.9 模块级质量要求

只记录本模块特有的刷新周期、响应时间、弱网反馈、审计、数据留存等要求。真正跨模块的要求留在系统级共享规则中。

### 5.10 模块验收标准

模块验收标准直接放在模块末尾，并覆盖主流程、关键分支、权限限制、异常恢复和关键边界。产品、研发和测试读完模块后应能直接完成模块评审，不再到文末寻找对应验收内容。

### 5.11 模块待确认事项

详细记录本模块的待确认问题、当前保守表达和影响。文末索引只提供导航，不重复详细说明。

## 6. 全局基线与模块规则的分配原则

采用“全局基线一次定义，业务事实和例外回到所属模块”的方式。

适合放在系统级共享规则中的内容包括：

- 三级组织结构；
- 默认组织数据范围；
- 上级组织默认只读；
- “今日、近 7 日、近 30 日、自定义时间”的统一含义；
- 通用导出上限和导出记录；
- 通用审计要求；
- 敏感字段与脱敏基线；
- 系统级性能、安全和兼容要求。

必须放在对应业务模块中的内容包括：

- 实时监控刷新周期；
- 滞留时长计算和阈值规则；
- 自建库失败后的业务结果；
- 告警上报失败后的状态；
- 车辆离场匹配失败后的处理；
- 任何会改变具体业务结果的模块规则和例外。

模块可以用自然语言说明沿用哪些全局基线，但不能要求读者自行把全局权限、模块规则和动作例外拼接成业务结论。

## 7. draw.io 流程图交付规则

流程图同时提供两种形态：

1. `.drawio` 可编辑源文件；
2. 从源文件导出的 SVG 预览图。

SVG 就近插入 PRD 对应章节，保证直接阅读；`.drawio` 源文件用于后续修改。不得把 draw.io 原始 XML 放入 PRD 正文，也不再使用 Mermaid 作为正式流程图格式。

流程图层级为：

- 一张系统整体业务流程图；
- 每个存在状态变化或跨角色协作的业务模块至少一张模块流程图；
- 复杂模块按子业务拆分局部流程图；
- 纯查询、纯展示、纯配置且没有业务状态变化的页面不强制画图。

一张图只表达一个明确闭环。流程图必须能看出角色、系统动作、关键分支、异常出口和结果，不能只画页面跳转。

## 8. Design 内容到 PRD 的承接关系

| Design 内容 | PRD 落点 |
| --- | --- |
| 产品定位、问题、目标、成功判断 | 产品定义与范围 |
| 本期范围、明确不做、保守边界 | 产品定义与范围 |
| 组织、角色、默认数据范围 | 系统全景与共享规则 |
| 核心业务闭环 | 系统总流程及对应业务模块 |
| 业务对象与关系 | 所属模块开头 |
| 状态与业务规则 | 所属业务阶段附近 |
| 外部系统边界 | 系统概览及所属模块详细说明 |
| 菜单、端与页面 | 系统映射表及所属业务阶段 |
| 页面详细设计 | 业务阶段下的页面与动作 |
| 统计口径与通用交互 | 系统共享规则或所属模块 |
| 异常与恢复 | 对应动作或所属模块 |
| 产品级非功能要求 | 系统级或模块级质量要求 |
| 验收标准 | 所属模块末尾 |
| 待确认事项 | 所属模块及文末索引 |

该承接关系用于约束写作者回读 Design，不作为最终 PRD 中的覆盖证明。生成 PRD 时应逐章回读真实 Design，发现遗漏后直接修正正文，不额外生成覆盖报告、检查回执或中间证明文件。

## 9. 明确不采用的结构

新结构明确不采用以下做法：

1. 按管理端和移动端拆分同一业务闭环；
2. 将“移动端小程序”作为独立业务模块；
3. 以页面清单代替业务阶段；
4. 将所有字段集中到大模块末尾；
5. 按页面重复相同字段定义；
6. 将所有异常集中到全文末尾；
7. 设置与模块内容重复的验收标准汇总；
8. 在文末重复展开所有待确认事项；
9. 用一张巨图表达全部系统细节；
10. 用行数、表格数量或覆盖回执证明 PRD 已完整承接 Design。

## 10. 写法设计的承接关系

正文写法采用“结构化自然语言”：以动作名称作为阅读锚点，用连续自然语言完整说明操作人、前置状态、关键字段、校验、成功结果、状态变化、后续责任人、失败结果和恢复方式；不采用固定标签式正文，也不采用过度压缩的纯叙事。

字段、状态、权限、流程图、异常、验收、待确认事项及生成后回读等具体写法，统一以 `docs/plans/2026-07-31-prd-writing-design.md` 为准。本文只定义 PRD 结构，不重复展开写法规则。
