# PRD 全量分片写作 Skill 修订执行与验收方案

> 日期：2026-08-04  
> 状态：待执行  
> 执行对象：其他 AI  
> 适用范围：ShitPM 的 PRD Skill、PRD 模板、PRD 写作规则和 Review 规则  
> 核心目标：取消“普通 PRD / 大型 PRD”的不稳定判断，所有 PRD 统一采用分片读取、分片写入、增量落盘方式。

## 1. 本轮要解决的问题

当前 PRD 生成存在以下确定性风险：

1. 不同需求、不同模型反复遗漏 `4.x.6 功能详细说明`。
2. 当前 Skill 默认“一次读取 Design、一次生成完整 PRD”。
3. 当前 Skill 将模块写作草稿放在临时位置，最后要求主 Agent 再统一生成一次完整 PRD，重新制造上下文瓶颈。
4. `4.x.6` 只是模板建议，没有成为每个业务模块的不可跳过交付条件。
5. Design 的页面、区块、字段和动作在 PRD 中被过度压缩，页面名称可能保留，但交互和业务约束丢失。

## 2. 已确认的设计决策

### 2.1 所有 PRD 统一分片

不再根据 Design 大小判断使用“普通 PRD”还是“大型 PRD”。所有 PRD 都执行同一条内部流程：

> 全局扫描 → 建立完整骨架 → 分片深读 → 分片直接写入最终 PRD → 分片回读 → 有限范围整合检查。

小项目只会产生较少的分片，不另设一次性写作路径。

### 2.2 默认采用单 Agent 串行分片

流程不得依赖 subagent。宿主支持 subagent 时，可以并行加速材料读取或模块分析，但不是完成条件。

单 Agent 必须能够独立完成：

- 读取全局 Design 信息；
- 按业务闭环读取模块材料；
- 直接修改最终 `output/prd/prd.md`；
- 中断后根据已落盘内容继续执行。

### 2.3 分片直接写入最终文件

分片完成后，直接填充最终 `output/prd/prd.md` 对应的 `4.x` 模块。

禁止采用以下路径：

> 分片草稿全部完成 → 主 Agent 重新读取全部草稿 → 整篇重新生成 PRD。

“统一整合”只能做局部修正，包括名词、编号、页面归属和跨模块共用规则；不得重新概括、压缩或改写已经完成的模块正文。

### 2.4 `4.x.6` 是硬性结构约束

每个有页面或业务动作的功能模块必须存在：

```text
#### 4.x.6 功能详细说明
```

模块不能以“无内容”“实际没有内容”为理由省略该章节。没有页面和业务动作的模块不得被创建为功能模块。

## 3. 修改范围

### 3.1 必改文件

1. `skills/spm-prd/SKILL.md`
2. `templates/prd.md`
3. `references/prd-writing-rules.md`

### 3.2 按实际影响修改的文件

1. `skills/spm-prd-review/SKILL.md`
2. `contracts/prd-review-checklist.md`
3. `references/prd-scene-checklist.md`
4. `contracts/context-loading.manifest.json`
5. `references/prd-writing-examples.md`

上述文件只有在现有内容与新流程冲突时才修改。不得为了本轮任务新增综合检查器、覆盖率 JSON、承接矩阵或执行回执。

### 3.3 不得修改

- `output/design/design.md`
- 用户项目的 `output/prd/prd.md`
- Design confirmation
- 既有产品事实
- 与本轮无关的脚本、模板和 Skill
- Git 提交和远程推送

## 4. Skill 修订内容

### 4.1 替换生成路径

删除“普通 PRD / 超大型 PRD”二选一流程，改成固定流程：

#### 阶段 A：全局扫描

只读取并建立以下信息：

- 产品目标和范围；
- 系统边界；
- 共用角色、权限和数据范围；
- 核心业务对象；
- 共用状态和规则；
- 业务闭环；
- 页面清单与页面归属；
- Design 待确认事项。

全局扫描的目标是建立导航，不要求把全部页面正文同时保留在上下文中。

#### 阶段 B：建立最终 PRD 骨架

直接创建或维护最终 `output/prd/prd.md`，先写入：

- 文档信息；
- 产品概述；
- 总体说明；
- 全部业务模块标题；
- 每个模块的固定子章节；
- 待确认事项索引。

每个有业务页面的模块必须预先创建 `4.x.6 功能详细说明`。

#### 阶段 C：模块分片写入

每次只处理一个业务闭环或一个明确的业务模块。当前模块的输入包括：

- 全局共用事实的精简视图；
- 当前模块的业务闭环；
- 当前模块对应的对象、状态、权限；
- 当前模块对应的页面、区块、字段和操作；
- 当前模块涉及的异常、恢复和验收；
- 当前模块的待确认事项。

完成当前模块后，直接写入最终 `prd.md`，然后立即按当前 Design 片段回读修正。

#### 阶段 D：有限范围整合

整合阶段只处理：

- 模块编号；
- 标题层级；
- 名词统一；
- 页面归属；
- 全局规则引用关系；
- 跨模块状态和对象名称；
- 待确认事项索引。

禁止重新生成全文，禁止把模块正文压缩成摘要。

### 4.2 增加模块完成条件

每个模块完成前必须确认：

1. `4.x.6 功能详细说明`存在；
2. Design 页面均有模块内落点；
3. 页面不只有名称，还写了页面职责和业务阶段；
4. 核心动作写清角色、前置条件、输入、处理、成功结果、状态影响、失败结果和恢复方式；
5. 页面字段的展示、编辑、筛选、只读、来源和校验差异没有丢失；
6. 权限、数据范围和允许状态没有被全局摘要替代；
7. 模块验收和待确认事项已就近写入；
8. 没有新增 Design 未确认的高影响事实。

### 4.3 增加中断恢复规则

如果发生上下文压缩、中断或宿主重启：

1. 读取当前 `prd.md` 的章节骨架；
2. 找到最后一个未完成模块；
3. 只重新读取该模块对应的 Design 片段；
4. 保留已完成模块，不重新生成；
5. 继续直接写入最终文件。

不得因为中断而重新读取全部 Design 并整篇重写 PRD。

## 5. 模板修订内容

`templates/prd.md` 必须明确：

1. `4.x.6 功能详细说明`是功能模块必需章节；
2. 页面和动作必须在该章节按业务阶段展开；
3. 页面字段表只能补充字段使用差异，不能替代动作正文；
4. 模块完成前不能跳过功能详细说明、异常处理、验收标准或待确认事项；
5. 模板示例不能诱导模型只写模块摘要。

保留自然语言写作原则，不把正文改造成“页面目标、关键动作、状态变化、异常提示”等标签堆叠。

## 6. 写作规则修订内容

在 `references/prd-writing-rules.md` 中增加以下硬规则：

1. 所有 PRD 默认分片写作；
2. 分片边界来自业务闭环，不按固定字数机械切割；
3. 分片必须直接落盘到最终 PRD；
4. 最终阶段不得整篇重写；
5. 每个功能模块必须包含 `4.x.6 功能详细说明`；
6. 每个 Design 页面必须在一个功能模块的功能详细说明中落点；
7. 省略章节前必须证明该模块没有对应内容；有页面或动作时不得省略；
8. 交互细节只能展开 Design 已确认事实，不得自行补造权限、状态、默认值、校验、提示、异常恢复或外部行为。

## 7. Review 规则修订内容

Review 不只检查 PRD 是否存在模块标题，还要按模块检查：

- `4.x.6` 是否存在；
- 页面是否落在 `4.x.6`；
- 页面区块和动作是否被压缩成空泛摘要；
- 高影响字段、状态、权限、异常和恢复是否有实际落点；
- 是否出现角色页、组织页、审批页等页面语义被重新解释的问题。

第一阶段优先使用 Skill 自检和人工语义审查，不新增检查脚本。现有确定性脚本只作为辅助证据，不能因为退出码为 0 就判定模块完整。

## 8. 执行顺序

1. 读取当前 `spm-prd`、模板、写作规则和 Review 规则；
2. 删除普通/大型 PRD 分支和最终整篇重写要求；
3. 写入固定的全量分片流程；
4. 强化 `4.x.6` 和页面落点约束；
5. 同步修改模板和写作规则；
6. 检查上下文装载规则是否仍然要求一次性读取 Design；
7. 必要时同步 Review 规则；
8. 用简单样本生成一次；
9. 用复杂真实 Design 的副本生成一次；
10. 中断一次模块写作后恢复，确认可以从最终 PRD 继续；
11. 按验收文档执行验收；
12. 只报告结果，不执行 Git commit 或 Git push。

## 9. 停止条件

出现以下任一情况必须停止并报告，不得打补丁：

- 无法确定 Design 的模块边界；
- 页面无法归属业务闭环；
- Design 的高影响事实发生冲突；
- 当前 Skill、模板和上下文装载规则无法形成同一条流程；
- 为了通过检查需要新增覆盖率 JSON、承接矩阵或综合门禁；
- 需要修改用户项目的 Design 或 PRD 才能证明 Skill 有效。

## 10. 交付物

执行完成后应交付：

- 修改后的 `skills/spm-prd/SKILL.md`；
- 修改后的 `templates/prd.md`；
- 修改后的 `references/prd-writing-rules.md`；
- 实际受影响且已同步的 Review 或上下文规则文件；
- 简单样本和复杂样本的验收结果；
- 中断恢复测试结果；
- 未执行 Git commit、Git push 的明确说明。

## 11. 总体验收原则

必须同时满足以下四层条件：

1. **规则层通过**：Skill、模板、写作规则和 Review 规则描述同一条分片落盘流程；
2. **结构层通过**：所有功能模块均有 `4.x.6 功能详细说明`，页面在该章节有明确落点；
3. **行为层通过**：生成过程可以分片读取、分片直接写入，并能在中断后继续；
4. **语义层通过**：Design 的业务事实没有高影响遗漏、冲突或未授权新增。

任意一层不通过，整体不通过。

## 12. 规则层验收

### 12.1 必须存在的规则

检查：

- `skills/spm-prd/SKILL.md`
- `templates/prd.md`
- `references/prd-writing-rules.md`
- 实际受影响的 Review 和上下文规则文件

必须明确写出：

1. 所有 PRD 默认分片写作；
2. 不再根据普通/大型 PRD 做路径判断；
3. 分片边界来自业务闭环；
4. 分片直接写入最终 `output/prd/prd.md`；
5. 最终阶段不整体重写 PRD；
6. 每个有页面或动作的模块必须有 `4.x.6`；
7. 每个 Design 页面必须在某个模块的 `4.x.6` 中落点；
8. 中断后从最终 PRD 和当前 Design 片段恢复；
9. 不依赖 subagent；
10. 交互细节不得越过 Design 事实边界。

### 12.2 必须删除的旧规则

以下内容不得继续作为默认路径：

- “普通 PRD 只执行一次 writing”；
- “超大型 PRD 发生问题后才使用 module”；
- “主 Agent 最终只写入一次完整 PRD”；
- “完整读取全部 Design 后再一次性写作”；
- 允许有页面的模块省略功能详细说明。

## 13. 模板层验收

检查 `templates/prd.md`。

每个模块模板必须能表达：

1. 模块目标与边界；
2. 业务对象与关系；
3. 角色、权限和数据范围；
4. 业务流程；
5. 状态和业务规则；
6. `4.x.6 功能详细说明`；
7. 页面和业务阶段；
8. 页面字段使用差异；
9. 动作及其完整因果链；
10. 异常和恢复；
11. 验收标准；
12. 待确认事项。

以下情况不能通过：

- `4.x.6` 只是注释或示例，不是模块必需章节；
- 模板允许模型只写模块摘要；
- 页面只有名称，没有业务阶段和动作；
- 页面字段表被当作功能详细说明的替代；
- 模板重新引入“关键动作”“状态变化”“异常提示”等标签式正文。

## 14. 生成行为验收

### 14.1 简单样本

使用一个包含至少两个业务模块、多个页面和一个跨模块共用对象的简单 Design 副本。

必须观察到：

- 先产生完整 PRD 骨架；
- 每个功能模块预先存在 `4.x.6`；
- 模块按顺序直接写入最终 `prd.md`；
- 已完成模块不会因为后续模块生成而被重新概括；
- 最终阶段只做局部编号、名词和引用修正。

### 14.2 复杂样本

使用复杂真实 Design 的副本，不修改用户原始项目。

必须满足：

- 所有业务闭环都有对应功能模块；
- 每个功能模块都有 `4.x.6`；
- 页面正文没有退化为模块摘要；
- 高影响流程、权限、状态和异常仍可定位；
- 管理端和被审单位端页面落在真实业务闭环；
- 系统管理、组织机构、角色和审批流程等页面不能被合并成无差别的“系统配置”摘要。

### 14.3 中断恢复

在完成至少一个模块后中断执行，再由同一 AI 或另一个 AI 继续。

通过条件：

1. 能从最终 `prd.md` 判断已完成模块和未完成模块；
2. 不需要重新读取全部 Design；
3. 已完成模块内容保持不变；
4. 继续写入当前模块后，整体章节结构仍然完整；
5. 不因恢复而重新生成整个 PRD。

## 15. 结构层验收

### 15.1 模块章节

- 每个 `4.x` 模块都有 `4.x.6 功能详细说明`；
- `4.x.6` 不是空章节；
- `4.x.6` 下至少存在一个业务阶段、页面或动作；
- 模块验收标准和待确认事项仍然存在。

### 15.2 页面落点

对 Design 页面清单逐项检查：

- 每个页面在 PRD 正文出现；
- 页面归属的业务闭环正确；
- 页面在对应模块的功能详细说明中出现；
- 页面没有只出现在总体页面清单中；
- 同一页面没有被多个模块重复定义且互相冲突。

### 15.3 页面执行细节

抽取每个模块至少一个高影响页面，检查是否写明：

- 进入条件和业务上下文；
- 页面职责；
- 主要字段及使用差异；
- 可执行动作；
- 操作角色和允许状态；
- 成功结果；
- 状态或对象变化；
- 失败结果；
- Design 已确认的恢复路径。

## 16. 语义层验收

验收不能只看章节和标题，还要对照 Design 判断：

1. 目标和范围没有缩小；
2. 页面没有被错误合并；
3. 角色和权限没有扩大或反转；
4. 状态和状态转换没有丢失；
5. 字段属性、来源、只读、编辑和校验没有被过度压缩；
6. 异常和恢复没有被“系统提示失败”概括掉；
7. Design 的待确认事项没有被静默拍板；
8. PRD 没有新增 Design 未授权的默认值、分页、排序、超时、重试、提示文案或外部行为；
9. 模块可以脱离其他模块独立理解；
10. 共用规则和模块特有规则没有互相覆盖。

## 17. 不得作为通过依据的内容

以下内容不能单独证明通过：

- PRD 行数、字符数或标题数量增加；
- `prd-style-lint.py` 或 `prd-consistency-check.py` 返回 0；
- 生成过多少次；
- 使用了多少个 AI 或 subagent；
- 存在模块草稿、上下文包或执行日志；
- 生成过程没有报错。

这些只能作为辅助证据，最终必须回到真实 PRD 和确认版 Design 的语义对照。

## 18. 最终验收报告

执行 AI 必须报告：

1. 修改文件清单；
2. 删除或替换的旧规则；
3. 新增的全量分片规则；
4. 简单样本结果；
5. 复杂样本结果；
6. 中断恢复结果；
7. `4.x.6` 章节完整性结果；
8. 页面落点和高影响语义抽查结果；
9. 仍存在的已知限制；
10. 明确说明未执行 Git commit 和 Git push。

只有以下条件全部满足时，才能报告“PRD Skill 分片写作修订完成”：

- 不再依赖普通/大型 PRD 判断；
- 不依赖 subagent；
- 不再要求最后整体重写；
- 所有模块均直接写入最终 PRD；
- 中断后可以恢复；
- 每个模块都有完整 `4.x.6`；
- 页面、字段、动作、权限、状态和异常没有高影响遗漏；
- 简单样本和复杂样本均通过；
- 未修改用户正式 Design 和 PRD；
- 未执行未经授权的 Git commit 或 Git push。
