## 1. 本轮要解决的问题

依据：`docs/reports/2026-08-04-mattpocock-skills-philosophy-analysis.md` P0-1 与 P0-2。Matt Pocock 的元 skill `writing-great-skills` 是两轮优化的共同理论来源。

### 1.1 否定式指令（negation）

> Negation — steering by prohibition backfires: *don't think of an elephant* names the elephant and makes it more available, not less. Prompt the **positive** — state the target behaviour so the banned one is never spoken; keep a prohibition only as a hard guardrail you can't phrase positively, and even then pair it with what to do instead.

当前各 SKILL 否定句分布（grep `不要|不得|禁止|避免|绝不|不可|不能|勿|严禁|不准`）：

| SKILL | 否定句数 | 观察 |
|---|---|---|
| spm-prd | 23 | 大部分是事实边界/阻断硬护栏，少量操作性否定可正面化 |
| spm-align | 12 | 有"不能只留在对话上下文"等操作性否定 |
| spm-design | 7 | 有"不要把规则包存在视为分析已完成"等操作性否定 |
| spm-prototype-mark | 7 | 待逐句分类 |
| spm-prototype-review | 6 | 待逐句分类 |
| spm-prd-review | 5 | 待逐句分类 |
| spm-design-review | 5 | 待逐句分类 |
| spm-fix | 3 | 大部分硬规则 |
| spm-prototype | 2 | 待分类 |
| spm-start | 2 | 待分类 |

**问题**：操作性指令的否定式措辞（"不要自动执行 X""不要把 A 当作 B""不能只读 C"）会反向激活被禁行为，且没有告诉模型"应该怎么做"，是 SKILL 层的行为治理缺口，与 R14/R15 发现的"指令与实现不符"同类——措辞层问题，不是程序问题。

### 1.2 完成判据缺失（completion criterion）

> Each step ends on a **completion criterion**, the condition that tells the agent the work is done. Make it *checkable* (can the agent tell done from not-done?) and, where it matters, *exhaustive* ("every modified model accounted for", not "produce a change list") — a vague criterion invites **premature completion**.

现状勘察：

| SKILL | 完成判据现状 |
|---|---|
| spm-prd | **已有范本**：模块完成条件 10 项（阶段 C）；但阶段 A/B/D 和最终检查步骤没有显式判据 |
| spm-design | 写作动作内自检有回读清单，但"分析动作完成"没有显式判据；简单/完整模式完成条件不统一 |
| spm-align | 提问环节、写回环节没有显式完成判据；"Align 已完成"判定条件缺失 |
| spm-fix | 执行流程 7 步只有失败处理，没有"每步完成 = 什么状态"的判据 |
| spm-prd-review | 审查输出要求有，但"审查完成"判定条件不显式 |
| spm-design-review | 同上 |
| spm-prototype-review | 同上 |
| spm-prototype | 生成完成判据不显式 |
| spm-prototype-mark | 标注完成判据不显式 |
| spm-start | 只读扫描，判据天然简单，但可补"输出完整性"判据 |

**核心缺口**：模型执行 SKILL 时不知道"这一步算不算做完"，尤其有上下文压力时倾向提前收尾——这是 ShitPM 执行纪律根因（"模型自觉遵守流程假设证伪"）在 SKILL 层的对应物。现有程序化守门（落盘存在性、编排器 next/accept）在出口把关，但步骤中途的 premature completion 没有 SKILL 层约束。

## 2. 已确认的处理原则

### 2.1 否定句三分类处理（P0-1）

逐句分类，不得一刀切：

| 类型 | 定义 | 处理 |
|---|---|---|
| A 硬护栏 | 事实边界、阻断规则、安全红线，无法正面表述或正面化会失去约束力（如"不得替 Design 拍板冲突""不得把 PRD 提升为 Design 事实"） | 保留否定，但**必须配对正面替代指令**："不得 X；应 Y" |
| B 操作性否定 | 表述的是"应该怎么做"却用了否定形式（如"不要只把 align.md 当作 Design 唯一输入"） | **改写为正面陈述**："以材料资产为主输入，align.md 作为索引" |
| C 冗余否定 | 与其他句子重复、或删除后行为不变（no-op） | 删除整句，不保留 |

### 2.2 正面化改写规则（P0-1）

1. 找出否定句真正要求的目标行为，直接陈述目标行为；
2. 目标行为不明确时，参考该 SKILL 相邻的正面指令或 references 里的格式规范补全；
3. 改写后不得丢失原约束力度：能正面化的必须正面化，正面化会变弱的归入 A 类硬护栏；
4. 每处保留的硬护栏（A 类）后面必须紧跟"应…"或"要…"替代指令，不允许只有"不得 X"没有"应 Y"；
5. 不改变任何语义、命令、路径、阶段编号和既有规则；只动措辞。

### 2.3 完成判据两条标准（P0-2）

1. **可检查（checkable）**：模型能区分"做完"与"没做完"——判据必须是可观察的状态，不是"认真""全面""合理"这类形容词。
2. **穷尽（exhaustive）**：判据覆盖该步骤的全部产出物——"每个 Design 页面都落点"，不是"完成页面落点"。

### 2.4 判据写法规则（P0-2）

每个可执行步骤结尾用统一格式给出判据：

```text
完成判据：<可观察状态，尽量枚举，至少覆盖该步骤全部产出物>
```

1. 用"已/存在/非空/一致/无遗漏"等可验证词，不用"好/全/充分"；
2. 该步骤有几个产出物就写几项，逐项列出；
3. 判据与该步骤对应的确定性脚本、模板章节或落盘文件绑定（如"`4.x.6` 存在且非空"）；
4. 判据不得引入新动作（不新增检查步骤，只是把"做完"说清楚）；
5. 与现有"模块完成条件""写作内自检"等既有清单合并，不重复建设。

### 2.5 共同边界

- 只改 `skills/*/SKILL.md`；
- 不新增脚本、检查器、门禁、回执、JSON；
- 不改变任何命令、路径、阶段编号、规则语义；
- 不动 references/、templates/、contracts/、schemas/、scripts/；
- 不改用户项目 `.workflow/` 和 `output/`；
- 不改测试文件；
- 不执行 Git commit 和 push。

## 5. 优化二：完成判据显式化

### 5.1 通用要求

先读 SKILL 全文，标记所有"可执行步骤"（有动作、有产出、有阶段标识），然后为每个步骤补判据。判据位置：该步骤指令段落末尾，统一用 `完成判据：` 开头。

### 5.2 分 SKILL 判据草案（执行 AI 需按实际上下文调整）

**spm-prd**：
- 阶段 A 全局扫描：`完成判据：导航信息九项全部建立（目标范围/系统边界/角色权限/核心对象/非页面字段/共用状态/业务闭环/页面清单/待确认事项）；未要求保留全部页面正文于上下文。`
- 阶段 A-1 风险清单：`完成判据：风险清单已建立且记录事实冲突与高影响未知的 4 列内容；识别路径 6 步全部执行；阻断规则无命中或已记录。`
- 阶段 B 骨架：`完成判据：`prd.md` 已创建或维护；文档信息/概述/总体说明/全部模块标题/固定子章节/待确认索引均存在；有页面模块均已预建 `4.x.6`；writing pass 已运行。`
- 阶段 D 整合：`完成判据：7 项整合范围全部处理；引用均指向当前 `prd.md` 真实章节；无"见 6.1"式失效引用；已触达的已完成模块已按变更失效规则重验收。`
- 最终检查：`完成判据：两次脚本均已运行并逐项处理输出；最终 `prd.md` 已直接阅读；`status.json` 已更新且未在检查前更新。`

**spm-design**：
- 简单模式：`完成判据：来源事实逐项落入 Design；目标-能力-场景-流程-页面-动作-字段-状态-权限-规则-异常-验收链路完整；字段表八列齐全逐项；操作表角色×状态明确；状态机闭环规则满足；`design.md` 完整可读。`

- 通用：`完成判据：两个输出（`design.md` 及约定输出）可读取；写作自检完成；无未暴露高影响事项；才能告知用户"Design 已完成，请确认"。`

**spm-align**：
- 材料读取：`完成判据：材料资产按顺序读取完成；可定位事实与来源行范围已收集；无效材料已标注未伪造。`
- 提问环节：`完成判据：所有高影响未知均已提问或列为待确认；每次只问一个；能从材料查到的不再追问。`

- Align 完成：`完成判据：Align 产物可读取；无高影响未知悬空未记录；已告知用户 Align 形成且 Design 将自动继续。`

**spm-fix**：
- 每步：`完成判据：<该步动作的输出物已就位>；例如步骤 1"改什么/改成什么"已明确；步骤 4 传播契约已读取且受影响最深阶段/分支已判定；步骤 5 事实源已局部覆盖且无多版本；步骤 6 confirmation 失效已处理；步骤 7 实际分支检查已运行。`

**spm-prototype**：`完成判据：原型页面生成且可运行；Design 已确认；未引入 Design 未授权架构/技术；页面覆盖清单可核对。`

**spm-prototype-mark**：`完成判据：标注系统已注入；关键点标记与备注已按 design 生成；复制到 prototypemark 目录完成。`

**spm-start**：`完成判据：当前产物、Design confirmation、可用动作已扫描并输出；未修改任何文件；未给唯一下一步。`

### 5.3 注意事项

- 判据必须绑定该 SKILL 现有产物/脚本/模板，不发明新名词；
- 判据要短（每步 1-3 行），不把整个自检清单重复一遍——已有清单的步骤直接引用（如"按 4.2 模块完成条件逐项确认"）；
- 判据不得成为"新增检查动作"——它是判定"做完了"的表述，不是新任务。

## 6. 执行顺序（单 AI 同轮，两项一起完成）

1. 读取全部 10 个 SKILL.md；
2. 按否定句数量从多到少处理每个文件；**每个文件内先做否定句分类与正面化（优化一），再补完成判据（优化二）**，避免同一文件两轮改动冲突；
3. 每个文件完成后立即 grep 复核：否定句数量减少且剩余均为已配对的 A 类硬护栏；所有可执行步骤均有 `完成判据：`；
4. 全量完成后抽读：改后语义未变、判据可检查/穷尽/不新增动作；
5. 只报告结果，不执行 Git commit 或 push。

## 7. 停止条件

- 改写导致约束力度下降或语义变化 → 停止，还原该句并报告；
- 某句无法确定正面化是否丢失约束 → 归 A 类并补替代，不强行改写；
- 判据无法写"可检查状态"（只能写形容词）→ 停止，说明原因并报告，不改写规则本体来迁就判据；
- 补判据或正面化需要修改 references/contracts 或新增脚本才能完成 → 停止，报告，不越界修改；
- 判据与既有模块完成条件冲突 → 停止，报告冲突位置。

两项优化各自的验收层全部通过，整体才算通过：

- grep 全仓 `不要|不得|禁止` 总数较改前显著下降（目标：硬护栏占比 ≥80%）。

### 10.2 语义与一致性层（抽读）

- 改写后无约束丢失、无行为语义变化（改前/改后相邻段落比对）；
- 命令、路径、阶段编号、规则引用与改前完全一致；
- 对 spm-prd（模块装载指令、最终检查顺序）、spm-align（提问与写回规则）、spm-design（规则包使用）、spm-fix（失败处理）、三个 review（审查输出）、prototype/mark/start（核心指令）各抽 2 处改写前后对照，确认行为指令等价。

### 10.3 禁止出现

- 新增否定句（本轮只减不增）；
- 把硬护栏改写后失去阻断力（如"不得替 Design 拍板"改成"可以提出建议"）；
- 改后出现新的语义承诺或行为要求。

## 11. 优化二验收：完成判据

### 11.1 覆盖层

- grep `完成判据：` 覆盖全部 10 个 SKILL；
- 每个 SKILL 的可执行步骤均有对应判据，无步骤遗漏；
- 已有模块完成条件的步骤（spm-prd 阶段 C）不重复，用引用表述。

### 11.2 可检查/穷尽层（抽读）

抽 3 个 SKILL 各 5 条判据：

- 每条判据是否可区分"完成/未完成"；
- 是否遗漏该步骤的产出物；
- 是否引入无法观察的内部状态（如"已充分理解"）。

### 11.3 不增负层

- 改后各 SKILL 步骤数与改前一致（只加判据行）；
- 无新增脚本、JSON、回执、检查器引用；
- 无新增"必须运行 X 检查"类命令。

## 12. 不得作为通过依据的内容

- PRD/SKILL 行数、字符数变化；
- 仅 grep 否定句数量减少（可能是误删或分类错误）；
- 判据行数多（可能是不知所云的重复）；
- 只有部分 SKILL 完成两项优化；
- 把已有清单改名成判据（如 spm-prd 模块完成条件原样存在不算本轮产出）；
- 修改了 references 或 scripts 而 SKILL 措辞未动。

## 13. 最终验收报告

执行 AI 必须报告：

1. 每文件否定句 A/B/C 分类统计表 + 修改前后否定句数量；
2. 每 SKILL 步骤-判据对照表 + 补判据数量与步骤覆盖数；
3. 至少 10 处典型改写对照（改前 → 改后 → 分类）与 10 处典型判据示例；
4. 保留的 A 类硬护栏清单及各自配对替代；
5. 语义抽读与可检查/穷尽/不增负自评结论；
6. 无法写出可检查判据的步骤清单及原因；
7. 仍存在的无法正面化或无法配对的句子及原因；
8. 明确说明未执行 Git commit / push。

只有以上全部通过，才能报告"SKILL 两层治理优化完成"。
