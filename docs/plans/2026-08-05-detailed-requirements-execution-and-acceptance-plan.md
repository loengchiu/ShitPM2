# PRD“详细需求说明”章节重写专项——执行与验收计划

> 日期：2026-08-05  
> 状态：待确认  
> 适用对象：当前 `V2` 分支的 PRD 生成规则、执行流程和真实项目重跑  
> 真实项目：`D:\work\交投软件中心\智慧服务区\智慧停车区`  
> 目标章节：PRD `4.x.6 功能详细说明`  
> 重要边界：只优化“详细需求说明”章节的写法和生成验收，不重新讨论 Design，不重构整篇 PRD，不使用已废弃的分支名称。

## 一、问题定义

### 1.1 本次真正要解决的问题

当前 PRD 的事实覆盖和结构检查已经比较完整，但“详细需求说明”仍然容易出现以下写法：

- 先写“页面职责、使用对象、所属业务侧、入口与返回”；
- 再按 UI 区块盘点字段和展示内容；
- 最后把 Design 操作逐条拼成动作；
- 每个页面使用相同的句式、相同的动作层次和相同的异常表达；
- 页面写了很多内容，但读者仍然看不出用户要完成什么业务判断；
- 页面正文没有自然说明判断结果如何进入下一个业务环节。

这不是事实遗漏问题，而是产品规格的组织和表达问题。

### 1.2 最终目标

详细需求说明章节交付后，产品、研发、测试不需要重新拼接页面清单、字段表、状态表和权限表，就能顺着正文读出：

1. 这个业务阶段要解决什么问题；
2. 谁在什么前提下使用页面；
3. 用户依据哪些信息做什么判断或决定；
4. 系统按照什么规则处理；
5. 成功后对象、状态、页面和数据如何变化；
6. 失败、无数据、权限不足或外部协作异常如何处理；
7. 下一步由谁接手，进入哪个业务环节。

“一眼像资深产品经理”不是文风评分，也不是关键词命中，而是上述业务因果链在正文中自然成立。

## 二、范围和不做事项

### 2.1 本次范围

本次只处理以下内容：

- `4.x.6 功能详细说明`的业务模块、页面、动作组织；
- 页面开头的语境说明；
- 页面区块、字段、展示行为在动作中的落点；
- 动作合并、动作命名和动作正文；
- 主链路、关键分支、状态变化、角色衔接和异常恢复的自然表达；
- PRD Skill 的生成模式和详细需求说明硬约束；
- 与上述规则直接相关的参考文档、模板提示和确定性检查职责；
- 真实项目 `output/prd/prd.md` 中 `4.x.6` 的重新生成和验收。

### 2.2 明确不做

- 不修改确认版 `output/design/design.md`；
- 不重新定义业务范围、角色、权限、状态、字段或统计口径；
- 不修改 `4.x.6` 以外的 PRD 章节，除非编号或内部引用因本次页面组织变化必须同步；
- 不根据 Prototype 或旧 PRD 补造产品事实；
- 不把已废弃分支的规则或命名重新带入当前方案；
- 不新增“资深度评分器”“语义评分脚本”“统一检查器”或新的证明性回执；
- 不用脚本数量、覆盖率、动作数量、上下文装载成功或退出码证明写作质量；
- 未经确认不修改 Skill、脚本、模板和正式项目 PRD；
- 不执行 `git commit`、`git push`。

## 三、现状基线和判断

### 3.1 可继续保留的能力

以下能力仍然有价值，但必须回到辅助位置：

- Design confirmation 和事实哈希：负责确认输入是否有效；
- Design 模块片段提取：负责让模型读到正确的业务事实；
- 确定性文风检查：负责发现标签式正文、明确占位符、重复标题等稳定问题；
- 明确事实冲突检查：负责发现新增页面、字段、状态、权限和字段属性冲突；
- 分片读取：负责控制上下文规模，不负责决定正文应该怎么写。

### 3.2 当前执行上的核心偏差

当前流程把以下内容变成了更容易被模型完成和报告的任务：

- 页面、字段、操作是否全部有落点；
- 动作数量是否承接；
- Design 索引是否覆盖；
- 规则、场景和回执是否装载；
- 章节、状态、权限和引用是否可定位。

这些内容可以证明“材料承接得比较全”，但不能证明“正文像资深产品经理”。

当前规则还要求页面保留大量元数据和区块信息。于是模型可以通过“页面元数据 + 区块列表 + 操作段落”完成形式要求，而不必完成“业务判断和下一环节”的重组。

### 3.3 本次执行的基本判断

本次不把问题归结为“模型能力不足”，也不把问题归结为“规则数量不够”。正确的处理方式是：

- 减少会把模型引向证明和拼接的机械目标；
- 把业务判断、动作重组、页面语境和下一业务环节写成生成时的硬约束；
- 把最终语义验收交给主 Agent 直接回读真实 PRD；
- 脚本只处理模型不适合稳定完成的确定性问题。

## 四、目标写法定义

### 4.1 模块必须先按业务结果组织

功能模块不以页面清单或菜单为主线，而以业务闭环或业务结果为主线。

模块开头应让读者知道：

- 这个模块处理的业务对象是什么；
- 业务从哪里开始；
- 通过哪些页面或角色推进；
- 最终产生什么业务结果；
- 结果如何衔接到下一个模块。

不允许把模块开头写成页面目录或字段目录。

### 4.2 页面只能作为业务承接载体

页面开头可以有一段简短语境，但不能再使用以下结构作为页面主体：

```text
页面职责：……
使用对象：……
所属业务侧：……
所处业务阶段：……
入口与返回：……
页面区块：……
页面展示行为：……
```

这些事实仍然要保留，但要融入业务语境、动作前提、动作结果或权限说明中。页面正文必须进入用户任务和业务动作，不能停留在页面元数据层。

### 4.3 每个页面必须形成业务判断链

除纯展示且没有业务判断的页面外，每个页面必须能从正文中读出：

```text
用户在什么业务前提下进入
→ 需要判断或完成什么
→ 依据哪些信息判断
→ 系统和用户分别做什么
→ 形成什么业务结果
→ 下一步由谁继续
```

不要求正文出现这些箭头或固定小标题，也不要求所有页面使用相同段落数量。要求的是业务因果链必须自然存在。

对于纯查询、纯查看、返回等简单动作，只写触发和业务结果，不强行补不存在的表单、确认和复杂异常。

### 4.4 动作必须按业务结果重新组织

Design 的操作表是事实输入，不是 PRD 动作目录。

允许：

- 把服务区切换和车位类型切换合并为“切换查看范围”；
- 把播放、暂停、静音、全屏和截图合并为“控制视频播放”；
- 把多个简单卡片入口合并为“进入主题汇总”；
- 把查询、筛选、重置等没有独立业务结果的浏览动作融合到“查看列表”或“定位记录”中。

不允许：

- 为了证明每个 Design 操作都有落点，强行一对一生成动作；
- 把“点击”“打开”“切换”“返回”直接当作业务动作标题；
- 合并后丢失角色、前置条件、状态、数据范围、失败结果或后续去向；
- 用“支持相关操作”“可进行相应处理”掩盖合并后的具体规则。

动作标题优先使用“动词 + 业务对象或业务结果”，例如：

- “定位异常车辆”；
- “确认滞留告警”；
- “提交核查结果”；
- “查看组织汇总”；
- “控制视频播放”。

### 4.5 动作正文按复杂度写

| 动作类型 | 最低要求 |
|---|---|
| 简单查询、查看、返回 | 触发条件、查看范围或返回结果；Design 已定义的特殊展示或异常必须承接 |
| 普通表单、保存、提交、修改 | 前置条件、输入与校验、系统处理、成功结果、失败时的数据和页面保留 |
| 多角色、多状态、多分支、破坏性或外部协作 | 允许角色和状态、关键分支、状态变化、数据副作用、失败恢复、后续衔接角色 |

内容必须融入自然语言，禁止使用以下标签式正文：

```text
触发：
处理：
成功结果：
失败结果：
失败与恢复：
```

### 4.6 字段和区块服务于业务判断

字段不再按“页面上有什么”机械罗列，而要说明它在当前动作中的作用：

- 用户通过它判断什么；
- 它是用户输入、系统计算、接口返回还是关联带出；
- 它何时只读、何时可编辑；
- 它如何影响按钮、状态或提交结果；
- 它为空、异常或超长时如何呈现。

区块只有在承载业务判断、状态变化、关键操作或异常结果时才展开。区块很多或存在子分组时可以使用列表；区块少且内容短时优先使用自然句。

### 4.7 结果必须衔接下一业务环节

动作结果中应直接写明：

- 对象或状态变成什么；
- 页面、按钮、字段或列表如何刷新；
- 下一步由谁继续；
- 下一步进入哪个页面或业务环节。

“返回列表”“刷新页面”“跳转详情”只有在它们具有业务意义时才作为结果说明，不能代替业务结果。

### 4.8 颗粒度基准：规则要细，不是篇幅要长

本次参考 [2red Product Monster PRD examples](https://github.com/Kira2red/2red-product-monster-skills/blob/main/skills/2red-product-monster-prd/references/examples.md) 的目的，是借鉴其“可实现、可观察、可测试”的颗粒度，不迁移其固定章节、标签、图表工具或示例中的具体数值。

该参考中的四类示例共同体现了以下颗粒度：

1. 页面或功能的入口位置和业务目标；
2. 用户在什么条件下可以操作，什么条件下不可操作；
3. 操作前、操作中、操作后的界面状态；
4. 输入字段、字段联动、默认值、校验时机和错误反馈；
5. 成功结果、失败结果、超时、风控、无数据和离开页面后的行为；
6. 静态文案、动态内容来源、状态标签、颜色、脱敏和超长文本处理；
7. 状态或数据变化后，页面、按钮、列表和历史记录如何变化。

这里的“颗粒度”不是字数、条目数量或固定小标题数量，而是每条规则能否独立回答一个实现或测试问题。好的正文读者可以从中直接提炼出测试场景，例如“前置条件—操作—期望结果”，而不是只能得到“支持导出”“支持联动”“异常时提示”等概括性结论。

外部 Skill 将微观交互归纳为八类覆盖维度，本项目将其作为动作写作和验收时的适用性清单：

| 维度 | 本项目需要关注的内容 |
|---|---|
| 文本与数据展示 | 静态/动态内容、空数据、脱敏、截断、换行和来源 |
| 按钮与操作 | 可见、可用、置灰、禁用、重复点击、成功和失败 |
| 表单与输入 | 输入字段、联动、默认值、字符限制、校验时机和错误提示 |
| 加载态 | 首屏、局部、处理中、加载失败和重试 |
| 弹窗 | 触发、关闭、取消、确认、遮罩和多弹窗关系 |
| 错误态 | 接口错误、权限不足、数据不存在和用户可恢复方式 |
| 异常与降级 | 超时、网络异常、外部协作失败、离线或局部功能不可用 |
| 边界数值 | 刷新频率、超时、分页、文件上限、操作频次和长度限制 |

八类维度不是每个动作都必须全部出现。简单查看动作只覆盖适用项；普通表单、状态变更和复杂协作动作必须逐项判断是否适用，适用时不得遗漏。

结合本项目，最终采用以下组合：

- 采用 `main` 的业务组织：模块按业务结果，页面按用户动作，主链路和下一环节连续可读；
- 采用外部示例的行为颗粒度：关键动作写清可见条件、过程状态、结果、失败和边界；
- 采用当前 V2 的事实边界：所有角色、权限、状态、字段、数值、文案、外部行为仍以确认版 Design 为准；
- 不采用外部示例的固定“位置/目标/按钮状态与交互”模板，不把所有页面强行拆成相同结构；
- 不采用外部示例中的 PlantUML、Mermaid 或示例业务数值，除非当前项目 Design 已确认且符合本项目交付规则。

颗粒度验收的核心问题是：

> 研发能否据此实现，测试能否据此设计场景，产品能否据此判断业务结果？

如果只能证明“页面上有哪些控件”，但不能回答以上问题，仍然是不合格的详细需求说明。

### 4.9 数据型功能必须同时写清“来源”和“口径”

字段表写了“系统统计”“接口返回”“系统计算”，只能说明数据从哪里来，不能说明数据对谁成立、按什么范围计算、如何与页面其他数据保持一致。

以下数据型内容必须在页面、动作或统计说明中就近写清，不能只依赖全局角色权限或字段表：

| 口径维度 | 必须回答的问题 |
|---|---|
| 数据对象 | 统计的是车辆、记录、告警、任务、车位还是组织；一条数据按什么对象计数 |
| 组织范围 | 服务区管理员、区域中心、服务中心分别看到哪些服务区、区域或组织；当前选择范围如何影响结果 |
| 时间范围 | 今日、近 24 小时、自然日、查询周期或实时当前值的起止时间 |
| 统计口径 | 总数、去重数、当前在场数、平均值、最大值、最小值、占用率的分子和分母 |
| 包含与排除 | 哪些状态、异常记录、无效数据、重复记录或未完成记录纳入或排除 |
| 筛选传递 | 服务区、时间、车型、状态等条件是否同时作用于卡片、列表、趋势、图表和导出 |
| 下钻关系 | 从指标或图表进入明细时，是否带入同一组织范围、时间范围和筛选条件 |
| 刷新与一致性 | 更新频率、数据时间点、部分失败时哪些数据保留、不同卡片是否允许时间不一致 |
| 空值与零值 | 无数据、确实为零、数据缺失、统计失败分别如何展示 |
| 权限和敏感信息 | 指标是否对所有角色可见，车辆级下钻、手机号、公司信息和导出是否有额外限制 |

举例：

- “今日入场车辆”不能只写“系统统计”，还要说明当前角色看到的是授权服务区、所属区域还是所属服务中心范围，以及“今日”的时间口径；
- “车位占用率”不能只写“系统计算”，还要说明选定服务区和车位类型下的已占用数量、车位总数、无车位数据和分母为零时的展示；
- “24 小时趋势”不能只写“展示趋势”，还要说明时间窗口、统计粒度、当前选择范围、缺失时间点和点击下钻是否继承条件；
- “平均停靠时间”不能只写“系统计算”，还要说明统计对象、是否只纳入完整入离场记录以及当前角色的数据范围；
- “导出当前结果”不能只写“导出 Excel”，还要说明导出的组织范围、时间范围、筛选条件、敏感字段和权限校验。

如果 Design 已定义，必须承接；如果 Design 未定义且会改变统计结果、数据边界或权限，必须列为待确认，不能用“按权限”“按配置”“按业务规则”替代。

## 五、执行模式

### 5.1 四种执行模式

| 模式 | 触发条件 | 处理方式 |
|---|---|---|
| 首次生成 | 目标 PRD 尚不存在 | 根据确认版 Design 生成详细需求说明 |
| 重新生成 | 用户明确要求重跑、重新生成、整体重写或本次质量问题涉及多个页面 | 详细需求说明整体重新写；旧 PRD 只在初稿完成后用于回归，不作为写作模板 |
| 局部修复 | 用户明确指定页面、动作或问题 | 只修改指定范围；不得借机重写无关页面 |
| 中断续写 | 执行中断或上下文压缩 | 从最后一个未完成模块继续；规则发生变化时，受影响模块必须重新生成 |

本次真实项目采用“重新生成”模式，因为问题已经出现在多个页面的组织方式，不是局部错字或单个动作遗漏。

### 5.2 重新生成的严格顺序

1. 读取并确认 Design；
2. 建立全局业务导航和模块边界；
3. 只装载当前模块 Design 事实和详细需求写作规则；
4. 先在模型内部完成该模块的业务结果、页面任务和动作重组；
5. 直接写入详细需求说明；
6. 主 Agent 立即回读该模块，发现页面元数据化、动作清单化或业务链断裂时直接重写；
7. 所有模块完成后，主 Agent 重新通读整个详细需求说明；
8. 旧 PRD 只用于回归事实、异常和待确认事项，不复制旧句子、旧页面结构或旧动作组织；
9. 运行确定性检查；
10. 处理真实问题后再次回读，最后才更新状态。

### 5.3 真实项目的隔离方式

正式项目重跑先使用隔离副本：

- 保留当前 `prd.md`、`prd.md.v32.bak` 和 Design；
- 不覆盖正式交付物；
- 先生成试写样本；
- 试写通过后再生成完整 `4.x.6`；
- 完整章节通过事实和语义验收后，才替换正式 PRD 中对应章节；
- 替换前后保留可回退副本。

除 `4.x.6` 外的章节默认原样保留。若页面编号、内部引用或模块标题发生变化，只同步修正真实受影响的引用。

## 六、Skill、参考文档和脚本的职责调整

### 6.1 `skills/spm-prd/SKILL.md`

只保留执行协议和不可违反的核心要求：

- 本次写作范围是 `4.x.6 功能详细说明`；
- 明确当前执行模式，重新生成不得退化为局部微调；
- Design 是唯一产品事实源；
- 页面必须围绕用户任务、业务判断和下一业务环节组织；
- Design 操作必须按业务结果重新组合，不按数量逐条复刻；
- 高影响未知必须待确认；
- 每个模块写完后直接回读并修正；
- 最终由主 Agent 直接阅读真实 PRD 并否决语义不合格结果。
- 写作规则和写作示例必须联合装载；示例不是可选的“遇到难点再查”材料，而是模型学习目标颗粒度和表达方式的必要输入。

不得把完整写作手册、所有场景清单和大量示例重复塞回 Skill。

### 6.2 `references/prd-writing-rules.md`

作为详细需求说明的唯一规范源，承载：

- 页面和模块业务组织；
- 页面语境和动作优先原则；
- 动作复杂度分级；
- 动作合并和动作命名；
- 字段、区块、状态、权限、异常和角色衔接；
- 自然语言、列表和表格的使用边界；
- 资深产品经理式正文的正反例引用。

### 6.3 `references/prd-writing-examples.md`

至少提供以下真实写法对照：

1. 简单查看动作；
2. 普通表单提交动作；
3. 多角色状态流转动作；
4. 查询和统计动作；
5. 多区块页面；
6. 少区块页面；
7. 移动端和跨角色页面；
8. UI 文案、动态来源、长文本和异常恢复；
9. 页面元数据清单、动作流水账和标签式正文反例。

示例必须展示“如何重组业务”，不能只是展示禁用词。

### 6.4 `templates/prd.md`

模板只保留章节骨架、页面和动作标记以及极少量提示。

模板不得出现会诱导所有页面都照抄的固定元数据字段块，不得要求每个页面都使用相同的页面职责、使用对象、入口与返回句式。

### 6.5 脚本处理原则

| 类别 | 处理方式 |
|---|---|
| Design confirmation、文件存在性、片段提取、Markdown 解析 | 保留 |
| 明确新增页面/字段/状态/权限、字段属性和枚举冲突 | 保留，作为事实冲突门禁 |
| 标签式正文、明确占位符、重复标题等稳定坏味道 | 保留 |
| `design-index`、覆盖率、操作数量、模块完成计数 | 只作导航或诊断，不作质量证明 |
| `possible_omission`、语义无法判断、权限无法提取等结果 | 交给主 Agent 回读，不得自动宣称通过或失败 |
| 只生成回执、证明 JSON、执行记录且没有真实消费者的工具 | 先审计消费者，无消费者则退役 |
| 新增语义评分器或统一语义检查器 | 不实施 |

脚本调整前必须先检查真实消费者。删除旧工具时同步删除只验证已废弃行为的测试，不为了维持测试数量保留废弃流程。

## 七、分阶段执行计划

### 阶段 0：冻结基线

输入：

- 当前 Skill、规则、模板和脚本；
- 确认版 Design；
- 当前真实 PRD；
- `main` 分支中已验证的详细需求说明写法和样本。

动作：

1. 确认 Design confirmation 和哈希；
2. 记录当前 `prd.md` 的详细需求说明范围；
3. 记录当前页面清单、模块清单和待确认事项；
4. 确认工作区已有用户改动，不覆盖无关文件；
5. 明确本次执行模式为“重新生成”。

通过条件：

- 输入文件可读；
- Design 已确认；
- 详细需求说明边界清楚；
- 没有把旧 PRD当作写作输入；
- 正式项目有可回退副本。

### 阶段 1：确定写作规则和消费者

动作：

1. 盘点 Skill、规则、模板、示例、场景清单、Review 清单和脚本；
2. 标记每条规则属于“事实边界”“写作硬约束”“写作建议”还是“确定性检查”；
3. 移除或降级把覆盖率、动作数量、回执当作质量的表达；
4. 将“业务判断、下一业务环节、动作重组、页面非元数据化”提升为生成硬约束；
5. 确认规则与示例实际装载路径，模块写作至少同时装载一个简单动作示例和一个复杂动作示例；
6. 规定示例只提供颗粒度和表达参考，不提供产品事实；
7. 同步修改直接消费者，不复制第二套规则。

通过条件：

- 详细需求说明只有一个规范来源；
- Skill 中有明确执行模式和重写要求；
- 规则文件中有明确正例和反例；
- 模块写作上下文同时包含规则和适配复杂度的正例；
- 没有新增语义检查器；
- 所有保留脚本都有真实消费者和明确输出用途。

### 阶段 2：四类页面试写

在真实项目隔离副本中先试写以下页面：

1. `车流实时监控`：实时监测、统计、视频和异常展示；
2. `滞留告警详情与处理`：告警状态、多角色处理和异常恢复；
3. `两客一危核查任务（移动端）`：移动端、角色衔接和状态提交；
4. `监控点位管理`：配置表单、绑定关系和外部视频接入。

每个页面必须先完成内部业务重组，再写正文。试写阶段不追求全量覆盖，重点验证：

- 页面是否从业务任务开始；
- 动作是否按业务结果组织；
- 简单动作是否足够简洁；
- 复杂动作是否自然写出条件、结果、状态和衔接；
- 区块和字段是否服务于判断；
- 文本是否仍然像页面元数据清单。

阶段 2 通过后才能全量重写。

### 阶段 3：试写人工验收

由主 Agent 和用户共同检查试写页面。检查时不先看执行日志、覆盖率、历史评分或生成器自述，只看：

- 确认版 Design；
- 试写后的详细需求说明；
- 必要时查看旧 PRD做事实回归。

如果任一试写页面仍然出现“元数据开头 + 区块清单 + 动作拼接”，阶段 2 不通过，回到规则和示例修正，不进入全量重写。

### 阶段 4：完整重写 `4.x.6`

动作：

1. 按业务闭环建立模块顺序；
2. 每个模块先确定业务结果和角色衔接；
3. 每个页面先确定用户任务、判断依据和下一环节；
4. 按业务结果合并简单动作；
5. 按动作复杂度写正文；
6. 将字段、区块、状态、权限、异常和待确认事项放到真实使用位置；
7. 每个模块完成后立即回读和修正；
8. 全部完成后由主 Agent 通读整个 `4.x.6`；
9. 只在初稿完成后用旧 PRD做事实回归。

通过条件：

- 所有 Design 页面均有业务落点；
- 所有高影响事实没有静默新增；
- 所有关键 Design 操作的业务结果均承接；
- 页面和动作不再以元数据和 UI 区块作为主要组织轴；
- 主链路、关键分支、状态、权限、异常和后续衔接完整。

### 阶段 5：确定性检查和问题修正

顺序固定：

1. 最后一次正文写入；
2. 主 Agent 回读本次受影响模块；
3. 运行保留的确定性检查；
4. 只修正真实的事实冲突、格式问题和明确坏味道；
5. 若再次修改正文，回到第 1 步；
6. 最后直接阅读真实 `prd.md`；
7. 确认内容不再变化后更新状态。

脚本结果不直接转化为“资深产品经理质量通过”。

### 阶段 6：用户验收和交付

交付用户检查：

- 车流实时监控；
- 滞留告警详情与处理；
- 两客一危核查任务（移动端）；
- 监控点位管理；
- 至少一个简单查询页面；
- 至少一个普通表单页面；
- 至少一个跨角色状态页面。

用户确认通过后，才将隔离副本中的 `4.x.6` 替换到正式 PRD。

## 八、验收标准

### 8.1 语义硬验收

以下任一项失败，详细需求说明不通过：

1. 页面主体仍然是页面职责、使用对象、入口返回和区块字段清单；
2. 页面没有自然说明用户要做的判断或业务任务；
3. 业务动作标题仍主要是“点击、打开、切换、返回、播放”等 UI 行为；
4. Design 操作被机械一对一复刻，简单浏览动作没有按业务结果合并；
5. 动作只写按钮和跳转，没有处理规则、业务结果或状态影响；
6. 复杂动作缺少角色、状态、关键分支、失败恢复或下一步衔接；
7. 页面正文需要读者跨多个表格才能拼出主链路；
8. 多数页面使用同一套模板句式，替换字段名后仍完全相同；
9. 为了追求完整新增 Design 未确认的高影响事实；
10. 确认版 Design 的待确认事项被静默拍板。

### 8.2 产品规格硬验收

以下内容必须在适用处可定位：

- 触发角色和业务前提；
- 查询或统计的对象、范围和口径；
- 表单字段、必填、来源、校验和提交条件；
- 状态、权限、数据范围和状态驱动操作；
- 成功结果和失败结果；
- 页面停留、刷新、跳转和数据保留；
- 空数据、异常、并发变化和外部协作失败；
- UI 文案、动态数据来源和超长文本处理；
- 下一步衔接角色和业务环节。

简单动作不适用的内容不得强行补写。

### 8.2.1 颗粒度硬验收

对于普通表单、状态变化、多角色协作、异步操作、外部接入和异常处理动作，必须达到以下颗粒度：

- 能定位操作前的角色、状态、数据范围或页面条件；
- 能定位用户输入、系统计算、接口返回或关联带出的数据来源；
- 能定位操作中的加载、禁用、处理中或等待状态；
- 能定位成功后的数据、状态、按钮、列表、历史记录或页面变化；
- 能定位失败、超时、无数据、权限不足、重复操作或外部失败的处理；
- 能定位静态文案、动态文案和超长文本的展示规则；
- 能定位下一步由谁继续或进入哪个业务环节。

每个条目或自然句优先表达一条独立规则，避免把多个条件、结果和异常压缩成“支持相关处理”。同一个动作不要求机械拆成“位置、目标、交互、异常、文本”等固定小节，也不要求简单动作覆盖全部维度。

通过颗粒度验收的最低表现是：测试人员可以从动作正文直接抽出至少一条正常场景和适用的异常场景；研发人员不需要再向产品追问“什么时候可点、成功后变什么、失败后留不留数据、谁接着处理”。

### 8.2.2 数据范围和统计口径验收

以下对象出现任意一种时，必须单独进行数据范围和统计口径验收：

- 指标卡片；
- 数字统计；
- 图表和趋势；
- 汇总列表；
- 组织下钻；
- 导出结果；
- 按组织、时间、车型、状态或任务范围筛选的页面；
- 任何“当前”“今日”“实时”“平均”“占用率”“完成率”“异常数”等业务结果。

验收时逐项确认：

1. 当前角色能看到的组织和数据范围是否明确；
2. 页面选择器、筛选条件、指标卡片、明细列表、趋势和导出是否使用同一范围；
3. 时间窗口和统计时点是否明确；
4. 分子、分母、去重规则、状态纳入和排除规则是否明确；
5. 无数据、零值、缺失和统计失败是否区分；
6. 指标下钻后的明细是否继承组织、时间和筛选条件；
7. 敏感字段、车辆级明细和导出是否遵循角色权限；
8. 缓存、刷新和局部失败是否可能展示超出当前权限或过期范围的数据。

“字段来源已写”“全局权限章节已写”“页面有服务区选择器”都不能代替以上验收。

### 8.3 写作质量硬验收

以下问题必须为零：

- 标签式正文；
- 动作流水账；
- “用于承载”“按常规处理”“支持相关操作”等模糊占位；
- 原因腔替代业务规则；
- 反复重复默认角色；
- 空标题、空栏目、伪缩进和机读稳定标识泄漏；
- 以区块清单替代用户动作；
- 以覆盖率或脚本回执替代语义结论。

### 8.4 事实和一致性验收

- 页面、字段、状态、权限和枚举没有明确新增；
- 明确字段属性和权限没有冲突；
- Design 待确认事项仍然保留；
- 页面操作、状态变化和角色衔接没有互相矛盾；
- 当前 PRD 内部引用可定位；
- `4.x.6` 以外章节没有被无授权改写。

### 8.5 自动化回归验收

运行现有、与本次改动直接相关的测试。测试清单在执行阶段根据实际消费者确定，不为了“测试数量完整”运行无关测试。

至少包括：

- `prd-style-lint`；
- `prd-consistency-check`；
- context 装载和资源完整性测试；
- 规则、模板、示例和消费者引用测试；
- 已修改脚本的单元或回归测试。

自动化结果只能证明确定性行为没有回归，不能单独证明写作质量。

## 九、失败回退和重新执行

### 9.1 试写失败

如果试写页面仍然模板化：

1. 不进入全量重写；
2. 记录具体失败片段；
3. 判断是规则、示例、上下文、执行模式还是主 Agent 回读失败；
4. 修正唯一原因；
5. 重新试写同一页面；
6. 不通过则继续停留在试写阶段。

### 9.2 全量重写失败

如果全量结果仍然与旧 PRD高度相似，先判断：

- 是产品事实本身决定了相似；
- 还是正文结构、句式和动作组织被旧 PRD或模板继承；
- 是执行模式错；
- 还是主 Agent 没有执行最终语义否决。

不能直接通过增加校验脚本解决。必要时回到阶段 1或阶段 2。

### 9.3 事实冲突

发现 Design 内部存在高影响冲突时：

- 停止受影响模块；
- 保留冲突位置和影响对象；
- 不在 PRD 中自行裁决；
- 回到 Design Fix或等待确认。

### 9.4 用户不接受

用户若认为“仍不像资深产品经理”，不以主观评分否定或接受全部结果，而是请用户指出具体页面和段落。下一轮只针对可复现的写作缺陷分类处理，避免再次扩大为整套脚本和流程重构。

## 十、完成定义和最终报告

本专项只有同时满足以下条件才算完成：

1. Skill、规则、模板和脚本职责已按本计划调整；
2. 四类试写页面通过人工语义验收；
3. 真实项目 `4.x.6` 已按“重新生成”模式全量重写；
4. 主 Agent已直接回读真实详细需求说明并完成必要修正；
5. 确定性检查已运行并处理真实问题；
6. 详细需求说明通过事实、一致性和资深产品经理式写作验收；
7. `4.x.6` 以外章节没有无授权变化；
8. 正式项目 PRD 已由用户确认或明确标记为待用户验收；
9. 没有用脚本数量、覆盖率、运行回执或动作数量替代语义验收。

最终报告固定包含：

```text
一、专项结论
二、执行模式和输入基线
三、Skill、规则、模板、示例和脚本变更
四、四类试写页面验收
五、真实项目 4.x.6 全量重写结果
六、事实和一致性检查结果
七、资深产品经理式语义验收结果
八、4.x.6 以外章节变化
九、未解决问题和待用户确认事项
十、Git 工作区状态
```

## 十一、待确认事项

本计划提交确认后，才执行以下动作：

1. 修改 PRD Skill 和详细需求说明规则；
2. 清理或降级无真实质量价值的证明性流程；
3. 准备并验收四个真实页面试写；
4. 对真实项目 `4.x.6` 做完整重新生成；
5. 运行确定性检查和人工语义验收；
6. 将通过验收的章节写回正式 PRD。
