# Design 推断值机制优化执行与验收方案

> 日期：2026-08-05
> 状态：待执行（用户已拍板方向）
> 目标：把"低影响未知 → 保守表达（不写）"改为"低影响未知 → AI 直接写推断值 + confirmation 推断值汇总表一次拍板"；高影响未知维持"问/待确认"不变
> 依据：用户反馈"默认值、排序、分页、超时、重试、补偿、逐字提示文案、历史数据处理方式或外部系统行为这些 AI 可以根据业务推断，不需要逐条确认，工作量太大"；同时 AGENTS.md §1.11"高影响未知必须问用户"保持不变

## 1. 问题与根因

### 1.1 现状

`references/prd-writing-rules.md` §2 与 `spm-prd` 事实边界规定：不得自行补造页面、字段、角色、权限、状态、流程、接口参数、**默认值、排序、分页、超时、重试、补偿、逐字提示文案**、历史数据处理方式或外部系统行为；**低影响未知采用不承诺具体值的保守表达**。

R16 动作交互四问进一步把"Design 未定义交互细节（如具体按钮、确认文案、去向）"一律**列为待确认**。

### 1.2 问题

1. **展示层细节（默认值/排序/分页/提示文案）被一刀切禁止推断**：AI 无法提供草案，用户被迫逐条决定，工作量倒挂——用户要写 PRD 正是为了把这些细节交给 AI；
2. **交互四问把低影响交互细节（文案/样式/反馈措辞）一律列为待确认**：待确认清单膨胀，与 AGENTS.md §1.11"高影响未知才问用户"冲突（口径漂移）；
3. **审计系统教训的真实边界被误读**："刷新页面重试"×122 的病灶是**机械重复/套话**，不是"写了默认值"——禁止推断把合理的场景化推断和机械填充一起禁掉了。

### 1.3 必须保留的防线

- **高影响未知必须问/待确认**（AGENTS.md §1.11）：权限、数据范围、状态机、流程/审批、删除传播、外部系统契约、历史数据处理方式、数据层超时/重试/补偿、金额与统计口径、范围边界；
- **禁止把推测伪装成已确认事实**：推断值必须有登记机制，confirmation 时可见、可拍板；
- **禁止机械重复文案**：推断值必须基于业务语义场景化，套话填充（同一失败/恢复话术跨场景重复）仍是缺陷。

## 2. 目标行为

### 2.1 事实分级（Design 侧）

| 级别 | 范围 | 处理 |
|---|---|---|
| 已确认 | Design/Align/材料明确写出 | 直接承接 |
| **可推断（低影响展示层）** | 默认值、排序、分页、逐字提示文案、标签/颜色/展示格式、界面层超时/重试提示、低影响交互细节（按钮文案/反馈措辞/停留跳转） | **直接写推断值**到 Design 正文，并登记到 decision-notes 推断值清单 |
| 必须确认（高影响） | 权限、数据范围、角色、状态机、流程/审批、删除传播、外部系统行为/契约、历史数据处理方式、数据层超时/重试/补偿、金额与统计口径、范围边界 | 问用户或待确认，进 Design 待确认事项，不进推断值 |

### 2.2 推断值登记（Design 写作时）

- 每条推断值登记到 `output/design/decision-notes.md` 的"推断值清单"段：`值 | 位置 | 推断依据（一句话）`；
- 登记是 AI 写作行为的组成部分（与"生成后回读"同级），不新增脚本/检查器/回执；
- 推断值不进 `confirmed_facts`（`design-fact-format.md` 材料事实层不变）——推断值在 Design 正文直接呈现，清单只用于 confirmation 呈现与 Review 核对；
- 依据写不出"为什么这么推断"的（纯套话）不写，改保守表达或待确认。

### 2.3 confirmation 推断值汇总表

spm-design 发"Design 已完成，请确认"前，把推断值清单呈现为**推断值汇总表**：

```text
推断值汇总表（请一次性确认，接受/修改/拒绝）：
| # | 位置 | 推断值 | 推断依据 | 确认结果 |
```

- 用户一次扫表拍板：全部接受 / 修改个别 / 拒绝个别；
- 修改或拒绝的值回写 Design 正文（修改的值写入，拒绝的改保守表达或待确认）；接受的值即确认基线；
- 拍板结果更新到 decision-notes 推断值清单（确认结果列）；
- 高影响待确认项**不进此表**，维持原有单独询问流程。

### 2.4 PRD 承接

- PRD 只承接确认后 `design.md`（含已拍板的推断值），**不在 PRD 阶段自行新增推断值**；
- Design 中未拍板的推断值在 PRD 中按待确认处理，不静默使用；
- rules §2"不得静默新增"保留（防 PRD 阶段新增），措辞调整为"PRD 只承接 Design 已确认事实（含 confirmation 拍板过的推断值）；默认值、排序、分页、提示文案等推断值在 Design 阶段产生并登记，PRD 不得自行补造 Design 未确认的值"。

### 2.5 Review 检查

design-review-checklist 增加"推断值登记完整"检查项：Design 正文出现默认值/排序/分页/提示文案等推断值但 decision-notes 推断值清单无对应记录 → 问题（推断值未经 confirmation 可见化）；机械重复文案（同一话术跨场景重复）仍按既有检查项。

## 3. 边界（可推断 vs 必须确认，逐项）

| 项 | 归类 | 处理 |
|---|---|---|
| 默认值（筛选/表单/时间范围） | 可推断 | 写值+登记 |
| 排序（默认字段/方向） | 可推断 | 写值+登记 |
| 分页（每页条数/控件） | 可推断 | 写值+登记 |
| 逐字提示文案（操作反馈/空态/异常提示） | 可推断 | 写值+登记（场景化，禁套话） |
| 标签/颜色/展示格式 | 可推断 | 写值+登记 |
| 界面层超时/重试（查询失败提示重试、加载超时提示） | 可推断 | 写值+登记 |
| 低影响交互细节（按钮文案/反馈措辞/停留跳转） | 可推断 | 写值+登记 |
| 二次确认/权限入口显隐/破坏性分支/多出口去向 | 必须确认 | 待确认/问 |
| 权限、数据范围、角色 | 必须确认 | 待确认/问 |
| 状态机、流程/审批 | 必须确认 | 待确认/问 |
| 删除/作废/归档传播 | 必须确认 | 待确认/问 |
| 外部系统行为/契约 | 必须确认 | 待确认/问 |
| 历史数据处理方式 | 必须确认 | 待确认/问 |
| 数据层超时/重试/补偿（重复提交/数据一致性） | 必须确认 | 待确认/问 |
| 金额、统计口径、业务数字 | 必须确认 | 待确认/问 |
| 范围边界 | 必须确认 | 待确认/问 |

## 5. 禁止事项

- 不新增检查器、门禁、回执、覆盖率 JSON 或推断值证明文件（推断值清单是 decision-notes 的段落，不是新资产）；
- 不高影响静默拍板：必须确认清单不因本方案放开；
- 不改用户正式项目；不执行 commit/push（用户另行指示）。

## 6. 验收标准

### 6.1 静态同步

- rules/SKILL/design-writing/模板/checklist 五处有对应段落（可推断范围、登记格式、汇总表、Review 项）；
- 高影响清单（权限/状态机/删除传播/外部系统/历史数据/数据层超时重试）仍为"必须确认"，无遗漏放宽；
- 现有测试全绿。

### 6.2 功能验收（构造样本）

- 构造含展示层推断值的 Design 样本：AI 按规则写值并登记到 decision-notes 推断值清单（值+位置+依据）；
- confirmation 汇总表可生成：推断值逐条在表中，含位置与依据；
- 高影响项不进推断值清单（构造含权限/历史数据场景验证仍走待确认）；
- 套话检测：无依据的推断值被规则拒绝（评审口径，非脚本）。

### 6.3 文档验收

- 执行报告按本方案 §7 格式输出；
- 未新增检查器/回执/JSON。

## 7. 执行 AI 最终报告格式

```text
一、结论（通过 / 有问题需修改 / 阻塞）
二、实际修改文件清单
三、静态同步核对（五处落点）
四、功能验收（样本登记/汇总表/高影响隔离/套话拒绝）
五、自动化结果（测试清单与结果）
六、未解决问题
七、Git 状态（未执行 commit/push 说明）
```
