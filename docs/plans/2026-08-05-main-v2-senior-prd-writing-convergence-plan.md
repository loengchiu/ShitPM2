# main/V2 详细需求说明融合收敛方案

> 日期：2026-08-05  
> 状态：待执行  
> 关系：本方案接替 `2026-08-05-prd-rule-landing-remediation-plan.md` 和 `2026-08-05-main-prd-writing-merge-remediation-plan.md` 的后续工作。前两份方案的执行结果保留为历史证据，但不再把“规则归属收敛”当作最终完成标准。  
> 最终目标：让 V2 的 `4.x.6 功能详细说明` 一看就是资深产品经理写出的产品规格，而不是规则拼接、交互检查清单或模板填空。  
> 核心边界：不是把 main 逐条迁移到 V2，而是结合 main 的表达质量与 V2 的事实边界、结构和交付约束。

## 1. 先重新判断已完成结果

上一轮执行已经完成了部分基础治理：

- PRD 动作规则集中到 `references/prd-writing-rules.md`；
- `SKILL.md`、模板、示例和 Review 清单的重复规则有所收敛；
- 简单动作不再被统一“四问”硬性绑架；
- 页面区块列表式表达、Design 操作表十列、推断值机制和 lint 增强已保留。

但这不等于最终目标已经完成。上一轮验收主要证明了：

- 文件之间的职责关系更清楚；
- 合成样本能满足预设关键词；
- 现有测试没有回归。

它没有充分证明：

- 动作正文是否真的有资深产品经理的业务判断；
- 主链路、关键分支、状态变化和角色衔接是否自然；
- UI 文案、字段展示、长文本和异常边界是否写得具体；
- 文档是否高密度但不机械；
- 复杂项目中是否仍然出现模板腔、流水账和重复说明。

因此本方案不是继续做“规则落点修补”，而是做一次 **main 与 V2 的写作质量融合验收和收敛**。

## 2. 融合原则：保留两版各自的长处

### 2.1 保留 main 的写作长处

main 作为“资深产品经理写法”的参考，不是要被逐字迁移。需要保留它的以下判断：

- 页面内按用户动作组织，动词短语直接作为动作名；
- 页面开头只交代页面语境，进入正文后按动作写规格；
- 页面区块是辅助信息，区块多时用列表，区块少时用自然句；
- 按操作顺序写主链路，关键分支单列，状态变化直接落到结果；
- 短句优先，一句表达一层规则，少讲原因，多写可执行规格；
- UI 文案直接嵌入正文，用双引号标出；
- 动态展示说明数据来自系统计算、接口返回、关联带出还是用户输入；
- 超长文本写清截断、换行、滚动或悬停查看全文；
- 自然段、数字编号列表和 `·` 并列列表按语义选择；
- 默认角色可见性在模块权限区统一说明，特殊角色限制才写在动作正文；
- 下一步衔接角色写在动作结果之后；
- 用“手机号不合法时”“弱网环境下”“倒计时归零后”等场景条件引出规则；
- 不用“界面元素”“交互逻辑”“异常处理”等术语标签把一个动作拆碎。

### 2.2 保留 V2 的产品事实和交付长处

V2 不回退到 main 的旧结构，继续保留：

- 确认版 Design 是唯一产品事实源；
- 高影响未知必须待确认，低影响推断值走 Design 登记与确认；
- 页面、动作和业务阶段的 V2 组织方式；
- `###### 页面名称` 和 `**动作名称**` 标记；
- 状态、权限、数据范围、字段属性、异常恢复和删除传播的完整性要求；
- 非页面字段回读、三处交叉比较和已完成模块变更失效；
- draw.io 源文件 + PNG 流程图交付；
- 分片读取和直接写入最终 PRD；
- Design 操作表十列和已有确定性 lint。

### 2.3 必须融合而不是二选一的部分

| 主题 | main 提供 | V2 提供 | 最终写法 |
|---|---|---|---|
| 动作完整性 | 自然、按时序、主链路清楚 | 事实、权限、状态和异常不能丢 | 按动作复杂度写完整，不套固定四段 |
| 页面区块 | 动作优先、区块为辅 | 页面职责、展示行为、状态驱动展示可回读 | 页面语境简写，动作正文承接业务规格 |
| 交互细节 | 写字段、反馈、文案、边界 | 未确认事实不能自行补造 | 已确认直接写，推断值承接 Design，不能决定的列待确认 |
| 复杂度 | 简单短写、高复杂细写 | 高影响事项必须阻断或回 Design | 篇幅和覆盖随业务复杂度变化 |
| 角色 | 默认角色不重复、衔接角色写在结果后 | 权限和数据范围必须准确 | 权限基线集中说明，特殊限制和角色衔接就近写 |

## 3. 资深产品经理写法的质量标准

最终详细需求说明必须同时满足以下五个判断：

### 3.1 读者能顺着业务顺序读下去

读者不需要在页面区块、字段表、状态表和权限表之间来回拼接，能够从动作正文读出：

1. 谁在什么业务前提下做什么；
2. 系统如何处理；
3. 用户看到什么；
4. 对象和状态如何变化；
5. 失败或分支如何处理；
6. 下一步由谁继续。

### 3.2 信息密度高但不堆砌

- 不写背景原因、价值判断和空泛目标；
- 不把字段定义表完整搬进每个动作；
- 不重复默认角色、公共权限和全局规则；
- 不用“支持相关操作”“按常规处理”“用于承载”等模糊句；
- 不为了显得完整而补无依据的排序、分页、按钮、超时或提示。

### 3.3 复杂度与篇幅匹配

| 动作类型 | 写作要求 |
|---|---|
| 简单查询、查看、返回 | 说明触发和业务结果；没有特殊交互不强行扩写 |
| 普通表单、提交、修改 | 写输入字段、校验、处理、成功结果和失败保留 |
| 多角色、多状态、多出口、破坏性或外部协作 | 写角色衔接、允许状态、确认、分支、状态、副作用和恢复 |

### 3.4 规格落到可实现、可验证的细节

适用时必须写清：

- 字段展示、可编辑、必填、默认、取值和联动；
- 按钮可见、可点、置灰或隐藏条件；
- UI 文案、空状态、错误提示和状态标签；
- 长文本截断、换行、滚动或悬停查看；
- 数据来自系统计算、接口返回、关联带出还是用户输入；
- 网络异常、校验失败、并发变化、重复操作和外部协作失败；
- 状态变化后页面、按钮、字段和列表如何刷新。

### 3.5 读起来不像模板

禁止：

- `触发：`、`处理：`、`成功结果：`、`失败与恢复：`等标签式小节；
- 连续点击步骤拼成流水账；
- 每个动作使用完全相同的失败话术；
- 所有页面都强行拆成相同区块列表；
- 每个动作都强行写满入口、表单、反馈、分支四段；
- 只写标题、空栏目或伪缩进；
- 把“为什么这样设计”写成原因腔，替代具体规则。

## 4. 关联参考内容必须整体复核

本方案不只复核 `main:references/prd-writing.md`，还要复核它的支撑内容：

| 参考内容 | V2 当前对应物 | 本次处理 |
|---|---|---|
| `main:references/prd-writing.md` | `references/prd-writing-rules.md`、`references/prd-writing-examples.md` | 作为写法参考，按融合决策表吸收，不整份覆盖 |
| `main:references/prd-writing.profile.json` | `contracts/prd-writing.profile.json` | 保留确定性禁用表达式和粒度约束，确认路径变化没有丢规则 |
| `main:references/prd-glossary-format.md` | `references/prd-glossary-format.md` | 保留术语章节和来源边界，不把名词规则塞进动作规则 |
| `main:references/prd-versioning.md` | `references/prd-versioning.md` | 保留版本记录规范，不与详细需求说明混写 |
| `main:references/prd-scene-checklist.md` | `references/prd-scene-checklist.md` | 保留七类场景覆盖，增加“是否写成资深规格”的回读问题 |
| `main:templates/prd.md` | `templates/prd.md` | 只吸收局部写作提示，保留 V2 章节和标记 |
| Review 参考 | `contracts/review-checklist.md`、`contracts/prd-review-checklist.md` | Review 只验证证据，不成为第二套写作规则 |
| 上下文路由 | `contracts/context-loading.manifest.json` | 验证所有 references 仍能在 writing/module/review 路径装载 |

验收标准不是“每个文件都出现同一句话”，而是：

- 规则来源唯一；
- 支撑 references 没有漏装载；
- 示例能够展示目标写法；
- 真实 PRD 读起来达到质量标准。

## 5. 执行方案

### 第一步：冻结已执行成果，建立融合决策表

不先重写文件。先列出 main 与 V2 每条规则的处理结果：

- 保留 main 写法；
- 保留 V2 约束；
- 两者合并；
- V2 已有更强规则，main 只作为示例；
- main 与 V2 冲突，不迁移；
- 已存在但需要补真实示例；
- 仅在 references 中复核，不进入 Skill。

融合决策表只作为本次执行材料，不新增运行时资产。

### 第二步：以 `references/prd-writing-rules.md` 为融合后的规则源

调整规则内容，重点不是增加更多条目，而是把以下内容写成一套连贯规范：

- 页面和动作的业务组织；
- 按复杂度决定动作篇幅；
- 主链路、分支、状态和角色衔接；
- 字段、展示、文案、长文本和异常边界；
- 三种表达形式的使用条件；
- 默认角色可见性和特殊权限的落点；
- 事实边界与推断值承接。

“动作覆盖触发条件、操作过程、操作结果、异常处理”保留为内容要求，但不拆成固定四段，也不让简单动作虚构不存在的要素。

### 第三步：重做示例，而不是继续堆规则

`references/prd-writing-examples.md` 至少提供以下对照：

1. 一个简单动作；
2. 一个普通表单动作；
3. 一个多角色状态流转动作；
4. 一个包含 UI 文案、长文本和动态来源的动作；
5. 一个多区块页面；
6. 一个少区块页面；
7. 一个默认角色集中说明、特殊角色就近说明的页面；
8. 对应的流水账、标签小节、原因腔和重复话术反例。

每个例子只说明它解决的阅读问题，规范正文回到 `prd-writing-rules.md`。

### 第四步：收敛消费者

- `skills/spm-prd/SKILL.md`：只保留流程和“按融合规则回读”的要求；
- `templates/prd.md`：只保留章节和局部提示；
- `references/prd-scene-checklist.md`：添加资深规格的回读问题；
- `contracts/prd-review-checklist.md`：验证主链路、信息密度、角色衔接、状态结果和异常边界；
- `contracts/prd-writing.profile.json` 与 `prd-style-lint.py`：保持现状，除非发现确定性误报；
- `scripts/python/probe-prd-action-tier.py`：先判断是否有稳定消费者；如果只是一次性探针，不能作为最终质量证明，按仓库准入原则处理。

### 第五步：真实样本验收

使用正式项目的隔离副本，不修改正式 `output`，选择至少三类模块：

- 简单列表/查询模块；
- 普通表单和状态变更模块；
- 多角色、多状态或外部协作模块。

每类模块抽查至少三个动作，人工回答：

- 这段是否先讲业务动作，而不是先盘点 UI；
- 是否知道谁做、何时做、做完变成什么；
- 研发和测试是否能直接找到字段、按钮条件、文案、异常和恢复；
- 是否有重复、空话、模板化句式；
- 是否像资深产品经理，而不是“规则检查通过的 AI 文档”。

## 6. 验收要求

### 6.1 规则验收

- main 的目标写法与 V2 的事实边界已形成融合决策；
- 不存在“main 全量覆盖 V2”或“V2 全量压过 main”的简单迁移；
- 关联 references、模板、profile 和装载链全部复核；
- Skill 没有重新承载完整格式手册；
- 不新增规则总表、覆盖率 JSON、回执或新的编排阶段。

### 6.2 真实产物验收

通过条件：

- 页面开头语境简洁，正文按动作组织；
- 动作名称是业务动词短语；
- 简单动作简洁，中高复杂动作完整；
- 主链路按顺序，关键分支单列；
- 状态变化和下一步角色落在结果处；
- UI 文案、动态来源、超长文本和异常边界写得具体；
- 默认角色不反复出现，特殊角色限制写在动作处；
- 区块多才拆列表，区块少不强拆；
- 没有标签式正文、流水账、原因腔、空栏目和重复套话。

不通过条件：

- 只是把“四问”全部写出来；
- 只是把 references 关键词补齐；
- 只是 lint 和测试全绿；
- 页面和动作仍然像模板填空；
- 为了完整而补造 Design 未确认事实。

### 6.3 自动化回归

运行现有相关测试：

- `test-prd-simplification`
- `test-prd-style-lint`
- `test-prd-consistency-semantics`
- `test-design-simplification`
- `test-design-index`
- `test-context-loading`
- `test-shitpm-regression`
- `test-resource-integrity`

测试只证明没有确定性回归，不能代替真实样本的资深产品经理质量验收。

## 7. 范围边界

- 不修改正式项目的 `output/design/design.md`、`output/prd/prd.md`；
- 不回滚 Design 操作表十列、推断值机制、页面列表式格式和已有 lint；
- 不把 main 的小模块嵌套、Mermaid 或旧标记带回 V2；
- 不把“资深产品经理风格”做成评分器或新的检查器；
- 不执行 `git commit` 或 `git push`。
