# PRD 质量回退防止——检查补强计划与验收

> 日期：2026-08-05  
> 状态：待用户确认，尚未实施  
> 适用范围：ShitPM 的 PRD 生成、PRD Review 和相关确定性检查  
> 关联问题：智慧停车区本轮 PRD 后半段质量下降，见目标项目 `.workflow/reviews/prd-review-5.md`

## 一、目标

防止后续 PRD 出现以下回退：

- 前半段按业务闭环展开，后半段压缩成指标、按钮或字段摘要；
- Design 页面只出现在页面清单，未进入 `4.x.6` 正文；
- 统计页只有指标名称，没有统计范围和计算口径；
- 高影响动作只写“支持处理”，没有状态条件、输入和结果；
- 脚本出现确定性冲突时，仍被描述成“全绿”；
- 上游 Design 引用被写成无法定位的裸章节号。

目标不是建立新的总门禁，而是让已有的生成规则、Review 规则和少量确定性检查真正覆盖这次暴露的失败模式。

## 二、根因判断

现有规则已经写过“统计口径”“前端可独立开发”“后端业务闭环”等要求，但仍然漏过本次问题，主要有三点：

1. 规则是总原则，没有要求统计页和复杂动作逐页完成；生成到后半段时容易退化成摘要。
2. `prd-consistency-check.py` 能发现字段、页面、状态的名称冲突，但不能判断统计口径是否足够，也不能确认页面是否只在清单中出现。
3. Review 虽然检查了后半段，但没有强制从最后模块开始逆向阅读，也没有要求对每个统计页分别回答前端和后端的独立开发问题。

因此，本计划采用“规则强化 + 少量确定性检查 + 真实缺陷回归”的组合，不把业务判断塞进脚本。

## 三、方案取舍

### 方案 A：只补 Skill 和 Review 清单

优点是改动最小，能覆盖统计口径、状态条件、页面摘要化等语义问题。

缺点是页面落点、裸引用、确定性冲突仍可能靠人工遗漏。

### 方案 B：新增一个统一 PRD 质量检查器

表面上覆盖面最大，但会把统计口径、状态合理性和页面业务语义包装成脚本规则，容易误报，也会重新制造检查回执和复杂门禁。

### 方案 C：混合补强，采用本方案

保留 AI 对业务语义的判断，只补三类脚本能稳定识别的问题：

- 页面清单页面是否进入 `4.x.6` 正文；
- `§x.x` 裸引用是否指向真实章节或明确写成 `Design §x.x`；
- Design 未定义字段是否被 PRD 字段定义直接新增。

统计口径、状态条件、角色衔接、动作结果和文本损坏仍由生成者回读与独立 Review 判断。

## 四、实施范围

### 4.1 生成端规则

修改：

- `skills/spm-prd/SKILL.md`
- `references/prd-writing-rules.md`

补充以下硬要求：

1. 含统计、看板、趋势、下钻或导出的模块，必须按页面或子闭环分片生成，不得一次压缩多个统计页。
2. 每个 `4.x.6` 页面完成前，必须确认：
   - Design 页面已落正文，或正文明确写出被合并的原页面名称；
   - 页面形态、区域、关键字段和操作入口可确定；
   - 数据来源、组织范围、时间范围和统计/校验口径可确定；
   - 状态、权限、异常、成功结果和下一环节可确定。
3. 生成顺序完成后，从最后一个模块向前回读至少两个模块，专门检查是否出现摘要化和事实密度下降。
4. `prd-consistency-check.py` 出现 `deterministic_conflict` 时，不得标记为“全绿”或人工放行；必须修复正文，或先修正检查器本身并重新运行。
5. 高影响未知仍回到 Design，不允许用“或”“按业务规则”“按配置”等模糊表达保留不可执行分支。

### 4.2 Review 端规则

修改：

- `skills/spm-prd-review/SKILL.md`
- `contracts/prd-review-checklist.md`

补充以下 Review 顺序和判定：

1. 先审最后一个业务模块，再向前审查，避免审查疲劳导致后半段被宽松放行。
2. 对每个统计页分别从前端和后端回答：
   - 前端能否确定页面区域、指标、筛选、空态、失败和下钻；
   - 后端能否确定对象、范围、时间、状态纳入、计算、写入和下游结果。
3. 对每个复杂动作分别检查角色、允许状态、输入、校验、成功后的对象和状态变化、失败保留和下一责任人。
4. 任何页面只在清单出现、统计只有指标名、状态条件出现“或”但没有分支依据、或 Design 引用无法定位，至少记录为 P1。
5. 脚本没有评估权限或语义项时，Review 必须明确写“未评估”，不能写成通过。

### 4.3 确定性检查

优先修改现有脚本，不新增总检查器。

#### `prd-style-lint.py`

扩展现有跨节引用检查：

- 识别 `见 §6.8`、`（§10.1）`、`按 §13.5` 等裸引用；
- 如果目标是当前 PRD 的真实章节则通过；
- 如果目标不是当前 PRD 章节，则要求正文明确写成 `Design §x.x`；
- 保留当前对普通数字章节引用的检查。

#### `prd-consistency-check.py`

增加“页面正文落点候选”输出：

- Design 页面名称只出现在页面清单或总体说明，未出现在对应 `4.x.6` 正文时，列为 `possible_omission`；
- 如果 PRD 明确写出两个 Design 页面被合并，则不直接判错，交由 Review 判断合并是否丢失业务结果；
- 保留现有未知字段、页面和状态的确定性冲突；
- 不判断统计口径是否正确，不判断状态迁移是否合理。

## 五、回归验收设计

### 5.1 确定性脚本验收

新增或补充现有测试，至少覆盖：

1. `见 §6.8`、`（§10.1）` 被识别为裸引用问题。
2. `见 Design §6.8` 不被误报。
3. 当前 PRD 的“主题指标”继续被识别为确定性多出字段。
4. 页面只在 `§3.5 页面清单` 出现时，被列为可能遗漏。
5. 页面在 `4.x.6` 中明确写出合并关系时，不被直接判定为确定性错误。
6. 当前合法的内部章节引用不被误报。

### 5.2 语义 Review 验收

使用本次智慧停车区 PRD 作为负向样本，独立 Review 必须发现：

- “两客一危统计”没有 `4.x.6` 正文落点；
- 4.5.6.2–4.5.6.4 缺少统计闭环；
- “主题指标”是未授权泛化字段；
- 告警处理缺少表单值和状态分流；
- 监控点修改/解绑既写支持又写不开放；
- 车辆详情进离场字段文本损坏。

不得只依靠脚本结果完成验收。

### 5.3 正向样本验收

使用一个简单只读/列表页面样本和一个统计页面样本，确认：

- 简单页面不会被强迫补写不存在的保存、提交和异常分支；
- 明确合并页面不会被误报为漏页；
- 统计页面在正文中能读出范围、时间、指标、空值、失败和下钻；
- 规则没有要求新增 API、数据库、缓存、队列或代码实现细节。

### 5.4 真实运行验收

在实施后的真实运行中：

1. 先在隔离副本上运行生成和 Review，不覆盖正式 PRD。
2. 运行 `prd-style-lint.py` 和 `prd-consistency-check.py`。
3. 对脚本确定性冲突逐条修复，不允许状态记录写“全绿”。
4. 由独立 Review 从末模块向前回读。
5. 再在确认版 Design 上重新生成受影响模块，比较“负向样本能被发现、正向样本不误报”。

## 六、通过标准

本计划只有同时满足以下条件才算完成：

- Skill 和 Review 规则已明确加入页面落点、统计页逐页验收、复杂动作验收和逆向回读；
- 裸引用和页面正文落点的确定性检查已覆盖，并有回归测试；
- 当前智慧停车区负向样本能稳定暴露本次主要问题；
- 简单页面和合法页面合并场景不产生明显误报；
- 脚本确定性冲突不会再被记录成“全绿”；
- 统计口径、状态条件和权限判断仍由 AI Review 负责，不新增语义检查器；
- 未新增覆盖率报告、评分器、统一检查器、回执或签名类资产；
- 未修改 Design 事实，未修改当前智慧停车区正式 PRD；
- 未执行 `git commit` 或 `git push`。
