## 一、目标和核心方案

本次专项只解决一个问题：

> 让 LLM 把主要注意力用于写出资深产品经理式的 `4.x.6 功能详细说明`，不再让大量机械规则、重复清单和半语义脚本干扰生成。

采用以下结构：

```text
确定性脚本准备事实和骨架
→ LLM 按业务闭环生成详细需求说明
→ LLM 做一次语义回读和直接修正
→ 脚本检查确定性错误
→ 人工盲验收写作质量
```

本次不再通过增加规则数量、检查器数量、覆盖率和执行回执解决问题。

### 2.3 已确认问题

1. `context-pack.py` 只识别 `闭环X：名称`，不能直接识别真实 Design 的 `### 4.2 车流和车位实时监测`；
2. 当前 lint 可以通过格式检查，但不能识别正文是否真正形成业务判断链；
3. 当前一致性检查会把对象级字段因缺少页面位置判成幻觉；
4. Design 操作按业务结果合并后，可能被判成操作遗漏；
5. “保存失败、已加载、未保存”等页面过程状态可能被识别为业务状态；
6. 规则、模板、清单和示例中存在大量相同或近似要求；
7. 当前完成条件仍偏向“有落点、已装载、已运行”，而不是“业务正文已经写好”。

## 三、成功标准

### 3.1 写作结果

详细需求说明必须让产品、研发和测试直接读出：

1. 用户在什么业务前提下进入；
2. 当前需要判断或完成什么；
3. 判断依据来自哪些字段、状态、数据和统计口径；
4. 用户和系统分别做什么；
5. 成功后对象、状态、数据和页面如何变化；
6. 失败、无数据、无权限和外部异常时如何继续；
7. 下一步由谁接手，进入哪个业务环节。

### 3.2 上下文目标

以下指标只用于验证精简是否有效，不用于证明语义质量：

| 指标 | 当前值 | 目标上限 |

| `SKILL.md` 行数 | 300 | 160 |
| `SKILL.md` 估算 token | 约 5,430 | 2,500 |
| module pass 非 Design 上下文 | 约 11,490 token | 4,000 token |
| 同一真实模块总上下文 | 约 15,630 token | 9,000 token |
| writing pass 上下文 | 约 12,657 token | 6,500 token |

### 3.3 规则治理

- 一个规则只有一个权威位置；
- Skill 只保留行为协议；
- references 只保留模型真正需要理解的写作知识；

- 脚本只处理确定性问题；
- 不新增统一检查器、语义评分器和证明性回执。

## 五、目标职责分工

### 5.1 脚本负责的工作

脚本负责以下确定性内容：

- 文件、路径、确认记录和哈希；
- Design 索引和模块片段；
- 业务闭环与页面的明确映射；
- PRD 顶层骨架和固定章节；
- 页面清单、业务对象、角色基线、字段、状态、验收和待确认事项的确定性归位；
- 标题、编号、终端后缀、空章节和重复项；
- 内部引用目标；
- 标签式正文、占位符、明确流水账和明确 UI 动作标题；
- 明确字段属性、枚举和权限反转；
- 最终产物存在性和状态更新。

脚本不得负责：

- 业务闭环是否讲清楚；
- 页面是否形成业务判断链；
- 动作合并是否合理；
- 数据统计口径是否充分；
- 页面是否像资深产品经理写作；
- 根据解析结果自动补写产品事实。

### 5.2 LLM 负责的工作

LLM 负责：

- 按业务结果组织模块；
- 按用户任务和业务判断组织页面；
- 按业务结果合并和命名动作；
- 按动作复杂度决定颗粒度；
- 将字段、区块、状态、权限和异常放到真实使用位置；
- 就近写清角色数据范围和统计口径；
- 写清状态变化、失败恢复和下一责任人；
- 判断高影响未知并保留待确认；
- 生成后直接回读真实正文，发现元数据化、清单化和业务链断裂时立即重写。

### 5.3 references 负责的工作

references 只保留：

- 模块按业务结果组织；
- 页面业务判断链；
- 动作合并与复杂度；
- 字段和区块的业务作用；
- 结果与下一业务环节；
- 数据范围与统计口径；
- 事实边界；
- 适配页面类型的正例。

### 5.4 模板负责的工作

模板只保留：

- PRD 顶层骨架；
- 模块固定章节；
- 页面标题占位；
- 动作标题占位；
- 字段表最小骨架。

模板不再重复完整写作规则。

6. 只修复真实问题；
7. 再次回读最终正文；
8. 通过验收后才替换正式 PRD 对应章节。

### 阶段 7：最终交付

1. 用户阅读最终 `4.x.6`；
2. 核对事实、待确认事项和内部引用；
3. 核对 `4.x.6` 以外章节是否存在非必要变化；
4. 提供执行和验收报告；
5. 未经授权不提交、不推送。

## 八、验收方案

### 8.1 Skill 和上下文验收

必须同时满足：

- `SKILL.md` 不超过 160 行、约 2,500 token；
- module pass 非 Design 内容不超过约 4,000 token；
- 同一真实模块总上下文不超过约 9,000 token；
- writing pass 不超过约 6,500 token；
- module pass 不装载完整模板和 profile；
- 场景自检不超过十个语义问题；
- 同一规则不在多个文件重复定义；
- 不存在新增证明性资产。

### 8.2 `context-pack.py` 验收

- 真实项目编号式业务闭环可直接匹配；
- 模块片段包含正确闭环和相关页面；
- 不包含无关闭环；
- 片段超阈值时明确失败；
- 页面显式追加仍可用；
- 不要求 Agent用页面名替代业务闭环名。

### 8.3 `prd-style-lint.py` 验收

- 页面元数据连续块可识别；
- UI 动作词直接作为动作标题可识别；
- 标签式正文、占位符和流水账继续可识别；
- 正常引用不产生大批无价值提示；
- lint 结果不包含语义质量结论。

### 8.4 `prd-consistency-check.py` 验收

| 测试样本 | 期望结果 |
|---|---|
| 字段只在对象表出现，没有页面位置 | 不判幻觉 |
| 多个浏览操作合并成一个业务动作 | 不判确定性遗漏 |
| “保存失败、已加载、未保存” | 不判业务状态 |
| 字段必填与 Design 相反 | 确定性冲突 |
| PRD 新增 Design 不存在的枚举值 | 确定性冲突 |
| 同一角色权限允许变禁止 | 确定性冲突 |
| 动作是否完整承接无法可靠判断 | 需要语义判断 |

### 8.5 四页语义硬验收

出现以下任一项，该页面不通过：

1. 页面主体仍是页面职责、使用对象、入口返回和区块清单；
2. 用户要完成的判断或业务任务不可读；
3. 动作标题主要是点击、打开、切换、返回、播放；
4. Design 操作被机械一对一复刻；
5. 正文只有控件、字段和跳转，没有业务处理和结果；
6. 复杂动作缺少角色、状态、关键分支、失败恢复或下一责任人；
7. 需要跨多个表格才能拼出主链路；
8. 页面之间使用可互换的模板句式；
9. 数据型页面只写来源，没有范围和口径；
10. 新增 Design 未确认的高影响事实。

通过页面必须自然回答：

```text
业务前提是什么
→ 用户要判断或完成什么
→ 依据哪些信息和口径
→ 用户与系统分别做什么
→ 结果如何改变对象、状态和页面
→ 失败后如何继续
→ 下一步由谁处理
```

不要求固定标题、固定标签或固定段落数量。

### 8.6 数据范围和统计口径验收

涉及指标、统计、趋势、汇总、下钻和导出时，逐项确认：

1. 不同角色可见的组织和数据范围；
2. 页面选择范围如何作用于指标、列表、趋势、视频和导出；
3. “今日”“实时”“近 24 小时”等时间窗口；
4. 统计对象、分子、分母、去重和平均值规则；
5. 纳入和排除的状态、异常、重复和未完成记录；
6. 下钻是否继承组织、时间和筛选条件；
7. 无数据、零值、数据缺失和统计失败是否区分；
8. 刷新、缓存和部分失败是否可能显示旧范围或越权数据；
9. 明细、敏感字段和导出是否存在额外权限。

“全局权限已写”“字段来源已写”“页面有服务区选择器”不能代替该验收。

### 8.7 事实验收

- 页面、字段、状态和枚举没有无依据新增；
- 明确字段属性没有冲突；
- 权限和数据范围没有反转；
- Design 待确认事项仍保留；
- 自动动作、删除传播和外部协作未被静默补全；
- 旧 PRD 事实回归没有恢复旧写法；
- `4.x.6` 以外章节没有无授权变化；
- 内部引用可以定位。

### 8.8 用户验收

用户最终只需判断：

1. 四页试写是否明显不是旧版的局部改写；
2. 完整 `4.x.6` 是否达到“一眼像资深产品经理写的”。

如果用户指出具体失败页面，按可复现的问题修改规则、示例或执行方式，不增加语义检查脚本。

## 九、停止和返工条件

出现以下任一情况立即停止当前阶段：

- 业务闭环片段无法可靠提取；
- 精简过程中删除了事实边界或关键语义责任；
- 四页试写仍出现页面元数据清单；
- 四页中两页及以上不通过；
- 用户认为试写与旧版没有实质区别；
- 一致性脚本继续以大量误判阻断交付；
- 解决问题需要新增统一检查器、语义评分器或证明性回执；
- 真实项目出现 Design 高影响冲突。

返工只能修改与失败直接相关的单一原因，不同时增加新规则、新脚本和新检查层。

## 十、最终交付物

1. 精简后的 PRD Skill；
2. 唯一的详细需求说明写作规范；
3. 按页面类型装载的正例；
4. 精简后的场景自检；
5. 最小 PRD 模板；
6. 修正后的上下文装载；
7. 收窄后的文风和一致性脚本；
8. 与真实行为对应的测试；
9. 四页隔离试写；
10. 通过验收后的真实项目 `4.x.6`；
11. 最终执行和验收报告。

最终报告包含：

```text
一、专项结论
二、输入和事实基线
三、Skill、references、模板和脚本变更
四、上下文预算前后对比
五、脚本误判修正结果
六、四页盲验收结果
七、真实项目 4.x.6 重写结果
八、事实和数据口径验收
九、4.x.6 以外章节变化
十、未解决问题和 Git 状态
```

## 十一、确认后执行顺序

用户确认本计划后：

1. 冻结基线；
2. 修复确定性输入和检查边界；
3. 精简 Skill、references、模板和上下文；
4. 运行自动化回归；
5. 生成四页隔离试写；
6. 等待四页盲验收；
7. 通过后完整重新生成 `4.x.6`；
8. 完成事实、语义和用户验收；
9. 未经授权不提交、不推送。
