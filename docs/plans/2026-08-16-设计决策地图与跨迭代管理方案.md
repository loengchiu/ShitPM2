# ShitPM 多文件 Design 架构改造执行与验收计划

> 日期：2026-08-16
> 状态：架构决策已确认，待其他 AI 执行和验收
> 执行对象：ShitPM `V2` 分支
> 执行范围：Design 多文件事实体系、上下文装载、PRD / Prototype 下游依据、fix 传播、旧单体迁移入口
> 实施边界：只修改 ShitPM 仓库及隔离测试项目；不修改任何正式业务项目，不执行 Git commit 或 push

## 一、本轮结论

本轮把 ShitPM 的 Design 从单体文件改造成多文件产品事实体系：

~~~text
Design 是唯一产品事实体系
≠
Design 必须是唯一物理文件
~~~

最终采用：

> 设计地图负责低分辨率导航，设计集清单负责机器定位，系统级基线、跨模块契约和模块设计共同承载正式产品事实。

本轮同时完成以下旧机制替换：

- 用文件级 Design 依据替换整篇 `design.md` 哈希确认；
- 用写入前事实边界替换 `decision-notes.md` 推断值登记；
- 用目标事实闭包装载替换整篇 Design 默认读取；
- 用局部影响传播替换“修改 Design 后停止并要求重新确认”；
- 用一次性迁移提示词处理少量旧项目，不建设长期旧格式兼容层。

本计划既是实施依据，也是验收依据。执行 AI 不需要重新设计产品架构，只需按文件任务、执行阶段和验收矩阵完成改造。

## 二、当前基线和真实问题

### 2.1 单体 Design 的实际问题

当前 `output/design/design.md` 同时容纳：

- 系统目标与边界；
- 核心对象、关系、角色、权限和数据范围；
- 跨模块交接；
- 模块流程；
- 页面、区块、字段、操作、状态和异常。

审计系统当前 Design 约 112,540 token。完整 Design 与 PRD 合计约 167,179 token。能力较弱或上下文较小的 AI 一次读取整篇时，容易出现：

- 系统规则被页面细节淹没；
- 小模块任务也加载整套系统；
- 模块关系散落，容易漏读或错接；
- 其他模块规则被误套到当前模块；
- fix 无法稳定定位唯一事实归属；
- 局部变化导致整篇哈希失效。

### 2.2 当前实现绑定旧架构

实施前基线扫描显示：

- 26 个活动文件直接引用 `output/design/design.md`；
- 10 个活动文件引用 `decision-notes.md`；
- 12 个活动文件引用 `design-confirmation`；
- `design-index.py` 只编译单个 `design.md`，使用整篇 `design_sha256`；
- `stage-context.py` 把 Design 是否确认作为 PRD、Prototype 可用条件；
- 当前索引测试仍包含旧格式回退和 confirmation 哈希失效。

因此，本轮不是只改一个 Skill，而是一次跨 Skill、契约、脚本、模板、Schema 和测试的统一替换。

### 2.3 当前可复现基线

实施前已确认：

- `python scripts/python/test-shitpm-regression.py`：通过；
- `python scripts/python/test-resource-integrity.py`：通过；
- `python scripts/python/test-design-index.py`：16 项通过；

## 三、成功标准

### 3.1 产品行为

实施完成后必须满足：

1. Design 仍是唯一产品事实体系，每项正式事实只有一个归属处；
2. 系统级事实、跨模块交接和模块内部事实分开承载；
3. 小模块任务只读取目标模块及必要基线、契约；
4. 强关联模块通过跨模块契约衔接，不因物理拆分而割裂；
5. PRD 和 Prototype 是并列下游，均直接承接当前 Design 事实闭包；
6. fix 能从问题位置找到唯一事实归属，并同步所有实际存在且受影响的下游；
7. 用户不再执行“确认 Design”或确认哈希；
8. 高影响未知只阻塞真正依赖该事实的任务；
9. 旧项目通过一次性提示词迁移，新运行路径不保留旧格式兼容分支；
10. 项目文件夹继续作为跨迭代版本容器，ShitPM 不建设内部版本系统。

### 3.2 性能和复杂度

新机制必须满足：

- 日常动作不增加新的模型调用轮次；
- 日常动作不全量扫描全部 Design；
- 不增加固定 Review；
- 不新增语义评分器、覆盖率回执或证明性报告链；
- 文件指纹随正常读取计算，不重复读取同一文件；
- 单文件修改保持轻量；
- 多文件修改只保护实际受影响文件；
- 完整系统任务按业务链逐模块处理；
- 上下文不足时只提醒用户调用 Matt `handoff`，不建设自动切任务机制。

### 3.3 上下文参考

以下数值只用于提醒，不是硬门禁：

| 区间 | 参考判断 |
|---|---|
| 96K | 最佳深度推理区间 |
| 128K | 安全区间 |
| 160K | 危险区间 |
| 192K | 上限 |

ShitPM 不能清除同一 Codex 任务已经进入上下文的内容。模块完成后只是不再重复装载前一模块正文；当剩余上下文不足以可靠继续时，完成当前模块、写入下游依据，然后提醒用户调用 `C:/Users/guduj/.codex/skills/handoff/SKILL.md`。

## 四、目标目录和事实归属

### 4.1 最终目录

~~~text
output/design/
├── 设计地图.md
├── 设计集清单.json
├── 系统级基线/
├── 跨模块契约/
└── 模块设计/
~~~

不再生成：

- `output/design/design.md`；
- `output/design/decision-notes.md`；
- `未决问题/`；
- `明确排除项/`；
- `合并视图/`。

### 4.2 三类正式事实

| 位置 | 回答的问题 | 典型内容 |
|---|---|---|
| `系统级基线/` | 它是什么 | 系统边界、核心对象、项目生命周期、组织角色、权限、数据范围 |
| `跨模块契约/` | 模块之间如何交接 | 触发条件、输入输出、状态衔接、数据传递、失败和人工处理 |
| `模块设计/` | 模块内部如何处理 | 模块流程、页面、字段、操作、局部状态、规则、异常和验收 |

判断方法：

~~~text
删除某个模块后仍然成立 → 系统级基线
只在模块交接时成立 → 跨模块契约
只影响一个模块内部 → 模块设计
~~~

一个文件承载一组具有共同业务原因、共同影响范围，并且通常一起变化的事实。不按页面机械拆分，也不按单条事实碎片化。

### 4.3 未决和明确排除项

未决和排除都是产品事实状态，直接写在拥有该事实的正式 Design 文件中：

| 范围 | 正式位置 |
|---|---|
| 系统级 | 对应系统级基线 |
| 跨模块 | 对应跨模块契约 |
| 模块内部 | 对应模块设计 |

设计地图只保留高影响摘要和链接；设计集清单只登记稳定 ID、状态、归属和影响，不复制正文。

### 4.4 临时完整 Design

只有用户明确要求导出、打印、人工通读或对外发送时，才生成：

`.workflow/runtime/完整Design临时视图.md`

文件顶部必须声明：

~~~text
这是由当前 Design 文件自动生成的临时阅读视图。
它不是产品事实源，不得作为 PRD、Prototype、Review 或 fix 的默认输入。
~~~

日常任务和完整 Review 都不依赖该文件。

## 五、三个最小机读契约

本轮只新增三个有稳定消费者的确定性契约。它们分别解决定位、下游影响和中断恢复，不承担业务语义判断。

### 5.1 设计地图格式

`设计地图.md` 至少包含：

1. 系统目标与边界；
2. 主业务链；
3. 模块与职责；
4. 跨模块契约；
5. 系统级或高影响未决、排除项入口。

地图中的正式引用统一写成：

~~~markdown
- `MOD-001` [审计整改](模块设计/审计整改/整改跟踪与销号.md)：负责整改任务、材料和销号。
- `CON-001` [问题与整改](跨模块契约/问题与整改.md)：定义问题生成整改事项的交接。
- `DEC-001`（待明确）→ [整改与项目档案](跨模块契约/整改与项目档案.md)
~~~

地图链接使用相对 `output/design/` 的中文路径。地图中的 ID 和链接必须能在设计集清单中定位。

### 5.2 设计集清单.json

路径固定为：

`output/design/设计集清单.json`

最小结构固定为：

~~~json
{
  "schema_version": "shitpm-design-set/v1",
  "set_sha256": "...",
  "files": [
    {
      "id": "MOD-001",
      "path": "模块设计/审计整改/整改跟踪与销号.md",
      "type": "module",
      "module": "审计整改",
      "business_chains": ["整改并行业务链"],
      "depends_on": ["SYS-003", "CON-001"],
      "sha256": "..."
    }
  ],
  "decisions": [
    {
      "id": "DEC-001",
      "title": "整改材料追加档案失败后的处理",
      "owner_file_id": "CON-003",
      "status": "pending",
      "affects": ["MOD-006", "MOD-008"]
    }
  ]
}
~~~

字段规则：

- `schema_version` 固定为 `shitpm-design-set/v1`；
- `set_sha256` 按文件 ID 排序后，由 `id + path + sha256` 确定性计算，只用于排查和临时视图，不形成门禁；
- `files[].id` 使用 `MAP-001`、`SYS-001`、`CON-001`、`MOD-001`；
- `decisions[].id` 使用 `DEC-001`；
- ID 创建后不因文件移动、中文重命名或章节调整而改变；
- `type` 只允许 `map`、`system`、`contract`、`module`；
- `path` 必须相对 `output/design/`，使用 `/`，不得使用绝对路径或 `..`；
- `module` 只有 `module` 类型必填，其他类型为 `null`；
- `depends_on` 从当前文件指向当前文件成立所必需的上游文件；程序从目标 ID 沿该字段递归读取依赖闭包，反向影响由程序计算，不重复维护 `affects` 文件关系；
- `decisions[].status` 只允许 `defined`、`pending`、`excluded`；
- `decisions[].affects` 保存受该高影响事项影响的正式 Design 文件 ID；
- 普通页面、字段、按钮不进入 `decisions`；
- 业务正文不进入 JSON。

设计地图自身登记为 `MAP-001`，但地图链接不作为事实闭包依赖，避免加载一个模块时沿地图反向加载整套系统。

### 5.3 下游 Design 依据

路径固定为：

~~~text
.workflow/provenance/prd.json
.workflow/provenance/prototype.json
~~~

两份文件使用同一结构：

~~~json
{
  "schema_version": "shitpm-design-inputs/v1",
  "artifact": "prd",
  "targets": [
    {
      "target_id": "prd:审计整改",
      "target_name": "审计整改",
      "output_path": "output/prd/prd.md",
      "output_locator": "## 4.6 审计整改",
      "status": "current",
      "check_status": "passed",
      "affected_by": [],
      "design_inputs": [
        {
          "id": "SYS-003",
          "sha256": "..."
        },
        {
          "id": "CON-001",
          "sha256": "..."
        },
        {
          "id": "MOD-001",
          "sha256": "..."
        }
      ]
    }
  ]
}
~~~

字段规则：

- `artifact` 只允许 `prd` 或 `prototype`；
- `target_id` 在对应下游内唯一；
- `output_locator` 对 PRD 使用模块标题，对 Prototype 使用路由或源码模块目录；
- `status` 只允许 `current`、`affected`、`incomplete`；
- `check_status` 只允许 `passed`、`failed`、`not_run`；
- `affected_by` 只保存发生变化的 Design 文件 ID；
- `design_inputs` 保存该业务模块实际读取的 Design 文件 ID 和指纹；
- 路径通过设计集清单解析，不在依据记录中重复保存 Design 路径；
- 只有实际存在的下游才建立记录；
- 记录不保存业务正文，不构成第二事实源。

下游完成局部同步并通过针对性检查后，更新 `design_inputs`，将 `status` 改为 `current`、`check_status` 改为 `passed`，并清空 `affected_by`。

### 5.4 Design 修改事务

Design 修改运行目录固定为：

~~~text
.workflow/runtime/design-change/
├── single/
│   ├── active.json
│   ├── staged/
│   └── backup/
├── active.json
├── staged/
└── backup/
~~~

`single/` 只服务单文件快速路径；根目录下的 `active.json`、`staged/` 和 `backup/` 只服务多文件保护路径。两条路径使用同一 Schema 和恢复命令，不引入模型调用或人工确认。

`active.json` 最小结构：

~~~json
{
  "schema_version": "shitpm-design-change/v1",
  "mode": "multi",
  "phase": "staging",
  "files": [
    {
      "id": "CON-001",
      "path": "跨模块契约/问题与整改.md",
      "before_sha256": "...",
      "staged_sha256": null
    }
  ],
  "artifacts": [
    {
      "role": "manifest",
      "path": "output/design/设计集清单.json",
      "before_sha256": "...",
      "staged_sha256": null
    }
  ]
}
~~~

字段规则：

- `mode` 只允许 `single`、`multi`；`single` 时 `files` 必须恰好一个目标；
- `phase` 只允许 `staging`、`replacing`、`verifying`；
- 新增文件的 `before_sha256` 为 `null`；
- 删除文件的 `staged_sha256` 为 `null`；
- `artifacts.role` 只允许 `manifest`、`prd_provenance`、`prototype_provenance`；设计集清单必须且只能登记一次，provenance 只登记本次实际需要修改的文件；
- `artifacts.path` 使用项目相对路径，只允许指向 `output/design/设计集清单.json`、`.workflow/provenance/prd.json` 或 `.workflow/provenance/prototype.json`；
- 单文件与多文件事务互斥；`stage-single` 和 `begin` 发现任一活动事务时必须停止并提示先执行 `recover`；
- 任一单文件或多文件 `active.json` 存在时，PRD、Prototype、Review 和 fix 不读取正在变化的 Design 集合；
- 恢复时只处理 `files` 和 `artifacts` 登记的文件，不扫描或回滚无关模块。

单文件快速路径固定使用 `.workflow/runtime/design-change/single/`，只建立轻量事务：`stage-single` 登记一个目标文件，备份该文件、当前设计集清单和实际受影响的 provenance，并返回 `single/staged/` 中的临时写入路径。`commit-single` 生成候选清单和 provenance，针对性检查通过后依次替换登记文件；全部验证通过后才删除 `single/active.json`、`single/staged/` 和 `single/backup/`。检查失败时正式文件保持不变；替换途中中断时，下游被事务标记阻止，`recover` 恢复旧完整状态或完成已准备完整的新状态。

多文件保护路径才创建 `active.json`、`staged/` 和 `backup/`，并按以下顺序执行：

~~~text
登记目标文件和修改前指纹
→ 备份目标正式文件、设计集清单和实际受影响的 provenance
→ 写入 staged Design、候选清单和候选 provenance
→ 检查目标文件及相互引用
→ phase=replacing
→ 替换登记的 Design 和 artifacts
→ phase=verifying
→ 验证地图、设计集清单和下游影响
→ 删除 active.json、staged 和 backup
~~~

## 六、目标运行行为

### 6.1 统一事实闭包选择

所有 Skill 复用同一套选择路径：

~~~text
读取设计地图和设计集清单
→ AI 在当前正常分析中识别对象、动作、模块和业务链
→ 定位一个或多个目标 Design 文件 ID
→ 程序沿 depends_on 计算正向依赖闭包
→ 加载必要系统级基线、跨模块契约和目标模块
→ 契约不足时才读取相邻模块内部设计
~~~

目标识别不增加独立模型调用。程序只负责 ID、路径、依赖和指纹，不判断业务语义。

### 6.2 各 Skill 读取边界

| Skill | 默认读取范围 |
|---|---|
| `spm-start` | 地图、清单、Design 修改状态、下游受影响状态、产物概况；不读取详细模块 Design |
| `spm-align` | 用户材料、Align 资产；需要读取历史 Design 时按目标事实闭包读取 |
| `spm-design` | 目标事实闭包；新系统、全系统重设计或结构调整时进入完整系统路径 |
| `spm-design-review` | 目标文件、必要基线、直接契约、真正相关的相邻模块 |
| `spm-prd` | 目标业务模块的事实闭包；成功后记录 PRD 模块依据 |
| `spm-prd-review` | 用户指定 PRD 模块及该模块记录的 Design 依据 |
| `spm-prototype` | 目标业务模块的事实闭包；成功后记录 Prototype 模块依据 |
| `spm-prototype-review` | 用户指定原型模块及该模块记录的 Design 依据 |
| `spm-fix` | 从问题位置定位事实归属、事实闭包和实际存在的受影响下游 |
| `spm-prototype-mark` | 原型对应页面及其 Design 依据；PRD 仍为可选辅助 |

完整 Review 和完整生成必须由用户目标或系统级变化明确触发。

### 6.3 Design 变化后的处理

| 变化情况 | 处理 | 是否询问用户 |
|---|---|---|
| Design 没变，下游不一致 | 只修错误下游 | 否 |
| 用户明确说明改什么、改成什么 | 修改唯一事实归属，并同步所有实际存在且受影响的下游 | 否 |
| 文件移动、拆分、排版或措辞整理，语义不变 | 更新指纹和依据，下游继续有效 | 否 |
| 外部未知修改 | 当前任务触达时标记相关下游 `affected`，不自动传播 | 否 |
| 新产品选择、事实冲突或指令不完整 | 停在具体业务问题 | 是 |

询问必须是具体业务问题，例如：

> 整改材料追加档案失败时，整改业务本身是否仍可成功？

不得询问用户是否确认 Design 或是否确认哈希。

### 6.4 fix 传播

当用户已经说明正确结果时，一次 fix 可以连续完成：

~~~text
定位问题类型
→ 找到正式事实归属
→ 修改 Design
→ 计算受影响下游
→ 同步所有实际存在且受影响的 PRD / Prototype 模块
→ 运行针对性检查
→ 更新下游依据
~~~

只同步实际存在的下游：

- 只有 PRD：只同步 PRD；
- 只有 Prototype：只同步 Prototype；
- 两者都存在：同步所有实际受影响模块；
- 两者都不存在：只修 Design。

### 6.5 完整系统任务

采用：

> 全局骨架常驻 + 按业务链处理模块包 + 最后轻量汇总。

全局骨架只包含地图、清单、必要系统基线、目标模块清单和已完成下游状态。每次只新增当前模块包，不主动重复装载前一模块正文。

完成模块通过下游依据记录判断，不新增全系统进度文件。最终只检查：

- 目标模块是否全部存在；
- 每个模块依据是否仍有效；
- 跨模块双方是否使用同一契约；
- PRD 结构或 Prototype 构建是否通过；
- 是否仍有受影响、失败或未完成模块。

完整语义 Review 仍由用户明确触发。

### 6.6 防漂移边界

AI 可以直接决定：

- 默认排序、分页；
- 普通按钮文案；
- 成功、失败、空态提示；
- 标签颜色和展示格式；
- 不改变业务结果的低影响交互。

AI 不得自行决定：

- 角色、权限和数据范围；
- 流程、审批和状态机；
- 删除、撤回、作废和归档传播；
- 对象关系和生命周期；
- 跨系统失败、重试和补偿；
- 历史数据处理；
- 金额和统计口径；
- 产品范围和系统边界。

高影响事实不明确时，在其正式归属处标记未决或询问具体业务问题。下游只能承接正式 Design 中已经存在的事实。

## 七、旧项目迁移和跨迭代边界

### 7.1 不建设旧格式兼容层

现有旧项目只有 3～4 个。新运行路径不增加：

- 旧格式检测分支；
- legacy 模式；
- 旧 confirmation 兼容；
- 单体 Design 回退读取。

新项目直接使用多文件 Design。旧项目由用户手工复制项目文件夹后，执行：

`docs/plans/2026-08-16-旧单体Design迁移提示词.md`

迁移完成后只按新架构运行。

### 7.2 迁移原则

迁移采用完整暂存和一次切换：

~~~text
旧 design.md 暂时仍是事实源
→ 临时区域构建完整多文件 Design
→ 检查覆盖、归属、依赖和重复
→ 一次切换
→ 旧 design.md、decision-notes 和 confirmation 迁入 migration-backup
~~~

迁移只改变组织，不改变产品事实。旧 `design.md` 每段内容必须：

- 迁入明确的新归属；
- 有证据地合并重复内容；
- 有证据地标明废弃；
- 无法判断时在对应归属处标记未决。

现有 PRD、Prototype 不修改正文。迁移 AI 只允许读取其模块标题、路由和源码模块目录，用于建立下游依据；不得根据下游正文反向补充 Design。无法建立可靠映射的下游模块标记为 `affected` 并报告。

切换成功后，旧文件按原相对路径移入：

~~~text
.workflow/migration-backup/output/design/design.md
.workflow/migration-backup/output/design/decision-notes.md
.workflow/migration-backup/.workflow/confirmations/design.json
~~~

原项目中不存在的旧文件不创建空备份；迁移备份只用于追溯，不进入新事实闭包。

### 7.3 项目文件夹就是版本容器

ShitPM 不建设内部版本号、迭代指针或自动目录管理。用户继续手工复制完整项目文件夹：

~~~text
审计系统-V1.0/       历史冻结
审计系统-当前迭代/    继续工作
~~~

设计集清单只使用相对路径，因此复制项目后不需要重写绝对路径；第一次使用时只校验相对路径和文件指纹。

### 7.4 本轮不做

- 测试环境差异走查 Skill；
- 产品迭代管理系统；
- 自动复制或管理历史项目目录；
- Codex 自动切任务或清上下文；
- 宿主级插件、App Server 或 MCP 编排器；
- 外部 Issue Tracker；
- 默认使用 grilling；
- 修改任何正式业务项目；
- Git commit 或 push。

## 九、文件级实施任务

### 任务 B：实现 design-set.py

至少提供以下子命令：

~~~text
check             校验清单、路径、ID、依赖、地图引用和指纹
closure           根据目标文件 ID 沿 depends_on 输出递归依赖闭包
stage-single      建立单文件轻量事务并返回临时写入路径
commit-single     检查并提交单文件、候选清单和实际受影响的 provenance
begin             创建多文件 active.json、staged 和 backup
commit            检查并提交多文件修改
recover           从单文件或多文件中断状态恢复旧完整集合或完成已准备完整的新集合
record-inputs     写入 PRD / Prototype 模块依据
check-inputs      检查指定下游模块是否 current / affected / incomplete
~~~

程序只处理确定性文件关系，不判断“需求是否合理”“语义是否变化”。语义变化类型由当前 Design 动作传入：`fact` 或 `organization`。

完成判据：全部子命令有 `--help`、确定性退出码和测试；单文件替换中断也可恢复；不调用模型、不联网、不生成证明性报告。

完成判据：多文件结构可确定性编译；重复 ID、重复页面归属、缺失路径和指纹不一致能被识别；旧单体不再进入日常下游。

## 十二、场景验收矩阵

### 12.1 结构与契约

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A-01 | 新项目首次 Design | 只生成五项目录结构；没有旧 `design.md`、decision-notes 和 confirmation |
| A-02 | 清单合法项目 | Schema、ID、相对路径、依赖和指纹全部通过 |
| A-03 | 重复 ID | `check` 明确失败并定位重复 ID |
| A-04 | 非法路径 | 绝对路径、`..`、不存在路径被拒绝 |
| A-05 | 依赖错误 | 不存在 ID 和依赖环被拒绝 |
| A-06 | 地图引用错误 | 地图中的 ID 或链接无法定位时失败 |
| A-07 | 指纹错误 | 当前目标文件指纹不一致时明确报告，不把其他模块一并判错 |

### 12.2 上下文和事实闭包

| 编号 | 场景 | 通过标准 |
|---|---|---|
| B-01 | 单模块 PRD | 读取地图、清单、目标模块、必要基线和契约；不读取无关模块 |
| B-02 | 强关联模块 | 通过共同契约衔接；契约足够时不读取相邻模块全文 |
| B-03 | 契约不足 | 只增加真正需要的相邻模块，不升级为全系统扫描 |
| B-04 | 无关模块有未决 | 当前目标不依赖该事项时继续执行 |
| B-05 | 当前目标有未决 | 阻塞并指出具体业务事实，不要求确认 Design |
| B-06 | spm-start | 不读取模块正文，不计算全部文件指纹 |
| B-07 | 完整系统任务 | 按业务链逐模块处理，已完成且依据有效的模块不重复生成 |

### 12.3 写入和恢复

| 编号 | 场景 | 通过标准 |
|---|---|---|
| C-01 | 单文件检查失败 | 正式文件和清单保持修改前状态 |
| C-02 | 单文件成功 | 只替换目标文件并更新其指纹和真实下游影响 |
| C-03 | 单文件替换中断 | 下游被 `single/active.json` 阻止；recover 恢复正文、清单和 provenance 的一致状态 |
| C-04 | 多文件提交前中断 | 旧 Design 集合继续有效，staged 不成为事实源 |
| C-05 | 多文件替换中断 | 下游被 active.json 阻止；recover 恢复旧完整集合或完成完整新集合 |
| C-06 | 清单和 provenance 中断 | 备份可恢复，不能留下正文新、清单旧或下游依据半更新 |
| C-07 | 生效顺序 | 删除对应 active.json 后新集合才对下游生效 |
| C-08 | 无关文件 | 修改不备份、不检查、不重写未登记的无关模块 |

### 12.4 下游和 fix

| 编号 | 场景 | 通过标准 |
|---|---|---|
| D-01 | PRD 模块生成 | provenance 只记录实际读取的 Design 文件 |
| D-02 | Prototype 模块生成 | 与 PRD 使用相同事实闭包，但记录独立 |
| D-03 | Design 未变、PRD 错误 | 只修 PRD，不修改 Design 和 Prototype |
| D-04 | 用户明确修改事实 | 修改 Design 后连续同步所有实际存在且受影响的下游，无确认停顿 |
| D-05 | 只有一个下游 | 不创建不存在的另一份下游 |
| D-06 | 外部未知修改 | 当前触达模块标记 `affected`，不自动改写下游 |
| D-07 | 纯组织变化 | 更新 ID、路径、指纹依据，下游保持 `current` |
| D-08 | 针对性检查失败 | 保留 `affected` 或 `incomplete`，不得伪装通过 |
| D-09 | 针对性检查通过 | 更新依据并消除受影响状态 |

### 12.5 迁移和版本容器

| 编号 | 场景 | 通过标准 |
|---|---|---|
| E-01 | 旧单体迁移 | 原内容全部有新归属、证据化重复/废弃或未决 |
| E-02 | 迁移切换前失败 | 旧 design.md 仍是唯一活动事实源 |
| E-03 | 迁移切换成功 | 旧 design.md、decision-notes、confirmation 退出活动路径 |
| E-04 | 现有 PRD / Prototype | 不改正文；能映射则建立依据，不能映射则标记 `affected` |
| E-05 | 项目文件夹复制 | 相对路径保持有效，不指向旧项目绝对路径 |
| E-06 | 新运行路径 | 不存在旧单体 fallback 或 legacy 模式 |

### 12.6 性能与用户体验

| 编号 | 场景 | 通过标准 |
|---|---|---|
| F-01 | 日常局部任务 | 不增加独立模型调用、固定 Review 或全量 Design 扫描 |
| F-02 | 指纹计算 | 与正常文件读取合并，不为记录依据重复读取 |
| F-03 | 用户交互 | 不要求输入“确认 Design”、确认哈希或选择 Design 文件 |
| F-04 | 上下文不足 | 完成当前模块并提醒 handoff，不声称已经清除上下文 |
| F-05 | 完整视图 | 用户未要求时不生成；生成后明确不是事实源 |

### 12.7 复杂真实项目副本（独立必过项）

复杂验收使用：

~~~text
只读来源：D:/work/交投软件中心/审计系统
隔离副本：D:/work/ShitPM/.tmp/acceptance/审计系统
~~~

执行 AI 必须先确认复制目标位于仓库 `.tmp/acceptance/`，不得在来源目录直接迁移或写入。副本中至少验证：

1. 使用迁移提示词把当前大 Design 拆为多文件；
2. “整改跟踪与销号”只装载其模块、必要系统基线和直接契约；
3. “被审计单位协同与转办”只装载其自身事实闭包；
4. “整改与反馈”“整改与项目档案”通过契约衔接，不默认装载三个模块全部页面；
5. 记录两个模块包的实际文件清单和 token 估算；
6. 普通模块包优先落在 96K 内，超过 128K 时必须指出具体过大文件和继续拆分位置；
7. 迁移前后的产品事实覆盖、PRD、Prototype 正文和来源正式项目均无改动。

无法访问来源项目时，不得伪造复杂验收通过；自动化和小型夹具可以继续，但最终结论必须标记“复杂真实项目验收未完成”。

## 十三、总体通过门槛

只有同时满足以下条件，才能报告本轮通过：

- A～F 全部验收项通过；
- 0 个 P0；
- 0 个未解决 P1；
- 十个 Skill 和所有活动消费者已同步；
- 三个 Schema、四类模板和 `design-set.py` 已进入真实执行路径；
- 旧 confirmation、decision-notes 和单体日常 fallback 已退出活动路径；
- 局部任务没有新增模型轮次、固定 Review 或全量扫描；
- 单文件和多文件失败恢复均有真实测试；
- PRD、Prototype 和 fix 的下游依据行为有真实测试；
- 迁移提示词在隔离旧项目中完整执行一次；
- 审计系统复杂真实项目副本验收完成；
- Codex 安装映射通过；
- 未修改正式业务项目；
- 未执行 Git commit 或 push。

问题分级：

- P0：事实源并存、数据丢失、半成品 Design 被下游读取、权限/状态等高影响事实被静默补造、旧 confirmation 仍阻断主流程；
- P1：事实闭包错误、下游影响遗漏、迁移覆盖不完整、局部任务全量扫描、无法恢复中断；
- P2：不影响事实和执行结果的文案、格式或局部提示问题。

## 十四、不得作为通过依据

以下内容不能单独证明通过：

- 旧测试仍然全部通过；
- 新增测试数量很多；
- 脚本退出码为 0；
- Schema 文件存在；
- 设计集清单字段齐全；
- Skill 写了“按需加载”；
- 生成了 provenance 或运行回执；
- 没有发生运行时报错；
- AI 自述“没有增加模型调用”；
- 只在简单三模块项目中通过，未验证强关联、事务中断和迁移。

必须使用最终 Skill 行为、真实文件读取范围、正式产物、下游依据和失败恢复结果验收。

## 十五、停止和返工条件

出现以下情况必须停止当前阶段并报告：

1. 需要修改已确认的系统级、跨模块或高影响产品事实才能继续；
2. 设计集清单开始保存业务正文或复制详细页面规格；
3. 新工具开始判断业务语义或自动补写产品事实；
4. 为证明执行过程新增覆盖率 JSON、签名、回执链或综合门禁；
5. 日常局部任务需要全量扫描全部 Design 才能运行；
6. 单文件或多文件失败后无法恢复到一个完整事实集合；
7. 多个 Skill 各自实现不同的事实闭包算法；
8. 为保留旧测试而恢复 confirmation、decision-notes 或单体 fallback；
9. 需要修改正式业务项目才能证明方案有效；
10. 实际改造范围扩大到测试环境差异走查、迭代管理或宿主插件。

返工只修复失败项的直接原因，不同时增加新层级、新回执和新检查器。
