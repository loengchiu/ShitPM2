# Design ABC 责任与双下游事实源优化计划（讨论稿）

> 日期：2026-09-12  
> 状态：待讨论，不得直接执行  
> 执行对象：后续由其他 AI 执行，主 Agent 负责最终验收  
> 决策人：产品负责人（PM）  
> 目标：在不牺牲 PRD 与 Prototype 事实一致性的前提下，削减 Design 的过度分析、重复中间产物和固定格式负担

## 1. 文档定位

本文是基于当前仓库规则、Align / Design 契约、模板、上下文装载清单和既有执行验收计划形成的讨论稿，不是运行时规则，也不是已批准的执行指令。

在 PM 与其他 AI 讨论并确认前，不得据本文修改 `skills/`、`references/`、`contracts/`、`schemas/`、`templates/` 或脚本。

本文解决的是 Design 阶段的产品契约问题，不直接修改任何真实项目的 Design、PRD 或 Prototype 业务事实。

## 2. 背景与已发现问题

### 2.1 当前目标发生了修正

初步看起来，问题像是 ABC 三层导致 Design 过度设计，因此容易产生“减少 Design 内容”的直觉方案。但 PM 已明确补充：

> Design 同时服务 PRD 和 Prototype。如果 Design 不把产品事实定义完整，两个下游会各自补充，最终产生事实不一致。

因此，本轮不能把 Design 改成只确认方向的轻量文档。Design 仍必须是 PRD 和 Prototype 的唯一产品事实源。

真正需要削减的是：

- 与当前需求无关的分析维度；
- 将复杂场景规则套用到简单场景；
- A/B/C 的重复中间交接资产；
- 为满足固定格式而产生的空章节和“无 / 不适用”填充；
- 将实现细节伪装成产品事实；
- 按页面数量、步骤数量或材料数量机械触发的复杂分析。

不得削减的是：

- 范围内会影响 PRD 或 Prototype 结果的产品事实；
- 页面、区块、字段、操作、状态、权限、反馈、异常结果和验收中实际适用的内容；
- 能改变用户看到什么、能做什么、数据如何变化、状态如何变化、谁负责以及如何判断成功的内容。

### 2.2 当前契约的主要薄弱点

1. `simple` 仍然承担了大量 full 模式要求，实际表现为“缩小版 full”。
2. `full` 的 A/B/C 清单容易被模型理解成必须逐项填满的覆盖清单。
3. 规范多次写“按适用性”，但没有提供足够明确的最小排除规则，导致模型倾向于全部展开。
4. 页面属性、八列字段表、十列操作表和状态机表被过度普遍化，事实完整与表达格式没有分开。
5. 多套跨层自检、写作自检、质量标准和专项规则内容重复，增加执行负担并诱发补全。
6. A/B/C 分析资产、冲突资产和 Design 简报仍保留较重的中间结构，与“ABC 是分析责任而非程序节点”的原则不完全一致。
7. `align-notes.schema.json` 过于贫弱，无法充分表达当前输入版本、未决事项影响范围和 Align 是否对应最新输入。
8. `context-pack.py` 将适用性为 `unknown` 的卡片按适用处理，可能把不确定性直接转换成更多规则。
9. `design-set.py` 主要保护文件关系和指纹，不能也不应承担业务完整性判断；当前规则需要明确这一边界。
10. 模板中的“按需章节”与“无内容时必须填无”并存，容易制造形式完整、实际冗余的正文。

## 3. 已形成的产品决策

以下内容来自本轮 PM 已明确确认的共识，执行前不得擅自改写：

### 3.1 两种模式继续保留

继续保留 `simple` 和 `full`，但重新定义其边界：

- `simple`：单一主流程、小范围业务闭环；
- `full`：多个角色、多个阶段、状态流转、权限差异、跨系统或明显分支。

模式依据是业务结构复杂度，不是页面数量、材料数量、关键词或文档长度。

### 3.2 Design 仍是唯一产品事实源

Design 是 PRD 和 Prototype 的唯一产品事实源。PRD 和 Prototype 只能承接 Design，不得各自补写会改变产品语义的事实。

如果发现 PRD、Prototype 与 Design 冲突，应回到 Design 修正，再同步受影响下游，不以 Review 或下游文件覆盖 Design。

### 3.3 Design 的完成标准

Design 完成，不代表所有可能的产品问题都被提前穷举，而是代表：

- 当前范围内的主流程完整；
- 所有会影响 PRD 和 Prototype 的产品事实已经定义；
- 会改变业务结果的边界、异常和责任已经定义；
- 未能安全决定的高影响事项已经显式列为未决，并标明影响范围；
- PRD 和 Prototype 不需要自行猜测高影响产品语义。

### 3.4 必须定义的产品事实

只要会改变以下任一项，就必须进入 Design：

- 用户看到什么；
- 用户能做什么；
- 数据如何变化；
- 状态如何变化；
- 谁负责；
- 如何判断成功。

这包括实际适用的页面、区块、字段、操作、状态、权限、规则、反馈、异常结果和验收。

### 3.5 事实完整与格式适配

产品事实必须逐项完整，但表达格式按复杂度选择：

- 简单页面可以用紧凑清单、短表或自然语言；
- 复杂页面和多角色流程可以使用详细字段表、操作表和状态机表；
- 不得用“基本字段”“相关信息”“支持查询等”代替具体事实；
- 不要求所有页面机械使用八列字段表、十列操作表或状态机表。

### 3.6 复杂规则按业务影响触发

以下情况需要详细展开：

- 多个业务状态；
- 角色责任变化；
- 审批、驳回、撤回、作废、删除、恢复；
- 权限或数据范围差异；
- 外部系统或人工交接；
- 批量处理、文件处理；
- 失败后存在不同业务结果；
- 涉及数据完整性、责任归属、生命周期或验收口径。

普通单步查询、简单只读展示和不改变业务结果的普通交互，不因页面数量或步骤数量被迫展开复杂异常、补偿或状态模型。

### 3.7 A/B/C 的定位

A/B/C 继续保留，但定位为三种分析责任，而不是固定任务图、固定章节目录或固定 JSON 数量：

- A：理解问题、目标、角色和边界；
- B：理解业务如何运行；
- C：确认产品如何承接。

full 模式只分析当前需求实际涉及的内容。不适用项应简短排除，不生成空章节，也不为了覆盖清单主动创造新业务事实。

### 3.8 统一事实清单

保留一份按业务事实登记的统一事实清单，记录：

- 页面；
- 区块；
- 字段；
- 操作；
- 状态；
- 权限；
- 规则；
- 异常；
- 验收；
- 未决事项。

每条事实应注明适用范围和影响对象，用于帮助 PRD 和 Prototype 从同一事实集合读取和判断。

A/B/C 不再要求各自产出完整的重复中间文件，除非后续能够证明某个中间资产存在真实、稳定且不可替代的消费者。

### 3.9 未决事项按影响范围阻塞

高影响未决事项不阻塞整个项目，只阻塞受影响的页面、字段、操作、流程或验收。

每条未决至少说明：

- 问题是什么；
- 会影响哪些产品事实；
- 当前暂不采用什么假设；
- 需要谁决定。

下游不得把未决事项自行补成已确认事实。

### 3.11 Design Review 同步纳入本轮

Design Review 必须与生成侧在同一轮同步修改，否则生成侧采用“事实完整、格式适配复杂度”的新规则后，Review 仍会按旧的固定页面属性、八列字段表、十列操作表和全量横切能力要求判定，形成生成与审查互相冲突的契约。

Review 继续保留独立第二意见，但核心职责调整为：

- 审查范围内影响 PRD 和 Prototype 的产品事实是否完整；
- 审查业务闭环、角色责任、权限、数据范围、状态、操作结果、异常和验收是否互相一致；
- 识别未经授权的高影响假设；
- 检查高影响未决事项是否被明确记录，以及受影响内容是否被正确局部阻塞；
- 检查 Design 是否足以作为两个下游的共同事实源。

Review 不再把是否使用固定表格、是否填满固定页面属性本身当作默认缺陷。只有格式造成事实遗漏、歧义或下游无法承接时，才升级为 Review 问题。

默认 Review 只审 Design，不主动读取 PRD 或 Prototype。只有用户明确要求双下游对照时，才把 PRD 和 Prototype 纳入审查范围。

继续保留 P0/P1/P2 和“通过 / 有问题需修改 / 阻塞”三档结论；取消强制输出五维 L0-L3 评分。五个质量维度可以保留为 Review 的观察角度，但不再形成第二套固定评分负担。

## 4. 本轮目标

### 4.1 产品目标

优化后，PM 能得到一份同时满足以下要求的 Design：

1. 作为 PRD 和 Prototype 的共同事实基线；
2. 范围内页面、字段、操作和业务结果不遗漏；
3. 复杂业务的状态、权限、责任和异常不被过度简化；
4. 简单业务不被迫生成无关的对象模型、状态机、权限矩阵和异常清单；
5. A/B/C 仍能承担深度分析责任，但不再产生重复的过程负担；
6. 未决事项不会被两个下游分别猜测；
7. Design 正文按产品经理理解顺序组织，不暴露内部分析过程。

### 4.2 质量目标

质量判断以最终 Design 和双下游承接结果为主，不能以以下内容替代质量判断：

- 中间文件数量；
- A/B/C 是否生成了固定数量的 JSON；
- 上下文包数量或哈希；
- 规则包读取回执；
- `design-set.py check` 退出码；
- 页面、字段或章节数量；
- 文档篇幅。

## 5. 明确不做

本轮不得实施以下内容：

- 不把 Design 降级为只确认方向的摘要稿；
- 不允许 PRD 或 Prototype 自行补写高影响产品事实；
- 不删除页面、字段、操作、状态、权限、反馈、异常结果和验收中实际适用的事实；
- 不取消 Align 的事实形成责任；
- 不取消 full 模式的 A/B/C 分析责任；
- 不恢复固定的 A1-A5、B1-B6、C1-C4 等细粒度任务图；
- 不新增章节覆盖率、事实数量、页面数量或文档篇幅门禁；
- 不新增“统一完整度检查器”“综合门禁”“最终验证回执”或机器质量签名；
- 不把脚本用于判断业务语义、权限、状态机、流程或异常是否正确；
- 不为了减少上下文而删除规则，只能通过按适用性装载减少无关内容；
- 不直接批量改写所有历史 Design；
- 不修改真实项目业务事实；
- 不提交 Git commit 或 push，除非后续获得明确授权。

## 7. 建议执行阶段

### 阶段 0：建立当前基线

#### 执行内容

1. 记录仓库 `git status --short` 和当前分支。
2. 读取计划内文件的当前版本，确认没有遗漏的真实消费者。
3. 搜索所有对 `simple`、`full`、A/B/C、Design 事实清单、A/B/C baseline、`design-brief`、`align-notes`、`design-set` 的引用。
4. 运行与上下文装载、Design 清单、资源完整性和相关回归测试。
5. 区分已有失败和本轮新增失败，不把基线失败伪装成改造结果。

#### 完成条件

- 现有规则、模板、Schema、脚本和测试的关系可追溯；
- 已确认每个计划内文件的真实消费者；
- 已列出当前实际存在的重复中间资产和重复规则；
- 没有在基线阶段修改业务规则。

### 阶段 1：先收敛产品契约，不改脚本

#### 目标

先把“事实必须完整”和“过程可以精简”写成唯一、清晰、产品经理可理解的规则，避免先改脚本导致契约继续漂移。

#### 重点调整

1. 重写 `simple/full` 的定义和选择说明。
2. 将 full 的 A/B/C 从“全量责任清单”改成“按当前需求适用性承担的分析责任”。
3. 明确 simple 仍需完整承接范围内下游事实，但不展开无关复杂模型。
4. 建立“下游影响判断”：会改变用户看到什么、能做什么、数据、状态、责任或验收的内容必须定义。
5. 为不适用项提供最小排除表达，避免用空章节填充。
6. 明确复杂规则由业务影响触发，不由页面数量、步骤数量或材料数量触发。
7. 明确低影响推断不能改变业务结果、责任、权限、数据范围、状态和验收。
8. 明确 Design 正文是唯一产品事实源，事实清单只做机器定位辅助。

#### 阶段验收

- 产品规则中不存在“Design 可以少写事实、让下游自行补充”的表述；
- simple 不再被描述为 full 的缩小版；
- full 不再要求对不适用的所有 A/B/C 子项展开正文；
- 事实完整性和表达格式已经明确分离；
- 同一条产品原则只有一个权威表述，其他文件只保留指针。

### 阶段 2：重整 Align 与统一事实清单

#### 目标

保证详细材料事实不会在 Align 或 A/B/C 过程中丢失，同时减少重复记录。

#### 重点调整

1. Align 继续完整保留材料中已确认的产品事实，但增加材料内容分类，区分：
   - 需求事实；
   - 现状事实；
   - 方案候选；
   - 示例或说明；
   - 历史废弃内容；
   - 未决讨论。
2. 只有可确认的需求事实和当前有效现状事实进入事实基线；候选方案和示例不能静默变成确认事实。
3. 统一事实清单按业务事实记录，至少覆盖页面、区块、字段、操作、状态、权限、规则、异常、验收和未决。
4. 每条事实记录来源、状态、适用范围和影响对象。
5. 评估是否可以用统一事实清单替代 A/B/C 各自重复的完整分析资产。
6. 只保留确有消费者的中间材料；没有稳定消费者的资产从活动主流程移除，而不是迁移到新名称下。
7. 调整 `align-notes.schema.json`，使其至少能够绑定当前输入版本，并表达未决事项和影响范围；具体字段以执行前真实消费者分析为准，不得预先臆造 Schema。

#### 阶段验收

- 详细材料中的页面、字段、操作、规则、状态、异常和验收事实可回查；
- 材料中的候选方案、示例和废弃内容不会被当作确认事实；
- PRD 和 Prototype 可以从同一套事实清单定位其所需事实；
- A/B/C 中间资产没有重复承载同一份完整事实；
- 未决事项能定位到受影响的页面、字段、操作或验收。

### 阶段 3：重写 Design 写作与模板

#### 目标

在保持事实完整的前提下，消除固定格式造成的文档膨胀。

#### 重点调整

1. 将固定页面属性分成基础属性和条件属性：
   - 所有页面需要的基础信息；
   - 列表、表单、状态、权限、外部协作、批量和文件等条件信息。
2. 页面无相关内容时直接省略对应章节，不用“无”“无特殊规则”制造填充。
3. 字段和操作事实仍逐项定义，但允许按复杂度选择表达方式。
4. 八列字段表和十列操作表保留为复杂页面的推荐结构，不再作为所有页面的唯一表达方式。
5. 只有状态影响操作、责任、数据结果或生命周期时，才使用完整状态机；展示状态不自动变成业务状态。
6. 只有异常会改变业务结果、状态、数据完整性、责任或用户下一步时，才详细展开；普通加载失败允许简写或省略。
7. 删除、导出、分页、批量、文件和自动动作等专题规则改为按实际业务影响触发，不能当作所有页面的默认清单。
8. 验收保留所有可观察业务结果，但不把每个视觉细节都升级为独立验收项。

#### 阶段验收

- 简单只读页不会生成空状态机、权限矩阵、异常清单或无关非功能章节；
- 复杂表单、审批、状态流转和跨系统场景仍能完整表达字段、操作、状态、权限、失败和恢复；
- 任何影响 PRD 或 Prototype 的事实都没有因格式精简而丢失；
- 模板不再同时要求“按需省略”和“无内容必须填无”；
- 下游阅读者可以从紧凑表达中准确判断产品语义，不需要自行猜测。

### 阶段 4：收敛上下文装载和中间资产

#### 目标

减少无关规则读取，不删除必要规则。

#### 重点调整

1. 将当前需求实际适用的规则分为常驻规则和条件规则。
2. `simple` 只装载最小业务闭环、事实承接和当前页面/流程所需规则。
3. `full` 装载 A/B/C 责任，但不因 full 自动装载所有状态、字段、权限、流程、跨系统和非功能卡片。
4. `unknown` 适用性不能无条件等同于 `applicable`；应采用保守最小规则或明确提示，不得因为未知自动扩大分析范围。
5. 评估是否删除 A/B/C 重复中间资产的装载入口和对应交接规则。
6. 保持 context pack 是上下文视图，不将其变成产品事实源或质量证明。
7. 保留必要的确定性文件检查，但不新增业务质量门禁。

#### 阶段验收

- simple 不会因为默认规则包而读取完整 full 规则；
- full 不会因为模式选择而机械装载所有专项卡；
- 规则未被删除，只是按适用性分层；
- `unknown` 不会静默扩大适用范围；
- A/B/C 交接资产减少后，Design、PRD 和 Prototype 仍能从统一事实源继续工作。

### 阶段 5：同步脚本、Schema 和测试

#### 目标

让确定性工具与新的产品契约一致，但不让脚本接管业务判断。

#### 重点调整

1. 修改脚本前确认其真实消费者和当前失败证据。
2. `design-set.py` 继续只负责文件集合、路径、ID、依赖、地图引用和指纹等确定性关系。
3. 明确 `design-set.py check` 不代表 Design 语义完整，不把退出码写成产品质量证明。
4. 评估 `check_manifest_against` 是否需要补齐候选事务的确定性文件检查，避免候选提交与正式检查口径不一致；仅限文件关系，不扩展到业务语义。
5. 校准 `align-notes.schema.json`、上下文运行时 Schema 与实际消费者，删除不再使用的字段和资产契约。
6. 删除或改写验证已废弃行为的测试；新增测试只覆盖当前产品行为。
7. 不新增事实覆盖率、章节计数、字段数量或业务语义解析门禁。

#### 阶段验收

- Schema、脚本、Skill、reference、模板之间不存在明显的旧路径、旧模式或旧资产引用；
- 确定性脚本没有承担业务语义判断；
- 旧测试不会要求已经删除的复杂中间流程继续存在；
- 新测试覆盖 simple、full、无材料、有材料、材料冲突、用户回答和局部未决阻塞等关键路径；
- 文件关系检查通过不能被表述为 Design 质量通过。

### 阶段 6：真实场景回归与双下游一致性验收

#### 目标

使用真实或接近真实的简单项目和复杂项目，验证“事实完整但过程更精简”是否成立。

#### 场景 A：简单只读或查询需求

验收重点：

- 选择 simple 后只形成单一主流程和必要产品事实；
- 页面、字段、筛选、查询动作、结果、空态和必要反馈完整；
- 不生成无关状态机、权限矩阵、跨系统补偿或完整对象模型；
- PRD 与 Prototype 对页面、字段和查询结果表达一致；
- 仅由展示表达差异导致的内容，不被错误升级为业务冲突。

#### 场景 B：简单表单需求

验收重点：

- 表单字段、必填、校验、提交、保存结果、失败反馈和后续去向完整；
- 不因单一提交动作生成无关审批、并发、外部系统或复杂生命周期；
- PRD 和 Prototype 使用同一字段与操作事实；
- 表单中任何会影响提交结果的默认值、状态或权限已经定义或列为未决。

#### 场景 C：复杂多角色状态需求

验收重点：

- full 仍完成 A/B/C 三类分析责任；
- 多角色责任、业务状态、允许操作、状态变化、权限、数据范围和异常恢复完整；
- 回退、驳回、撤回、终态和状态驱动展示不会被过度压缩；
- 复杂字段和操作能够使用详细表达；
- PRD 与 Prototype 不需要自行决定高影响语义。

#### 场景 D：材料详细且存在候选方案或历史内容

验收重点：

- 材料中的有效产品事实没有被摘要丢失；
- 示例、候选方案、历史废弃内容不会静默进入确认事实；
- 冲突和未决事项保留来源、影响和处理边界；
- Design 只保留当前有效的产品语义和明确未决事项。

#### 场景 E：局部高影响未决

验收重点：

- 未决事项只阻塞受影响内容；
- 不受影响页面和模块仍可继续生成 PRD/Prototype；
- 受影响页面、字段、操作或验收不会被下游自行补全；
- 用户回答后，受影响事实可以回写并继续下游承接。

#### 双下游一致性检查

由产品经理或独立审查 AI 对照最终 Design、PRD 和 Prototype，重点检查：

- 页面是否一致；
- 页面结构和关键区块是否一致；
- 字段名称、含义、来源、展示/编辑条件是否一致；
- 操作入口、可用条件、成功结果和数据/状态变化是否一致；
- 角色、权限和数据范围是否一致；
- 异常结果、恢复方式和后续责任是否一致；
- 未决事项是否被两个下游错误补成不同事实。

验收关注的是事实一致性和产品可用性，不关注 Design 是否更长、生成了多少中间文件或运行了多少步骤。

## 8. 失败处理与停止条件

执行中出现以下情况必须停止并报告，不得自行扩大范围：

- 无法确认某条规则的产品意图；
- 发现删除格式要求可能导致 PRD/Prototype 缺少事实；
- 发现 PRD 和 Prototype 的真实消费者依赖某个准备删除的中间资产；
- 统一事实清单的粒度无法支持双下游定位；
- simple/full 的边界在真实案例中仍无法判断；
- 发现需要用户决定的流程、权限、状态、数据范围、角色责任或系统边界；
- 现有用户修改可能被覆盖；
- 测试失败无法区分基线问题与本轮问题；
- 需要新增业务语义检查脚本才能完成验收；
- 精简后出现 PRD 与 Prototype 事实分叉；
- 文档、模板、Schema 和脚本无法形成唯一事实源。

不得用以下方式掩盖失败：

- 把“脚本通过”写成“产品质量通过”；
- 把“没有发现遗漏”写成“已证明没有遗漏”；
- 把未决事项写成默认值；
- 把下游生成成功写成 Design 事实完整；
- 把简单案例通过写成复杂案例也通过；
- 把局部迁移写成全量完成。

## 9. 最终完成定义

只有同时满足以下条件，执行 AI 才能报告本轮改造完成：

1. `simple/full` 的产品边界已经统一；
2. Design 仍明确是 PRD 和 Prototype 的唯一产品事实源；
3. 范围内影响下游的产品事实仍然完整；
4. 不适用的复杂分析不再被机械展开；
5. A/B/C 保留分析责任，但不再要求重复的固定中间资产；
6. 字段、操作、状态、权限、异常和验收的表达格式可以按复杂度适配；
7. 高影响未决事项能够按影响范围局部阻塞；
8. Align 能区分有效事实、现状、候选方案、示例、废弃内容和未决讨论；
9. PRD 和 Prototype 从同一事实源读取，并在真实案例中保持一致；
10. 相关自动化测试通过，且基线失败与本轮失败已经区分；
11. 简单案例和复杂案例都完成了真实产物验收；
12. 没有新增只生成报告、回执、签名或业务语义门禁的工具；
13. 所有未验证项、遗留问题和需要 PM 决策的事项都已明确列出；
14. 未执行 Git commit 或 push，除非另有明确授权。

## 10. 执行者最终交付格式

执行者最终回复必须按以下顺序说明：

1. **结论**：本轮是否完成，以及是否达到“事实完整、过程精简、双下游一致”。
2. **产品契约变化**：simple/full、ABC、事实源、未决事项和表达格式的变化。
3. **文件修改范围**：实际修改文件及其职责变化；未修改的计划文件不虚构为已同步。
4. **中间资产处理**：哪些保留、删除或降级，以及真实消费者依据。
5. **验证证据**：自动化测试、真实简单案例、真实复杂案例和 PRD/Prototype 对照结果。
6. **遗留问题**：未验证项、失败项、需要 PM 决策项和后续风险。

不得只回复“已完成”“测试通过”或“门禁通过”。

## 11. 待 PM 与其他 AI 讨论的问题

执行前仍需讨论以下事项：

1. 统一事实清单是否作为正式运行时资产，还是只作为 Design 正文的机器定位辅助？
2. A/B/C 中间 JSON 的真实消费者有哪些，哪些可以删除？
3. simple/full 是否只由用户选择，还是允许 AI 根据需求结构提出升级建议？
4. 页面、字段、操作、状态和异常的最小表达格式分别是什么？
5. 哪些低影响细节可以由模型直接推断，哪些必须保守表达或省略？
6. 未决事项的局部阻塞范围如何被 PRD 和 Prototype 准确读取？
7. Align 中的“现状事实、方案候选、示例、历史废弃内容”是否需要正式分类？
8. `align-notes.schema.json` 是否需要增加输入版本、事实清单引用和影响对象？
9. `context-pack.py` 对 `unknown` 适用性的处理应采用什么保守规则？
10. `design-set.py` 是否只保留文件关系检查，还是还需要支持事实清单的确定性定位？

在以上问题没有形成共同结论前，不建议进入实施阶段。
