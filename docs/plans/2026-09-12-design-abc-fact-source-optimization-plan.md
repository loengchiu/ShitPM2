> 日期：2026-09-12

## 1. 文档定位

本文是 Design ABC 责任与双下游事实源优化的执行与核验依据。文档记录了本轮优化的决策基线、各阶段执行内容、根因修复、核验闭环结论及回归验证记录。

本计划涉及的所有规范、契约、Schema 与脚本调整均已落实，不直接修改任何真实项目的业务数据。

## 2. 背景与已发现问题

### 2.1 当前目标发生了修正

初步看起来，问题像是 ABC 三层导致 Design 过度设计，因此容易产生“减少 Design 内容”的直觉方案。但 PM 已明确补充：

> Design 同时服务 PRD 和 Prototype。如果 Design 不把产品事实定义完整，两个下游会各自补充，最终产生事实不一致。

因此，本轮不能把 Design 改成只确认方向的轻量文档。Design 仍必须是 PRD 和 Prototype 的唯一产品事实源。

真正需要削减的是：

- 与当前需求无关的分析维度；
- 将复杂场景规则套用到简单场景；
- A/B/C 的重复中间交接资产；
- 为满足固定格式而产生的空章节和“无 / 不适用”填充；
- 将实现细节伪装成产品事实；
- 按页面数量、步骤数量或材料数量机械触发的复杂分析。

不得削减的是：

- 范围内会影响 PRD 或 Prototype 结果的产品事实；
- 页面、区块、字段、操作、状态、权限、反馈、异常结果和验收中实际适用的内容；
- 能改变用户看到什么、能做什么、数据如何变化、状态如何变化、谁负责以及如何判断成功的内容。

### 2.2 当前契约的主要薄弱点

1. `simple` 仍然承担了大量 full 模式要求，实际表现为“缩小版 full”。
2. `full` 的 A/B/C 清单容易被模型理解成必须逐项填满的覆盖清单。
3. 规范多次写“按适用性”，但没有提供足够明确的最小排除规则，导致模型倾向于全部展开。
4. 页面属性、八列字段表、十列操作表和状态机表被过度普遍化，事实完整与表达格式没有分开。
5. 多套跨层自检、写作自检、质量标准和专项规则内容重复，增加执行负担并诱发补全。
6. A/B/C 分析资产、冲突资产和 Design 简报曾保留较重的中间结构，但当前主链已基本不再使用；本轮重点是确认消费者后删除死引用，而不是重建中间资产。
7. `align-notes.schema.json` 过于贫弱，是否需要补充输入版本和未决影响范围，必须以真实消费者为依据，不能预先造字段。
8. `context-pack.py` 对适用性为 `unknown` 的卡片处理过于机械，可能把不确定性直接转换成更多规则。
9. `design-set.py` 主要保护文件关系和指纹，不能也不应承担业务完整性判断；当前规则需要明确这一边界。
10. 模板中的“按需章节”与“无内容时必须填无”并存，容易制造形式完整、实际冗余的正文。

## 3. 已形成的产品决策

以下内容来自本轮 PM 已明确确认的共识，执行前不得擅自改写：

### 3.1 两种模式继续保留

继续保留 `simple` 和 `full`，但重新定义其边界：

- `simple`：单一主流程、小范围业务闭环；
- `full`：多个角色、多个阶段、状态流转、权限差异、跨系统或明显分支。

模式依据是业务结构复杂度，不是页面数量、材料数量、关键词或文档长度。

### 3.2 Design 仍是唯一产品事实源

Design 是 PRD 和 Prototype 的唯一产品事实源。PRD 和 Prototype 只能承接 Design，不得各自补写会改变产品语义的事实。

如果发现 PRD、Prototype 与 Design 冲突，应回到 Design 修正，再同步受影响下游，不以 Review 或下游文件覆盖 Design。

### 3.3 Design 的完成标准

Design 完成，不代表所有可能的产品问题都被提前穷举，而是代表：

- 当前范围内的主流程完整；
- 所有会影响 PRD 和 Prototype 的产品事实已经定义；
- 会改变业务结果的边界、异常和责任已经定义；
- 未能安全决定的高影响事项已经显式列为未决，并标明影响范围；
- PRD 和 Prototype 不需要自行猜测高影响产品语义。

### 3.4 必须定义的产品事实

只要会改变以下任一项，就必须进入 Design：

- 用户看到什么；
- 用户能做什么；
- 数据如何变化；
- 状态如何变化；
- 谁负责；
- 如何判断成功。

这包括实际适用的页面、区块、字段、操作、状态、权限、规则、反馈、异常结果和验收。

### 3.5 事实完整与格式适配

产品事实必须逐项完整，但表达格式按复杂度选择：

- 简单页面可以用紧凑清单、短表或自然语言；
- 复杂页面和多角色流程可以使用详细字段表、操作表和状态机表；
- 不得用“基本字段”“相关信息”“支持查询等”代替具体事实；
- 不要求所有页面机械使用八列字段表、十列操作表或状态机表。

### 3.6 复杂规则按业务影响触发

以下情况需要详细展开：

- 多个业务状态；
- 角色责任变化；
- 审批、驳回、撤回、作废、删除、恢复；
- 权限或数据范围差异；
- 外部系统或人工交接；
- 批量处理、文件处理；
- 失败后存在不同业务结果；
- 涉及数据完整性、责任归属、生命周期或验收口径。

普通单步查询、简单只读展示和不改变业务结果的普通交互，不因页面数量或步骤数量被迫展开复杂异常、补偿或状态模型。

### 3.7 A/B/C 的定位

A/B/C 继续保留，但定位为三种分析责任，而不是固定任务图、固定章节目录或固定 JSON 数量：

- A：理解问题、目标、角色和边界；
- B：理解业务如何运行；
- C：确认产品如何承接。

full 模式只分析当前需求实际涉及的内容。不适用项应简短排除，不生成空章节，也不为了覆盖清单主动创造新业务事实。

### 3.8 事实源与机器定位

Design 正文是 PRD 和 Prototype 的唯一产品事实源；`设计地图.md` 和 `设计集清单.json` 只负责正式文件的组织、定位、依赖和指纹，不承载第二套产品事实，也不新增“统一事实清单”。

A/B/C 的分析结论必须落入正式 Design 文件或未决事项，但不需要先写入独立的 A/B/C JSON 或另一套事实登记资产。下游读取 Design 正文；确定性工具只能提供定位、结构和一致性辅助，不能替代产品语义判断。

### 3.9 未决事项按影响范围阻塞

高影响未决事项不阻塞整个项目，只阻塞受影响的页面、字段、操作、流程或验收。

每条未决至少说明：

- 问题是什么；
- 会影响哪些产品事实；
- 当前暂不采用什么假设；
- 需要谁决定。

### 3.10 模型推断边界

模型可以补充不改变以下内容的低影响表达细节：业务结果、责任、权限、数据范围、状态和验收。

会改变上述内容的事实，必须来自用户或材料、由已确认事实明确推导，或者进入未决事项。不能仅因为“看起来合理”就写入 Design。

下游不得把未决事项自行补成已确认事实。

### 3.11 Design Review 同步纳入本轮

Design Review 必须与生成侧在同一轮同步修改，否则生成侧采用“事实完整、格式适配复杂度”的新规则后，Review 仍会按旧的固定页面属性、八列字段表、十列操作表和全量横切能力要求判定，形成生成与审查互相冲突的契约。

Review 继续保留独立第二意见，但核心职责调整为：

- 审查范围内影响 PRD 和 Prototype 的产品事实是否完整；
- 审查业务闭环、角色责任、权限、数据范围、状态、操作结果、异常和验收是否互相一致；
- 识别未经授权的高影响假设；
- 检查高影响未决事项是否被明确记录，以及受影响内容是否被正确局部阻塞；
- 检查 Design 是否足以作为两个下游的共同事实源。

Review 不再把是否使用固定表格、是否填满固定页面属性本身当作默认缺陷。只有格式造成事实遗漏、歧义或下游无法承接时，才升级为 Review 问题。

默认 Review 只审 Design，不主动读取 PRD 或 Prototype。只有用户明确要求双下游对照时，才把 PRD 和 Prototype 纳入审查范围。

继续保留 P0/P1/P2 和“通过 / 有问题需修改 / 阻塞”三档结论；取消强制输出五维 L0-L3 评分。五个质量维度可以保留为 Review 的观察角度，但不再形成第二套固定评分负担。

## 4. 本轮目标

### 4.1 产品目标

优化后，PM 能得到一份同时满足以下要求的 Design：

1. 作为 PRD 和 Prototype 的共同事实基线；
2. 范围内页面、字段、操作和业务结果不遗漏；
3. 复杂业务的状态、权限、责任和异常不被过度简化；
4. 简单业务不被迫生成无关的对象模型、状态机、权限矩阵和异常清单；
5. A/B/C 仍能承担深度分析责任，但不再产生重复的过程负担；
6. 未决事项不会被两个下游分别猜测；
7. Design 正文按产品经理理解顺序组织，不暴露内部分析过程。

### 4.2 质量目标

质量判断以最终 Design 和双下游承接结果为主，不能以以下内容替代质量判断：

- 中间文件数量；
- A/B/C 是否生成了固定数量的 JSON；
- 上下文包数量或哈希；
- 规则包读取回执；
- `design-set.py check` 退出码；
- 页面、字段或章节数量；
- 文档篇幅。

## 5. 明确不做

本轮不得实施以下内容：

- 不把 Design 降级为只确认方向的摘要稿；
- 不允许 PRD 或 Prototype 自行补写高影响产品事实；
- 不删除页面、字段、操作、状态、权限、反馈、异常结果和验收中实际适用的事实；
- 不取消 Align 的事实形成责任；
- 不取消 full 模式的 A/B/C 分析责任；
- 不恢复固定的 A1-A5、B1-B6、C1-C4 等细粒度任务图；
- 不新增章节覆盖率、事实数量、页面数量或文档篇幅门禁；
- 不新增“统一完整度检查器”“综合门禁”“最终验证回执”或机器质量签名；
- 不把脚本用于判断业务语义、权限、状态机、流程或异常是否正确；
- 不为了减少上下文而删除规则，只能通过按适用性装载减少无关内容；
- 不直接批量改写所有历史 Design；
- 不修改真实项目业务事实；
- 不提交 Git commit 或 push，除非后续获得明确授权。

## 7. 建议执行阶段

### 阶段 0：建立当前基线

#### 执行内容

1. 记录仓库 `git status --short` 和当前分支。
2. 读取计划内文件的当前版本，确认没有遗漏的真实消费者。
3. 搜索所有对 `simple`、`full`、A/B/C、Design 事实清单、A/B/C baseline、`design-brief`、`align-notes`、`design-set` 的引用，并核对 Align 当前对需求事实、现状事实、候选/示例、废弃内容和未决讨论的区分方式及真实消费者。
4. 运行与上下文装载、Design 清单、资源完整性和相关回归测试。
5. 增加一个不纳入正式产物的最小基线探针：使用官方 `templates/design-module.md` 的八列表字段表，填写至少一个字段，并准备与之对应的最小 PRD；分别运行 `stage-prep.py`、`design-index.py compile` 和 `prd-consistency-check.py`，完整记录提取数量、冲突分类、退出码和原始输出。探针结束后清理临时文件。
6. 当前已知探针结果必须作为既存基线缺陷登记，而不是本轮成果：`prd-consistency-check.py` 将对应 PRD 字段判为 hallucinated 并以 `deterministic_conflict` 退出。根因可复现：`stage-prep.py:265` 要求字段表表头精确含“字段”和“类型”两列，而 `templates/design-module.md:75` 的权威八列表头既不是精确“字段”、也完全没有“类型”列。执行时仍需保存实际原始输出作为证据。
7. `design-index.py compile` 的结果（**已复验并正式关闭**）：在最小探针中曾出现 `fields: 0 / pages: 0 / blocks: 0` 但 `errors: 0`、`ok: true` 的静默归零。经使用规范 Design 目录复验排查，根因为清单条目需显式声明 `type: "module"`，写为非 `module`（如 `MOD`）时会走 `_parse_nonmodule` 逻辑跳过区块字段提取；修正清单类型配置后解析出 `pages: 1 / blocks: 1 / fields: 2` 正常，属于调用方配置契约要求而非脚本缺陷，本条观察正式关闭。
8. 将探针中由官方模板导致的字段漏读或一致性假红与其他基线失败分开记录。
9. 区分已有失败和本轮新增失败，不把基线失败伪装成改造结果。

#### 完成条件

- 已用官方 Design 模板最小探针记录字段表解析的当前基线，包括 `stage-prep.py`、`design-index.py compile` 和 `prd-consistency-check.py` 的实际输出；
- 已确认每个计划内文件的真实消费者；
- 已列出当前实际存在的重复中间资产和重复规则；
- 没有在基线阶段修改业务规则。

### 阶段 1：先收敛产品契约，不改脚本

#### 目标

先把“事实必须完整”和“过程可以精简”写成唯一、清晰、产品经理可理解的规则，避免先改脚本导致契约继续漂移。

#### 重点调整

1. 重写 `simple/full` 的定义和选择说明。
2. 将 full 的 A/B/C 从“全量责任清单”改成“按当前需求适用性承担的分析责任”。
3. 明确 simple 仍需完整承接范围内下游事实，但不展开无关复杂模型。
4. 建立“下游影响判断”：会改变用户看到什么、能做什么、数据、状态、责任或验收的内容必须定义。
5. 为不适用项提供最小排除表达，避免用空章节填充。
6. 明确复杂规则由业务影响触发，不由页面数量、步骤数量或材料数量触发。
7. 明确低影响推断不能改变业务结果、责任、权限、数据范围、状态和验收。
8. 明确 Design 正文是唯一产品事实源，现有设计集清单只做正式文件定位和依赖管理，不新增统一事实清单。

#### 阶段验收

- 产品规则中不存在“Design 可以少写事实、让下游自行补充”的表述；
- simple 不再被描述为 full 的缩小版；
- full 不再要求对不适用的所有 A/B/C 子项展开正文；
- 事实完整性和表达格式已经明确分离；
- 同一条产品原则只有一个权威表述，其他文件只保留指针。

### 阶段 2：清理无消费者的 A/B/C 中间资产

#### 目标

### 阶段 4：收敛上下文装载和中间资产

#### 目标

减少无关规则读取，不删除必要规则。

#### 重点调整

1. 将当前需求实际适用的规则分为常驻规则和条件规则。
2. `simple` 只装载最小业务闭环、事实承接和当前页面/流程所需规则。
3. `full` 装载 A/B/C 责任，但不因 full 自动装载所有状态、字段、权限、流程、跨系统和非功能卡片。

5. 阶段 2 已负责确认并清理无消费者的 A/B/C 中间资产，本阶段只负责清理其余上下文装载入口和无关规则引用，不重复设计或迁移中间资产。
6. 保持 context pack 是上下文视图，不将其变成产品事实源或质量证明。
7. 保留必要的确定性文件检查，但不新增业务质量门禁。

#### 阶段验收

- simple 不会因为默认规则包而读取完整 full 规则；
- full 不会因为模式选择而机械装载所有专项卡；
- 规则未被删除，只是按适用性分层；
- `unknown` 不会静默扩大适用范围；
- A/B/C 交接资产减少后，Design、PRD 和 Prototype 仍能从 Design 正文继续工作。

### 阶段 6：同步脚本、Schema 和测试

#### 目标

让确定性工具与新的产品契约一致，但不让脚本接管业务判断。

#### 重点调整

1. 修改脚本前确认其真实消费者和当前失败证据。
2. `design-set.py` 继续只负责文件集合、路径、ID、依赖、地图引用和指纹等确定性关系。
3. 明确 `design-set.py check` 不代表 Design 语义完整，不把退出码写成产品质量证明。
4. 在不新增业务语义门禁的前提下，核对并适配当前 Design 正文的读取锚点：`stage-prep.py`、`design-index.py`、`prd-consistency-check.py` 对字段、页面和状态表达的识别不能因格式精简而整体漏读、误读或静默判空；如需修改，测试真实解析行为而不是恢复八列/十列硬约束。
   适配方向（不得照抄为硬约束，仅为避免执行时二选一违规）：不新增“类型”列的前提下，`stage-prep.py` 的字段表识别条件应放宽为“表头中存在含‘字段’的列即可作为字段名来源，不再要求同时存在‘类型’列”，使 `templates/design-module.md` 的权威八列能被直接识别；若该放宽会导致脚本承担语义判断，则改为在 Design 侧固定一个字段锚点标记，并将该标记写入阶段 3 定义的最小可解析形态。

#### 阶段验收

- Schema、脚本、Skill、reference、模板之间不存在已确认应删除的旧路径、旧模式或旧资产引用；
- 确定性脚本没有承担业务语义判断；
- 旧测试不会要求已经删除的复杂中间流程继续存在；

- 文件关系检查通过不能被表述为 Design 语义质量通过。

### 阶段 7：最小真实场景回归与双下游一致性验收

#### 目标

用最少但有区分度的真实场景，验证“事实完整、过程精简、Review 不机械加码”是否成立。

#### 必做场景 A：简单只读需求（含简单表单变体）

验收重点：

- simple 只形成单一主流程和必要产品事实；
- 页面、字段、筛选、查询动作、结果、空态和必要反馈完整；
- 若改用简单表单变体，额外确认字段必填、校验、提交、保存结果、失败反馈和后续去向完整；
- 不生成无关状态机、权限矩阵、跨系统补偿或完整对象模型；
- Design、PRD 和 Prototype 对页面、字段和业务结果保持一致；
- 仅由展示表达差异导致的内容，不被错误升级为业务冲突。

#### 必做场景 C：复杂多角色状态需求（含一个局部高影响未决）

验收重点：

- full 仍完成 A/B/C 三类分析责任，但不要求生成独立 A/B/C 中间资产；
- 多角色责任、业务状态、允许操作、状态变化、权限、数据范围和异常恢复完整；
- 回退、驳回、撤回、终态和状态驱动展示不会被过度压缩；
- 复杂字段和操作能够使用详细表达，简单部分不被迫套宽表；
- 嵌入一个会影响局部页面或操作的高影响未决，验证问题、影响对象、暂不采用假设和决定人已记录，且只阻塞受影响内容；
- 受影响页面、字段、操作或验收不会被下游自行补全；用户回答后可以回写并继续承接。

#### 必做场景 F：Design Review 回归

至少验证以下 Review 行为：

1. simple 查询或只读 Design：没有状态机、权限矩阵或八列/十列表格，但业务事实完整时，不因格式缺失自动判 P1。
2. full 多角色状态 Design：使用详细表达但遗漏某个关键状态出路、角色权限或失败结果时，Review 能定位为实际业务缺口。
3. 高影响未决 Design：未决已明确记录且局部阻塞时，不把未决本身自动判为缺陷；若受影响内容仍被正文拍板，则判定为问题。
4. 不适用专项：没有外部系统、批量、文件或删除传播的需求，不因缺少对应章节自动判错。
5. 仅 Design Review：没有 PRD/Prototype 输入时仍可完成 Review，不把下游缺失当作输入阻塞。
6. 明确要求双下游对照：Review 能指出 Design、PRD 和 Prototype 的事实差异，并明确建议回写 Design 或修正下游的方向；不直接修改任何产物。
7. Review 输出：保留 P0/P1/P2 和三档结论，不要求输出 L0-L3 评分，不生成新的机读报告或验证回执。

#### 双下游一致性检查

仅在用户明确要求双下游对照时，由产品经理或独立审查 AI 读取最终 Design、PRD 和 Prototype，重点检查：

- 页面结构和关键区块是否一致；
- 字段名称、含义、来源、展示/编辑条件是否一致；
- 操作入口、可用条件、成功结果和数据/状态变化是否一致；
- 角色、权限和数据范围是否一致；
- 异常结果、恢复方式和后续责任是否一致；
- 未决事项是否被两个下游错误补成不同事实。

验收关注的是事实一致性和产品可用性，不关注 Design 是否更长、生成了多少中间文件或运行了多少步骤。

阶段 7 的验证矩阵固定为三个必做场景，不扩展成每个场景都重复跑全部下游：

- A、C：验证 Design 生成、必要的 PRD/Prototype 承接，以及结果事实一致性；
- F：默认只验证 Design Review；只有用户明确要求双下游对照时，才增加 PRD/Prototype 对照；
- B 作为 A 的简单表单变体；D 使用真实审计系统材料作为输入；E 作为 C 中的局部未决变体，不另立场景。

## 8. 失败处理与停止条件

- 无法确认某条规则的产品意图；
- 发现删除格式要求可能导致 PRD/Prototype 缺少事实；
- 发现 PRD 和 Prototype 的真实消费者依赖某个准备删除的中间资产；
- `simple/full` 的模式边界仍无法在真实案例中判断；
- 发现需要用户决定的流程、权限、状态、数据范围、角色责任或系统边界；
- 现有用户修改可能被覆盖；
- 测试失败无法区分基线问题与本轮问题；
- 需要新增业务语义检查脚本才能完成验收；
- 精简后出现 PRD 与 Prototype 事实分叉；
- Design 正文、设计地图、设计集清单、脚本读取结果无法形成可追溯的事实承接；

不得用以下方式掩盖失败：

- 把“脚本通过”写成“产品质量通过”；
- 把“没有发现遗漏”写成“已证明没有遗漏”；
- 把未决事项写成默认值；
- 把下游生成成功写成 Design 事实完整；
- 把简单案例通过写成复杂案例也通过；
- 把局部迁移写成全量完成。
