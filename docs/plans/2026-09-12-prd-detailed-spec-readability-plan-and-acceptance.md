# PRD 详细需求说明可读性与信息一致性优化执行与验收计划

> 日期：2026-09-12
> 状态：待 PM 审阅后执行。本文件在 PM 确认前不构成可开工依据；执行开始后由执行 AI 在 §12 追加记录，不得改写 §1–§11。
> 决策人：产品负责人（PM）
> 目标：在不牺牲「研发只读 `4.x.6` 能独立开发」这一交付目标的前提下，消除 `4.x.6 功能详细说明` 的机器排版腔、提高复杂流程/状态/权限表达的方差稳定性；把可机械判断的排版形态纳入硬错误，把“人不读得下去”交给 Review 和 PM 试读判断。

## 1. 文档定位

本文是 PRD 写作契约改造的执行与核验依据。文档记录决策基线、实测证据、执行阶段、失败停止条件、最终完成定义与交付格式。

本轮改造对象是 ShitPM 自身的 PRD 契约（Skill / 规范 / 示例 / 模板 / profile / lint / 一致性脚本 / Review 清单），**不是真实项目的业务事实**。真实项目只用于产生重写样本与验收对照（见 §7 阶段 3），任何真实项目文件修改前必须先做带时间戳的整目录备份。

## 2. 背景与已发现问题

### 2.1 用户提出的三个问题与一个人性化判据

PM 在真实项目产出上发现：

1. `4.x.6` 的表达 AI 味十足，人类难读懂；
2. 重要的流程怎么走、状态怎么变化、谁有查看/操作权限，有时写得好有时写得差（**方差问题，不是平均问题**）；
3. 描述排版又长又臭。

补充判据：PRD 最终读者是研发与测试。**一段话如果研发需要读第二遍才能提取事实，它就是缺陷**，与它是否符合规范无关。

### 2.3 四条根因（全部有复现路径）

**A. lint 的封闭词表可以被整份绕过，这是设计层面必然失效。**
`scripts/python/prd-style-lint.py:62-72` 从 `contracts/prd-writing.profile.json` 的 `forbidden_expressions` 生成标签正则，生成形态固定为 `\*\*<词>[：:]\*\*`，即要求**冒号在加粗之内**；同时词本身必须命中封闭词表。实测三重验证：

| 输入 | 现有正则是否命中 |
|---|---|
| `**页面目标：** 这是正文`（词在表中 + 冒号在内） | 命中 |
| `- **页面目标**：这是正文`（词在表中 + 冒号在外） | **不命中** |
| `- **默认排序**：按账期倒序。`（词不在表中） | **不命中** |

后果：把旧版标签体 PRD（145 行 `- **X**：`）直接喂给 lint → **0 error、1 warning、exit 0**。

**B. 规范要求三种表达，真实产出只用一种。**
`prd-writing-rules.md §1` 定义了自然段 / 数字编号 / `·` 并列三种表达，但没有规定「什么时候必须转列表」。实测结果：规范自己的优秀样本 6 页里有 5 页用了 `·` 列表（共 17 项），真实 PRD 5 页全部为 0 项。**段长膨胀（avg 143 vs 125、max 504 vs 215）是这件事的下游结果，不是独立的病灶。**

**C. 流程/状态/权限的表达没有强制信息槽，全靠 AI 每次重新发明结构。**
`prd-writing-rules.md §5` 只写了「按复杂度写」，未给出槽位清单与逐槽判断要求；§3/§4 是事实域清单，不是落点结构。因此同一份 PRD 里有的动作写了角色×状态，有的只写了一句业务结果。

**D. 权限维度在机器上完全不存在。**
`scripts/python/prd-consistency-check.py` 实测（`--module 租金清分`）：`prd_permission_pages_count: 0`、`prd_roles_count: 0`、`permissions.not_evaluated: true`、`exit_reason: needs_semantic_judgment`、**exit 0**。权限写全与写漏，脚本输出完全一样。复现原因是三处硬编码限制：

1. `:727 extract_prd_permission_pages` 候选章节只有 `权限汇总 / 权限定义 / 权限规则`，不含模块级 `4.x.3 角色与权限`；
2. `:844 / :929` 用 `re.match(r'^#{1,2}\s+')` 判断进出权限章节 —— 而 `#### 4.1.3` 是四级标题，**永远进不去**；
3. `:811 _extract_perm_pairs_from_table` 要求表头首列含 `模块 / 操作对象 / 页面 / 对象`，且「单元格非空即视为该 pair 存在」——写入「否」会被当成有权限。

补充：`.workflow/reviews/` 中该项目从未跑过 PRD Review（只有 16 份 design-review、2 份 prototype-review）—— 说明 C、D 两类问题缺少任何人把关。

### 2.4 两个外部「去 AI 味」方案的当前迁移结论

**kill-ai-slop**：核心定义是「slop = 决定的缺席，而非用了某个词」，机器只捞候选、是否 slop 由人判，护栏明确写着「扫描通过 ≠ 页面变好」。**可迁移：形态层清单，以及「机器捞候选 + 人判是否 slop」这条边界。**

**human-writing**：其实测变更记录的精神是「1.0 用字符串禁令拦 AI 味，模型会换一套字面继续做同样的事；读者认的是姿势不是字」—— 这正是 A 根因的标准诊断书。**可迁移：动作级禁令方法论、三层检查、脚本不得自行增加未写明的硬禁词。不可迁移：节律/修辞层。**

节律层在 PRD 题材上的失效证据（双向跑过，本轮不主动引入；其他 AI 如有新证据，可在复核时指出）：

| 指标 | 真实 PRD 4.1.6 | 规范优秀样本 | 判据方向是否成立 |
|---|---|---|---|
| 句长变异系数 CV | 0.549 | 0.420 | 该技能认为 CV 小 = 机器味，这里**反向** |
| 「的」字密度 | 1.26% | 0.69% | 但 `prd-writing-rules.md` 自身也是 1.22% → 不能当阈值 |
| 段首 6 字重复 | 服务中心财务 ×9 / 服务区管理员 ×5 | 服务区管理员 ×5 | 同题材无法区分 |

原因：该技能治的是**文学性中文**的 AI 味（修辞动作贫乏）；PRD 的 AI 味是**信息架构贫乏**（事实无层级、没有未做决策、靠堆砌凑篇幅）。前者管「怎么写」，后者管「怎么组织」。

## 3. 本轮共同确认的治理方案

> 本节根据 PM 与本次讨论逐项确认的结果修订。它记录的是待其他 AI 复核的方案基线，不代表已经开始执行。

### 3.1 交付目标不变

4.x.6 仍是研发和测试的唯一自包含交付单元。读者只看该章节，就应能确定产品行为，不需要打开 Design、Prototype 或旧 PRD，也不需要向 PM 补问普通细节。可读性优化不能用“回去查 Design”来交换。

### 3.2 本轮治理解决什么问题

本轮同时处理三类问题：

1. **一次读懂**：研发和测试能够直接提取角色、条件、对象、动作、校验、结果、状态变化和失败恢复。
2. **表达稳定**：同一份 PRD 中，不同页面和不同动作的详细程度不再主要依赖模型临场发挥。
3. **自然可读**：保留业务事实密度，减少汇报腔、口号、抽象名词堆叠、长句堆步骤和没有新增信息的重复。

本轮不把“AI 味”缩减为词语问题。重点检查信息是否按动作和因果组织，读者是否需要自行补主语、拆步骤或猜状态。

### 3.3 4.x.6 的组织方式

4.x.6 采用以下稳定骨架：

- 业务阶段；
- 页面名称；
- 页面引入段；
- 独占一行的动作名称；
- 动作正文。

页面引入段和动作标题提供稳定落点，但动作正文不强制拆成固定小标题。正文按照业务复杂度承担适用的信息责任，避免所有页面都长成同一种模板。

### 3.4 页面引入段

页面引入段必须交代四项内容，但不规定固定句数、字数或列表格式：

1. 谁在什么前提下进入页面；
2. 进入页面要完成什么判断或任务；
3. 结果交给谁，或进入什么后续状态；
4. 页面与上游、下游页面如何衔接。

引入段不提前陈列页面全部字段和规则，也不加入“核心支撑、重要节点、形成闭环”等评价性句子。

### 3.5 动作正文的责任

三档复杂度用于生成和 Review 时判断需要覆盖的内容，不转写成固定的正文标签。

| 动作复杂度 | 适用动作 | 至少判断的内容 |
|---|---|---|
| 简单 | 查询、查看、返回、打开详情 | 操作角色、可用条件、页面或数据结果 |
| 普通 | 新增、编辑、保存、提交、修改 | 前置条件、输入与校验、系统处理、成功结果、失败保留或恢复 |
| 复杂 | 多角色、多状态、多分支、破坏性操作、外部协作 | 角色与状态、关键分支、状态变化、失败恢复、下一步衔接 |

槽位不是固定标题。某项不适用时可以不写，但生成和 Review 必须明确判断过，不能因为模型遗漏而静默缺失。简单动作不得为了填槽位扩写成复杂动作。

### 3.6 自包含与重复

4.x.6 保持自包含。同一事实可以在状态规则、功能详细说明和字段定义中重复出现，但每次出现必须增加新的使用上下文，例如角色、状态、条件、对象、输入、校验、计算、结果、异常、恢复方式、展示方式或上下游关系。

第二处只换词重述第一处，未增加新的使用信息，属于原地重述。Review 只处理这类无效重复，不要求删除为了让研发独立阅读所需的有效重复。

### 3.7 权限表达

每个业务模块的角色与权限章节提供“角色 × 业务能力”矩阵：

- 行是角色；
- 列是业务能力；
- 单元格写“可、否或条件”；
- 复杂条件在表下注释中展开；
- 能力按业务动作组织，不按按钮或图标组织。

矩阵用于表达模块级权限边界。4.x.6 仍然按动作写清具体状态、组织范围、数据范围、例外条件和退回后的处理。

矩阵缺失或无法提取时，一致性检查必须明确标记权限维度未评估，不能把未提取写成权限一致，也不能把矩阵当成自动覆盖正文冲突的依据。

### 3.8 短矩阵与流程图

4.x.6 可以使用短矩阵作为扫读锚点，适合表达角色差异、状态与动作、固定选项及其结果。短矩阵不能代替动作正文，也不要求每个页面都出现矩阵。

复杂流程是否配流程图按理解收益决定。三个以上角色、多分支、退回重试回环或复杂状态变化通常值得配图；简单顺序不必为了形式画图。正文必须自包含，不能只写“具体流程见图”。

### 3.9 自然中文规则

生成正文时遵循以下规则：

1. 先写角色和动作，再写条件、处理和结果；
2. 一个句子尽量只承载一个主要动作；
3. 一个自然段只推进一个主要业务判断；
4. 用具体动词替代抽象名词；
5. 用可验证的产品结果替代价值评价；
6. 不在产品正文评价方案是否先进、完整、务实或有效；
7. 不主动制造“不是……而是……”等对比结构；
8. 不用“通过……实现……”包住核心事实；
9. 不用“形成闭环、提升效率、强化管理”等总结句代替流程和状态；
10. 未确认事实直接标记待确认，不用概念化表达掩盖未知。

“赋能、抓手、底座、协同、支撑、闭环”等词不能单独作为禁词判断。是否需要修改，要看它是否替代了具体动作、条件或结果。

### 3.10 lint 与 Review 的边界

lint 只对机器能够稳定判断的形态问题报 error：

- 加粗标签体，例如 **字段名：** 正文和 **字段名**：正文；
- 连续多行加粗标签；
- 用加粗短语模拟标题层级；
- 明显使用多层列表代替正文结构；
- 明确违反已确定的 Markdown 结构。

段落长度、列表项长度、逗号数量、页面列表密度、可能的抽象总结和可能的重复，只能作为 warning 或候选提示，不能单独宣判可读性失败。

脚本不得自行增加 profile 中没有写明的硬禁词或形态。词表不能承担“判断 AI 味”的责任。Review 和 PM 负责判断自然度、信息因果、重复是否有效以及研发能否第一遍提取事实。

### 3.11 Review 的判断方式

Review 不再只判断“有没有提到”。对每个重要动作，按复杂度检查适用的信息责任，并为结论保留具体证据：

- 谁可以执行，谁不能执行；
- 什么条件或状态下可以执行；
- 操作的对象是什么；
- 用户需要输入或确认什么；
- 什么情况允许或拒绝提交；
- 系统保存、计算、通知或生成什么；
- 成功后状态、页面、记录和下一步如何变化；
- 失败后内容、状态和恢复路径如何处理。

Review 问题必须定位到页面、动作或段落，说明缺失内容对研发、测试或权限判断的影响。不得用“流程不完整”“权限已覆盖”等无法复核的结论代替证据。

### 3.12 真实验收原则

真实验收使用租金清分 PRD，能源数据监测 PRD 不纳入当前 spm-prd 产物基线。

- Design 是产品事实裁判；
- 旧 PRD 与新 PRD 逐页对照，用于发现改写中的信息损失；
- 文本差集只用于定位候选，不能作为唯一的无损证明；
- PM 进行研发视角的任务式试读，判断新 4.1.6 是否能一次提取关键事实；
- lint 和 consistency 的结果只能作为辅助证据，不能替代最终产物阅读。

## 4. 本轮目标

### 4.1 产品目标

改造后，4.x.6 应同时满足：

1. 研发和测试第一遍可以提取关键产品事实；
2. 页面和动作具有稳定的组织方式，但不会被迫套用完全相同的句式；
3. 复杂流程、状态变化和权限条件有明确落点；
4. 4.x.6 仍然可以独立评审和开发；
5. 产品正文以具体动作、条件、处理、结果和恢复方式为主，减少空泛总结和汇报式表达；
6. 机器能够稳定发现已确定的排版形态错误；
7. 权限矩阵可以被一致性检查提取，无法提取时明确标记未评估。

### 4.2 质量目标

最终质量以 PRD 的可读性和事实承接为准，不以以下结果单独替代：

- lint 退出码或 issue 数量；
- consistency exit 0；
- 重写前后字数变化；
- 列表数量或段落数量达到阈值；
- 示例文件检查通过。

### 4.3 建议记录的观察指标

真实重写时可以记录以下指标，用于前后对照和定位问题，但不单独作为通过条件：

- 形态 error 数量；
- 过长段落和过长列表项数量；
- 每页动作数量及复杂度覆盖情况；
- 权限矩阵提取到的角色和能力数量；
- Design 到新 PRD 的事实对照结果；
- PM 任务式试读中需要二次解释的动作数量。

不把“每页至少一组列表”“自然段不超过 250 字”“列表项不超过 100 字”设为本轮普遍硬门槛。它们可以作为观察指标或候选提示，最终由 Review 判断是否影响理解。

## 5. 明确不做

- 不改变 4.x.6 的自包含交付目标，不引入指向 Design 的替代方案；
- 不要求所有页面使用相同的正文小标题；
- 不把每页列表数量、段落字数或列表项字数当作普遍可读性硬门槛；
- 不用封闭词表判断 AI 味；
- 不把一句话的自然度交给脚本单独判定；
- 不删除为了自包含而必须保留的有效重复；
- 不以文本差集作为事实无损的唯一证明；
- 不把流程图或短矩阵变成所有页面的强制资产；
- 不为了降低篇幅删除业务事实；
- 不新增综合检查器、验收回执、机器签名或只生成报告的工具；

## 8. 失败处理与停止条件

出现以下任一情况，停止实施并报告，不得自行降级或绕过：

- 新规范与既有事实承接要求冲突；
- 为满足形态检查必须删除或改变业务事实；
- 发现权限矩阵无法表达真实的状态或组织条件，且需要新的产品决策；
- Design 到新 PRD 的事实对照出现无法解释的缺口；
- 旧新对照无法判断某项内容是改写还是丢失；
- PM 试读发现同一动作存在两种合理解释；
- lint 或 consistency 结果异常，无法区分工具问题和内容问题；
- 为让无关的既存基线测试通过而需要扩大本轮范围；
- 改造导致新的确定性假冲突；
- 需要修改真实项目的 Design、Prototype 或其他业务文件。

不得用以下方式掩盖失败：

- 把 lint exit 0 写成 PRD 可读；
- 把脚本提取到角色写成权限已一致；
- 把示例通过写成真实项目通过；
- 把字数变少写成事实无损；
- 把只重写一个页面写成完整模块完成；
- 用自动生成的 PASS 文本替代 PM 试读。
