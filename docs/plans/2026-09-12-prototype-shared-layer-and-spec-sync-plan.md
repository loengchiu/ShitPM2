## 一、背景与问题

### 1.1 目标（本次改造要服务的三件事，按优先级）

| 优先级 | 目标 | 当前状态 |
|---|---|---|
| 1 | **省 Token**（AI 改一页读得越少越好） | 改一页需读约 1000 行源码 + 约 60KB 规范，估算 44k token |
| 2 | 风格统一一致 | 两工程主题曾不同步；模板内 92 处样式覆盖；硬编码色值 |
| 3 | 部署更新方便 | **本次不动**（负责人已确认现状可接受） |

### 1.2 已核实的问题根因（均为实测数据，非推断）

**根因 A：共享层太薄，规范只能靠每一页自觉**

审计工程 `shared/` 531 行 vs 页面层 12212 行，共享层占比 **4.2%**。结果：

| 横切内容 | 重复处数 | 后果 |
|---|---|---|
| 版权行（研发单位：广西计算中心） | 28 处手写 | 改一次要动 28 处 |
| 返回按钮 | 23 处手写 | 同上 |
| 分页配置 | 22 处手写 | 同上 |
| 空字段显示 `—` | 规范要求，66 页仅 **1 页**做到 | **落地率 1.5%** |

**根因 B：模板里的示例页自己就没用共享件（AI 是照示例抄的）**

11 个共享件，示例页实际只用了 2 个（页脚、详情列表），其余全是手写原生控件。
→ 规范写得再细也没用：**AI 生成新页面时参考的是示例页，不是规范文档**。这是"落地率 1.5%"的第二个机制，比"页面不自觉"更根本。

**根因 C：规范文档与代码已不同步，而 AI 每次都要读**

| # | 问题 | 证据 |
|---|---|---|
| C1 | `visual-spec.md` 色值表是旧值 | 文档 `#0559a8`/`#232e3c`/`#fafbfc` vs 代码 `#0563BC`/`#1f2937`/`#f9fafb` |
| C2 | `tablerTokens.ts` 大部分是死数据且带旧值 | 仅 `chart` 段被 `TablerChart.jsx` 使用；`tablerCssVariables`（61-93 行）从未注入（`main.jsx` 只引 `tablerTheme` 的 `tablerCssVars`）；`colors` 段仍是全套旧值 |
| C3 | `shell.md` 的示例写不出来 | 用 `var(--spm-color-primary)`，该变量未被注入；页面示例违反共享件规范 |
| C4 | 两份规范对同一写法表述冲突 | `writing.md` §四写 `fixed:"right"`，`page-types.md` 要求统一 `start/end` |
| C5 | 模板自带坏链 | `Home.jsx` 3 处 `navigate('/demo-form')`，`routes.jsx` 注册的是 `/form-demo` → 命中"页面不存在" |
| C6 | 硬编码色值 | `DesignGallery` `#8e8b82`、`DetailDemo` `#6c6a64`，均非规范值 |
| C7 | 图表标签色未同步 | `tablerTokens.chart.label` 仍为旧次要色 `#626976` |

> **修正说明**：2026-09-11 记录中称"tablerTokens.ts 是死代码"——**该说法不准确**。文件内 `chart` 段是活代码。准确表述见 C2。

**根因 D：审计工程的自动比对近乎空转**

66 个页面只有 **17 个 `data-field` 字段标记**，`data-page` 为 0。v3 验收的 762 条"可能遗漏"主因是缺标记，不是结构问题。（本次不补标记——负责人确认收益不匹配投入。）

**根因 E：一致性门禁对模板示例页无效**

`prototype-consistency-check.py` 硬编码排除 `modules/demo/` → 模板自带的示例页完全脱离门禁，而它恰恰是 AI 抄写的对象。

## 二、决策记录（ADR 摘要）

### ADR-1：不做页面 spec 化 / 渲染引擎

- **结论**：否决。
- **理由**：spec 化的核心卖点是"人能自己改配置"。负责人明确不具 HTML 能力、不会自己改原型，改动方式固定为「截图 → 交给 AI 改」→ 该收益归零。剩余收益仅为省约 3k token（占已优化后成本的 20%），代价是 800–1500 行引擎 + 66 页迁移 + 一致性门禁推倒重做（会重演 ProComponents 声明式配置导致 DOM 锚点大面积丢失的教训）。
- **不变**：保留 JSX 全部表达自由度。

### ADR-2：不做"一页一文件 / 一页一独立地址"

- **结论**：本次不做。
- **理由**：负责人明确"单页独立地址完全不重要"。且 hash 路由下每页已有可分享的独立网址（如 `#/archive?p=r03`）。在共享层尚未加厚时拆分，会把横切改动从扫 12 个文件放大到扫 66 个，**是负收益**。

### ADR-3：不做单文件 HTML 分发版

- **结论**：不做。负责人确认无"打包成单文件发给别人双击打开"的需求。

### ADR-4：部署链路本次不动

- **结论**：保持现状（本地 `原型工具.bat` + Cloudflare `wrangler pages deploy`，固定 URL）。
- **未做的三项**（记录在案，将来可做）：① `npm run deploy` 脚本化 ② preview URL 做评审版本锚定 ③ 部署后自动冒烟。

### ADR-5：自动检查放在「生成侧自检」，不放在 Review 卡口

- **结论**：生成完成时由 AI 自检，不合格自行修正后交付。
- **依据**：`contracts/review-checklist.md` 反模式表明列"把一致性校验当门禁"是禁止项——一致性问题只能作为审查结论依据，不得阻塞 Review 流程。**不得违反本仓库既有契约**。

### ADR-6：生成侧可条件读规范，Review 侧必须照读

- **背景**：A-4 为省 Token，把 `visual-spec.md` 在**生成侧**改为条件读。但 `skills/spm-prototype-review/SKILL.md` 第 7 步明确要求读取该文档，检查项 17/18/19/20/21 均以它为权威规则来源。
- **结论**：**两侧的读取策略不同，且必须保持不同**。生成侧省的是"每次都要读"，Review 侧该读必须读。
- **依据**：review SKILL 第 8 步原文已预判该风险——"不存在的场景标记不适用，**不因生成路径变短而漏审**"。
- **风险**：执行 A-4 时最易发生的误伤是把 Review 侧一并改成条件读，导致视觉审查失去判据。

### ADR-7：Q1–Q13 全部决策

| 编号 | 问题 | 决策 |
|---|---|---|
| Q1 | 审计 66 页存量动不动 | **C**：只做低成本横切下沉，不动页面结构 |

## 五、工作块 C：生成侧自检门禁（对应 Q12=A + ADR-5）

### C-1 新建脚本

`scripts/python/prototype-shared-guard.py`

**检查项**（只做纯字符串/结构匹配，误报可控）：

1. 页面层出现已下沉结构的重复实现：
   - `modules/` 下出现"研发单位"等版权行字样
   - 手写分页配置（`pageSize` / `showSizeChanger`）
   - 手写返回按钮
   - 硬编码非规范色值
2. 单文件行数超阈值（>300 行）→ 报错
3. 两工程 `shared/ui` 哈希不一致 → 报错

**输出**：命中即 `exit 1`，打印文件与行号。

**白名单**：支持 `--allow <pattern>`，用于确有理由的特殊页（如 `DesignGallery` 控件样张台）。

### C-2 接入方式

在 `skills/spm-prototype/SKILL.md` 的"生成完成"节点加入该脚本：**跑不过就自己改完再交付**，不把红字抛给负责人。

### C-3 与 Review 的边界（务必遵守）

本脚本只在**生成侧自检**使用。**不得**接入 `spm-prototype-review`，也**不得**在 Review 流程中作为阻塞条件——`contracts/review-checklist.md` 已明列"把一致性校验当门禁"为反模式。

## 六、工作块 D：审查侧同步（2026-09-12 补入）

> 补入原因：负责人指出改造只覆盖了 `spm-prototype`，未核对 `spm-prototype-review`。核查后确认**需要改**。

### D-0 先说核查结论：审查侧不会因删改而失效

已核实 `skills/spm-prototype-review/` 与 `contracts/prototype-review-checklist.md`：

| 将被删改的令牌 | 审查侧引用数 |
|---|---|
| `tablerTokens` | 0 |
| `--spm-color-*` / `--spm-space-*` 等 | 0 |
| 旧色值 `#0559a8` / `#232e3c` / `#626976` | 0 |
| `size="middle"`、`fixed:"right"` | 0 |

契约引用的 17 个规范与脚本路径**全部有效**（无失效链接）。
→ **A-1 / A-2 的删改不会让审查侧崩**。需要改的是下面三处逻辑冲突。

### D-1【必须】修复"下沉之后反而判不合格"的误报（触发源：B-2）

- **冲突**：检查项 25 把"空字段 `—`"列为**页面必须写出**的项；检查项 19 / 22 的"高频结构 / 已承担实现"清单里没有页脚、返回、分页、空字段。
- **后果**：B-2 把这些下沉进共享件后，页面**不再手写** → Review 会按现条文判"未按规范执行"，**改得越彻底，报得越多**。
- **修法**：判定基准从"页面是否写了"改为"**页面是否绕过共享件默认行为**"；并把下沉清单补进检查项 19 / 22 的"高频结构"定义。

### D-2【必须】钉死两侧读取策略的差异（触发源：A-4）

见 ADR-6。执行 A-4 后需**同时**确认：review SKILL 第 7 步的 `visual-spec.md` 读取要求**未被一起改成条件读**。

### D-3【必须】写清自检脚本与 Review 的分工（触发源：C-1）

- **冲突**：新脚本 `prototype-shared-guard.py` 的检查项与检查项 19 / 22 / 25 高度重叠。不写清就会出现两种偏差——Review 重复报已在自检中修掉的问题（噪音），或反过来认为"脚本过了就不用审"（违反 ADR-5）。
- **修法**：在检查项 14 补充一句——生成侧自检结论是**线索不是结论**；脚本退出码 0 不代表通过（沿用既有"退出码 0 不代表无遗漏"口径）；Review 只做语义与闭环判断，不重复做字符串级判定。
- **边界**：仍遵守 ADR-5，**不得**把该脚本接入 Review 作为阻塞条件。

### D-4 验收

- 逐项确认检查项 19 / 22 / 25 的新表述与 B-2 最终下沉清单一致
- 确认 review SKILL 第 7 步读取要求未被 A-4 误改
- 跑回归套件（含 `test-resource-integrity.py` 的引用路径检查）
