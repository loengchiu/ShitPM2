## 3. 根因证据

### RC-1｜上游没有把数据结果拆成可确认的产品事实

- **根因描述**：Align 和 Design 只要求保留或考虑“展示字段、统计指标、判断、计算、时间、统计口径、数据来源”，没有定义一个重要数据结果必须回答哪些问题，也没有按直接数据、派生数据、汇总统计和周期结算分级。模型可以用“系统生成”“系统统计”“上游汇总”完成字段来源列，却没有被迫暴露权威值、范围、更新、公式和异常中的未知。
- **复现步骤**：
  1. 读取 `references/design-analysis-protocol.md:92-95` 和 `references/design-writing.md:77-105`；
  2. 检查 `contracts/context-loading.manifest.json:63-87` 的 Design cards；
  3. 对照能源数据监测、智慧停车区、租金清分的正式 Design/PRD。
- **复现结果**：规范包含“统计口径”“字段来源”等名词，但没有逐数据结果完成判据；Design cards 没有 data；真实 Design 可以保留“系统统计/计算”并进入下游。
- **为什么不是表象级补丁**：只给租金清分补账期或给停车区补几个公式，换成金额汇总、告警数量、完成率、排名或同比仍会复现。
- **现有机制为什么没解决**：Design 自检检查事实是否有落点，却没有检查每个重要数据结果是否闭合；“金额与统计口径属于高影响项”只能禁止推断，不能帮助识别具体缺了什么。
- **证据边界**：
  - **已证明**：规范粒度和 Design card 确实缺少数据专项责任，三个真实项目存在对应产物缺口。
  - **仅推断**：并非每个存量 Design 都存在该问题；现金流量分析映射展示了部分正向结果。
  - **待验证**：引入数据口径闭包后，模型是否能在同一输入下稳定发现缺口，由 T-6/T-7 A/B 验证。

### RC-2｜PRD 的验收单位和章节落点错误

- **根因描述**：PRD 当前以页面、动作和 `4.x.6` 为核心验收单位。统计页只要整体提到来源、时间和计算，就可能被认为完成；没有要求逐个重要数据结果闭合。同时 `4.x.5` 缺少规则放置指导，`4.x.7` 却天然提供“来源或约束”列，导致公式和口径被压缩到字段表。
- **复现步骤**：
  1. 读取 `templates/prd.md:71-96`；
  2. 读取 `references/prd-writing-rules.md:23-81` 和 `:116-158`；
  3. 对照能源监测 PRD `:134-140` 与 `:194-199`、停车区 PRD `:724-742`。
- **复现结果**：模块正文能列出指标，字段表能标记“系统统计或计算”，但读者仍无法逐项还原来源、范围、公式、精度和更新。
- **为什么不是表象级补丁**：问题来自完成判据和章节职责，不是某个字段忘记补充；所有多指标页面和跨页面复用规则都会受影响。
- **现有机制为什么没解决**：`4.x.6` 自包含目标把公共规则与页面应用混在一起；字段表禁止替代动作正文，但没有明确禁止字段表成为关键数据口径的唯一落点。
- **证据边界**：
  - **已证明**：现有模板和规则存在明确的放置引导空白，真实产物出现了相同分散模式。
  - **仅推断**：章节结构是高概率诱因，不代表所有模型都会把规则放入字段表。
  - **待验证**：改为模块自包含并明确 `4.x.5/4.x.6/4.x.7/4.x.9` 分工后，是否减少重复又提升可读性。

### RC-3｜适用上下文和示例没有稳定到达生成动作

- **根因描述**：当前 dashboard 示例质量较高，但不是 module pass 默认内容；Design 没有 data card；Skill 也没有在识别数据型模块后显式追加 data card 和对应示例的完成条件。
- **复现步骤**：
  1. 读取 context manifest 中 Design card 和 PRD example_sections；
  2. 按当前 `spm-prd` 命令执行 module pass，不额外传 dashboard example；
  3. 查看输出 pack 的 section IDs。
- **复现结果**：默认只包含 simple-readonly 与 multi-role-state 示例，统计型示例是否出现依赖执行者主动追加参数。
- **为什么不是表象级补丁**：即使参考文件写得正确，只要分支指针弱或未装载，实际生成仍不会稳定使用。
- **现有机制为什么没解决**：manifest 支持 card/example 按需选择，但当前 Skill 没把数据类型判定与参数选择绑定为完成条件。
- **证据边界**：
  - **已证明**：当前选择关系和默认装载内容可由 manifest 与 context-pack 输出直接验证。
  - **仅推断**：模型是否因为没看到示例而遗漏，需要 A/B 辅助判断，不能只凭上下文清单断言。
  - **待验证**：新增 data card 和三档示例后，非数据页面不加载、数据页面能准确加载。

### RC-4｜现有验证证明结构存在，不能证明数据结果可解释

- **根因描述**：lint 和 consistency 正确地只承担确定性问题，但历史计划和测试容易把页面落点、字段出现和脚本退出码当成主要回归证据；Design/PRD Review 又没有逐数据结果任务式试读标准。
- **复现步骤**：
  1. 运行或阅读页面正文落点测试；
  2. 使用只有“展示统计指标”的正文；
  3. 对照研发需要回答的来源、范围、时间、聚合、公式、更新和异常问题。
- **复现结果**：页面落点判断可以正确通过，但数据语义仍不可开发。
- **为什么不是表象级补丁**：增加“系统统计”等关键词 warning 只能制造误报，不能理解业务口径；必须改变生成自检和人工 Review 的任务。
- **现有机制为什么没解决**：旧验收侧重页面落点、末模块摘要化和结构冲突，没有将“给定样例记录能否算出唯一结果”作为产物层通过条件。
- **证据边界**：
  - **已证明**：确定性检查边界明确，不能覆盖语义完整性。
  - **仅推断**：所有存量 Review 都漏检尚未证明，本轮只证明当前契约没有强制逐数据结果回答。
  - **待验证**：新 Review 责任能否稳定区分完整、缺失和不适用数据项。

  - 普通直接数据的篇幅没有无理由显著增加。
- **不能据此宣布的结论**：单个 A/B 不能证明所有领域稳定。

#### T-7｜四类真实项目任务式试读

- **输入**：现金流量分析映射、能源数据监测、智慧停车区、租金清分的现有 Design/PRD。
- **动作**：
  - 现金流量分析映射验证直接计数正例不会被过度扩写；
  - 能源数据监测验证指标、比例、来源、刷新和字段表分散问题；
  - 智慧停车区验证平均值、汇总、趋势、下钻和“主题指标”泛化；
  - 租金清分验证周期锚点、起止边界、取数版本、公式、精度、尾差和重算锁定。
- **必须留下的证据**：每个样本的已确认事实、缺失事实、适用数据档位、试读问题答案和上游回退位置。
- **完成判据**：
  - 正向事实被保留，未因新规则制造不存在的复杂性；
  - 负向缺口能定位到 Align/Design/PRD/Review 中正确一层；
  - 任何未确认业务规则均未写成建议默认值；
  - 正式项目文件哈希与 T-0 相同。
- **不能据此宣布的结论**：不能宣布四个项目的正式 PRD 已修复。

#### T-8｜分层收口与执行报告

- **输入**：T-0~T-7 全部证据。
- **动作**：回读修改文件，运行 CRLF-aware diff check、目标测试和 host verify；生成执行报告；删除临时完整 PRD、副本、worktree 和服务。
- **必须留下的证据**：最终 git diff、测试结果、A/B 摘录、真实项目哈希对照、临时目录清理结果和三层结论。
- **完成判据**：
  - 每项改动能追溯到 RC-1~RC-4；
  - 规范、实现、产物分别有结论；
  - 所有失败、未评估和未验证事项如实保留；
  - 未 commit、未 push、未修改正式业务项目。
- **不能据此宣布的结论**：若 T-6 因模型接口阻塞或 T-7 未完成，只能报告部分完成。

### 7.2 每项改动卡

#### F-1｜数据口径闭包唯一参考

- **表象**：各阶段只提“统计口径”，没有统一可执行责任。
- **根因**：RC-1。
- **根因证据**：Design 协议概括项、缺 data card、真实 Design 的“系统统计/计算”。
- **修复层**：规范层。
- **修改内容**：新建共享参考，定义触发、四档责任、同名一致性、未知边界和试读问题。
- **不修改哪一层**：不写项目公式，不改业务产物，不新增程序判断。
- **最终产物证据**：完整/缺失输入 A/B 能分别生成和阻断。
- **仅有哪种证据时仍不能宣布完成**：只有新 reference 文件时不能宣布完成。

#### F-2｜上游 Align/Design 数据事实形成

- **表象**：PRD 到写作阶段才发现来源、时间、公式和精度缺失。
- **根因**：RC-1。
- **根因证据**：三真实项目 Design 缺口和现有 Align/Design 完成判据。
- **修复层**：规范层与上下文实现层。
- **修改内容**：决策簇、Design data card、规则拥有者、Design 自检和 Design Review。
- **不修改哪一层**：不让 Design 自动选择业务口径，不修改 Prototype。
- **最终产物证据**：缺失输入在上游形成 pending decision，PRD 不继续补造。
- **仅有哪种证据时仍不能宣布完成**：只有 data card 可加载时不能宣布完成。

#### F-3｜PRD 模块自包含和数据规则落点

- **表象**：重要规则散落在字段说明，正文只列指标。
- **根因**：RC-2。
- **根因证据**：模板章节引导与能源/停车 PRD。
- **修复层**：规范层。
- **修改内容**：明确 `4.x.5/4.x.6/4.x.7/4.x.9` 职责，将自包含单位改为单业务模块。
- **不修改哪一层**：不增加全局指标字典，不要求每页固定宽表。
- **最终产物证据**：新 PRD 可在模块内连续读出公共规则和页面应用。
- **仅有哪种证据时仍不能宣布完成**：只有模板注释更新时不能宣布完成。

#### F-4｜数据上下文与三类示例按需装载

- **表象**：好示例存在但数据型模块不一定读取。
- **根因**：RC-3。
- **根因证据**：manifest 默认 examples 与 Skill 命令。
- **修复层**：实现层。
- **修改内容**：manifest 增加 data card 和 direct-data、aggregate-data、periodic-calculation 示例键；Skill 根据适用性显式选择。
- **不修改哪一层**：不修改 context-pack 的选择算法与阶段模型（D-8 授权的 unknown 归一一行除外），不增加关键词识别。
- **最终产物证据**：pack 输出与 A/B。
- **仅有哪种证据时仍不能宣布完成**：只有 manifest JSON 通过时不能宣布完成。

#### F-5｜Design/PRD Review 数据结果试读

- **表象**：结构检查通过但数据仍不可解释。
- **根因**：RC-4。
- **根因证据**：页面落点测试和当前 Review checklist。
- **修复层**：规范层与产物验收层。
- **修改内容**：逐重要数据结果回答八类适用问题，以第二种合理实现作为失败信号。
- **不修改哪一层**：不新增自动语义检查器，不把 Review 设为门禁。
- **最终产物证据**：正例不误报、负例能定位到上游。
- **仅有哪种证据时仍不能宣布完成**：只有 Review 文档新增检查项时不能宣布完成。

#### F-6｜同模型 A/B 与真实项目验证

- **表象**：过去容易用 lint、脚本和规则文字证明质量。
- **根因**：RC-4。
- **根因证据**：旧计划主要验证页面落点与检查器，缺少逐数据结果的同输入产物对照。

- **不修改哪一层**：不正式回修业务项目。

## 8. 失败/停止条件

| 触发条件 | 说明 | 处理动作 | 是否允许继续 |
|---|---|---|---|
| A/B 无法固定同一模型、同一输入 | 无法归因规则变化 | 停止 T-6，记录阻塞；其他规范工作可完成但整体最多部分完成 | 条件允许 |
| 修改 context-pack 生产算法超出 D-8 授权范围 | D-8 仅授权适用性 unknown 一行修复，其余生产算法改动超出最小实现边界 | 停止并提出新增决策，不自行扩展 | 否 |
| 数据规则在多个文件出现相反或重复定义 | 唯一事实源失败 | 停止后收敛到共享参考，删除重复语义 | 否 |
| 非数据简单页面也加载复杂数据示例 | progressive disclosure 失败 | 回到 manifest/Skill 选择逻辑修正 | 否 |
| 完整输入的新 PRD 只增加套话，没有增加可回答事实 | 产物层无改善 | 回到规范和示例修正，不宣布完成 | 否 |
| 缺失输入的新 PRD 仍补造周期、公式、范围或精度 | 高影响边界失败 | 回到 Align/Design 停止规则修正 | 否 |
| 正式业务项目文件哈希变化 | 超出本轮范围 | 立即停止，恢复本轮误改并核验 | 否 |
| JSON 无法解析或 context selection 失败 | 运行时实现损坏 | 修复后重跑目标测试 | 否 |
| 仅测试通过但 A/B/试读未完成 | 产物证据不足 | 标记部分完成，不得宣布完成 | 否 |
| 出现既有基线失败 | 可能与本轮无关 | 记录原始失败，区分基线与本轮，不顺手扩大修复 | 视影响 |

## 9. 最终验收

### 9.1 规范是否正确

- **权威文件**：`references/data-definition-rules.md` 及各阶段薄指令、Review checklist、PRD 模板。
- **规则一致性证据**：全仓搜索数据口径、统计口径、系统统计、系统计算、字段来源、自包含等相关表述；逐项确认没有第二套不同清单。
- **冲突表述检查**：重点检查“只读 `4.x.6`”旧规则、字段表职责、统计页旧专项、Align 单问题规则与新决策簇规则。
- **高影响未决事项**：所有具体项目公式、周期、范围、精度和数据版本仍属于业务项目待确认，不在通用规范中拍板。
- **结论**：执行后填写 `[通过 / 部分通过 / 未通过]`。

### 9.2 实现是否正确

- **修改文件**：context manifest、`context-pack.py` 适用性 unknown 一行修复（D-8）和直接受影响的现有测试；其余生产脚本不修改。
- **确定性行为证据**：JSON 解析、context section stage、card/example 正选与非适用不选、适用性 unknown 不装载、资源完整性、host verify。
- **消费者/回归证据**：Design 和 PRD context pack 实际输出 section IDs；Codex bundle 映射验证。
- **基线失败与本轮失败**：执行报告分别记录，不能把既有失败算作本轮失败，也不能用既有失败掩盖本轮回归。
- **结论**：执行后填写 `[通过 / 部分通过 / 未通过]`。

### 9.3 产物是否有效

- **目标产物**：两组同模型同输入 A/B、四类真实项目试读记录。
- **事实对照证据**：输入哈希、模型标识、旧新规则版本、输出差异和每项事实来源。
- **真实场景/研发试读证据**：抽样数据结果必须能回答业务含义、来源、范围、时间、纳入排除、计算、更新和异常；存在改变结果的第二种合理实现即失败。
- **用户可见或可操作结果**：后续生成的 PRD 应把关键数据口径放入可连续阅读的模块正文，而不是只写指标名或字段表短语。
- **仍未验证的内容**：未正式回修四个业务项目，不能声明其现有 PRD 已解决；未覆盖所有行业和数据类型。
- **结论**：执行后填写 `[通过 / 部分通过 / 未通过]`。

### 9.4 总结结论

- **规范层**：执行后填写 `[通过 / 部分通过 / 未通过]`。
- **实现层**：执行后填写 `[通过 / 部分通过 / 未通过]`。
- **产物层**：执行后填写 `[通过 / 部分通过 / 未通过]`。
- **本轮总状态**：三层全部通过才可填写“已完成”；否则填写“部分完成”“已停止”或“未完成”。
- **不得省略的负面结论**：A/B 未满足同模型同输入、真实项目只读试读未完成、业务项目未正式回修、或仍存在未确认数据事实时，必须逐项写明。
