## 1. 判据与用法

本计划每一条都必须回答三个问题，答不全不得进入执行序列：

1. **这个表象由哪条根因产生？**（证据可复现，非推断）
2. **该根因还产生了哪些表象？**（一个根因通常解释多个问题）
3. **修掉根因后，原先准备做哪些表象级改动可以删除？**（删除项要显式列出）

反面判据：如果一条改动只能修掉报告里的某一个具体实例，而同类实例换一种输入还会复现，则它不进入本计划 —— 说明根因未找对。

## 3. 根因清单

### RC-1｜Design 事实读取存在多套并行机制，新流程仍消费已宣告退场的旧机制

**契约原文**（`contracts/metadata-anchor-rules.md` §五职责划分表）：

> `stage-prep.py`：**旧版兼容：新主流程不默认调用**；仅旧项目兼容诊断

**实际实现**（`prd-consistency-check.py`）：

| 维度 | `design-index.py`（新机制） | `stage-prep`（契约声明退场） | 检查器实际使用 |
|---|---|---|---|
| pages / blocks / fields / operations | ✅ `:640-643` | ✅ | **index 优先**（`:1997` `_compare_indexed_structure`） |
| states | ✅ `:644` `_extract_states(pages)`，含 `ATTRIBUTE_ALIASES` 别名表（`:61`） | ✅ | ❌ **stage-prep**（`:2002`）；为空时**第三条路径**：用 **PRD 侧提取器** `extract_prd_states` 去读 **Design 文本**（`:2005-2010`） |
| permissions | ❌ 无实体（`roles` 在 page/operation 的 `attributes` 里，不必另提） | ✅（坏的） | ❌ **stage-prep**（`:2011`） |
| modules / non_page_fields | ❌ | ✅ | ❌ **stage-prep**（`:2012`、`:2014`） |
| page.roles / operation.roles | ✅ **必填属性**（`:34`、`:39-47`）、结构化提取、已过校验、真实项目 100% 填写 | ❌ 不产出 | ❌ **无人消费** ← P1-4 的现场 |

`design-index.py` 是唯一带 `REQUIRED_ATTRIBUTES`（必填属性表）、`ATTRIBUTE_ALIASES`（别名归一）、`_extract_states`（含散文过滤黑名单）的**权威 Design 读取器**；检查器只用了它的一半（结构比对），另一半（states/permissions/modules）仍走旧机制。

**为什么它不是「补关键词表」能修的**：`metadata-anchor-rules.md:42` 已登记过同类失败 ——「状态/权限提取到章节标题」，当时的修法是在状态侧打补丁（`_extract_states_from_content` 改解析列表项）。同一个 bug 类今天在权限侧原样复现，说明**问题在旧机制的启发式本质，不在某一项关键词**。

**由此解释的表象**：P1-4（权限恒空）、P0-1 的 Design 侧一半、P1-3（八列覆盖不足）、P2#7（两套机制各写一份属性定义）。

### RC-2｜比对模型 `permissions[{page, role}]` 没有任何一方的产物背书

**两侧的真实产物形态**：

| 侧 | 规范依据 | 实际形态 |
|---|---|---|
| Design | `templates/design-module.md` 页面属性「适用角色」、操作表「适用角色」列（必填） | **页面/操作 → 角色**，单侧属性，无「权限实体」 |
| PRD | `templates/prd.md:52`、`references/prd-writing-rules.md:17,87` | **4.x.3「角色 × 业务能力」矩阵**，行=角色、列=能力 |

**检查器比的是 `permissions[{page, role}]` 二元组** —— 这个形态**两侧都不产出**。它只存在于已退场的旧 metadata 机制（`metadata-anchor-rules.md:65` 的 `PERM-` 前缀、`:109` 的 `permissions.json`）。新机制里没有任何权限实体定义。

后果：两侧都只能靠启发式「猜」出这个形态，猜法不同 → 结果只能是**恒空**（`not_evaluated`）或**恒假红**（`deterministic_conflict`），不存在第三种可能。这正是当前观测到的两个极端状态。

**为什么它不是「修解析 bug」能修的**：即使读取器全部修好、Design 侧正确读出 66 页 roles，PRD 侧的能力列仍然没有到页面名的映射 —— 已实测模拟：`missing=66`、`hallucinated=["角色与权限"]`、`exit=1`。**修读取器修不掉「两侧没有共同连接键」。**

**由此解释的表象**：P0-1（能力列当页面名）、P1-4 的另一半。

## 4. 修复方案（按根因）

### F1（修 RC-1）Design 事实读取收敛到单一权威机制

**原则**：`design-index` 可用时，**所有维度从索引取**；`stage-prep` 只在索引不可用（旧格式项目）时作为显式回退，并标记来源。

| 步骤 | 内容 |
|---|---|
| F1.1 | `design_permissions` 改为从索引的 `page.attributes.roles` / `operation.attributes.roles` 聚合为 `{page, role}`；聚合规则见下方「角色切分」 |
| F1.2 | `design_states` 改为读索引已有的 `states`（`:644`），**删除**「stage-prep → 空 → `extract_prd_states(design_text)`」这条第三路径 |
| F1.3 | 索引不可用时保留 legacy 回退，但输出必须带 `design_source: "legacy"` 与告警（与 F3 合并） |
| F1.4 | `modules` / `non_page_fields` 索引当前无对应概念：**本期不扩索引**，仅标注为待收敛项（见待决策 D4），避免一次性重写 |

**角色切分规则（实测锚定，勿凭推断）**：
1. **先剥括号再切分**（顺序不可反）：`re.sub(r'[（(][^）)]*[）)]', '', v)` —— 括号内的限定说明可能含 `、`，先切会被误拆。
2. 按 `[、,，；;]` 切分。
3. 排除指代与动态描述：`全部用户`、`全部适用角色`、`当前操作用户`、`原发起人`、`当前整改经办人`，以及「具备…权限的…」条件式描述。
4. `/` 连接保持整体（`项目组长/主审` 是同一角色的两种叫法）。

**验收锚点**：真实项目 `page.roles` / `operation.roles` 填写率 100%（审计系统 66/66 页 + 262/262 操作；租金清分 5/5 + 32/32；能源数据监测 4/4 + 12/12）。

**收敛后的收益**：`stage-prep.generate_design_metadata` 在一致性检查中退场；`_extract_permissions_from_content` 及其关键词表一并失效，P1-3、P2#7 的诱因随之消除。

### F2（修 RC-2）显式定义比对模型的合法性边界

**不是**「再写一个更聪明的映射」，而是**承认并写明：确定性比对只在两侧同为页面/对象语义时成立**。

| PRD 侧形态 | 是否与 Design（页面/操作 × 角色）同构 | 处理 |
|---|---|---|
| 「行 = 对象/页面」矩阵 | ✅ 同构 | 确定性比对，保持现状 |
| 「行 = 角色」能力矩阵（官方模板形态） | ❌ 不同构（列是业务能力，不是页面） | 列标记为 capability，**不进入 page ID 空间**；维度输出 `not_evaluated` |
| 自然语言段落（审计系统等存量） | ❌ 无页面锚点 | 同上 |
| `## 权限汇总` + `### 页面名` + `- role：action`（旧格式） | ✅ 同构 | 保持现状（防回归） |

具体改动：
1. `extract_prd_permission_pages` 排除**权限章节自身标题**（用 `_find_prd_permission_ranges` 返回的 `start` 行号比对，不做标题文本匹配）。
2. 「行 = 角色」分支不产出 page。
3. `both_sides_extracted` 收紧为「两侧都具备 page 语义事实」才放行确定性比对。
4. 不同构时 `permission_evaluation.status = "not_evaluated"`，**输出两侧事实**（Design 角色清单 + PRD 4.x.3 提取结果）供 AI 核对，不得走 `deterministic_conflict`。

**决策点**：是否要恢复权限的确定性比对能力？若要，必须统一两侧口径（改动面大、需回退 09-12 刚定的「角色 × 业务能力」规范、存量 PRD 需迁移）。见待决策 D1。

### F3（修 RC-3）提取器自检：输入存在但输出为空必须报诊断

1. `design-index.py` 增加 `invalid_type` 校验，与 `design-set.py:150` 的 `VALID_TYPES` 对齐（本地常量 + 注释标明同步来源，不跨文件 import，避免循环依赖）。
2. 每个提取维度输出诊断：命中文件数、命中条目数、命中的章节/表头；**提取结果为 0 且输入非空时进入 `errors` 或 `warnings`**。
3. 装载契约加完整性校验：规范文件中的示例块若无对应 marker，报 warning（覆盖 P2#8a）。

**判据**：让「提取器坏了」和「产物真没有」在输出上可区分 —— 这是 RC-3 的根因，逐个加错误码不算修好。

### F4（修 RC-4）枚举 → 与规范同源
