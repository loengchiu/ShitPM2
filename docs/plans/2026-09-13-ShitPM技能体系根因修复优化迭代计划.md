## 3. 根因证据

### RC-1｜跨层语义契约没有稳定落点

- **根因描述**：
  - Design、PRD、Prototype 需要表达同一组页面、字段、操作、状态和权限，但当前体系没有明确区分“产品事实身份”“人读表达名称”“实现锚点”和“业务能力身份”。`design-index.py` 虽生成了内部实体 ID 和父子关系，PRD 检查却主要按名称是否出现在全文中判断，Prototype 主要依赖 `data-page`/`data-field` 等字符串锚点。名称、关系、能力和状态因此被当成同一种东西使用。
  - 这不是单个页面漏写的问题。换一个页面名、字段别名、合并页面或把多个页面动作重组到同一业务闭环，现有机制仍会出现假红、假绿或只能人工解释的大量输出。
- **复现步骤**：
  1. 查看 `D:/work/ShitPM/scripts/python/design-index.py` 的 `REQUIRED_ATTRIBUTES`、实体 `id` 生成和 `parent/page_id` 关系。
  2. 查看 `D:/work/ShitPM/scripts/python/prd-consistency-check.py` 的 `compare_indexed_structure`：页面/字段缺失主要按归一化名称是否出现在 PRD 正文中判断，操作不做一对一匹配。
  3. 查看 `D:/work/ShitPM/scripts/python/prototype-consistency-check.py`：Prototype 侧按显式 `data-*` 字符串锚点与 Index 名称集合比较。
  4. 在审计系统和租金清分上复跑，观察缺失、变体、未锚定和语义判断项目同时出现。
- **复现结果**：
  - 设计索引已具备 `id`，但下游并未形成统一的“实体身份 + 父子关系 + 事实类别”使用口径。
  - 审计系统 PRD 检查出现 `missing=15`、`hallucinated=1`，而租金清分结构项为 0 但权限仍未评价；这说明结构名称通过不等于跨层事实闭环。
  - 小程序在 Index 指纹失效后回退 legacy，假缺失放大到 `missing=173`、`hallucinated=15`——同一份 PRD，仅读取路径不同就产生百量级差异，是“同名≠同实体、Index 失效放大假红”的最强活证据。
- **为什么不是表象级补丁**：
  - 只增加同义词、放宽模糊匹配、补更多 `data-*` 或把缺失结果改成 warning，都不能解决“同名不等于同实体、业务能力不等于页面、状态出现不等于状态机一致”的问题。
- **现有机制为什么没解决**：
  - Design Index 的职责被写成“派生索引”，但没有把下游可消费的身份/关系契约写成唯一规则。
  - PRD 的人读正文不能直接依赖实现锚点，Prototype 又不能仅凭 UI 文案证明完整业务语义；两个下游缺少分层的比较边界。
- **证据边界**：
  - **已证明**：Index 产生实体 ID/父子关系；PRD 检查仍有全文名称匹配和不做操作一对一比较；Prototype 检查依赖显式锚点。
  - **仅推断**：统一身份/关系契约会显著减少当前大规模假红和语义解释成本，但收益仍需同一输入的前后对照验证。
  - **待验证**：一个复杂真实模块和一个小型模块在采用新契约后，是否能减少错误分类、人工复核项和下游返工。

### RC-2｜主流程仍存在多套读取路径和隐式 legacy 回退

- **根因描述**：
  - 规范已经声明 `stage-prep.py` 只是旧版兼容，但 `prd-consistency-check.py` 仍直接加载其 `generate_design_metadata`；状态仍由另一套旧提取逻辑提供。于是“当前格式是否被理解”被旧解析器的兼容能力掩盖，工具无法明确告诉调用者是当前格式不支持、事实不存在还是解析路径失效。
- **复现步骤**：
  1. 查看 `D:/work/ShitPM/scripts/python/prd-consistency-check.py` `_load_design_entities_from_md`，确认其调用 `load_sibling("stage-prep.py", "stage_prep").generate_design_metadata(...)`。
  2. 查看同文件状态来源分支，确认 `design_state_source = "legacy"` 或 `"legacy-prd-extractor"`。
  3. 对照 `D:/work/ShitPM/USAGE.md` 中“主流程不依赖 `stage-prep.py`”的声明。
  4. 在真实项目运行 PRD 检查，观察结构、状态、权限分别来自不同路径。
- **复现结果**：规范和实现互相矛盾；当前真实输出即使 `design_index` 已启用，`state_source` 仍为 `legacy`。
- **为什么不是表象级补丁**：
  - 增加一条回退、再包一层统一函数或将旧输出改名，都会继续维持多源读取和静默降级；下一种 Design 表达仍会复现。
- **现有机制为什么没解决**：
  - 没有为“当前格式主路径”“legacy 兼容路径”“不可评估路径”定义严格切换条件和停止语义。
  - `load_verified_index` 已存在，却没有被所有需要 Design 结构的消费者统一使用。
- **证据边界**：
  - **已证明**：当前 PRD 检查主结构和状态仍存在 legacy 路径。
  - **仅推断**：删除主流程 legacy 回退后，部分存量项目会更早暴露真实格式问题；这是预期的可见性提升，不等于质量退化。
  - **待验证**：现有 7 个真实项目中有多少能直接由当前 Index 读取，多少需要先修 Design 格式或明确标为 legacy。

### RC-3｜权限与状态没有共同的业务语义模型

- **根因描述**：
  - Design 当前常按“页面/操作 × 角色”表达权限，PRD 可能按“角色 × 业务能力”或自然语言表达；页面角色、操作责任、能力授权、数据范围和状态前置条件不是同一维度。当前脚本无法可靠映射，就只能输出 `not_evaluated` 或 `cannot_extract`。
  - 状态同样存在层次混淆：页面主要状态、对象生命周期状态、过程展示状态和状态迁移边都被不同解析器部分提取。
- **复现步骤**：
