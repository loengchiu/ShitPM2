## 0. 已确认结论

### 0.1 要解决的问题

研发和测试几乎没有时间阅读 PRD。继续要求他们以 PRD 作为日常执行入口，不符合真实协作行为。

本轮将 Mark 从“原型上的补充浮窗”升级为：

> 原型主规格层：只承载原型无法直接展示、但研发实现和测试判断必须知道的内容。

日常阅读关系调整为：

| 内容 | 主要承载位置 |
|---|---|
| 原型已经可见的页面、字段、按钮、布局和普通交互 | Prototype |
| 原型无法直接展示，但影响实现或验收的条件、规则、权限、状态、异常和口径 | Mark |
| 冲突时用于裁决的完整产品事实 | Design |
| 完整归档、评审和跨团队说明 | PRD |

PRD 继续保留，但不再作为研发和测试日常必读材料。

### 0.2 内容准入门槛

进入 Mark 的内容必须同时满足：

1. 原型无法直接展示，或仅看原型无法确认条件、结果和边界；
2. 会影响研发实现或测试判断。

只满足一项，不进入 Mark。

应标内容：

- 字段的必填、只读、条件显隐、默认值、来源、单位和精度；
- 金额、统计和数据计算口径；
- 操作前置条件、执行后果、撤销和回滚；
- 不同状态下的可用动作、状态迁移和终态；
- 角色、操作和数据范围权限；
- 0 值、负数、重复提交、外部系统失败等异常边界；
- 字典表、旧功能、外部数据和模拟数据依赖；
- 原型无法直接观察的验收预期；
- Design 中仍待确认的高影响事实。

不标内容：

- 页面标题、字段名、按钮名等原型已经可见的文字；
- 页面布局、组件样式和视觉层级；
- 可直接观察的列表字段、按钮存在性和普通交互；
- 大段 PRD 原文、模块背景和业务价值描述。

### 0.3 内容表达目标

每个角标按需回答：

- 原型上看不出来的规则是什么；
- 在什么条件、角色或状态下成立；
- 系统执行后的结果是什么；
- 测试如何判断通过或不通过；
- 规则来自哪个 Design 文件、章节，处于什么确认状态。

内容按需分组：实现规则、权限与数据范围、状态与操作、异常与边界、数据口径、验收判断、来源与确认状态。没有内容的分组不展示。

### 0.4 最终交付判据

> 研发和测试只打开带标注原型，不打开 PRD，也能知道页面怎么实现、异常怎么处理、权限怎么限制、结果是否符合预期。

## 3. 根因证据

### RC-1｜Mark 的定义仍是“模块摘要展示”，不是“不可见规格层”

- **根因描述**：当前 Skill 要求按模块聚合 Design/PRD 内容，并把原始描述、业务逻辑、前置条件和异常流程放进浮窗。它没有先判断哪些信息已经由原型表达，也没有区分哪些内容直接影响实现和验收。
- **复现步骤**：读取 Mark Skill 的初始化步骤 3、4 和硬规则，观察没有“原型直接可见则不标”的排除规则。
- **复现结果**：执行者会倾向把模块需求全部搬入标注，而不是只补充原型缺失的规格。
- **为什么不是表象级补丁**：只增加“少写一点”或“精简内容”仍无法判断哪些该保留；换一个模块后仍会重复可见内容。
- **现有机制为什么没解决**：完成条件是“关键需求点全部有定位”，不是“原型与 Mark 合起来足以实现和验收”。
- **证据边界**：已证明规范缺少可见性判断；实际项目重复程度需用 T-4 样例验证；新门槛能否稳定剔除重复内容待验证。

### RC-2｜缺少研发/测试事实提取模型和完整性判据

- **根因描述**：当前规范没有说明研发需要条件、结果和边界，测试需要可判断的预期。因此内容可能很多，但仍缺少关键实现条件或验收口径。
- **复现步骤**：将当前“按模块聚合”规则与测试经验中的字段、状态、权限、边界和依赖清单对照。
- **复现结果**：Mark 可能展示业务描述，但研发仍不知道删除是否影响关联账单，测试仍不知道 0 元、审批中或跨服务区时应看到什么。
- **为什么不是表象级补丁**：只在示例中补一两条规则，换页面后仍会漏掉权限、状态或异常类别。
- **现有机制为什么没解决**：没有“每个不可见事实必须有角标或无承接位结论”的闭合判据。
- **证据边界**：已证明缺少事实分类和完整性判据；分类是否导致内容膨胀需在 T-4 评估。

### RC-3｜数据结构只支持一段文本，无法区分实现规则和验收判断

- **根因描述**：`annotations.js` 只有 `title` 和 `content`，`MarkLayer` 直接渲染正文，无法稳定表达“条件、结果、异常、验收”等层次。
- **复现步骤**：读取 reference 的“标注数据”和 `MarkLayer` 示例，观察只有 `title`、`content`。
- **复现结果**：所有内容被压成一段文本，长规则难以定位。
- **为什么不是表象级补丁**：只修改示例文案而不改结构，下一次仍会退化为长段落。
- **现有机制为什么没解决**：没有规定 section、source 和 status 的数据形状。
- **证据边界**：已证明当前结构不支持分组和来源状态；扫读效率需实现后验收。

### RC-4｜来源只到“Design/PRD”层级，不能支撑追溯和冲突判断

- **根因描述**：当前来源字段是泛称，Mark 无法说明具体取自哪个文件和章节，也无法统一展示确认状态。
- **复现步骤**：读取 Mark Skill 第 51 行和 reference 第 159 行，观察没有文件、章节和状态字段。
- **复现结果**：浮窗只能显示“内容来源：Design 文件”，不能回答“来自哪一条”。
- **为什么不是表象级补丁**：只在正文末尾手写文件路径仍可能漏章节，也无法统一处理待确认状态。
- **现有机制为什么没解决**：数据结构没有 source/status 字段。
- **证据边界**：已证明来源不够具体；多文件 Design 下的追溯效果待 T-4 验证。

### RC-5｜缺少“无承接位”的合法出口

- **根因描述**：当前流程要求把需求点挂到组件上，但没有规定跨页面、后台、外部依赖或缺失页面状态时如何处理。
- **复现步骤**：选择只有后台影响、没有页面入口的规则，按当前流程寻找标注落点。
- **复现结果**：流程除强行挂载外没有其他合法路径。
- **为什么不是表象级补丁**：增加页面级标注不能解决不存在页面或状态的问题。
- **现有机制为什么没解决**：没有输出“无承接位”及建议补页面的步骤。
- **证据边界**：已证明规范缺少出口；错误挂载减少程度需 T-4 验证。

### RC-6｜原型成为主入口后，缺少可见事实的可信门槛

- **根因描述**：当前 Mark 只检查源码工程存在，不核对页面标题、字段名、按钮名、状态名和金额格式。原型成为主规格后，这些错误会被研发直接执行。
- **复现步骤**：读取当前前置检查，对照测试经验中的页面标题错误、金额单位和精度不一致。
- **复现结果**：Mark 可以在错误原型上继续标注，让测试误以为该原型已经可执行。
- **为什么不是表象级补丁**：只在报告里提醒“请检查原型”不能阻断错误传播。
- **现有机制为什么没解决**：没有把可见事实与 Design 冲突定义为 Mark 的停止条件。
- **证据边界**：已证明前置检查不核对可见事实；最小核对能否覆盖主要风险需 T-4 验证。

- 错误可见事实会阻断 Mark，而不是被包装成可信规格。

产物层不接受的替代证据：

- `npm run build` 通过；
- 浮窗能打开；
- 角标数量齐全；
- 某份 Mark 看起来内容很多。

产物层完成条件：

- 研发/测试试读或等价角色扮演能在不打开 PRD 时回答实现问题；
- 样例覆盖权限、状态、异常、金额口径和依赖；
- 待确认事实显示为待确认；
- 用户确认内容达到“主规格层”标准。

## 7. 每步完成判据

### 7.1 步骤判据

#### T-0｜基线与验收样例

- **输入**：当前 Mark Skill、reference、Prototype 指向、USAGE、模型建议、测试经验。
- **动作**：核对行号和规则；列出复杂业务规则、待确认事实、无承接位事实三个场景；确认不覆盖已有修改。
- **必须留下的证据**：文件路径、行号、场景清单、当前规则摘录。
- **完成判据**：三个场景均对应当前缺口；目标文件和消费者真实存在；未把历史 plan 当成当前事实源。
- **不能据此宣布的结论**：不能据此宣布 Mark 内容已经足够。

#### T-1｜重写 Mark 内容规范

- **输入**：T-0 基线、D-1/D-2/D-3 决策。
- **动作**：定义双重门槛、应标和不标清单、按需内容分组、每页完成判据、无承接位和可见事实冲突停止规则。
- **必须留下的证据**：修改后的 Skill 全文和逐条回读。
- **完成判据**：执行者能直接判断内容是否进入 Mark；无旧聚合规则；不引入脚本；明确不替代 Review。
- **不能据此宣布的结论**：不能仅凭规范文字宣布实际标注产物可用。

#### T-2｜结构化标注展示

- **输入**：T-1 新规则。
- **动作**：将数据改为可表达多个 section；增加 source 和 status；渲染 section 标题和正文；保留角标定位和副本边界。
- **必须留下的证据**：数据样例、组件代码、构建结果、浮窗截图或 DOM。
- **完成判据**：单/多 section 和待确认状态可展示；来源到文件和章节；无外部依赖；构建通过。
- **不能据此宣布的结论**：构建通过不能证明内容选择正确。

#### T-3｜术语与调用链收敛

- **输入**：新 Mark 定位、T-1/T-2 产物。
- **动作**：更新 `spm-prototype` 转交说明、USAGE 定位和模型建议；搜索其他 Mark 描述，只修正冲突内容。
- **必须留下的证据**：修改文件、冲突搜索结果、回读记录。
- **完成判据**：活动规则中只有一个 Mark 内容权威定义；`spm-prototype` 不重复维护内容规则；模型建议与新风险一致。
- **不能据此宣布的结论**：文档一致不能证明研发/测试愿意实际使用。

#### T-4｜临时项目验收

- **输入**：新 Skill、新 reference、临时项目。
- **动作**：初始化复杂规则原型，加入字段权限、状态限制、金额口径、异常回滚、待确认和无承接位场景；生成 Mark；由另一执行角色仅打开带标注原型回答问题。
- **必须留下的证据**：问题清单、回答记录、角标截图、无承接位报告、原始产物未修改的证据。
- **完成判据**：不打开 PRD 能回答必答问题；无可见内容重复；待确认明确；无承接位未硬挂；构建和主要交互通过。
- **不能据此宣布的结论**：不能宣布所有真实项目历史 Mark 已升级。

#### T-5｜最终验收与执行报告

- **输入**：T-0 至 T-4 证据。
- **动作**：回读修改文件；构建和检查交互；汇总三层证据；创建执行报告并记录残留风险。
- **必须留下的证据**：文件差异、构建输出、交互记录、试读结果、执行报告。
- **完成判据**：规范、实现、产物分别有证据；不把构建通过写成内容质量通过；未验证项明确列出。
- **不能据此宣布的结论**：不能宣布真实项目已全面采用 Mark 主规格层。

### 7.2 每项改动卡

#### F-1｜可见性双重门槛

- **表象**：Mark 重复展示原型已经可见的字段和按钮。
- **根因**：Skill 没有“原型不能直接表达且影响实现/验收”的判断。
- **根因证据**：Mark Skill 第 28 行。
- **修复层**：规范层。
- **修改内容**：在提取步骤最前方加入双重门槛和排除清单。
- **不修改哪一层**：不修改 Design、Prototype 和角标定位能力。
- **最终产物证据**：复杂页面 Mark 不含纯可见字段/按钮清单。
- **仅有哪种证据时仍不能宣布完成**：仅凭规则文字或不标数量少，不能证明研发/测试获得足够信息。

#### F-2｜不可见事实分类与完整性自检

- **表象**：权限、状态、异常和口径不稳定进入 Mark。
- **根因**：没有研发/测试事实分类和覆盖闭合条件。
- **根因证据**：当前只有“保留原始描述”，没有事实类别和无承接位出口。
- **修复层**：规范层。
- **修改内容**：加入字段、操作、状态、权限、数据口径、异常依赖、验收判断分类；要求每条不可见事实有角标或无承接位结论。
- **不修改哪一层**：不自动补写 Design 事实，不新增检查脚本。
- **最终产物证据**：T-4 场景中的复杂规则全部可回读。
- **仅有哪种证据时仍不能宣布完成**：覆盖页面数量或角标数量不能证明事实完整。

#### F-3｜section 化展示和来源状态

- **表象**：浮窗是一段长文本，来源只有泛称。
- **根因**：数据结构只有 title、content。
- **根因证据**：reference 第 32 至 43 行和第 159 行。
- **修复层**：实现层。
- **修改内容**：增加 sections、source、status；按需渲染，不强制空 section；来源显示到文件、章节和确认状态。
- **不修改哪一层**：不修改角标定位、拖拽、容器显示和构建架构。
- **最终产物证据**：构建后的浮窗截图和 DOM。
- **仅有哪种证据时仍不能宣布完成**：构建通过不能证明内容选择正确。

#### F-4｜无承接位输出

- **表象**：跨页面、后台或外部依赖规则可能被硬挂或遗漏。
- **根因**：流程没有合法出口。
- **根因证据**：当前 Skill 只要求给关键需求点定位。
- **修复层**：规范层。
- **修改内容**：无承接位时停止该条挂载，输出事实、影响页面、缺失承接和建议处理。
- **不修改哪一层**：Mark 不自动新增页面，不自动修改 Design。
- **最终产物证据**：无承接位场景报告。
- **仅有哪种证据时仍不能宣布完成**：只列问题而不指出影响页面或建议处理，不能视为完整。

#### F-5｜可见事实标前阻断

- **表象**：错误页面标题、字段名或金额格式可能被 Mark 包装成可信规格。
- **根因**：前置检查只确认源码存在。
- **根因证据**：当前初始化步骤 1。
- **修复层**：规范层。
- **修改内容**：标注前最小核对页面标题、字段名、按钮名、状态名、金额单位和精度；高影响冲突停止该页面标注。
- **不修改哪一层**：不做完整 Prototype Review，不自动修复原型。
- **最终产物证据**：冲突样例的停止记录。
- **仅有哪种证据时仍不能宣布完成**：单个页面通过不能证明全站原型正确。

#### F-6｜术语、USAGE 和模型建议同步

- **表象**：Mark 仍被描述为“设计/PRD 标注副本”或低风险辅助动作。
- **根因**：新定位没有同步到调用说明和模型建议。
- **根因证据**：`spm-prototype` 第 122 至 124 行、USAGE 第 271 行、模型矩阵第 30 行。
- **修复层**：规范层。
- **修改内容**：统一使用“原型主规格层/不可见规格标注”术语；按 D-2 调整模型建议；`spm-prototype` 只保留转交。
- **不修改哪一层**：不修改阶段推进逻辑和真实项目状态。
- **最终产物证据**：仓库搜索无冲突表述。
- **仅有哪种证据时仍不能宣布完成**：文档一致不能替代真实产物验收。
