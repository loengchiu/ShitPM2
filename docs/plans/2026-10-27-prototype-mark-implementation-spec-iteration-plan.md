## 3. 根因证据

### RC-1｜标注的内容单元是“规则句子”，不是“研发实现结构”

- **根因描述**：Skill 的应标内容按业务规则类型列举，执行时以 Design 章节为索引逐条摘句。状态机、字段刷新矩阵这类表格结构被改写成零散句子，迁移关系、行列对应和触发条件丢失。
- **复现步骤**：
  1. 打开 Design `租金清分.md`，定位 `#### 状态机：租金账单业务处理状态`（376 行）和 `#### 数据变更后的字段刷新`（254 行）。
  2. 打开 `annotations.js`，检索“状态机”“刷新”。
  3. 对照两者内容。
- **复现结果**：Design 有 17 行状态迁移和 9 类刷新事件；标注只有 2 处 source 路径提到状态机、4 处零散提及刷新，没有任何迁移表或刷新矩阵。
- **为什么不是表象级补丁**：只在账单详情页补两个角标，换成租金测算或结算表仍会缺；执行者仍会按 Design 目录摘句。
- **现有机制为什么没解决**：SKILL `:40-42` 的删除测试、可见性检查、完整性检查只判断“是否重复可见内容”和“是否已有角标”，不判断“是否回答了该元素的实现问题”。
- **证据边界**：
  - **已证明**：状态机和刷新矩阵在标注中缺失。
  - **仅推断**：研发因此需要回 Design 查表，尚未取得研发人员的实际阅读记录。
  - **待验证**：新结构能否让研发不打开 Design 完成状态实现。

### RC-2｜角标聚合维度是 UI 区域，不是可独立回答的问题

- **根因描述**：为控制角标数量和避免同区域重复，按页面和区块聚合，导致一个角标混合多个主题，同一动作的说明被拆到不同角标。
- **复现步骤**：
  1. 读取 SKILL `:30` 和 `:36`。
  2. 统计 `annotations.js` 的角标、section、items 数量。
  3. 搜索“确认应收”，观察其说明分布。
- **复现结果**：25 个角标、68 个 section、164 条 items；“确认应收”在角标 6 和 29 各写一半。
- **为什么不是表象级补丁**：把角标 6 和 29 合并，仍会形成更大的一坨；聚合维度不变，其他动作继续拆散。
- **现有机制为什么没解决**：Skill 没有角标粒度定义，只有“同一区域不重复”，等于把区域当作天然边界。
- **证据边界**：
  - **已证明**：区域聚合导致一标多主题、动作拆散。
  - **仅推断**：改为问题聚合后数量上升但阅读更快，尚未实测。
  - **待验证**：样本页的角标数量和阅读路径。

### RC-3｜准入判据缺少按 UI 元素类型的必答清单

- **根因描述**：Skill 用“原型无法直接展示且影响实现/验收”做准入，再列 9 条业务规则类型。执行者要自行判断某元素适用哪些条目，漏项没有硬信号。
- **复现步骤**：
  1. 读取 SKILL `:22-33` 的准入和应标内容。
  2. 在 `annotations.js` 检索排序、并发、日志、网络、超时、幂等、加载、空态。
  3. 观察命中数。
- **复现结果**：除“无权限”1 处外，其余全部为 0。
- **为什么不是表象级补丁**：逐条补当前页面仍会漏；没有“列表必答排序、操作必答异常”的清单，换页面重演。
- **现有机制为什么没解决**：自检是“是否已有角标”，不是“每个必答维度是否已回答”。
- **证据边界**：
  - **已证明**：规范条目存在但产物缺失。
  - **仅推断**：按元素类型强制必答能稳定补齐，尚未验证。
  - **待验证**：样本页按清单执行后的覆盖率和误报。

### RC-4｜状态语义二值化并默认已确认

- **根因描述**：`status` 只有 `confirmed` 和 `pending`，执行时默认全部 `confirmed`，没有核对事实源中的业务待定项。
- **复现步骤**：
  1. 统计 `annotations.js` 的 status 分布。
  2. 读取 Design `租金清分.md:315` 的“销量租金正式报表映射未确认”。
  3. 查看标注 18 的 status。
- **复现结果**：25 个全为 `confirmed`，0 个 `pending`；销量租金映射未确认仍标 `confirmed`。
- **为什么不是表象级补丁**：只把标注 18 改成 pending，其他项目仍会默认 confirmed。
- **现有机制为什么没解决**：自检只写“待确认内容不得展示为已确认”，没有要求汇总事实源的待定项逐条核对。
- **证据边界**：
  - **已证明**：存在真实待定事实被标为已确认。
  - **仅推断**：增加核对步骤可消除，尚未执行。
  - **待验证**：样本页的待定项能否被完整识别。

### RC-5｜标注与验证包之间没有消费者契约

- **根因描述**：标注来源只指向 Design，不引用验证包规则编号；测试拿到标注后需要自己转成用例。
- **复现步骤**：
  1. 读取验证包 `租金清分.md` 的 CAL/ST/PM 条目。
  2. 在 `annotations.js` 检索这些编号。
- **复现结果**：0 引用。
- **为什么不是表象级补丁**：只在一个角标补一个编号，其他规则仍断。
- **现有机制为什么没解决**：Skill 和 reference 都没有定义标注与验证包的对应关系。
- **证据边界**：
  - **已证明**：两者无引用。
  - **仅推断**：引用能减少测试转写成本。
  - **待验证**：样本页引用后的可读性。

### RC-6｜存量迁移没有路径

- **根因描述**：2026-10-20 计划明确“不批量迁移存量”，之后也没有迁移规则或工具。
- **复现步骤**：

- **复现结果**：`title + content` 单字段，无 sections、source 章节、status。
- **为什么不是表象级补丁**：只重做审计系统一个模块，其余模块仍旧。
- **现有机制为什么没解决**：Skill 的增量更新假设已有新结构，没有旧结构迁移入口。
- **证据边界**：
  - **已证明**：旧结构存在。
  - **仅推断**：迁移成本较高。
  - **待验证**：本轮是否纳入由 D-4 决定。

### RC-7｜一个角标同时服务研发和测试

- **根因描述**：Skill 定义 Mark 同时承载“研发实现和测试判断”，内容不区分读者。
- **复现步骤**：

  2. 观察同一角标内的“角色与去向”和“验收判断”。

- **为什么不是表象级补丁**：删掉验收判断会损害测试；保留则研发仍被干扰。
- **现有机制为什么没解决**：没有读者标记或筛选能力。
- **证据边界**：
  - **已证明**：内容混合。
  - **仅推断**：读者筛选能改善，尚未实现。
  - **待验证**：样本页是否需要筛选。

### RC-8｜角标定位没有重叠避让

- **根因描述**：角标坐标固定为 `top = rect.top - 8, left = rect.right - 14`，父子元素同时挂角标时必然重叠。
- **复现步骤**：

  2. 读取 `MarkLayer.jsx` 的角标样式计算。
- **复现结果**：Card 和 Card 内 li 各有一个角标，位置相邻。
- **为什么不是表象级补丁**：只调这两个坐标，其他父子组合仍重叠。
- **现有机制为什么没解决**：交互验证只检查浮窗避让，不检查角标之间重叠。
- **证据边界**：
  - **已证明**：代码上存在重叠条件。
  - **仅推断**：实际遮挡程度需浏览器观察。
  - **待验证**：样本页的角标间距。
