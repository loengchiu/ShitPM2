# 问题 2 根因：状态机结构门禁对 `####` 状态机误报（已修复）

日期：2026-07-30
关联：用户真实项目测试时，首次 `design-confirmation` 被状态机结构门禁拒（4× P1 孤岛 + 1× P2 迁移歧义），二次确认才通过（7 实体 0 违规）。

## 结论速览

- **用户的根因判断机制上正确**：`stage-prep.py:_infer_entity_from_headings` 只认 `###`（level 3）作实体边界，`####` 状态机被忽略、7 个并成 1 个实体，合并图里每个状态机各自的初始态无入路 → 误报"孤岛"；跨机同名 trigger 不同去向 → 误报"迁移歧义"。**已用实证复现。**
- **但"这不是设计缺陷，是误报"这个提法需要补三层因果**（见下）：它既是 parser 健壮性 bug，也是格式规范缺口，更是**确认门禁跑在已被主管线抛弃的 legacy 解析器上**这一架构问题。
- **已修复**：`_infer_entity_from_headings` 现在把"状态机/生命周期/状态流转"语义标题在 `###` 和 `####` 两级都当实体边界；并补了格式说明。实证：`####` 双状态机从 `entity_count=1` → `2`，误报孤岛消失；回归套件 37/0 不受影响。

## 一、根因实证（不是看报告，是跑出来的）

复现脚本构造两个各自合法闭环的状态机（订单状态 / 支付状态），"提交上报监管"在两机有合法不同去向：

| 写法 | entity_count | 结果 |
|---|---|---|
| `#### 状态机：X`（用户原写法，带空格）修复前 | **1** | P1 孤岛（`待付款` 无入路）+ 悬空误报 |
| `### 状态机：X`（每机一个） | 2 | 误报消失，仅剩夹具自身真问题 |
| `#### 状态机：X`（用户原写法）**修复后** | **2** | 误报孤岛消失 |

关键代码 `stage-prep.py:311`（修复前）：
```python
if h["level"] == 3 and h["title"] not in HEADING_BLACKLIST:
    return h["title"]
if h["level"] <= 2:
    break
```
只匹配 `level == 3`。`####`（level 4）被跳过，向上找最近的 `###`——若 7 个 `#### 状态机` 都在同一个 `### 关键对象生命周期与状态` 章节下，全部归并到该 `###`，得到 1 个合并实体。

调用链（确认门禁）：`design-confirmation.py:120` → `state-machine-check.py` → `stage-prep.py:generate_design_metadata` → `_infer_entity_from_headings`。`state-machine-check.py` 的 4 条结构规则（孤岛/悬空/回退/歧义）按 entity 分组执行，合并后必然误报。

## 二、对"这不是设计缺陷"的修正（三层因果）

1. **Immediate：parser 健壮性 bug（确认）**。`_infer_entity_from_headings` 把实体边界硬编码为 `level == 3`，无视 `####`。`#### 状态机：订单状态` 在语义上是独立状态机实体，应被识别——parser 太脆。
2. **Contributing：格式规范缺口（确认）**。`templates/design.md:88` 把状态章节定为 `### 关键对象生命周期与状态`，`####` 用于区块（line 126）。按模板自然写法，多个状态机就是 `#### 状态机：X` 嵌套在该 `###` 下——**格式并没有规定"每个状态机必须自己的 `###`"**。所以作者用 `####` 不是明显写错，而是模板引导下的合理选择。当前"7 实体 0 违规"是靠把 7 个改成各自 `###`（文档未写、写法别扭）才过的——这是个 workaround，下一个作者还会踩。
3. **Systemic：架构孤儿（确认，最重要）**。`design-index.py`（主管线）的 `_extract_states`（line 602-613）**根本不解析状态机迁移表**，只从每个页面的 `主要状态` 属性读逗号分隔的状态名，不建迁移图、不做孤岛/歧义判定。也就是说：**状态机结构检查整个挂在 legacy `stage-prep.py` 上，主管线早已不碰它**。确认门禁是唯一消费者，跑在废弃、欠文档的解析逻辑上——这正是"标题级不匹配就静默误报"却没被主管线兜住的根因。

## 三、已落地的修复

`scripts/python/stage-prep.py`：
- 新增模块级常量 `_STATE_MACHINE_HEADING_RE = re.compile(r"状态机|生命周期|状态流转")`。
- 改写 `_infer_entity_from_headings`：优先匹配 `###`/`####` 中带"状态机/生命周期/状态流转"语义的标题作实体边界；兜底仍用最近的 `###` 非黑名单标题。区块（`#### 区块：X`，不含上述关键词）不受影响，仍走兜底。

`references/design-state-format.md`：
- 新增"多状态机归并"注意：每个状态机用独立 `###` 或 `####` 标题，解析器按最近状态机标题归并实体。

**实证结果**：
- 修复前 `####` 双机 → `entity_count=1` + 孤岛误报；修复后 → `entity_count=2`，误报消失。
- 隔离验证：规范写法 `####` 状态机的终态（`已完成`）正确判 `is_terminal=True`，无假 P1。
- 回归：`test-shitpm-regression.py` 37 通过 0 失败（其 fixture 用 `### 任务状态机`，行为不变）。
