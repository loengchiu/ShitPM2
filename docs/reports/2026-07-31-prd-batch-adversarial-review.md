## 3. P1 发现

### P1-A 模板保留规则已禁的独立"模块业务对象及关系"标题

- **现象**：`templates/prd.md` 第 54 行（多小模块骨架）与第 102 行（单小模块骨架）的 HTML 注释骨架内仍示范：
  ```
  模块业务对象及关系：
  该模块涉及的核心业务对象及关系，1-2 句或小表；跨模块关联写明指向模块。
  ```
- **矛盾证据**：`references/prd-writing-rules.md:55` 规则 6.2.4 明确"大模块职责段落（6.2.2）顺带说明该模块涉及的核心业务对象及关系，1—2 句，**不单独起'模块业务对象及关系'标题**"；`skills/spm-prd/SKILL.md:81` 自检第 3 条亦要求"不单独起标题"。
- **影响**：模板注释骨架是 AI 生成 PRD 时模仿的对象。规则+自检说不要独立标题，模板骨架却示范独立标题，三者打架。AI 按模板生成会产出违反 6.2.4 的独立标题。
- **根因**：上一轮改规则 6.2.4 删独立标题时，未同步删除模板两处骨架内的示范块。
- **修法**：删除模板第 54、102 行的"模块业务对象及关系："标题行及其下说明，改为在前面"大模块职责与涉及页面"那一句后顺带融入对象关系（与规则 6.2.4 一致）。仅改注释，不动模板正文结构。

### P1-B glossary 引用规则已删除的标题名

- **现象**：`references/prd-glossary-format.md:70` 写"业务对象：Design 中定义的核心业务对象名称，与各模块开头'模块业务对象及关系'中一致"。
- **矛盾证据**：规则 6.2.4 已删该独立标题，对象关系现融入大模块职责段落。glossary 引用的标题名已不存在。
- **影响**：AI 生成 glossary 业务对象速览表时，按此引用会去模块开头找不存在的标题，或反过来复刻旧标题。
- **根因**：同 P1-A，改规则未同步改引用。
- **修法**：将第 70 行"与各模块开头'模块业务对象及关系'中一致"改为"与各大模块职责段落中提到的业务对象名称一致"。

## 4. P2 发现

### P2-A `prd-new-sample.md` 多处违规，不可作基线（印证 memory 结论）

逐条核对新规则，该样例仍有 4 处违规，上一轮 patch 只改了操作列和业务对象标题，未全面对齐：

| # | 违规点 | 证据 | 违反规则 |
|---|---|---|---|
| 1 | "删除"强动作未独立写执行角色 | 第 74 行把删除并入"操作计划"，仅写"删除当前计划（仅草稿、已驳回可删）"，未写由谁执行 | 6.4.10 |
| 2 | 状态含义放大模块层非小模块 | 第 29-37 行状态含义在大模块 5.1 层；5.1.1/5.1.2 小模块无状态含义段 | 6.2.8 |
| 3 | 流程图放大模块层非小模块 | 第 39-48 行流程图在大模块层；小模块无图 | 6.2.9 |
| 4 | 字段表拆 3 个实体子表 | 第 212/240/287 行用"**年度计划**/**审计项目**/**项目成员**"分 3 表 | 6.2.18 字面"一个大模块字段定义表" |

- **对比**：skill 真跑产物 `prd-5.1-skill-generated.md` 在这 4 点上均合规（状态含义/流程图在 5.1.1、5.1.2 小模块层；字段表为单连续表；删除动作第 51-52 行显式写"审计用户（按数据范围，即该计划编制人）"）。
- **结论**：memory 中"样例不可作文档基线"结论成立，且违规点比 memory 记录更多。`prd-new-sample.md` 不应作为合规基准样例。

### P2-B `prd-5.1-skill-generated.md` 只是单模块片段，不能直接作全文档基线

- **现象**：文件第 3 行声称"完整 PRD 其余 11 个模块按同流程生成"，但实际只生成 5.1 一个模块。
- **影响**：该文件规则符合度高于手工样例，可作 5.1 模块基准，但不是完整 PRD，不能直接替换 `prd-new-sample.md` 作全文档基线。
- **次要点**：第 105 行状态机表"已通过"行"含义"列写的是触发条件（"至少一个项目启动后自动进入执行中"）而非状态含义，格式瑕疵。
- **建议**：若要建立可信全文档基线，需用 skill 真跑完整 12 模块 PRD（memory 待办②，未做）。

### P2-C 承接缺口①（design 二章用户场景与目标）在 PRD 无落点，性质待确认

- **现象**：memory 列出的 5 个承接缺口中，②对象关系/③数据范围+敏感操作/④外部协作/⑤闭环详细动作已在规则 6.2.3/6.2.4/6.2.14 + 自检 2/3/4/5 就近补齐。唯独缺口①（design 二章"用户场景与目标"含角色职责/关键场景/成功标准）在 PRD 模板、规则、自检均无独立落点——模板 §1 文档概述只承接"产品目标/方案摘要"。
- **判断**：这可能是**合理边界**（PRD 是研发规格，用户旅程/场景更适合留在 design，PRD 只需承接角色职责——已在大模块权限规则——和范围）。但也可能是遗漏。memory 当时列为缺口①未说已补。
- **建议**：需用户确认是有意不补还是遗漏。若有意不补，建议在规则或 USAGE 显式说明"PRD 不重复 design 用户旅程，只承接角色职责与范围"，消除歧义。

### P2-D design 操作列笼统描述与 PRD 展开要求存在上下游张力

- **现象**：`test-fixture/output/design/design.md:1306` 等多处操作区写"按状态和权限显示"（笼统）；而 PRD 规则 6.4.11 要求 PRD 操作列按"角色×状态"展开可见性与可点性。
- **影响**：design 作为事实源给笼统描述，PRD 要从 design 权限规则+状态机推断展开每个按钮的角色×状态。AI 推断有臆造风险（design 未明确每个按钮的角色×状态时，PRD 展开可能补造）。
- **现状**：样例与真跑产物都成功展开了，说明可做，但依赖 AI 推断质量。
- **建议**：二选一——①design 侧也规范操作列写法（避免笼统"按权限显示"）；②PRD 规则 6.4.11 显式说明"从 design 模块权限规则+状态机推断展开，design 未明确时不得补造、标待确认"。

### P2-E test-fixture 旧对照文件遍布违规写法，存在误学风险

- **现象**：`test-fixture/output/prd/prd.md`、`test-fixture/v2-remediation/calibration/complex-inventory-shitpm-original-prd.md`、`test-fixture/output/design/design.md` 大量使用"按状态和权限显示/按状态显示/按权限显示"（grep 命中 30+ 处），违反新规则 6.4.11。
- **性质**：这些是历史产物/校准对照文件（带 original 前缀或位于 output 历史位置），违规是预期的（它们就是被对照改进的旧物）。
- **风险**：若 AI 读取 test-fixture 学习样例，会学到违规写法。当前定位靠命名约定区分，不够强。
- **建议**：在 test-fixture 加 README 说明哪些是合规基线、哪些是历史对照不可学；或将历史对照移到 `test-fixture/legacy/` 隔离。

### P2-F 自检未覆盖状态含义/流程图的层级归属

- **现象**：自检 12 条覆盖了状态机表位置（自检 6）、字段表 7 列（阅读质量自检第 10 项）、强动作角色与操作列展开（自检 12），但未覆盖 6.2.8（状态含义在小模块层）和 6.2.9（流程图在小模块层）。样例 P2-A 违规点 2/3 正是在这两条上出错。
- **建议**：自检补一条"状态含义与流程图位于对应小模块层，不集中到大模块"。

## 5. 正面结论（已验证合规）

- **AGENTS.md §2 不与 §1/USAGE 重复**：USAGE.md 经 grep 确认只含运行时命令用法，无 skill 编写原则性内容；§2 的 11 条中，§2.3"指令优先"明确标注"与 §1 #6 一致"属有意交叉引用，其余 10 条（可复用才做 skill、先 skill 后 plugin、SKILL.md 精简、references/scripts/templates 职责、description 触发契约、单一职责、输入输出、测试触发）均为 §1 未覆盖的新内容。§2 符合 §1 简化原则，未引入新工具/回执/中间结构。可保留。
- **spm-prd SKILL 无 footgun**：第 31-37 行 confirm 范式正确（上轮 P2-2 已修），"不得在用户未明确确认前运行 confirm"显式约束，命令一律由 AI 执行不甩用户。无自动 confirm、无甩命令行 footgun。
- **承接缺口②③④⑤ 已就近补齐**：对象关系（6.2.4 融入职责段）、数据范围+敏感操作（6.2.3 大模块开头权限规则）、外部协作（6.2.14 就近）、闭环详细动作（6.2.14 就近）均有规则+自检落点，符合就近原则，未过度集中到全局章节。
- **skill 真跑产物合规度优于手工样例**：证明 spm-prd skill 流程可产出符合新规则的 PRD，skill 流程本身可信。

## 6. 整体结论与建议

主干可放行。阻断点只有 P1-A/P1-B 两处配套同步遗漏，修法均为单点改动（删模板注释骨架的独立标题块、改 glossary 一句引用），不涉及流程或接线调整。

建议处理顺序：
1. 修 P1-A/P1-B（模板 + glossary 跟随规则 6.2.4 同步）。
2. 决定 P2-C（用户场景缺口是有意不补还是遗漏）。
3. 决定 P2-A/P2-B 样例策略：是否用 skill 真跑完整 12 模块 PRD 作新基线，替换 `prd-new-sample.md`。
4. P2-D/P2-E/P2-F 为改进项，可后续处理。

本审查未修改任何代码或规则文件，仅产出本报告。
