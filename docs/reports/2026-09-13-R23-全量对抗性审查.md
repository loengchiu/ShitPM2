## P0-1 合规 PRD 必被判 `deterministic_conflict`，且不可放行

**现象**：严格按 `templates/prd.md` 4.1.3 + `references/prd-writing-rules.md` §6 + `skills/spm-prd/SKILL.md` 完成条件 2 生成的 PRD（角色 × 业务能力矩阵，行=角色、列=业务能力），一致性检查输出：

```
exit=1  exit_reason=deterministic_conflict
permissions.missing      = ["核查任务详情", "滞留车辆列表"]
permissions.hallucinated = ["创建核查任务", "归档核查结论", "核实滞留原因", "角色与权限"]
permission_role_pairs    = missing 2 / hallucinated 4 / matched 0
permission_evaluation.status = "extracted"（双侧均提取 → 不走 not_evaluated 保护）
```

对照组（旧格式 `## 6. 权限汇总`）：`exit=0，matched=2`。

**根因**（`scripts/python/prd-consistency-check.py`）：
1. `_find_prd_permission_ranges`（:799）优先锁定 `4.x.3`，策略 1（:751）再取该范围内 `level in (3,4)` 的标题 → 唯一命中的是 `#### 4.1.3 角色与权限` 自身，`"角色与权限"` 被当成权限页面名注入（恒定 hallucinated 1 项）。
2. `_extract_perm_pairs_from_table`（:844）在「行=角色」矩阵下把**列名（业务能力）**当 `page` 输出，而 Design 侧 `page` 是**页面名** —— 两个 ID 空间不同，必然双向不匹配。

**为什么是 P0**：`skills/spm-prd/SKILL.md:112` 规定 `deterministic_conflict` 必须阻断修复；`contracts/prd-review-checklist.md:23` 本轮又新增「缺少角色 × 业务能力矩阵记 P1」。结果是**唯一合规的写法被判错误**，AI 只能删矩阵或把列名改成页面名来消除伪冲突，权限表达退化，或交付永久卡死。

**复现**：构造 Design（权限页=滞留车辆列表/核查任务详情）+ 含 `#### 4.1.3 角色与权限` 角色×业务能力矩阵的 PRD，跑 `python scripts/python/prd-consistency-check.py --project-root <dir>`。

**真实项目的真实状态（2026-09-13 复核修正）**：**已交付项目 PRD 已经在用 `#### 4.x.3 角色与权限`**（审计系统 11 处、租金清分 1 处、能源数据监测 2 处），写法是**自然语言段落**而非矩阵。当前 `permission_evaluation.status` 一律 `not_evaluated`、message 报「Design 权限为空」，因此双侧比较从未发生。**这个「Design 权限为空」是错误诊断**（见 P1-4），真实情况是 Design 侧权限事实完整但下游不消费。

因此 P0 不是「定时问题」：**一旦按 P1-4 修好 Design 侧权限读取，审计系统立刻输出 `missing=66`、`hallucinated=["角色与权限"]`、`exit=1`**（已模拟实测）。P0-1 与 P1-4 必须同时修，单独修任一项都会使情况更差：只修 P1-4 → 引爆百量级假红；只修 P0-1 → 权限维度继续恒漏检。

**ID 空间错配的成立条件（2026-09-13 复核修正）**：上面的 `deterministic_conflict` 出现在**我构造的 Design（含权限事实）+ 合规矩阵 PRD** 场景。真实项目当前是 `not_evaluated`（Design 侧未消费，见 P1-4），所以缺陷被掩盖。两条路径的对照：

| 场景 | 结果 |
|---|---|
| 修复前基线（`…readability-….md:109`） | `prd_permission_pages_count=0` → 恒 `not_evaluated`（漏检） |
| 真实项目现状（Design 有 roles，脚本不消费） | `not_evaluated` + 误报「Design 权限为空」（**漏检 + 错误诊断**） |
| Design 权限被消费 + 合规矩阵 PRD（构造） | `deterministic_conflict`（假红） |
| Design 权限被消费 + 存量自然语言 PRD（审计系统） | `missing=66` + `hallucinated=["角色与权限"]`（假红，已模拟） |

## P1-4 权限维度恒失效（按规范层 → 实现层 → 产物层分层判定）

> **本节经两轮修正。** 初版结论「Design 侧没有权限事实源」错误——把「提取器读不到」误判为「事实不存在」，方向全错。一修版改正了事实，但三层证据混在一起陈述，无法判断该改规范、改脚本还是改产物。**本版按固定顺序分层取证：先查规范是否规定读取，再查脚本实际读什么，最后查产物是否具备。**

**判据顺序（不得跳层）**：`规范层（规定读什么）→ 实现层（实际读什么）→ 产物层（有没有料）`。**禁止反向推断**——不得由「实现层读不到」直接推断「产物层没有事实」。恒空 / 恒 `not_evaluated` 时三层各有病因，修复方向完全不同（改规范 / 改读取器 / 改产物）。

### 第 1 层：规范层

| 规范文件 | 规定内容 | 是否规定读取来源 |
|---|---|---|
| `templates/design-module.md` | 页面属性「适用角色」、操作表「适用角色」列 = 必填 | — |
| `templates/design-system.md` | `## 五、权限与数据范围`（注释：系统级权限矩阵） | — |
| `skills/spm-prd/SKILL.md:69,78` | PRD `4.x.3` 写「角色 × 业务能力」矩阵，定位为**模块级权限边界机读与评审源** | ❌ 只规定 PRD 侧怎么写 |
| `skills/spm-prd/SKILL.md:112` | `deterministic_conflict` 必须阻断 | ❌ 只规定结果怎么处理 |
| 其余全部 skill / contracts | **无任何条款规定一致性检查的 Design 侧权限从哪里读** | ❌ **规范缺口** |

**规范层结论**：规范规定了「两侧各自写什么」，缺失「两侧怎么对接」。Design 侧两个必填属性 + PRD 侧矩阵形态都已定义，但**没有任何条款把两侧连起来**，读取来源完全由脚本实现自行决定。修法因此不是「在模板之间取舍」，而是补一条连接规范。

### 为什么 2026-09-12 的决策没有拦住

昨日计划（`docs/plans/2026-09-12-prd-detailed-spec-readability-plan-and-acceptance.md`）确实讨论了权限矩阵，`§3.7` 定了「行=角色、列=业务能力」，`§276` 还**预警**了「不动表头方向 → 权限维度永远 `not_evaluated`」。决策对、预警对，仍漏了，原因三个且互相叠加：

1. **决策只覆盖 PRD 侧表达形式，未覆盖 Design 侧读取来源。** `§3.7` 涉及 Design 侧只有一句假设——「Design 侧沿现有 Design 权限元数据提取，不要求本轮强行把 Design 标题改成 4.x.3」。这句**既无落地动作也无验收判据**：`§12.2.1` 第 8 号改动清单 5 条全是 PRD 侧，Design 侧一条没有。「沿现有元数据提取」从未被验证能否成立。
2. **验收把错误诊断当成了事实。** 昨日输出 message「Design 权限为空」，当时接受了这个理由（双侧判定正是为避免单侧空集合假冲突）。但三层取证显示 Design 权限**不为空**。该错误诊断从未被核实，沿用至今。
3. **昨日新加的保护机制掩盖了同时产生的新错误。** `both_sides_extracted` 成功阻止假冲突，代价是把 PRD 侧 9 个错误提取（8 个能力名 + 章节自身标题）一并吞进 `not_evaluated`。**租金清分昨天重写完矩阵的那一刻 `prd_permission_pages_count` 就从 0 变成 9，错误已经产生，只是没有暴露窗口。**

**方法论教训**：防假阳性的保护机制必须有配套的「提取物实际是什么」复核，否则会把假阳性换成假阴性。昨日验收只看了 `not_evaluated: true` 与 `matched_count: 0`，**没有打开看那 9 个提取结果是什么**——而 9 本身就是异常信号（Design 侧为空时，PRD 侧不该有任何「页面」）。

### 附带发现

1. **规范与存量实践不一致**：`templates/prd.md:55` 与 `prd-writing-rules.md:17,87` 要求 `4.x.3` 写「角色 × 业务能力」**矩阵**，但审计系统 11 个模块、租金清分、能源数据监测的实际写法都是**自然语言段落**（如「审计经办人与项目组长/主审承担编制、编辑、提交审批…」）。
2. **Design `roles` 属性缺约束**：实际填入内容混有权限条件式描述（「具备下载权限的内部审计人员」「有对应页签权限的用户」）与动态角色（「原发起人」「当前操作用户」），共 44 个 unique 角色中约 19 个属此类。`templates/design-module.md` 的「适用角色」注释未禁止这种写法。
3. **角色名双向比对噪声高**：以 Design 角色集合为词表检查 PRD `4.x.3` 段落出现情况，19 项未命中里约 15 项是表达差异/泛指/动态角色（噪声率约 79%），不可作为阻断判据。

## 方法备注（供后续轮次复用）

- 审查基线必须**先跑全量测试再找测试之外的洞**：本轮 P0 之所以存在，是因为测试夹具停留在旧 PRD 格式，新规范引入的新分支端到端零覆盖。
- 所有 P0/P1 结论均经主代理独立复现（构造合规样本 + 对照组对撞），子代理报告的结论未复现的已在正文标注来源。
- 静态构建通过不等于运行时无错：本轮坚持「构建 + 浏览器实跑 + 未导入组件静态审计」三件套。
- **教训（本轮 P1-4 初版结论错误）：不得把「读取器读不到」直接推断为「被读取的事实不存在」。** 初版看到 `stage-prep._extract_permissions_from_content` 关键词表不含官方标题，就写成「Design 侧没有权限事实源」，未去验证 Design 侧事实本身。正确顺序是：**先独立确认事实源的完整程度（读模板 + 查真实项目数据），再判断是事实缺失还是读取缺失**。两者的修复方向完全相反（改模板 vs 改读取器）。本次由 PM 质疑才发现，属方法缺陷而非信息不足。
- **推论**：当某个检查维度恒为 `not_evaluated` / 恒为空时，先查「上游事实是否真的为空」，再看「下游是否读了它」。空结果不能自证事实不存在。
