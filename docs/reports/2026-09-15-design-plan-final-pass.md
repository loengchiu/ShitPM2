## 2. 新发现：2 处 P1

### F-1｜T-8 的 A 组隔离不成立——用户级 skill 是符号链接，指向活动工作区

计划 T-8 步 2 用 `git worktree add --detach` 建 A 组 worktree，但 nothing 约束子代理从哪读 skill 与 reference。实测：

```
~/.workbuddy/skills/spm-design -> /c/Users/guduj/.workbuddy/shitpm/skills/spm-design
readlink -f C:/Users/guduj/.workbuddy/shitpm  ->  /d/work/ShitPM
```

活动工作区就是 skill 装载源。A 组子代理一旦调用 `spm-design`，读到的是 **B 组（活动树）的 SKILL.md 与 references** —— 而 T-3～T-6 改的正是这些文件。worktree 只隔离了 `scripts/`，没隔离本次 A/B 的**唯一处理变量**。

后果两种，都不可接受：A 组实为 A′≈B，质量无差异 → 按 §T-8「失败处理」回退 T-3/T-4（假阴性）；或执行者判"通道不可用"→ 直接标部分完成（漏掉本可完成的验证）。

**处置（写入 T-8 步 2 与完成判据）**：

- 首选串行：在 main 工作区 `git stash` 本轮未提交改动 → 跑 A 组 3 次（子代理自然读到 baseline 协议）→ `git stash pop` → 跑 B 组 3 次。全程不涉及 commit，符合"不得 commit"约束；执行报告须附 stash/pop 证据。
- 或用 worktree 时，在任务文本中固定 A 组 bundle root 为 worktree 绝对路径，并禁止读取 `C:/Users/guduj/.workbuddy/shitpm/**` 与经 `~/.workbuddy/skills` 自动加载。
- 无论哪种：**每次运行记录所用 SKILL.md 与 references 的绝对路径 + sha256，A/B 必须不同**——把这条加进 T-8 必须留下的证据。

## 3. 定性/口径不精确：2 处

### F-3（P2）｜「保留 4 条页面配对错误为真实 Design 问题」定性不准

计划的冻结预期是 errors 50→31，其中 4 条按"应保留的真实配对问题"处理。实测这 4 条的原文：

```
page_summary_missing_detail  清单中的“P-SET-03 月度汇总结算单管理页”没有正式页面定义
page_detail_missing_summary  正式页面“P-SET-03 月度汇总结算单管理页（非定向方案 B 专用；差额冲正调整单管理页签对非定向与定向单统一承载）”未出现在页面清单中
```

对照正文：清单行（:134）写 `P-SET-03 月度汇总结算单管理页`，正式标题（:296）写 `### 4.4 页面：P-SET-03 月度汇总结算单管理页（…）`。**同一实体在两处都存在**，差异只是标题尾部括注；比较器不归一括注 → 同一处不匹配被双向各报一次，且两条消息的事实陈述都不成立（页面确实在清单里）。P-SET-04 同理。

所以它不是一个"两条真实产品问题"，而是 1 个写作口径（标题挂括注）+ 1 个比较器归一化缺口。而 T-2 步 2 已要求候选侧"剥离括注"——两侧口径不一致。

**处置（三选一，写明即可）**：(a) 比较器同口径剥括注 → 这 4 条消失，冻结值变 pages=4 / errors=27；(b) 保留但标注为"已知假阳性 + 后续单独处理"，不计入产品事实、不作为冻结值的一部分；(c) 判定为写作规范问题，把"页面标题不得挂括注"写入页面标题规范，并在 T-0 台账中记为规范类问题。当前写法（保留为真实问题且不改产品事实）会让工具永久输出两条事实错误的报错，同时把 errors 冻结值抬到 31。

### F-4（P3）｜T-6 缺"约束类别差集"，而 R12 自证那是当时的真实缺口

T-5 步 4 已加维度差集。Fix 侧没有对应动作，但证据来自 R12 自己（:53）：

> 第 11 轮的承载面枚举表只列了三个约束（冲正单隔离、已作废限缩、冲正标记），**没有枚举"角色维度的可见性约束"这一类**。所以本轮 4 个 P1 里有 2 个属于**从未被任何一轮列入核对面**的类型。

即：Fix 的失手模式包含"约束清单本身缺一整类"。T-6 步 1–2 只做"问题 → 约束"，没有"本批约束类别是否覆盖关系维度清单"的差集检查。

**处置**：T-6 步 2 加一句——先列出本批涉及的约束类别，再对照关系维度清单确认是否有整类未进入枚举（有则单列记录，不静默跳过）。

## 4. 顺手做掉的风险排除（结论：新 fatal 不会误伤既有夹具）

担心"新增 `page_extraction_empty` 会让现有测试变红"。实测两类最可能的夹具形态：

| 夹具 | compile 结果 | 结构式判据 |
|---|---|---|
| 旧格式（`## 页面说明` + `## 字段清单` + `## 操作说明`，无固定标题结构） | pages/blocks/fields/operations = 0/0/0/0，`unsupported_format`，CLI diagnostics `no_entities_extracted` | 不命中 → 继续 legacy 降级 ✓ |
| `test-prd-consistency-semantics.py` 的 DESIGN 夹具（`# 设计基线` + `## 字段定义` 表 + `## 权限定义`） | 同上，全 0 + `unsupported_format` | 不命中 ✓ |

原因：字段/操作提取挂在页面或区块之下，无页面祖先时不产出实体；因此"有实体但无页面"只在**区块存在**时出现，与 unsupported_format 天然互斥——与计划判断一致。既有测试因新 fatal 变红的路径基本不存在。

另确认（与计划表述一致）：`_FATAL_ERROR_CODES`（design-index.py:1101）与 `_is_fatal_index_error`（:1104）**零调用方**，真实降级全部内联在 `load_verified_index`；`no_entities_extracted` 只在 `_extraction_diagnostics`（:1161）产出，其注释明确"不写入索引，写索引会改变指纹"，与持久 `page_extraction_empty` 拆分成立；`if not expected: enabled=True`（:1835–1844）无任何测试锁定。
