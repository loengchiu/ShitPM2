## 3. 未成立与新增问题

### 3.1 T-1 完成判据不可达：errors 是 31，不是 27

计划 T-1 完成判据写「隔离副本 pages 0→4、errors 50→27」。在真正的修复位置（改 `_normalize_label`）实跑，得 `pages=4` 但 **`errors=31`**：

```
新增 page_summary_missing_detail 2 + page_detail_missing_summary 2
```

原因：同一个正则还控制 `design-index.py:604` 的 `startswith("页面清单")`。
- 修前：`4.1 页面清单速览` → 归一化成 `1 页面清单速览` → 判False → **页面清单表从未被解析**；
- 修后：`页面清单速览` → 判True → 清单表首次进入比对，暴露清单行名与 `### 页面：` 标题名不一致（`P-SET-03/04` 标题带括号后缀）。

计划的 `27` 来自第一遍审计的**手工实验**（只改标题文本、未启用清单解析路径），不是修复代码后的结果。按计划字面执行，执行者会认为修复不完整，或误改清单解析逻辑。

附带实证：候选正则在全量测试上**无回归**（改前改后均 `77 passed`）——即既有测试不覆盖这条路径，T-1 的第 1 步（先写失败测试）是必需项，不能省。

### 3.2 T-1 动作链缺一环：`fatal` 集合无消费者

计划 T-1 第 4/5 步：生成 `page_extraction_empty` → 加入 fatal 集合 → 验证缺页 Index 不再以 enabled 继续使用。

实测：
- `_FATAL_ERROR_CODES`（`design-index.py:1101`）与 `_is_fatal_index_error`（`:1104`）**全仓库零调用方**，只有定义处；`_is_fatal_index_error` 是死函数。
- 消费者真正的降级分支只看 `_is_unsupported_format`（`prd-consistency-check.py:2173`、`:1826`）。
- 更关键：`_compare_indexed_structure` 在 `expected` 为空时**硬编码返回 `enabled: True, expected_count: 0`**（`prd-consistency-check.py:1835-1844`）。空索引被上报为"已启用、零预期"。

结论：只把错误码加进 `_FATAL_ERROR_CODES`，行为零变化。T-1 必须显式写"在 `prd-consistency-check.py` 增加 fatal 分支（或改 `_compare_indexed_structure` 的空集语义）"，否则第 5 步的验证无从通过。

另：RC-6 的影响面漏一个消费者。`prototype-consistency-check.py:342/401` 同样走 `load_verified_index`，但只在 `index is None or index_error` 时 fatal（`:409`）——pages=0 依旧静默。T-1 的文件清单只列了 design-index + prd-consistency-check + 两个测试。

### 3.5 T-7 对 F2 的修法会变红，且红在 `stage-prep` 不在测试

计划 T-7：「F2 必须对 `has_dead_state` 形成真实断言，并验证错误输入会失败」。

探针（用 F2 自己的夹具调 `stage_prep.generate_design_metadata`）：

```
待审核 → {"transitions": [], "is_terminal": true}
has_dead_state = False
```

`stage-prep.py:415` 把「触发动作与下一状态均为 `—`」的行判为终态，因此"非终态无出路"在确定性层**不可区分**。F2 的硬编码 evidence「检出非终态无出路状态: 待审核」不只是没断言——**断言本身不成立**。

T-7 必须写明变红之后改哪边（修 `stage-prep` 的终态判据 / 换夹具 / 删除该场景），否则执行者只有一条路可走：删测试，而这会把一个真实的检查缺口一起删掉。补充事实：该行为目前**只有 LLM 检查项**（`contracts/design-review-checklist.md:17`「非终态无出路、非初始态无入路…」），与 T-3/T-5 要建的关系实例方法直接相关。

另外 T-7 对 F 场景的清单不准：F1 与 F7 有真实断言（F7 断的是 `design-quality-rubric.md` 的**文档措辞**，非行为）；F3–F6 零断言；F2 计算未用。准确清单应替换计划原文。

### 3.6 T-8 没有执行通道

计划 T-8 要求"同一便宜模型、同一输入、各 3 次独立生成、Review 不得读取另一组答案"。

实测：`evals/` 目录不存在，仓库内没有任何"运行一次 Design 生成"的 harness。没有执行机制，T-8 无法落地，而 8 节又写明"无法获得同一模型同一输入的 A/B → 总状态只能部分完成"。建议 T-8 前置写死机制：`git worktree add --detach <temp> <baseline-commit>` 取 A 组规则，当前工作区为 B 组；每组各起 3 个独立子代理执行同一输入；产物分目录隔离并登记原始路径。

### 3.7 T-3 缺两条资源完整性硬约束

`test-resource-integrity.py` 会拦住新增文件：
- `:74-77`：`references/`、`contracts/` 顶层 md 超过 100 行必须有 `## 目录`（`design-business-closure.md` 必然超）；
- `check_context_manifest`：section 若用 `selector: marker`，源文件必须**恰好一对** `<!-- context:<id>:start/end -->`。

T-3 只写"manifest 或 Skill 真实指针"。另外 T-4 要改的"现有写作自检"应点名到 marker 章节：`design-writing-self-check`（`references/design-writing.md:203-234`）和 `design-verification-self-review`（`references/design-quality-rubric.md`，已在 `design-writing` 装载包内），不点名就有写重复章节的风险。
