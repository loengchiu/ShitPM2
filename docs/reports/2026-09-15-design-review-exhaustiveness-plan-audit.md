## 2. A 类：必须修改

### A1｜基线已过期：第 13 轮未纳入

计划 17:35 定稿，第 13 轮报告 17:28 落盘。逐轮结论行核对结果：

| 轮 | P0 | P1 | P2 | 结论 |
|---|---:|---:|---:|---|
| 1 | 1 | 4 | 3 | 阻塞 |
| 2 | 1 | 9 | 8 | 阻塞 |
| 3 | 0 | 0 | 0 | 通过 |
| 4 | 0 | 8 | 7 | 阻塞（推翻 r3） |
| 5 | 0 | 0 | 0 | 通过 |
| 6 | 0 | 2 | 11 | 阻塞（推翻 r5） |
| 7 | 0 | 2 | 10 | 阻塞 |
| 8 | 0 | 4 | 11 | 阻塞 |
| 9 | 0 | 5 | 10 | 阻塞 |
| 10 | 0 | 4 | 16 | 阻塞 |
| 11 | 0 | 5 | 12 | 阻塞 |
| 12 | 0 | 4 | 12 | 阻塞 |
| **小计（计划基线）** | **2** | **47** | **100** | 与计划完全一致 |
| **13** | **0** | **3** | **4** | 阻塞 |
| **合计（应为新基线）** | **2** | **50** | **104** | — |

第 13 轮不只是数字增加，它引入了两类计划尚未登记的方法学证据：

- **轴的口径缺陷**：⑯/④ 轴把正文括注、后缀当独立字段名 → 假阳性。固化结论：凡"拿正文串去字典/集合里找"的核对，必须先做串归一化（剥括注、剥"全部字段/与…入口"后缀、拆并列分隔符），否则会把"同一事物的两种写法"报成"缺一个事物"。
- **新的关系维度**：第 13 轮 3 个 P1 中 2 个属于"单据类型维度"（统称表述 ↔ 下辖单据类型的可见性差异），此前 13 轮任何一条轴都没有这一维——**这正是 RC-1 的又一例证，且它出现在计划成稿之前**。

**要求**：T-0 以逐轮结论行为唯一计数源重算，纳入第 13 轮，并登记上述两类证据。

### A2｜核心机制有空缺：枚举有了，"适用/排除"没有判据

T-1 要求"生成实际关系边，不做角色×状态×页面的无脑全笛卡尔积"；T-3 要求报告记录"明确排除项"。但：

- 什么关系算**适用**？判据未定义。第 13 轮出现的"单据类型维度"说明：不适用的判断本身就会漏（当时没人想到该维度存在）。
- 什么理由可以**排除**？依据未定义。没有依据要求的"排除项"就是新的漏检后门——审查者可以把难判的关系直接排除，报告反而更整齐。
- 判不准时怎么办？未定义。按 `review-checklist.md` §四，这类应落 `risk`，不得静默排除。

**要求**：①适用判据 = 关系两端实体在当前 Design 中都被实际声明（可定位到正文）；②排除必须引用具体正文事实（"未声明 X，故本关系不适用"），禁止以"看起来不重要"排除；③判不准 → `risk`，不得排除。

### A3｜验收判据不可靠（3 处）

| 判据 | 问题 | 建议 |
|---|---|---|
| 不变 Design 第二轮 Review 新增 P0/P1 = 0 | 把"没发现"当"不存在"；**奖励更浅的第二次审查**（第二轮只需少发现问题即可通过）；不满足还能反过来惩罚更认真的第二轮 | 改为：两轮独立审查各自输出同一张覆盖表（关系类型 × 实例数 × 结论/排除依据），验收看两表关系类型集合是否一致、同一实例是否有相反结论；"新增=0"降为参考指标 |
| 受控缺陷 P0/P1 检出率 100% | 缺陷集来自 T-0 从 12/13 轮派生，**方法也由同一批报告派生** → 近同义反复，100% 不构成证据 | 基准拆成"方法派生集（用于设计方法）"与"held-out 盲测集（不参与方法设计）"，检出率只用盲测集计；有条件再加一个项目外样本 |
| fast 中位耗时 ≤ 基线 1.25 倍 | 耗时口径未定义（墙钟 / 模型调用次数 / token？）；样本量未定义 | 明确口径与重复次数；口径未定前 D-2 不可判定 |

补充：**T-6 的同模型同输入 A/B 是单次采样（n=1 次生成）。** Design 生成是随机过程，1 次对比无法区分"方法有效"与"随机波动"。建议同输入重复 ≥3 次，或改用更稳的指标（缺陷**类别**命中率：候选覆盖了几类、基线覆盖了几类）。

### A4｜漏一条根因：审查单元规模超过可穷尽覆盖的预算

RC-1 把"每轮新增对照面"归因为"审查单位是维度而不是实例"。但第 13 轮自己提供了另一个解释的更直接证据：**同一批文本、同一个审查者，仅换一个观察角度就立刻捞出 6 个硬命中；而两次"通过"发生在采样恰好落在干净区域时**。这是采样（覆盖不完整），不是检查项命名问题。

关键事实（计划中完全没有）：当前 Design 规模为 4 文件 / 152KB，其中 `模块设计/模块设计.md` 单文件 **88KB**。在同一注意力预算下，把"检查项列表"换成"实例列表"只是把清单变长，不改变"审不完"。

**要求**：新增 RC-7（审查单元规模 vs 可穷尽覆盖预算），并在规范层给出对应修法：按业务闭环切分审查单元（单模块文件 = 一个可在单次内完整覆盖的闭合），跨模块只在显式契约层审，并定义单次审查单元上限。

### A5｜T-3 与既有契约冲突

T-3 要求"一次报告列完当前能发现的全部 P0/P1，不因已达到阻塞门槛提前停止"。`contracts/review-checklist.md` §四写的是"P2 写入 issues，但不计入审查结论；**P0 优先停止展开低优先级 P2**"，且常见错误表把"一次性输出全部检查项"列为反模式（审查者疲劳）。

**要求**：T-3 改为"P0/P1 列完不停，P2 可停"，并在 §9.1 的冲突表述检查里显式核这一条。

## 3. B 类：应修改

### B1｜F-2 与既有的技能内自检重复，未说明关系

`skills/spm-design/SKILL.md` §7 已要求 `simple-design` / `design-editor` 各自执行一次内部自检并按 `references/design-writing.md` 清单回读；`references/design-analysis-protocol.md` §5 已有 16 行对照表（来源↔Design、状态↔出路、异常↔恢复、自动动作↔失败责任、删除传播↔生命周期、枚举/上限↔来源、页面身份↔展示行为等）；T-2 的四条内容与之高度重叠。

计划没有说明 T-2 是**改写既有指令**还是**新增第二套自检**。若是后者，触犯 AGENTS §1.10（自检与生成合并）与 §1.9（复杂度换皮）。

**要求**：F-2 明确写成对 §7 + §5 的**增量改写**（增量只有一个：从"检查这一类"变成"逐实例检查并写排除依据"），并列出被替换的原句。

### B2｜D-1 是假二分，漏掉了唯一能同时降本增效的路径

D-1 的选项只有 A（instruction-first）与 B（写脚本）。但 RC-5 的结论只是"**固定轴脚本不能当裁判**"，不等于"不能用任何结构化手段"。计划里 `O-1` 排除了"继续扩设备租赁专项脚本"，却没有排除"在写作期让约束与承载位置成为可定位事实"。

**选项 C（建议列入 D-1）**：instruction-first + 写作期最小锚点。每条高影响约束在正文中带稳定标识，承载位置声明为该约束的引用点。效果：审查侧"枚举承载面"从判断降级为查找，Fix 传播从通读降级为定位。成本：生成期负担 + 锚点漂移风险。

必须同时写入的止损：本仓库有明确前例——`data-block` 类锚点曾在整文件重写中静默丢失，构建与浏览器实测都发现不了（第 ⑩/⑫ 类教训）。所以任何锚点方案必须附带"锚点缺失即失败"的确定性检查，否则等于没做。

**要求**：D-1 三个选项并列给出取舍，不做预先推荐；若选项 C 不采纳，需写明理由（而非合并进"不写脚本"）。

### B3｜13 轮里产出最高的动作没有被固化为规范

第 11、12、13 轮都靠同一动作发现关键问题：**逐编号回读修复方宣称的落地位置**（第 13 轮列为"第 12 轮修复的宣称 vs 实际"，逐项回读十余处位置）。计划只把它写成 T-4 的"必须留下的证据"，没有写进 Review 的固定动作。

**要求**：写入 `spm-design-review` / `design-review-checklist`：凡存在上一轮修复，Review 必须输出"宣称位置 ↔ 实际文本"对照表，逐编号回读，主体落点属实的也要写。

### B4｜没有定义"审查收敛"的停止条件

T-3 要求"列完当前能发现的全部"，但没有任何终止判据——这正是"挤牙膏"的另一半：没有终止条件，永远可以再找一轮。

**要求**：定义停止条件 = 覆盖表闭合（关系类型集合固定、每类实例数已列、每实例有结论或排除依据）；并规定**只允许"新关系类型"触发下一轮**，已知类型出现新实例视为覆盖失败（按缺陷处理），使收敛可诊断。

## 5. 实测发现（计划未覆盖，但直接决定本计划可行性）

### 5.1 事实

`design-index.py compile` 在设备租赁**真实 Design** 上（只读副本，未修改原产物）输出：

```text
ok = false
summary: {files: 4, pages: 0, blocks: 14, fields: 89, operations: 7}
errors : 50 条
  block_without_page ×14   missing_attribute ×14   combined_field_name ×9
  duplicate_entity ×5      block_without_items ×5  semantic_conflict ×3
```

即：**唯一权威索引在本项目提取到 `pages = 0`**（状态机 4 / 状态 28 / 字段 89 仍正常）。

### 5.2 单变量定位

页面标题被写成 `### 4.2 页面：P-SET-01 基础结算单管理页`。`design-index.py:_normalize_label` 只剥离**单级**编号（`^\d+[、.．)]`），"4.2" 剥掉 "4." 后剩 `2 页面：…`，无法匹配 `页面：` 别名；而区块标题 `#### 区块 1：…` 以别名开头，不受影响（故 blocks 仍为 14）。

单变量实验（仅去掉 `### N.N ` 编号前缀，其余不变）：

| | pages | errors |
|---|---:|---:|
| 原样 | 0 | 50 |
| 去编号前缀 | **4** | **27** |

### 5.3 影响

- `prd-consistency-check.py` 当前格式主路径以 verified Index 为页面/状态/权限唯一来源（`structure_source / design_state_source / design_permission_source = "design-index"`）。`pages = 0` 时 `_indexed_expected_entities` 只剩 field/operation，且 `page_name/block_name` 全为 `None` → **页面层结构对账静默空转**，页面级权限事实（page 的 roles / 数据范围）缺失，权限对账只剩 7 条操作级。
- 这些错误码都不在 `_FATAL_ERROR_CODES`（仅 `unsupported_format` / `invalid_type`）里 → 索引被判定为"可用"，消费方不会降级、不会报错，**输出结构仍是 `"enabled": true, "structure_source": "design-index"`**。
- 而 `design-set.py check` 只校验文件集合、路径、ID、依赖与指纹 → 通过。**全链路没有任何环节会暴露该问题。**

这属于"权威读取器在真实产物上返回空集"一类缺陷：形式上健康、事实上空转，与第 ⑫ 类教训（删掉锚点消费方等于取消检查）同族。

### 5.4 与本计划的关系

T-1 / F-1 要求"从当前 Design 枚举实际关系实例"，`F-5` 把 `design-index.py` 定位为确定性定位工具。**在 `pages = 0` 的产物上，任何基于索引的枚举都无从谈起**；而这一前提计划从未验证。

修法有两条，需用户选一侧（见 §7 决策）：写作侧禁止多级编号，或提取器侧容忍多级编号。后者是一行正则的事，但要把"已有项目是否普遍带编号"抽样确认后再定。

## 6. 更好的解决方案（建议）

### 6.1 核心判断

把"穷尽"当成**单一审查者的单次任务**是本轮困境的根源。13 轮数据给出的替代路径是：**按职责拆三层**，让机械的部分由机器穷尽，判断的部分由 LLM 承担，收敛的部分由明确停止条件保证。

### 6.2 三层方案

**层 1｜确定性候选枚举（新增，只出候选、不出结论）**

- 只回答两件事：①哪些实体之间声明了关系（页面属性、状态机、操作表、字段表、字典、契约、验收）；②哪些引用解析不到（名字引用了不存在实体、声明了但没有承载、承载了但没有声明）。
- 不做业务合理性判断，不设退出码门禁，输出候选清单 + `cannot_extract` 标记。
- 与既有先例同构：PRD 侧已有 `prd-consistency-check.py` 消费 `design-index` 做确定性对账；给 Design 内部做同构对账不是新增工具类别。
- 前提（必须先做，成本约一条命令）：**索引提取覆盖率实测**，即 §5。覆盖率不达标的实体类型不得进入枚举，且必须显式标注，不得静默返回空集。

**层 2｜LLM 逐候选判断**

允许排除，但排除必须引用正文事实；不可判定记 `risk`。这一层保留计划中正确的部分（双向核对、承载面枚举、修复宣称回读）。

**层 3｜收敛定义**

- 审查单元 = 一个业务闭环（单模块文件），跨模块只在显式契约层审；定义单次单元上限。
- 停止条件 = 覆盖表闭合；只有"新关系类型"可触发下一轮，已知类型的新实例按覆盖失败处理。

### 6.3 与计划方案的对比

| 维度 | 计划方案（D-1 A） | 建议方案 |
|---|---|---|
| 枚举方式 | 模型每轮现场发明关系实例 | 机械枚举候选 + 模型判断 |
| 完备性来源 | 模型这一次是否想到（同一风险换了作者） | 枚举由构造保证，判断交模型；遗漏显式标 `cannot_extract` |
| 排除 | 允许，无判据 | 允许，必须引用正文事实；判不准 = risk |
| 成本 | 每轮全量重读 152KB | 候选清单缩小判断面；但增加一次枚举运行 |
| 收敛判据 | 第二轮新增 P0/P1 = 0（可被更浅审查通过） | 覆盖表一致 + 新实例按缺陷处理 |
| 主要风险 | 与 6~13 轮同构地继续挤牙膏 | 候选误报消耗审查注意力；**已证明**（第 11~13 轮三种工具失败模式），故必须限定"只出候选、不设门禁" |
| 与本仓库原则 | 符合"指令优先" | 符合 §1.6（程序只做确定性问题）+ §1.7（四项证据）——枚举类缺陷有 13 轮复现、AI 自检反复漏、可低误报识别、结果直接触发修正 |

**两者不互斥**：计划的 RC-2/RC-3/RC-4/RC-6 修法（Fix 承载面闭环、Review 先独立后历史、真实产物验证、不设语义门禁）建议全部保留；建议方案替换的只是"枚举由谁做"与"收敛怎么判"。

### 6.4 一次性最小验证（建议插入 T-0 与 T-1 之间）

不必等 A/B 生成：**直接拿 13 轮历史就够**。

1. 在真实 Design 上跑索引覆盖率实测（§5.1），记录每类实体的提取数与非空率。
2. 用机械枚举产出候选清单，统计：命中了 50 个 P1 中的哪几条（按轮次报告的行号/实体定位）、误报候选多少条。
3. 判据：若候选能覆盖 ≥60% 的历史 P1 且误报候选 < 2 倍命中数 → 层 1 成立，进入规范落地；否则退回纯 instruction-first，并**在计划中如实写明穷尽性上限**。

这一步成本约一次脚本运行 + 一次人工核对，产出的是"脚本到底能不能帮上忙"的直接证据，比"先做 A/B 再看要不要脚本"快得多，也避免把最有杠杆的机制推迟到第二轮。
