## 1. 结论先行

**不是"人力测试 vs 脚本"的二选一。** 业界的实际分界线是**该判断能不能被机械判定**：

| 特征 | 交给谁 | 理由 |
|---|---|---|
| 可枚举、可穷举、有确定预期的组合（角色×动作、状态×事件、字段取值集合） | 脚本 | 人做会漏、会疲劳、会随版本回退 |
| 需要判断"这样写对不对""这个业务是否合理" | 人（且是对抗性的人） | 没有可匹配的签名，机器判不了 |
| 已经知道要查什么 | 自动化 | 契约、矩阵、不变量都能落成断言 |
| 还不知道要查什么 | 探索式审查 | 自动化的覆盖率上限＝你已知的问题清单 |

三条被反复印证的硬事实：

1. **OWASP 明确说扫描器找不到业务逻辑缺陷**：「这些缺陷没有签名可匹配。它们出现在看起来完全正常的代码里，因为缺陷不在任何一个单独的函数中——而在开发者假设与用户实际能做的事之间的缝隙里。」
2. **七个维度没有一个通用手段**。权限有权限矩阵、状态有状态机、结果去向有契约测试、字段来源有数据血缘——它们分属不同工具链，没有"一个平台全包"的成熟实践。
3. **唯一被公认的通用做法是"先把要查的东西写成清单"**：OWASP 的 *Write Down the Invariants*（把不变量用大白话写下来，然后逐条指出由哪段代码保证；如果答案是"UI 挡着"或"用户不会那样做"，就是不变量其实没被强制执行）。

## 2. 七个维度 × 主流手段对照

| 维度 | 业界主要手段 | 主导方 | 成熟度 | 代表工具/规范 |
|---|---|---|---|---|
| 权限 | 权限矩阵：角色 × 动作 × 数据范围**每一格都断言**，且允许与拒绝**双向**都断言 | 脚本 | 高 | 自研 matrix、OPA、Casbin |
| 流程 | 把工作流建模成**显式状态机**（服务端存储），拒绝跳步/重放/乱序；MBT 从模型生成路径 | 脚本 + 人定模型 | 高 | GraphWalker、AltWalker、Conformiq |
| 状态 | 合法迁移 + **非法迁移**都要测；「状态 × 事件」矩阵人工过一遍 | 脚本 + 人审 | 高 | GraphWalker、XState |
| 规则 | 判定表穷举条件组合；属性测试断言不变量；**变异测试**验证测试本身是否真能发现错 | 脚本 | 高 | Hypothesis / fast-check / jqwik、Stryker |
| 字段来源 | 列级数据血缘 + data contract + 内置数据测试（唯一/非空/可接受值/引用完整性）；「服务端重新推导」原则 | 脚本 | 中（偏数据工程） | dbt、OpenLineage、Great Expectations |
| 异常恢复 | 故障注入：**先写假设**再注入，有爆炸半径、停止条件、回滚；补偿链路与对账单独验证 | 脚本执行 + 人定假设 | 高（偏基础设施） | Chaos Mesh、AWS FIS、Litmus |
| 结果去向 | 消费方驱动的契约测试 + `can-i-deploy` 门禁；导出物用审批测试/金标快照比对 | 脚本 | 高 | Pact、ApprovalTests、Jest snapshot |

一个反直觉的发现：**「结果去向」在业界是靠契约测试解决的，而不是靠端到端测试**。GOV.UK Pay 明确说端到端测试"耗时、不可持续、资源密集，而且把微服务当单体测，拿不到微服务的好处"，于是转向契约测试。

## 3. 各手段的做法、出处与局限

### 3.1 权限：权限矩阵（脚本主导）

做法（原文五步，值得逐条对照 ShitPM 的权限审查）：

1. 先列出**全部角色**和**全部受保护动作**两张平表。仅这一步就常能发现"某个动作没人记得加角色""某个角色完全没有测试引用"。
2. 建**矩阵**而不是清单。清单只覆盖"有人想到要写下来的"；矩阵对每一格都显式断言允许与拒绝。
3. **把拒绝用例当一等断言**。只断言允许的矩阵，会在"新增权限但忘了在新入口加校验"时全绿通过——而那正是最典型的静默回归。
4. **缺格测试应阻塞 PR**，不是开个后续工单。作者明说这是策略决策，应写进贡献指南而不是靠 reviewer 记性。
5. **带真实资源边界测范围权限**：夹具里每个受限实体至少造两份（两个团队/两个租户），否则"跨范围拒绝"缺失时测试会静默通过。

出处：DEV Community《How to Write a Permission Test Matrix That Actually Catches Regressions》（已验证）。OWASP 侧对应 *Privilege Table*（动词＋名词构成权限，行=权限、列=角色，加一列"约束/备注"）与 *Contextual Authorization*（不仅"此人能否做 X"，而是"此人能否**在此状态、对此对象、此刻**做 X"）。

局限：矩阵规模随 角色×动作×范围 三维爆炸，需配合属性测试；只覆盖已建模的权限模型，模型本身漏了它查不出。

### 3.2 流程与状态：显式状态机 + 状态×事件矩阵

OWASP 把这条写成了规范要求，直接针对"多步流程"：

- **状态必须在服务端存储**，每一步校验当前状态；状态不匹配即拒绝。
- **不得把流程状态放在前端**（隐藏字段、客户端可读 cookie）——「客户端能设成任何值，这不是强制」。
- **拒绝已完成步骤的重放**（一次性操作：发奖励、核销券、领福利）。
- **部分完成状态要过期**（长期半成品的流程是"可利用不一致"的常见来源）。

工具侧：GraphWalker / AltWalker 从状态机生成测试路径，支持 state / edge / requirement 覆盖率判据；BrowserStack 与 LambdaTest 的 MBT 综述列出 FSM、状态图、判定表、数据流模型等建模形式。

局限（建模本身的教训）：**模型错则全错**——「MBT 的有效性取决于模型的准确性。如果模型有缺陷，会导致漏掉缺陷」，且建模需要技能与时间，"简单应用属于过度设计"。

### 3.3 规则：判定表 + 属性测试 + 变异测试

- **判定表**：多条条件组合的业务（资格、定价、折扣、税费）用判定表穷举；人工"从每个条件组合里挑代表值"会漏边界。
- **属性测试**：不当成"多写几个例子"，而是把系统不变量写成通用命题——守恒（总量不变）、往返（编解码回到原值）、等价（缓存路径＝非缓存路径）、幂等、单调、结构性约束（输出满足 schema）。金融系统的典型不变量：订单撮合前后总量守恒、币种换算往返回到原值（含舍入容差）、余额永不为负。代表性库：Hypothesis（Python）、fast-check（JS/TS）、jqwik（JVM）、FsCheck（.NET）、proptest（Rust）。
- **变异测试**：覆盖率的替代品。它不问"这行跑到了吗"，而问"这行改错了，测试会发现吗"。Stryker 官方支持 JS/TS、C#、Scala，30+ 变异算子。实测案例里两个模块都报 100% 覆盖率，但业务费用规则模块的变异分数只有 86%——存活的 5 个变异全是边界 off-by-one（`<= 1000` 改成 `< 1000`、`< 0` 改成 `<= 0`），也就是说：**满覆盖的绿徽章下藏着会出货的边界 bug**。

局限：等价变异体（改了对可观察行为无影响）永远杀不掉，所以 100% 不是合理目标，业务逻辑层 80%+ 是常见目标；变异测试慢（中型项目 10–30 分钟），通常放 CI 夜间或只对改动文件跑。

### 3.4 字段来源：数据血缘 + 数据契约 + 内置数据测试

- **列级血缘**是关键档位。表级血缘只说"这张表来自那几张表"，列级血缘能答"这个指标由上游哪几个具体列、经过哪几步转换算出"，把根因定位从小时压到分钟。
- **数据契约**：生产者与消费者之间的机器可读约定——schema、字段的**业务语义**、质量 SLA（时效、完整性、唯一性）、向后兼容承诺（哪种变更必须通知消费者）、责任人。
- **内置数据测试**（dbt 官方）：两类——singular（一个返回"失败记录"的 SQL，一次性断言）与 generic（参数化、可复用）；内置四个通用测试恰好覆盖四个维度：`unique`（唯一性）、`not_null`（非空）、`accepted_values`（取值集合）、`relationships`（引用完整性）。任何能用 `select` 表达的断言都可以写成 singular 测试，例如"退款总额非负"。
- **「服务端重新推导」原则**（OWASP）：凡是影响价格、访问、所有权、状态的值，都假设客户端编造、从可信数据重算。对应到字段来源审查就是：**每个关键字段都要能答出"谁写入、从哪来、依据什么"**。

局限：这套实践集中在数据工程/分析链路，业务应用侧的字段血缘成熟度低得多；血缘本身需要被验证，"假设血缘一旦采集就长期准确，是分析环境信任崩塌的常见原因"。

### 3.5 异常恢复：故障注入 / 混沌工程

AWS Well-Architected 把它列为可靠性最佳实践，做法是可迁移的：

1. **先选故障**：用 FMEA（失效模式与影响分析）做组件级分析，列出"设计上要抵御哪些故障"。
2. **给故障排优先级**：看频率 × 影响。
3. **写假设**：模板是「如果发生[具体故障]，[工作负载]将通过[缓解机制]维持[业务或技术指标]」。注意后半句必须是**业务或技术指标**，例如"服务 99 分位请求在 100ms 内""数据库读写错误少于一分钟"。
4. **注入并观察**：必须预设停止条件（AWS FIS 每个模板最多 5 条），爆炸半径最小化；先在非生产环境验证门限有效。
5. **验证假设并固化**：「如果系统能承受这些干扰，这个混沌实验就应该被保留为自动化回归测试，纳入 SDLC 与 CI/CD 流水线」。
6. **结果必须落盘**：时间、负载、条件、观测数据，供后续趋势分析。

关键判据说得很硬：**「如果你说不清业务假设，你就不是在跑混沌工程，你是在给平台团队找乐子。」**

局限：前提是可观测性成熟（metrics/logs/traces 齐全），"可观测性不成熟时混沌是破坏性的而非有信息量的"；金融等强监管场景需按受控生产变更管理（IAM、审批流、不可篡改审计）。成本上是"又一层平台"，只适合分布式、多依赖的系统。

### 3.6 结果去向：消费方驱动的契约测试

- 核心机制：消费者用测试描述它**实际用到**的请求/响应，生成契约（pact 文件）→ 发布到 Broker → 提供方拿契约对着真实实现回放验证 → `can-i-deploy` 在部署前检查"我要部署的版本是否与目标环境里的对端版本兼容"。
- 为什么比端到端测试好：GOV.UK Pay 的实践理由是端到端测试"时间开销大、不可持续、资源密集，而且是拿微服务当单体测"。契约测试不需要同时部署两端。
- 一个真实收益案例：信用检查服务把 `credit_score` 改名成 `creditScore`，自己单测全过、单独跑也没问题；没有契约测试时这会一路走到 staging 引发事故，有契约测试时提供方验证立刻失败、**阻塞合并**，两边五分钟对话解决。
- 契约与 schema（OpenAPI）不同：schema 是静态全量描述，契约是"按例子的契约"（contract by example），只覆盖消费者真正用到的部分——所以提供方未被使用的行为可以自由改动。
- 还有语言无关的**审批测试/金标快照**，专门处理"输出太复杂没法逐字段断言"的场景（PDF 报表、嵌套 JSON、导出 CSV、渲染 HTML）：先跑一遍、人审一遍、批准成基线，之后只比对差异。适用判据是"输出复杂到写断言变得脆弱"，不适用"含时间戳/随机 ID 且无法归一化"（必须先做冲刷/归一化）。

局限（重要教训）：GOV.UK Pay 踩了**循环依赖**——消费者改了契约但提供方无需改 API 时，双方流水线互相等对方先验证，导致谁也部署不了；解法是对提供方同时跑 master/test/staging/production 全部标签的契约。它还有"契约与提供方紧耦合"的副作用，工程师想让消费者契约先进分支、提供方后实现时会卡住（他们的绕法是不发布该 pact）。**这套机制的收益是在"多消费者、多团队、独立部署"时才成立**；单消费者场景集成测试更划算。

## 4. 社区与论坛的实际声音

### 4.1 「把状态机画成矩阵，而不是画成图」（HN，2022）

讨论帖 110 条评论，最受认同的补充正好是一个可迁移的审查技巧：

> 「描述状态机最抽象的方式是有向图，但（像几乎所有图问题一样）把它**分解成矩阵**往往同样清晰甚至更清晰。行是状态，列是事件，交叉点是迁移。能沿着某一列往下看、看清每个状态在某个事件到来时会发生什么，这让我发现了很多 bug。现在只要把状态机画成图，我就一定会同时给出矩阵表示。」

另一位实践者的经历更能说明收益形态：白板上一小时定下状态与事件（**连组件间的消息也被当作状态机事件**），团队分头重写代码，当天提交，第二天 QA 说"完美"；对照此前几个月是"QA 找到怪问题→有人调试→打补丁→宣称修好→其实破坏了另一个边界，永远如此"。

来源：Hacker News《Facts about State Machines》（内容经检索取得，直连受限未二次打开，见附表）。

### 4.2 「部署前检查业务流程本身能不能被绕过」（HN Show HN）

一位开发者提出的问题，几乎是 ShitPM 的存在理由：

> 「我们有为代码准备的扫描器、为系统准备的监控、多层控制与审计。但**业务流程本身，在它上线之前，很少被检查有没有逻辑漏洞**。KYC 开户、审批、支付、合规流程，往往是在会上设计、事后补文档的。」
>
> 他的做法是：把流程描述成状态机，然后跑静态检查——可达性、遗漏的评审步骤、没有补偿的不可逆动作。他管这叫"设计层面的业务流程漏洞"（business process vulnerabilities by design）。

来源：Hacker News《Show HN: Checking if financial processes can be bypassed before deployment》（同上，检索取得）。

**这条与 ShitPM 的 Design 审查思路高度重合**，价值在于：它说明"用状态机 + 静态规则在交付前查业务闭环"不是自造概念，而是有人在独立提出、并且在向真实从业者求验证（帖子里明确在问 fintech/银行/风险从业者"流程绕过在设计层面真实存在吗"）。

### 4.3 OWASP 对"为什么不能用自动化兜底"的解释

> 「自动化工具很难理解上下文，所以这类测试必须由人来做。」（业务逻辑测试）
>
> 「没有任何扫描器能替你找到这些 bug。它们没有可匹配的签名。它们出现在孤立看完全正常的代码里，因为 bug 不在任何一个单独的函数中——而在开发者假设与用户实际能做的之间的缝隙里。」

但 OWASP 同时给了自动化该做的部分：**不变量清单 + 针对每个不变量的失败测试**，并要求并发测试（两个请求竞争时断言终态一致：余额不为负、券只核销一次、奖励只发一次）与顺序测试（跳步、重放、乱序，期望结果都是拒绝而不是推进）。

### 4.4 一条被反复提到的边界

自动化套件"可能确认同一个错误假设在规模化下依然成立"。换言之：**断言写得弱，自动化只会把错的东西稳定地重复验证 N 遍**。这与"覆盖率高不等于质量高"是同一件事的两种说法。

## 5. 对 ShitPM 的可迁移启示

按"能落到 ShitPM 现有机制上"排序：

| # | 启示 | 对应 ShitPM 现状 | 建议动作 |
|---|---|---|---|
| 1 | **状态 × 事件矩阵**（HN） | 现有状态机检查是"孤岛/可达/终态"，属图视角 | 把矩阵作为人工审查清单的固化形式：行=状态、列=触发动作，空格子就是"某动作在某状态下没定义行为"，这是当前口径抓不到的 |
| 2 | **不变量清单**（OWASP） | Design 已有公式/规则/字段落点核对 | 在闭环回读里显式要求"写出该闭环必须永远成立的不变量，并指出由哪条规则/字段/操作保证"——比"逐个维度回读"更容易发现"写了但没人保证" |
| 3 | **权限矩阵双向断言**（dev.to） | 权限三态：合规矩阵可比对、自然语言 `not_evaluated` | 「只断言允许、不断言拒绝」的失效形态值得写进权限审查口径；跨范围（本项目 vs 其他项目）拒绝同理 |
| 4 | **变异测试思路**（Stryker） | 本轮刚用上 sabotage 反证法（还原缺陷看测试是否转红） | 已有实践，但只用于脚本测试；可推广到"Design 规则的回退反证"——把一条已写明的业务规则从产物里移除，看审查是否会漏报 |
| 5 | **契约测试 + can-i-deploy**（Pact） | Design→PRD 一致性检查本质是契约验证 | `can-i-deploy` 的语义（对端版本不兼容就不许部署）对应"Design 变更后下游未同步就不得视为完成"，可作为下游同步判据的表述参照 |
| 6 | **审批测试/金标**（ApprovalTests） | Prototype 视觉基线 | 适合导出物类产物（报表/CSV/PDF 字段清单）做基线比对，前提是先归一化时间戳与 ID |
| 7 | **混沌工程的假设模板**（AWS） | 异常恢复维度目前靠回读清单 | 假设模板可直接借用：「如果[故障]，[闭环]将通过[补偿机制]维持[业务结果]」——比"是否有失败重试"更可验证 |
| 8 | **流程状态不得放前端**（OWASP） | 原型/Demo 常有路由壳与前端状态 | 审查原型时可用于识别"UI 挡着就等于没挡"的假闭环 |

## 6. 明确不该迁移的部分

避免把调研结论变成新负担：

- **混沌工程工具链**（Chaos Mesh / AWS FIS）：前提是可观测性成熟，成本是"又一层平台"。ShitPM 是文档/Skill 工具链，无运行时系统可注入，只能借用其**假设模板与判据**。
- **MBT 建模工具**（GraphWalker 等）：需要持续维护模型，官方自己说"简单应用属过度设计"、"模型错则全错"。ShitPM 的"模型"是 Design 本身，不需要另起一套。
- **列级血缘平台**（OpenLineage / DataHub 等）：面向数据管道，业务应用侧收益不明，接入成本高。
- **变异测试全量跑**：慢（10–30 分钟起），只适合作为"验证审查本身有效性"的抽检手段，不适合做门禁。
- **权限矩阵"缺格即阻塞"的门禁形态**：这是工程团队的选择（`AGENTS.md` §1 明确反对把 Review 变成门禁），ShitPM 只应借用"双向断言"这个**审查判据**，不引入"缺格即失败"的机制。
