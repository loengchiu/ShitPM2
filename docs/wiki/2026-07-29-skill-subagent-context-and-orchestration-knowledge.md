# Skill、子代理与上下文编排知识总结

日期：2026-07-29

## 一、先说结论

今天确认的核心问题不是“模型不够聪明”，而是**运行方式没有被明确编排**：

1. Skill 负责定义“这一阶段应该做什么、不能做什么”。
2. 编排器负责决定“现在先做哪一个动作”。
3. 子代理负责执行一个边界清楚的动作，不负责重新规划整个流程。
4. 上下文必须按任务拆分，不能把全部历史、材料和中间产物反复装入每个阶段。
5. 原始材料的扫描、索引和事实提取应尽量提前完成，Design 阶段主要读取已经准备好的结果。
6. 零模型测试通过，不等于真实模型运行通过；模拟宿主的记录也不等于真实宿主的审计记录。

本次优化的目标是：**减少重复读取材料，控制上下文大小，让每个阶段只拿到完成当前任务所需的信息。**

---

## 二、Skill 是什么

### 2.1 Skill 不是一句提示词

Skill 是一组阶段规则，至少应说明：

- 当前阶段的目标；
- 必须完成的分析责任；
- 可以读取哪些输入；
- 应该生成哪些输出；
- 哪些事情不能在本阶段做；
- 完成后如何判断本阶段结束。

因此，Skill 不能只写“请生成一份文档”，而要明确输入、过程边界和输出要求。

### 2.2 Skill 入口与实际执行不是一回事

当前正式的 Design Skill 是：

```text
spm-design
```

不要把 `/spm` 当作正式的 Design 执行入口，也不能根据用户有没有输入某个命令，就判断子代理是否被启用。

必须区分：

- **入口**：用户如何要求系统进入某个阶段；
- **Skill**：该阶段应该遵守的规则；
- **编排器**：该阶段应该按什么顺序执行；
- **宿主**：实际启动模型和子代理的运行环境。

测试时必须记录实际执行的 Skill、实际动作和模型调用，而不能只记录用户输入的命令。

### 2.3 Align 与 Design 的关系

`spm-align` 是可选的需求整理阶段，不是 Design 的硬性前置。

如果使用 Align，它更适合完成：

- 整理目标和范围；
- 登记原始材料；
- 建立材料索引；
- 计算内容哈希；
- 提取可复用的材料事实；
- 标记不确定点和待确认问题。

`spm-design` 负责产品定义和 Design 基线。它不应该每次重新扫描全部原始文件，而应该优先读取 Align 或材料准备阶段已经生成的有效结果。

## 三、子代理是什么

### 3.1 子代理是执行单元，不是自动优化开关

启用子代理不会自动让流程变快。

只有在以下条件同时满足时，子代理才可能带来收益：

- 任务可以独立拆分；
- 子代理只拿到必要输入；
- 子代理不重复读取父任务的全部上下文；
- 子代理完成后只返回必要结果；
- 主流程不因为子代理失败而重复执行全部上游工作。

如果只是把同样的大上下文复制给多个子代理，子代理越多，成本和时间可能越高。

### 3.2 子代理不应该重新规划完整流程

主代理或子代理都不应该临时决定：

> “我先读所有文件，再重新设计一套流程，然后再决定下一步。”

正确做法是由编排器根据当前产物和依赖，返回**唯一的下一个动作**。子代理只执行这个动作。

每个子代理任务都应有：

- 明确的目标；
- 明确的输入文件和输入哈希；
- 明确的允许读取范围；
- 明确的输出文件或输出结构；
- 明确的完成检查；
- 明确的禁止输入。

### 3.3 Design 完整模式中的子代理分工

完整模式的主路径默认控制为三次核心模型动作：

1. Design 分析；
2. 业务模型挑战；
3. Design 写作，并在写作动作内部完成自查。

默认不再额外增加第四次独立成品审查。Review 是按需的独立第二意见，不是每次 Design 都必须执行的动作。

### 3.4 模拟宿主不能代表真实宿主

`fake-design-host.py` 只能证明编排器的程序逻辑可以运行，例如：

- 是否只返回一个下一动作；
- 是否能够按依赖顺序推进；
- 缓存命中时是否避免重复处理；
- 中断后是否能够恢复。

它不能证明真实 Codex 宿主中：

- 子代理一定按照同样方式启动；
- 子代理实际读取了哪些文件；
- 子代理继承了哪些隐藏上下文；
- 模型实际收到了哪些内容。

因此，模拟测试通过后，只能说“程序控制逻辑通过”，不能说“真实运行已经通过”。

## 四、上下文编排

### 4.1 上下文变慢的主要原因

本次运行中，最重要的性能风险是**同一批信息被多次重新读取和重新装入上下文**，包括：

- 完整聊天历史；
- 完整原始材料；
- 完整规则包；
- 完整 Align 产物；
- 完整 Design 中间产物；
- 前一阶段已经提取过的事实。

即使系统自动压缩上下文，只要这些内容不断被重新加入，整体输入仍然会持续膨胀。

所以，“自动压缩过几次”不能证明上下文问题已经解决。

### 4.2 材料准备应提前完成

推荐的材料处理顺序是：

```text
原始材料
  → 来源登记
  → 内容哈希
  → 索引建立
  → 事实提取
  → 材料事实资产
  → Design 读取
```

Design 阶段默认读取：

- 材料索引；
- 材料事实；
- 来源哈希；
- 必要时的定点原文片段。

Design 阶段不应再次扫描全部原始材料。

### 4.3 材料缓存和局部失效

材料没有变化时：

- 不重新读取全部原始文件；
- 不重新建立索引；
- 不重新提取事实；
- 材料事实提取次数应为 0。

只有某一个来源发生变化时，才让该来源及其下游结果失效。其他没有变化的来源和事实应继续复用。

判断材料是否变化，应以内容哈希为主，而不是只看文件修改时间。

### 4.4 阶段之间只传递必要内容

每个阶段都应该使用最小输入：

- 任务说明；
- 允许读取的文件；
- 输入哈希；
- 必要的材料事实；
- 上游阶段的结构化结果。

不应把整个上一阶段的聊天过程原样传给下一阶段。

也不应把全部规则正文、全部原始文件和全部中间文档一次性装入模型上下文。

### 4.5 必须分别记录三种成本

性能分析至少要分别记录：

1. **材料处理次数**：原始材料被扫描或事实提取了几次；
2. **模型调用次数**：实际调用了几次模型；
3. **上下文大小**：每次模型调用输入了多少内容。

只记录总耗时不够，因为“慢”可能来自：

- 材料读取重复；
- 模型调用过多；
- 上下文过大；
- 宿主排队或执行开销。

## 五、顺序编排

### 5.1 推荐的 Design 顺序

完整模式的推荐顺序是：

```text
材料准备
  → Design 分析
  → 业务模型挑战
  → Design 写作与写作内自查
  → 确定性检查
  → 完成
```

其中：

- 材料准备只在材料没有有效资产，或材料发生变化时执行；
- Design 分析必须先于业务模型挑战；
- 业务模型挑战必须先于 Design 写作；
- 写作完成后才做确定性检查；
- 确定性检查通过后才标记完成。

### 5.2 每次只推进一个动作

编排器每次只返回一个下一动作，不一次返回一长串让主代理自行安排。

这样做的好处是：

- 当前状态清楚；
- 每一步都可以单独记录；
- 中断后可以准确恢复；
- 失败时不会把整个流程重新跑一遍；
- 可以明确知道是哪一步增加了时间和上下文。

### 5.3 下游失败不能重跑有效上游

例如：

- Design 分析已经完成；
- 业务模型挑战已经完成；
- Design 写作失败。

正确行为是只重试写作，不重新读取材料、不重新做分析、不重新做挑战。

如果材料、分析或挑战没有变化，相关结果应继续复用。

### 5.4 中断后的恢复方式

中断后，应从第一个无效或未完成的动作恢复：

```text
已有有效材料
  → 保留
已有有效分析
  → 保留
已有有效挑战
  → 保留
从未完成的写作动作继续
```

不能因为运行记录丢失，就默认所有工作都失效并从头开始。

但如果产物的输入哈希已经陈旧，或者产物结构损坏，则必须从第一个陈旧或损坏的产物开始恢复。

### 5.5 规则包也有依赖关系

规则包变化会影响不同范围的工作：

- 分析规则包变化：分析及其下游失效；
- 挑战规则包变化：挑战、写作和检查失效；
- 写作规则包变化：写作和检查失效；
- 检查脚本变化：只重新做确定性检查。

不能因为某一个规则包变化，就把材料准备和全部阶段重新执行。

## 六、测试和真实运行的边界

### 6.1 三种“通过”不能混为一谈

必须区分：

| 结论 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 零模型测试通过 | 编排器程序逻辑正确 | 真实模型是否按计划执行 |
| 合成项目在线测试通过 | 小范围真实模型调用可运行 | 真实项目一定不会出现问题 |
| 真实项目运行完成 | 真实项目这一次得到了结果 | 运行过程一定高效、一定没有重复读取 |
| 宿主级审计通过 | 能检查真实调用、读取和上下文 | 业务设计质量自动正确 |

### 6.2 真实项目不能作为第一测试场

正确顺序是：

```text
零模型测试
  → 小型合成项目在线测试
  → 真实项目一次冷启动
  → 真实项目一次复用或恢复
```

如果在线测试工具不存在，或者宿主无法提供关键运行记录，就不能把真实项目运行称为正式验收。

### 6.3 观察性试跑的限制

如果业务上必须提前了解真实效果，只能做一次“观察性试跑”，并明确它不是正式验收。

观察性试跑必须记录：

- 总耗时；
- 模型调用次数；
- 每次调用的上下文大小；
- 材料事实提取次数；
- 是否重复读取材料；
- 是否启动子代理；
- 当前记录中哪些内容无法证明。

不能为了找问题而反复运行真实项目，因为每次运行都会消耗大量时间和 token，而且无法保证问题定位准确。

## 七、目前已经确认和仍未确认的内容

### 已经确认

- 编排器的零模型测试通过；
- 可以用程序控制单步动作和依赖顺序；
- 可以设计材料缓存、局部失效和中断恢复；
- 子代理可以被启动并完成一个小型任务；
- 通过合理拆分任务，可以避免每个阶段都重新读取全部材料。

### 仍未完全确认

- 真实 Codex 宿主是否始终按照编排器要求启动子代理；
- 子代理实际打开了哪些文件；
- 子代理是否继承了父任务的隐藏上下文；
- 每次模型调用实际收到的完整输入；
- 真实项目运行是否能稳定降低总耗时。

因此，当前最准确的状态是：

> **程序层面的编排方案已经通过自动测试；真实宿主层面的读取范围、上下文继承和性能效果仍待验证。**
