## 1. 目的、输入与边界

生成或修改 `output/design/design.md` 前，先完成 Align 需求事实形成，再按用户选择的模式分析。Align、用户原话、用户回答、详细材料事实、已有 Design 和明确提供的历史产物都是输入；`output/design/design.md` 仍是最终唯一产品事实源。

共同整理以下类型：

1. 已确认事实：材料明确写出或用户明确回答的目标、范围、页面、字段、操作、规则、状态、异常和约束；
2. 可直接推导结论：不引入新业务事实的必然结构；
3. 材料冲突：不同来源对同一事项的矛盾；
4. 明确废弃事实：用户或最新材料明确不再采用的旧内容；
5. 模型推测：只供分析参考，不能当作确认事实；
6. 高影响待确认：答案不同会改变流程、权限、数据范围、状态、集成、页面、字段、操作或验收的事项；
7. 低影响待确认：不阻塞继续但需要记录的事项。

没有材料时 `source_count=0` 合法；用户描述和回答可以形成事实，但不得伪造材料来源或行号。详细材料事实不能被短摘要替代，最终写作必须回读来源事实和所有适用的 ABC 结论。

Align 不承担最终方案决策；Design 不得绕过 Align，也不得把规则包或中间资产存在视为分析已完成。

## 2. 模式选择协议

用户已明确 simple 或 full 时直接采用；未明确时只询问一次：

> 本次 Design 使用简单模式还是完整模式？简单模式完成最小业务闭环；完整模式适合多角色、状态流转、数据隔离、跨系统或方案权衡，并承担 A/B/C 分析。

未获得选择前不正式写入 Design，不替用户自动判断或切换模式。

## 3. 简单模式协议

简单模式在一次分析写作动作中合并承担最小 A/B/C 责任，必须覆盖：

- 目标、用户、场景、成功判断、范围内外和系统边界；
- 端到端最小业务闭环、角色责任、关键对象、规则和必要状态；
- 权限、数据范围、页面、区块、逐项字段、逐项操作、反馈和异常；
- 适用的唯一性、时间、重复、并发、外部失败、文件/批量和产品级非功能要求；
- 可观察的验收条件。

只展开实际适用内容，不虚构干系人地图、用户旅程、状态机、权限或非功能章节。结束前必须做一次来源到 Design 的回读并直接修正。

## 4. 完整模式协议：A/B/C

完整模式按责任顺序完成 A、B、C；每层可以在一次完整思考中承担多个 Park 对应责任，不生成 Park 的细粒度程序节点。进入下一层前暴露并处理高影响未知。

### 4.1 A：需求理解

对齐 Park 的需求澄清、干系人、目标指标、用户场景与旅程、用户故事和范围边界责任，形成：

1. 业务背景、当前问题和不解决的代价；
2. 直接用户、业务责任人、上下游参与者、受影响方；
3. 各角色目标、责任、痛点、收益和可能冲突；
4. 业务目标、用户目标、组织目标、成功指标、判断口径和失败判定；
5. 关键场景的触发、前置、用户动作、信息需求、结束状态和后续责任；
6. 用户要完成的任务、用户故事和预期业务结果；
7. 范围内、范围外、暂缓、阶段边界、系统边界、人工边界、组织责任边界和外部依赖；
8. 材料冲突、推测和仍会改变方案的未知项。

A 完成标准：读者能回答为什么做、为谁做、解决什么、在什么场景发生、做到什么程度、不做什么、哪些内容不能安全决定。

### 4.2 B：业务建模

按业务特点选择适用责任，对齐 Park 的业务过程、用例、业务对象、对象关系、对象行为、生命周期与状态、决策与业务规则、异常与边界、数据流、逻辑数据模型、数据字典和业务模型审查：

1. 端到端主流程、替代流程和必要子流程；
2. 参与者、触发事件、输入、活动、输出、业务结果和系统/人工/外部边界；
3. 角色交接、责任归属和可观察结果；
4. 核心对象、对象职责、关键属性、归属/主从/数量/版本/历史关系；
5. 对象行为、触发条件、前置条件、后置条件和副作用；
6. 状态含义、进入条件、允许动作、下一状态、终态、可逆性和状态副作用；
7. 判断、计算、时间、权限、统计口径、适用范围和例外规则；
8. 失败、超时、重复、并发、部分成功、撤回、驳回、中止和恢复；
9. 数据来源、产生者、消费者、流向、存储责任和事实源；
10. 业务字段、枚举、格式、口径和数据关系；
11. 流程、对象、状态、规则、角色和数据之间的一致性。

B 不根据菜单或页面反推不存在的业务事实。没有真实状态变化时写“无状态机”，不机械生成完整数据模型。

### 4.3 C：系统需求与产品承接

对齐 Park 的系统功能、交互与原型、权限、系统数据、非功能、集成和验收责任，从 A/B 逐一承接：

1. 系统能力、功能域、模块和可验收功能项；
2. 产品端、菜单、导航、页面层级、父页面、入口、返回目标；
3. 角色可见菜单、可访问页面、不可见页面和无权限处理；
4. 每个页面的目的、适用角色、核心对象和承载功能；
5. 页面区块、字段全集、操作全集、前置条件、输入、确认、结果、反馈和失败恢复；
6. 加载、空、异常、无权限和关键业务状态；
7. 操作权限、数据权限、字段例外、敏感操作和职责分离；
8. 创建、查询、修改、归档、同步和审计所需的产品数据；
9. 必填、唯一性、完整性、一致性、保留期、脱敏和审计要求；
10. 外部系统触发、输入输出、时效、失败、补偿和责任边界；
11. 适用的性能、容量、安全、可用性、兼容、合规和审计要求；
12. 正常、规则、权限、交互、异常、边界和页面完成标准对应的验收条件。

C 完成标准：每个关键业务动作都有系统能力、数据、权限、反馈和验收承接；每个页面的字段、操作、状态和异常可落地；每个能力都可追溯到目标、场景、流程、规则或约束；C 不创建 A/B 不存在的高影响事实。

## 5. 跨层回读与挑战

完整模式至少回读以下关系；简单模式只检查实际涉及项：

| 对照 | 必问问题 |
| --- | --- |
| 来源事实 ↔ Design | 每个详细页面、字段、操作、枚举、规则、状态、异常和验收是否有落点或明确排除理由？ |
| 目标 ↔ 能力 | 每个目标和成功指标由哪些能力承接？ |
| 场景 ↔ 流程 | 每个关键场景是否从触发走到业务结果？ |
| 流程 ↔ 页面 | 每个系统动作是否有页面、操作或明确的系统能力承接？ |
| 动作 ↔ 权限/结果 | 谁在什么条件下操作，改变什么数据/状态，成功和失败如何反馈？ |
| 对象 ↔ 字段/状态 | 对象关系、字段、状态和数据变化是否一致？ |
| 规则 ↔ 操作/验收 | 规则是否覆盖全部适用操作，且能被验收观察？ |
| 状态 ↔ 出路 | 每个非终态是否都有合法出路，非初始态是否有入路？ |
| 异常 ↔ 恢复 | 失败、超时、重复、并发、部分成功和外部失败是否有产品结果、恢复方式和责任？ |
| 权限 ↔ 数据范围 | 操作权限、页面权限、字段权限和数据范围是否分开表达？ |
| 页面身份 ↔ 展示行为 | 业务侧、入口/菜单/路由、业务阶段、返回目标、区块目的、无权限、加载中/骨架屏、空态、异常态、超长文本、默认值和标签颜色是否能逐页定位？ |
| 自动动作 ↔ 失败责任 | 自动生成/挂号/归档/迁移是否有触发、成功、失败、状态保留、用户反馈和人工处理或待确认？ |
| 删除传播 ↔ 生命周期 | 主对象、子对象、关联、审批、日志、附件、历史、引用、查询可见性和恢复/审计追溯是否有规则或待确认？ |
| 枚举/上限 ↔ 来源 | 枚举是否有具体值或正式初始化清单；分页、导出、批量、首页和文件限制是否分别有来源或待确认？ |
| 事实 ↔ 推测 | 是否把模型推测写成已确认事实？ |
| 未知 ↔ 用户 | 是否存在未暴露的高影响拍板？ |

发现缺口时直接修正 `design.md`；不能安全决定时在正文“待确认事项”中说明影响、保守表达和确认责任。高影响冲突要记录冲突位置、冲突内容、影响对象和受影响模块，并停止受影响事实的继续写作。不输出独立完整度报告。

## 6. 分析与写作边界

内部可以有 Align、A、B、C 和写作动作，但最终正文按产品经理理解顺序组织，不粘贴任务编号、ABC 过程、回执、metadata 或提示词。重要结论不能只留在中间资产或 `decision-notes.md`；必须进入 `design.md`，或者作为明确待确认事项进入正文。

正式输出只有 `output/design/design.md` 和 `output/design/decision-notes.md`。Review、确认、PRD 和 Prototype 不属于首次生成前置。
