## 1. 目的与边界

本协议定义 `spm-design` 在生成或修改 `output/design/design.md` 前必须承担的分析责任。它服务于两种用户可选择的模式：**简单模式**和**完整模式**。

- 模式由用户明确选择；未指定时只询问一次。
- 系统不根据关键词、文件数量、历史产物或模型判断自动切换模式。
- Align 是可选输入，不是进入 Design 的前置条件。
- ABC 是完整模式的内部分析责任，不是最终 `design.md` 的目录。
- Review 是独立第二意见，不是 Design 首次生成的前置步骤；本协议不自动执行 Review，也不自动确认 Design。
- 内部分析可以使用任何实现机制，但最终产物只保留业务事实、待确认事项和审计用 `decision-notes.md`，不输出 Worker、提示词、稳定 ID、缓存或调试结构。

## 2. 共同输入整理

先从用户原始需求、可选 Align、现有 Design 及明确提供的背景材料中整理四类内容：

1. **已确认事实**：材料明确说出的目标、范围、角色、规则、流程、约束；
2. **可直接推导结论**：不引入新业务事实、能从已有事实必然推出的结构；
3. **材料冲突**：不同来源对同一范围、角色、规则、状态或责任的矛盾；
4. **高影响待确认**：如果静默选择会改变流程、权限、数据范围、状态、集成、验收或下游实现的事项。

整理结果只用于分析，不成为新的产品事实源。任何冲突都必须在分析阶段解决、保守表达或显式标记为“待确认”，不能藏在 `decision-notes.md` 中替代 Design 正文。

## 3. 模式选择协议

### 3.1 用户已明确模式

直接采用用户指定的“简单模式”或“完整模式”，不再次询问，不升级、不降级。

### 3.2 用户未明确模式

只提出一次选择问题：

> 本次 Design 使用哪种模式？
> - **简单模式**：适合小范围、低耦合变更，完成最小业务闭环；
> - **完整模式**：适合多角色、多对象、状态流转、跨系统或存在明显方案权衡的需求，完成 ABC 分析和一致性挑战。

用户选择后继续；未获得选择时停止正式写入，不替用户判断。

## 4. 简单模式协议

简单模式的目标是用最少结构完成可评审的业务闭环。必须回答：

1. 目标与预期结果；
2. 范围内、范围外和受影响的现有内容；
3. 直接使用者、执行者和必要责任人；
4. 从触发到完成的主路径；
5. 直接影响结果的关键规则和约束；
6. 必要功能、交互、数据和页面/字段落点；
7. 最可能且会改变结果的异常、失败或边界；
8. 适用的唯一性、时间边界、数据生命周期、重复操作和并发冲突的产品结果；
9. 可执行的验收条件。

按需补充：

- 只有存在状态变化的对象才定义状态机；无状态对象写明“无状态机”；
- 只有存在角色差异或敏感动作才展开权限；
- 只有存在外部系统才展开事实源、同步方向、失败、部分成功、重试、幂等、补偿和最终责任；
- 只有存在文件、导入导出或批量操作才展开格式、大小、数量、范围、上限和部分失败结果；
- 只有现状变更才说明兼容、迁移和受影响范围；
- 只有实际影响产品验收时才说明性能、安全、审计、留存和兼容要求，不展开技术实现。

简单模式不得为了形式完整生成无关干系人地图、虚构用户旅程、空的非功能章节、空状态机或与本次变更无关的完整系统重写。

## 5. 完整模式协议：ABC

完整模式在正式写作前依次完成 A、B、C 三类责任，并对每类结论执行挑战。每项只保留适用结论、对方案有影响的结论或“不适用”的理由。

### 5.1 A：需求理解

识别并说明：

- 原始诉求和要解决的真实问题；
- 直接用户、业务责任人、上下游参与者和受影响方；
- 目标、非目标、成功标准、失败判定；
- 关键场景、触发条件、完成路径和边界场景；
- 依赖、约束、现状基线、范围内外；
- 仍会改变方案的未知项及其影响。

A 的完成标准：读者能回答“为什么做、为谁做、解决什么、做到什么程度、不做什么”。

### 5.2 B：业务建模

从三个互相校验的视角建模：

**流程视角**

- 主链路、阶段、角色交接和业务结果；
- 条件分支、回退、撤回、驳回、重提、中止和失败；
- 每个动作的输入、输出、对象变化和责任归属；
- 跨模块、跨组织、跨系统的责任边界。

**对象视角**

- 核心业务对象、对象关系、数量/金额/版本/历史关系；
- 生命周期、状态、触发动作、状态副作用；
- 不可逆结果、审计记录、版本和并发影响。

**规则与责任视角**

- 业务规则、计算规则、决策条件、适用范围和例外；
- 角色职责、操作权限、数据范围和职责分离；
- 异常恢复、补偿和最终责任。

B 的完成标准：流程、对象、状态、规则、角色和数据能互相解释，不存在孤立的状态、角色或功能。

### 5.3 B3：业务模型一致性挑战

对每个关键动作逐项追问：

1. 谁在什么条件下执行；
2. 影响哪个对象、字段、数量、金额、版本或状态；
3. 成功和失败分别产生什么业务结果；
4. 回退、驳回、撤回或中止后是否能重新进入合法路径；
5. 每个非终态是否都有所有合法业务出路；
6. 每条规则是否覆盖全部适用操作，是否存在不对称；
7. 操作人是否符合真实职责，是否存在自确认或职责分离风险；
8. 范围排除项是否被功能、页面或集成重新引入；
9. 对象、关系、数量和历史是否会因部分成功而失真；
10. 唯一性冲突、重复提交、多窗口编辑或并发更新时，用户看到什么结果，哪份数据有效；
11. 新建、修改、删除、作废、归档、恢复后，当前数据、历史记录和关联数据如何变化；
12. 周期、截止时间、时区、自然日/工作日和统计口径是否足以唯一判断结果；
13. 文件、导入导出或批量操作是否明确范围、上限、部分失败和结果反馈；
14. 外部系统失败、超时或部分成功后，事实源、补偿入口、最终状态和责任人是否明确。

发现缺口后回到 B 修正；无法判断的高影响事项进入 Design 的“待确认”。不能把已知缺口留给 Review。以上问题只在场景实际存在时展开，不为不适用场景生成空规则。

### 5.4 C：系统需求

从 A/B 推导并逐一承接：

- 功能边界、页面入口、关键操作和反馈；
- 权限、数据范围和敏感操作保护；
- 字段、字典、校验、唯一性、默认值、业务来源、生命周期、历史和审计；
- 实际需要的列表默认查询、筛选、排序、分页和刷新口径；
- 实际需要的文件、导入导出、批量操作及部分失败结果；
- 集成事实源、同步方向、消息、超时、重复、部分成功、补偿和最终责任；
- 性能、安全、可用性、兼容、留存等实际产品级非功能要求；
- 覆盖主路径、分支、规则、数据副作用和异常的验收条件。

C 的完成标准：每个关键业务动作都有系统能力、数据、权限、反馈和验收承接；每个系统能力都能追溯到业务目标或约束。

## 6. 跨层挑战矩阵

完整模式必须逐项检查；简单模式只检查需求实际涉及的项。

| 编号 | 对照层 | 必问问题 | 典型缺口 |
| --- | --- | --- | --- |
| X1 | 目标 ↔ 功能 | 每个目标由哪些功能承接？ | 有目标无能力或有能力无目标 |
| X2 | 范围 ↔ 功能 | 排除项是否被重新引入？承诺是否遗漏？ | 范围与功能矛盾 |
| X3 | 场景 ↔ 流程 | 关键场景能否走到业务结果？ | 场景无法闭环 |
| X4 | 流程 ↔ 功能 | 人工步骤和系统步骤边界是否清楚？ | 责任落空或重复建设 |
| X5 | 流程 ↔ 状态 | 每个动作是否有状态结果？每个状态是否有触发来源？ | 状态孤岛、动作无状态 |
| X6 | 流程 ↔ 异常 | 失败、驳回、中止后是否有恢复路径？ | 断链、死循环 |
| X7 | 角色 ↔ 权限 | 谁能操作、谁能看哪些数据？ | 越权、自确认、范围越界 |
| X8 | 对象 ↔ 数据 | 对象关系、字段和数据变化是否一致？ | 统计或数量失真 |
| X9 | 规则 ↔ 操作 | 规则在所有适用动作中是否一致？ | 规则遗漏或不对称 |
| X10 | 规则 ↔ 验收 | 关键规则能否被测试验证？ | 无法判定完成 |
| X11 | 集成 ↔ 补偿 | 超时、重复、部分成功如何处理？ | 外部失败造成业务不一致 |
| X12 | 功能 ↔ 验收 | 每项功能有明确成功/失败判定吗？ | 功能描述无法交付 |
| X13 | 动作 ↔ 生命周期 | 新建、修改、删除、作废、归档、恢复分别改变哪些当前数据、历史和关联数据？ | 动作完成但数据结果不确定 |
| X14 | 规则 ↔ 边界 | 唯一性、时间口径、重复提交和并发冲突能否唯一判定？ | 同一场景产生多个合法解释 |
| X15 | 质量约束 ↔ 验收 | 实际适用的性能、安全、审计、留存和兼容要求是否可观察、可验收？ | 约束存在但研发和测试无共同口径 |

挑战结论必须修正正式 Design，或在正文显式写成待确认；不输出矩阵过程本身。

## 7. 四段职责与写作边界

内部执行分为四段：

1. **分析**：按模式整理事实和业务关系；
2. **挑战**：独立寻找冲突、断链、未授权假设和缺失出路；
3. **写作**：按业务闭环组织人类可读 Design，不按 ABC 逐项粘贴；
4. **成品审查**：检查分析结论是否丢失、事实是否冲突、是否可实现/可验收、是否引入无来源高影响事实。

只有四段都完成且没有未暴露的高影响缺口，才写入正式 `design.md`。四段是内部职责，不是最终文档标题，也不是用户需要审批的中间产物。

## 8. 输出与确认边界

正式输出只有：

- `output/design/design.md`：产品、研发和测试共同使用的唯一事实基线；
- `output/design/decision-notes.md`：只记录设计决策、偏离、权衡、待确认，用于审计。

不会自动执行 Review、不会自动写确认标记、不会把分析中间结果写入 Design 之外的产品事实文件。用户确认后，下游才可读取确认版 Design。
