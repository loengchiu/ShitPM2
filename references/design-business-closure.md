## 1. 这份规则解决什么

Design 的失败很少来自"缺一个章节"，而来自"章节都在，但它们描述的事实互相接不上"。典型形态：

- 写了角色、状态、操作，但没有一个操作能把某个非终态推到下一个状态；
- 写了公式里的金额项，但字段表和导出物里都没有它；
- 写了一条约束，却只落在被点名的那一句，同约束的其他承载面仍是旧口径；
- 同一对象按统称写了可见性，但它的细分类型实际需要不同口径。

这些都不是格式问题，也无法靠"检查维度是否存在"发现。原因是：维度存在不等于该维度下的**每个适用实例**都被判断过，也不等于**维度本身**已经齐全。

因此本规则只做一件事：把"业务闭环"拆成**可枚举的关系实例**，并规定每个实例必须有明确结论。

> 关系维度的来源与建模流程见 [design-analysis-protocol.md](design-analysis-protocol.md)；本文件不重复需求理解与 ABC 责任的定义，只定义闭合判断。

## 2. 业务闭环单元

**业务闭环单元**是审查、写作自检和影响面回扫的共同切分粒度，取以下两种之一：

1. **一个主业务对象的完整生命周期**：从创建到终态，包含期间的回退、作废、异常与恢复。
2. **一条端到端业务结果**：跨对象、跨角色完成的一个业务结果（如"一次月度结算完成并同步到列表、详情、统计与导出"）。

切分规则：

- 按生命周期或端到端结果切，**不按文件机械切**。一个模块文件可以包含多个单元，一个单元也可以跨多个文件。
- 单元的边界是"状态能否自洽闭合"，不是"标题层级"。
- 跨模块交接必须作为**独立的集成单元**审查，不能默认由任一模块单元覆盖。
- 单元划分完成后，每个单元携带直接相关的页面、角色、对象（含细分类型）、动作、状态、字段、规则、异常、出口。

## 3. 关系实例与关系维度

**关系实例**是"某个具体对象在具体条件下，与角色/状态/动作/数据/规则/结果之间的一条实际组合"。判断的对象是实例，不是维度名。

### 3.1 关系维度清单

逐单元枚举以下维度下的实例：

| 维度 | 要判断什么 |
|---|---|
| 角色与权限 | 谁能发起、谁能审批、谁能查看、谁能导出；同一动作在不同角色下的可用条件是否都成立 |
| 对象与细分类型 | 统称对象下的每个细分类型是否分别判断（见 3.2） |
| 状态与迁移 | 每个非终态是否有出路；每个终态是否可达且不可逆后果已声明；状态驱动展示是否覆盖每个状态 |
| 动作与前置条件 | 每个动作的可用条件是否覆盖该动作全部合法取值组合；输入项是否都有定义与落点 |
| 数据范围 | 每个角色在每个状态下能看到哪些数据；草稿与内部态是否对外部可见、可导出 |
| 规则与来源 | 公式与规则引用的每个量是否有来源定义、字段落点与展示位置 |
| 属性与字段集合 | 同类页面/对象的属性集是否一致（见 3.3） |
| 异常与恢复 | 每个自动动作与关键动作是否有失败状态、重试或人工处理路径 |
| 结果与去向 | 每个业务结果同步到哪些列表、详情、统计、导出与下游系统 |

### 3.2 对象细分类型

正文使用统称（如"基础结算单""费用""单据"）时，必须先把统称拆成细分类型，再逐类型判断权限、可见性、状态与数据范围。

判断要点：

- 统称下若存在**需要不同口径**的细分类型（例如"定向承租方租赁单"与"定向平台服务费单"对同一外部角色可见性不同），只写统称即为覆盖失败。
- 细分类型可以从数据范围、状态机实体、页面标题括注、字典条目中发现，不依赖固定命名。
- 同一细分类型在不同文件中若写法不同，按同一对象处理，并分别记录其出现位置。

### 3.3 属性集差集

同类页面或同类对象必须对**属性集合**做差集，而不是只核对单个属性值。

判断要点：

- 取同类页面（或同模块页面）已声明的属性名集合，逐页比对缺失项；缺失即候选，不是自动判错。
- 差集要识别**整页缺失**（某页完全没有该属性）、**整列缺失**（字段表整列为空）、**整组缺失**（一组相关字段只有部分落地）三种形态。
- 属性名写法不同但语义相同时（如"状态可见性限缩"与"按状态可见性限缩不可见"），先归一化再比对，不得因写法差异漏掉整页缺失。

### 3.4 承载面

**承载面**是一条业务约束在 Design 中可能被表达的位置类型。Fix 的影响面枚举就是"约束 × 承载面 × 对象"三维展开，因此承载面的清单是本文件的权威定义，其他文件引用而不各自枚举。

| 承载面 | 指什么 |
|---|---|
| 系统规则 | 系统级基线中的全局规则与约束 |
| 跨模块契约 | 模块之间约定的接口、状态交接与数据口径 |
| 页面 | 页面定义、页面清单条目、页面级数据范围与可见性 |
| 字段 | 字段定义、字段表列、字典条目 |
| 操作 | 操作定义、可用条件、确认、成功结果、状态变化、失败恢复、去向 |
| 状态机 | 状态、迁移、触发动作、终态与不可逆声明 |
| 导出 | 导出物（文件、工作表、PDF）的列定义、行级范围与脱敏口径 |
| 验收 | 验收标准与验收表 |
| 未决事项 | 已记录但尚未决定的高影响问题 |

使用要点：

- **承载面不等于文件**。一个承载面可能横跨多个文件（如"导出"同时涉及操作表与导出物定义），一个文件也可能包含多个承载面（模块设计文件通常同时含页面、字段、操作与状态机）。按文件枚举会漏，按承载面枚举才完整。
- 枚举时先问"这条约束在哪些承载面上会有表达"，再逐个承载面找具体位置；找不到表达不等于该承载面不适用，只说明该承载面缺失。
- 同一约束在不同承载面写法不同（统称、字面变体、兄弟页面）时，按 3.2 与 3.3 先拆类型、再做差集，不得按字面精确匹配。

### 3.5 候选实例的来源

关系实例必须先被枚举成候选集，才能逐项判定适用或排除。候选实例从以下来源枚举，不得只从当前正在阅读的段落现取：

- 页面与区块清单（含页面清单表格与正式页面标题）
- 状态机实体与状态集合（首列状态与下一状态列的目标态）
- 字段表与操作表（含所有列，不只是名称列）
- 角色清单与权限矩阵
- 字典条目与枚举值
- 导出物定义与验收表
- 跨模块契约与系统级基线

候选集不全本身记为**方法缺口**，与"已知维度下的实例遗漏"分开记录，不得混为一类，也不得用实例数充抵覆盖。

### 3.6 核心闭环最小回读集（Design fast）

Design 写作动作内不做全维度回读，只回读下列**六个高影响维度**（是 3.1 的子集，取"错了会改变流程、权限、状态、数据范围、系统边界或验收"的部分）。这是 fast 的成本边界，本清单为本文件的权威定义，其他文件引用而不各自枚举：

1. **权限与可见性**：谁能发起、审批、查看、导出。
2. **动作与前置条件**：每个动作的可用条件是否覆盖该动作全部合法取值组合。
3. **状态与迁移**：动作执行后主对象与关联单据分别进入什么状态；非终态是否都有出路。
4. **规则与来源**：公式与规则引用的每个量是否有来源定义、字段落点与展示位置。
5. **异常与恢复**：失败、超时、重复和外部失败是否有失败状态、重试或人工处理路径。
6. **结果与去向**：业务结果同步到哪些列表、详情、统计、导出与下游系统。

回读时同时应用两个横切手法：正文使用统称时必须先拆成细分类型再逐类型判断（3.2）；同类页面必须对属性集做差集，识别整页、整列或整组缺失（3.3）。

其余三个维度（对象与细分类型、数据范围、属性与字段集合）在 fast 阶段只做上述横切应用，其逐实例闭合留给 Review full。

## 4. 适用、排除与不确定

### 4.1 适用

满足以下任一条，即判定该关系实例**适用**，必须有结论：

- Design 已声明关系的两端（例如既写了角色也写了该角色在某状态下的可见性诉求）；
- 一端明确引用另一端（例如操作的可用条件引用了某状态、公式引用了某字段）；
- 该关系属于 3.1 维度清单中任一项，且该维度在本单元确有实例。

### 4.2 排除

排除一个适用实例时**必须引用正文事实作为依据**，并在结论中写出该依据。

- 没有正文依据的排除视为漏检，必须改记为 risk 或 decision。
- "本章节不适用"不等于"该实例不适用"；前者需要说明为什么本单元不存在这类实例。

### 4.3 不确定

- **risk**：一般语义不确定，或需要补充事实才能判断，但不改变流程、权限、状态、数据范围、系统边界或验收。
- **decision**：判断结果会改变流程、权限、状态、数据范围、系统边界或验收，必须由用户决定，不得由审查或修复静默补全。

risk 与 decision 都是**未闭合**，不得计为通过。

## 5. 三种责任与成本边界

| 责任 | 范围 | 时机 | 成本边界 | 产出 |
|---|---|---|---|---|
| **Design fast** | 只回读核心闭环与高影响关系 | 写作动作内，展示之前 | 不新增独立检查任务、报告或回执；发现已写事实矛盾时在同一动作内修正 | 修正后的 Design 正文 |
| **Review full** | 分单元逐实例判断，再做跨单元合并与集成单元 | 用户触发的完整审查 | 只输出一份结论；不修改、不确认、不推进 | 一份 Review 报告 + 覆盖摘要 |
| **Fix propagation** | 业务约束 × 影响对象 × 承载面 | 收到问题后 | 定点修改，不整篇重写 | 修改后的 Design 正文 |

三者的共同前提：都使用本文件的**关系实例、适用、排除、risk、decision、承载面**定义，不各自解释。

- fast 发现矛盾直接改，遇到 decision 停下来问用户。
- full 每个适用实例给出 pass/red/risk/decision/带依据的 excluded 五种结论之一。
- fix 把每个问题还原成业务约束，再枚举该约束的全部承载面；不得只改被点名的句子。

## 6. 本规则不负责的内容

- 不替用户决定角色权限、状态设计、数据范围、规则取值和系统边界——这些是 decision。
- 不把"维度已检查"当作"实例已覆盖"，也不把"关系存在"当作"关系正确"。
- 不规定具体的检查清单、优先级顺序或报告格式，那些属于各自的 Skill 与契约。
