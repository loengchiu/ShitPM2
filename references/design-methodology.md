# 设计方法论参考

> 本文件是设计阶段的方法论参考，不是固定执行步骤。
> Design 自身承担人读产物质量责任和用户确认责任，不依赖固定长步骤、固定问答、Review 前置或 metadata 必须生成。
> 模型可自主决定分析顺序和内部推理方式，本文件只提供方法论指引。

## 用户意图分析

从需求材料（可选 align.md、用户原始描述、业务资料）中提取所有用户角色，列出每个角色的核心任务：

> 角色A：[任务1] → [任务2] → [任务3]
> 角色B：[任务1] → [任务2]

每个任务必须是"用户要完成什么"，不是"系统有什么功能"。

## 页面推导

一个页面 = 用户的一次完整操作意图。

从角色任务推导页面，而不是从数据表推导页面：
- 用户在当前页面能否完成一个完整意图？能 → 页面拆分合理
- 用户需要在多个页面之间来回跳转才能完成一件事？是 → 合并或重组成任务流
- 同一个列表里混了用户根本不关心的数据？是 → 按角色或任务场景拆分

**反模式**：系统有入库申请表、审核表、确认表 → 建三个列表页（按数据表拆页面）
**正模式**：用户要"查看并跟踪入库申请状态" → 入库申请列表页（按用户意图拆页面）

## 模块组织

模块按业务域划分，不按技术层或数据层划分。

检查：一个模块下的页面是否属于同一个业务域的完整生命周期？
- 是 → 模块合理
- 否 → 按业务域重组

## 字段放置预判

对每个页面，先确定页面主任务，再按操作流排列字段区域：

1. 高频字段放高位
2. 只读与可编辑分开
3. 必填字段前置，选填后置或折叠
4. 同一条规则适用的字段必须在同一个区域/动作内

根据信息量决定布局策略：
- 字段 ≤5，无列表 → 单列直排，不需要分区
- 字段 6-15，或有列表 → 按操作上下文分 2-3 个区域
- 字段 >15，或有多个子表 → 用卡片分区、折叠面板、或分步骤 Tab

信息密度为"重"的页面，必须在页面清单的"主要功能"列注明分区策略。

## 与分析协议和质量标准的关系

本文件提供通用设计方法；模式责任、ABC 分析、B3 挑战、跨层挑战和质量分级以 `references/design-analysis-protocol.md`、`references/design-quality-rubric.md` 为准。方法论不得把 ABC 变成最终 Design 目录，也不得以 Review 或 metadata 替代首次 Design 责任。
