## 1. 定位与边界

本文件是 ShitPM 在真实项目中检查 Design 成品质量的运行时标准，供 `spm-design` 的生成成品自审和 `spm-design-review` 的独立 Review 使用。

本标准把批准产品目标转成可观察的质量维度，但不承担版本研发阶段的外部基准对比或产品验收：

- 不读取、不要求也不比较任何外部基准产物；
- 不假设项目中存在额外的基准 Skill、比较报告或裁决者；
- 不把测试夹具、历史评审、内部分析记录或其他项目产物作为当前 Design 的事实来源；
- 不根据量表补写输入中不存在的产品事实。

Design 的具体分析责任以 [Design 分析协议](design-analysis-protocol.md) 为准，组织和表达方式以 [Design 写作规则](design-writing.md)、[状态机格式](design-state-format.md) 与 [业务流程格式](design-flow-format.md) 为准。本文件只回答“成品是否达到当前模式要求”，不替代这些规则。

## 2. 两个使用区

### 2.1 生成成品自审

供 `spm-design` 在首次正式写入或修改 `design.md` 前使用。

生成者必须以当前输入事实和已形成的设计结论为边界，检查适用的质量维度、业务闭环、状态、权限、异常、跨层一致性和待确认问题，并在写入前修正能够修正的缺口。不能因为后续可以执行 Review，就把首次生成责任推迟给 Review。

生成自审只使用本文件的质量维度、缺陷等级和完成条件，不执行 L0–L3 正式评分，不生成 Review 审查结论，也不输出单独的评分报告。简单模式只检查最小闭环，不为满足量表而生成无关章节；完整模式必须完成 ABC 分析责任，但 ABC 过程不作为最终目录或评分证据。

### 2.2 独立 Review 评分

供 `spm-design-review` 在 Design 已生成后使用。

Review 者基于当前项目的输入基准和人读 Design 取证，按五个维度给出 L0–L3 等级，并把发现的问题映射为 P0/P1/P2。维度评分写入人读 Review；机读结果仍遵循 Review schema 和公共 Review 契约，不为评分增加未约定字段。

Review 不修改 Design、不自动 Fix、不自动确认、不自动推进阶段。需要修复时，只输出问题、影响对象和是否需要上游同步，由用户决定后续动作。

## 3. 共同证据原则

- 只依据当前项目可读取的输入基准、`design.md` 和允许读取的审计材料判断，不凭内部提示词、运行日志或 metadata 给成品加分；
- 每个 Review 分级必须引用 Design 中的段落、表格或其他可定位内容；生成自审不要求输出引用记录，但必须实际检查成品；
- “未提及”不等于“不适用”；只有结合目标、范围和业务场景给出理由，才能判断某项不适用；
- 输入事实、设计推导和待确认必须能够区分；未授权高影响事实不得因“看起来合理”而通过；
- 形式完整不能抵消业务断链；总体现象良好也不能抵消任一 P0/P1 缺口；
- 质量标准用于发现和分级问题，不授权新增流程、权限、状态、数据范围、模块边界或跨系统责任。

## 4. 五个核心维度及分级

L0–L3 只用于独立 Review 的维度评分。生成自审使用同一证据要求检查缺口，但不必输出等级。

- **L3 完整可交付**：覆盖适用事实、边界、异常和验收；关键关系互相解释；没有已知 P1 缺口。
- **L2 可用但有局部缺口**：主闭环可实现和评审，只有不改变主方案的 P2 缺口或少量低影响待确认；不存在未暴露的高影响断链。
- **L1 不完整**：能看出方向或主路径，但缺失关键角色、规则、状态、异常、权限、数据或验收，研发或测试必须自行猜测；通常至少存在一个 P1。
- **L0 失效**：与输入冲突、无法形成业务闭环、引入未授权高影响事实，或产物不可评审；通常存在 P0。

### 4.1 需求理解

| 等级 | 证据要求 |
| --- | --- |
| L3 | 目标、非目标、用户/责任人、场景、成功/失败标准、依赖约束和关键未知项均有边界，范围冲突已解决或明确待确认 |
| L2 | 目标、范围、主要用户和主场景清楚，局部背景或非关键未知项不完整但不影响方案 |
| L1 | 只有功能愿望或主路径，缺少真实问题、范围边界、责任人或成功标准 |
| L0 | 误解目标或范围，或者把明确排除项当成本期承诺 |

### 4.2 业务建模

| 等级 | 证据要求 |
| --- | --- |
| L3 | 流程、对象、关系、状态、角色、权限、规则、异常、回退/中止和责任闭环；每个关键动作有前置、结果和责任 |
| L2 | 主流程和核心对象闭环，少量非关键边界未展开；不存在状态孤岛、职责错误或关键回退断链 |
| L1 | 只有功能列表或线性步骤，缺少对象关系、状态出路、异常恢复或操作人，研发需要补充业务语义 |
| L0 | 核心业务模型互相矛盾，关键对象或状态不可达，或者流程无法完成 |

### 4.3 系统需求

| 等级 | 证据要求 |
| --- | --- |
| L3 | 功能、页面/交互、字段/数据、权限、集成、异常、非功能和验收均承接业务规则；关键操作可实现、可测试 |
| L2 | 主路径的系统承接完整，少量非关键交互或非功能细节待补，但不影响实现和验收设计 |
| L1 | 有页面、字段或功能描述，但业务规则、权限、异常、数据变化或验收无法落地 |
| L0 | 系统方案与业务目标冲突，或者缺少关键能力却声称目标已完成 |

### 4.4 跨层一致性

| 等级 | 证据要求 |
| --- | --- |
| L3 | 目标、范围、场景、流程、状态、规则、角色、功能、数据、集成和验收逐项互相解释，无新增高影响假设 |
| L2 | 主要跨层关系一致，只有局部引用或表述重复问题，不影响实现闭环 |
| L1 | 存在目标无功能、流程无状态、规则无验收、角色无权限或范围与功能矛盾等 P1 缺口 |
| L0 | 多层事实互相冲突，无法判断本期到底实现什么 |

### 4.5 问题发现

| 等级 | 证据要求 |
| --- | --- |
| L3 | 主动暴露输入冲突、业务断链、职责分离、边界、外部失败和未授权假设，并已修正或明确待确认 |
| L2 | 发现并处理主要高影响问题，少量 P2 风险已记录但不影响主方案 |
| L1 | 只复述输入，未挑战明显冲突、断链或高影响假设 |
| L0 | 掩盖问题、静默拍板，或者把 Design 阶段责任推给 PRD、Prototype 或 Review |

## 5. 缺陷等级

- **P0：阻断交付**。核心目标或范围被误解；关键业务结果不可达；确定性解析失败却允许确认；或者存在使 Design 无法作为事实源的根本冲突。必须修复，不能仅标记待确认。
- **P1：高影响业务缺口**。会改变流程、权限、数据范围、状态、对象一致性、集成补偿或验收，导致研发或测试必须自行做高影响决定。必须在确认前修复，或者在 Design 正文明确待确认并停止确认。
- **P2：局部质量问题**。不改变主方案的表达、重复、低风险边界或可延后细节。应修复或记录，不得用 P2 掩盖 P1。

## 6. 完成与判定

### 6.1 生成成品自审完成条件

完整模式必须满足：

1. 五个维度的适用责任均已在最终 Design 中形成证据；
2. 不存在 P0 或未处理 P1；
3. 产品、研发和测试能够从同一份 Design 判断业务如何运行、如何实现和如何验收；
4. 正文不出现 ABC 中间过程、内部分析记录、metadata、运行日志或机器调试结构；
5. 无法安全决定的高影响问题已经在 Design 正文标记待确认，而不是被静默补全。

简单模式必须满足：

1. 目标、范围、主路径、关键规则、必要功能/数据、适用状态/权限、异常和验收齐全；
2. 不生成与需求无关的完整模式章节；
3. 实际涉及状态、权限或集成时，相关内容不能省略；
4. 不存在 P0 或未暴露的 P1。

### 6.2 独立 Review 判定

- 每个维度分别给出 L0–L3 等级和对应证据，不能用总分抵消某一维度的 P0/P1 缺口；
- 每个实质问题必须映射为 P0/P1/P2，审查结论按 [Review 公共执行契约](../contracts/review-checklist.md#审查结论门槛) 判定；
- 维度等级用于解释质量状态，不另设一套与公共审查结论冲突的通过规则；
- Review 通过不等于 Design 确认，也不证明后续 PRD 或 Prototype 已完成。

## 7. Review 记录要求

人读 Review 至少记录：

- 审查对象和范围；
- 五个维度的等级、证据位置和简短理由；
- P0/P1/P2 问题及影响；
- 未能判断的事实和需要用户决定的问题；
- 人类可读性以及产品、研发、测试三类读者的可用性；
- 审查结论、`needs_upstream_sync` 和受影响对象。

机读 Review 只写公共 schema 允许的字段；五维评分保留在人读 Review 中，不得擅自扩展 schema，也不得把内部分析过程写入最终 Design。
