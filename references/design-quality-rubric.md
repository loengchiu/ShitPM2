# Design 质量标准

## 1. 适用范围

本标准用于冻结后的 Design 产物审查和 Park 对比。五个核心维度必须分别评分；总分不能抵消任一维度的 P1/P0 缺口。

评审对象：同一输入下的完整模式 `design.md` 与 Park 完整产物组合。简单模式另用“最小闭环”检查，不把完整模式的无关章节作为通过条件。

## 2. 证据规则

- 先冻结标准，再查看产物；
- 每个分级必须引用 Design 中的段落、表格或可定位原文；
- “未提及”不等于“不适用”；只有给出范围判断和理由才可判不适用；
- 事实、推导、待确认必须能区分；
- 没有真实 Park 产物时，只能标记“无法比较”，不能推断不低于 Park；
- 评审者不得依据内部提示词、Worker、运行日志或 metadata 给 Design 加分。

## 3. 五个核心维度及分级

各维度采用 L0–L3 四级：

- **L3 完整可交付**：覆盖适用事实、边界、异常和验收；关键关系互相解释；没有已知 P1 缺口。
- **L2 可用但有局部缺口**：主闭环可实现和评审，存在不改变主方案的 P2 缺口或少量待确认；不能有未暴露的高影响断链。
- **L1 不完整**：能看出方向或主路径，但缺失关键角色、规则、状态、异常、权限、数据或验收，研发/测试需要自行猜测；通常至少一个 P1。
- **L0 失效**：与输入冲突、无法形成业务闭环、引入未授权高影响事实，或产物不可评审；出现 P0。

### 3.1 需求理解

| 等级 | 证据要求 |
| --- | --- |
| L3 | 目标、非目标、用户/责任人、场景、成功/失败标准、依赖约束和关键未知项均有边界，范围冲突已解决或待确认 |
| L2 | 目标、范围、主要用户和主场景清楚，局部背景或非关键未知项不完整但不影响方案 |
| L1 | 只有功能愿望或主路径，缺少真实问题、范围边界、责任人或成功标准 |
| L0 | 误解目标/范围，或把明确排除项当成本期承诺 |

### 3.2 业务建模

| 等级 | 证据要求 |
| --- | --- |
| L3 | 流程、对象、关系、状态、角色、权限、规则、异常、回退/中止和责任闭环；每个关键动作有前置、结果和责任 |
| L2 | 主流程和核心对象闭环，少量非关键边界未展开；不存在状态孤岛、职责错误或关键回退断链 |
| L1 | 只有功能列表或线性步骤，缺少对象关系、状态出路、异常恢复或操作人，研发需补业务语义 |
| L0 | 核心业务模型互相矛盾，关键对象/状态不可达，或流程无法完成 |

### 3.3 系统需求

| 等级 | 证据要求 |
| --- | --- |
| L3 | 功能、页面/交互、字段/数据、权限、集成、异常、非功能和验收均承接业务规则；关键操作可实现、可测试 |
| L2 | 主路径的系统承接完整，少量非关键交互或非功能细节待补，但不影响实现和验收设计 |
| L1 | 有页面/字段或功能描述，但业务规则、权限、异常、数据变化或验收无法落地 |
| L0 | 系统方案与业务目标冲突，或无关键能力却声称完成 |

### 3.4 跨层一致性

| 等级 | 证据要求 |
| --- | --- |
| L3 | 目标、范围、场景、流程、状态、规则、角色、功能、数据、集成和验收逐项互相解释，无新增高影响假设 |
| L2 | 主要跨层关系一致，只有局部引用或表述重复问题，不影响实现闭环 |
| L1 | 存在目标无功能、流程无状态、规则无验收、角色无权限或范围与功能矛盾等 P1 缺口 |
| L0 | 多层事实互相冲突，无法判断本期到底实现什么 |

### 3.5 问题发现

| 等级 | 证据要求 |
| --- | --- |
| L3 | 主动暴露材料冲突、断链、职责分离、边界、外部失败和未授权假设，并已修正或明确待确认 |
| L2 | 发现并处理主要高影响问题，少量 P2 风险已记录但不影响主方案 |
| L1 | 只复述需求，未挑战明显冲突、断链或高影响假设 |
| L0 | 掩盖问题、静默拍板，或把 Design 阶段责任推给 PRD/Prototype/Review |

## 4. 缺陷等级

- **P0：阻断交付**。核心目标/范围被误解；关键业务结果不可达；确定性解析失败却允许确认；或存在会使产物无法作为事实源的根本冲突。必须修复，不能仅标记待确认。
- **P1：高影响业务缺口**。会改变流程、权限、数据范围、状态、对象一致性、集成补偿或验收；导致研发或测试必须自行做高影响决定。必须在确认前修复或在 Design 正文明确待确认并停止确认。
- **P2：局部质量问题**。不改变主方案的表达、重复、低风险边界或可延后细节。应修复或记录，不得用 P2 掩盖 P1。

## 5. 通过门槛

### 完整模式

1. 五个核心维度均至少 L2；
2. 不得有 P0；
3. 不得有未处理 P1；
4. Park 已确认有效的 P1/P2 问题，必须发现、修正或在正文提出待确认；
5. 产品、研发、测试都能从同一份 Design 判断如何运行、实现和验收；
6. 正文不出现内部分析过程或机器调试结构。

### 简单模式

1. 目标、范围、主路径、关键规则、必要功能/数据、适用状态/权限、异常和验收齐全；
2. 不生成与需求无关的完整模式章节；
3. 有状态/权限/集成时，相关内容不能省略；
4. 不得有 P0 或未暴露的 P1。

## 6. 盲审记录格式

每个结论至少记录：

- 样例代号和输入哈希；
- 五维等级及证据位置；
- P0/P1/P2 缺陷及其影响；
- 是否发现 Park 已知问题；
- 人类可读性和三类读者可用性；
- 评审者、时间、是否需要第三位裁决者。
