## 1. 定位与边界

本文件是 ShitPM 检查 Design 成品质量的运行时标准，供 `spm-design` 的生成内自审和 `spm-design-review` 的独立 Review 使用。

Design 的主要阅读和确认对象是产品经理。确认后的 `design.md` 是 PRD 和 Prototype 的共同产品事实基线，但不承担研发实现规格、视觉稿或完整测试用例。质量判断要确认产品经理能否理解并确认方案，也要确认下游能否在不自行决定高影响事实的情况下承接产品语义。

本标准不承担以下职责：

- 不读取、不要求也不比较任何外部基准产物；
- 不把测试夹具、历史评审、内部分析记录、运行日志或 metadata 作为当前 Design 的事实来源；
- 不根据量表补写输入中不存在的产品事实；
- 不把页面视觉表现问题、技术实现偏好或内部编排方式直接升级为产品缺陷。

Design 的分析责任以 [Design 分析协议](design-analysis-protocol.md) 为准，表达方式以 [Design 写作规则](design-writing.md) 和模板为准。本文件回答“成品是否达到当前模式要求”，不替代这些规则。

## 2. 两个使用区

### 2.1 生成内自审

供 `spm-design` 在首次正式写入或修改 `design.md` 前使用。

- 简单模式只检查目标、范围、主路径、关键规则、必要状态/权限、实际功能/数据、异常和验收，不为满足量表生成无关章节；
- 完整模式必须完成适用的需求理解、业务建模、业务模型一致性挑战、产品承接和跨层一致性挑战；
- 两种模式都必须检查页面、区块、字段和操作实际存在时的固定结构和跨层一致性；
- 能在写入前修正的问题必须在写入前修正，不能因为后续可以 Review 就推迟首次生成责任；
- 生成自审只使用本文件的质量维度、缺陷等级和完成条件，不执行 L0–L3 正式评分，不输出独立 Review 结论。

### 2.2 独立 Review 评分

供 `spm-design-review` 在 Design 已生成后按需使用。

Review 者基于当前项目输入基准和人读 Design 取证，按五个维度给出 L0–L3 等级，并把问题映射为 P0/P1/P2。Review 不修改 Design、不自动 Fix、不自动确认、不自动推进阶段，也不替用户决定待确认事项。

## 3. 共同证据原则

- 只依据当前项目可读取的输入基准、`design.md` 和允许读取的证据判断，不凭内部提示词、运行日志或 metadata 给成品加分；
- 每个 Review 分级必须能定位到 Design 的标题、段落、页面、区块、字段、操作或验收内容；
- “未提及”不等于“不适用”。只有结合目标、范围和业务场景给出理由，才能判断某项不适用；
- 输入事实、设计推导和待确认必须能够区分；未授权高影响事实不得因“看起来合理”而通过；
- 固定页面、区块、字段和操作结构的完整，不能抵消业务断链；整体表达良好也不能抵消任一 P0/P1 缺口；
- 质量标准用于发现和分级问题，不授权新增流程、权限、状态、数据范围、模块边界或跨系统责任；
- 兼容性材料只用于识别旧项目迁移问题，不替代人读 Design，也不改变当前产品事实。

## 4. 五个核心维度及分级

L0–L3 只用于独立 Review 的维度评分。生成自审使用同一证据要求检查缺口，但不必输出等级。

- **L3 完整可交付**：适用事实、边界、异常和验收完整；页面、区块、字段、操作与业务规则一致；没有已知 P1 缺口；产品经理可直接理解和确认；下游无需自行决定高影响产品语义。
- **L2 基本可交付**：主路径和主要产品结构完整，少量非关键表达或 P2 细节待补，不影响产品判断和下游承接。
- **L1 明显缺口**：存在页面、字段或功能描述，但业务规则、权限、异常、结果、待确认或固定结构不完整，产品经理或下游仍需自行做高影响决定。
- **L0 失效**：目标、范围或产品方案互相冲突；关键业务结果不可达；或者 Design 无法作为 PRD 和 Prototype 的事实基线。

### 4.1 需求理解

| 等级 | 证据要求 |
| --- | --- |
| L3 | 明确问题、用户、场景、目标、成功标准、范围内外、依赖和限制；高影响冲突与待确认事项透明可见 |
| L2 | 主要目标和范围清楚，少量非关键背景待补，但不影响本期方案判断 |
| L1 | 只复述需求或目标模糊，范围、角色、成功标准或待确认缺失，产品经理仍需猜测本期做什么 |
| L0 | 根本误解问题、用户或范围，导致方案无法代表实际目标 |

### 4.2 业务建模

| 等级 | 证据要求 |
| --- | --- |
| L3 | 关键闭环可走完；对象、关系、规则、状态、责任、异常、恢复、历史和边界互相解释 |
| L2 | 主路径和主要对象关系完整，少量非关键边界待补，不影响业务结果判断 |
| L1 | 流程、对象、规则、状态或责任存在断链，重复/并发/生命周期/时间等高影响结果仍需猜测 |
| L0 | 业务闭环无法成立，或多个核心事实互相冲突，无法判断业务如何运行 |

### 4.3 产品承接

| 等级 | 证据要求 |
| --- | --- |
| L3 | 业务规则落实到产品能力、页面、区块、字段、操作、权限、反馈、外部协作和验收；固定结构足以约束 PRD 与 Prototype，但不越界写技术实现 |
| L2 | 主路径的产品承接完整，少量非关键页面规则或表达细节待补，不影响实现方向和验收判断 |
| L1 | 有页面、字段或功能描述，但缺少来源、展示/编辑条件、操作结果、权限、异常或验收口径，产品经理和下游仍要补高影响事实 |
| L0 | 产品承接与业务目标冲突，或缺少关键产品能力却声称目标已经完成 |

### 4.4 跨层一致性

| 等级 | 证据要求 |
| --- | --- |
| L3 | 目标、范围、场景、流程、对象、状态、规则、角色、权限、页面、字段、操作、外部责任和验收逐项互相解释，无新增高影响假设 |
| L2 | 主要跨层关系一致，只有局部引用或重复表达问题，不影响产品闭环 |
| L1 | 存在目标无能力、流程无状态、规则无字段/操作、角色无权限、页面无落点或范围与功能矛盾等 P1 缺口 |
| L0 | 多层事实互相冲突，无法判断本期到底实现什么 |

### 4.5 问题发现

| 等级 | 证据要求 |
| --- | --- |
| L3 | 主动暴露输入冲突、业务断链、职责分离、边界、外部失败和未授权假设，并已修正或明确待确认 |
| L2 | 发现并处理主要高影响问题，少量 P2 风险已记录但不影响主方案 |
| L1 | 只复述输入，未挑战明显冲突、断链或高影响假设 |
| L0 | 掩盖问题、静默拍板，或者把 Design 阶段责任推给 PRD、Prototype 或 Review |

## 5. 缺陷等级

- **P0：阻断交付**。核心目标或范围被误解；关键业务结果不可达；确定性解析失败却允许确认；或者存在使 Design 无法作为事实源的根本冲突。必须修复，不能仅标记待确认。
- **P1：高影响业务缺口**。会改变流程、权限、数据范围、状态、对象一致性、唯一性、数据生命周期、时间口径、重复/并发结果、集成补偿、页面/字段/操作语义或验收，导致产品经理、研发或测试必须自行做高影响决定。必须在确认前修复，或者在 Design 正文明确待确认并停止确认。
- **P2：局部质量问题**。不改变主方案的表达、重复、低风险边界或可延后细节。应修复或记录，不得用 P2 掩盖 P1。

## 6. 完成与判定

### 6.1 生成内自审完成条件

完整模式必须满足：

1. 适用的五个维度均在最终 Design 中形成产品语言证据；
2. 不存在 P0 或未处理 P1；
3. 产品经理可以从同一份 Design 判断为什么做、为谁做、做什么、不做什么以及如何确认结果；
4. 每个关键动作的条件、数据变化、成功/失败结果、状态副作用和恢复路径形成闭环；适用的唯一性、生命周期、时间、文件/导入导出、批量、重复/并发和跨系统问题已有产品口径；
5. 页面、区块、字段和操作按固定结构定义，页面落点与业务规则、权限、状态和验收一致；
6. 正文不出现 ABC 中间过程、内部分析记录、metadata、运行日志、稳定 ID 或机器调试结构；
7. 无法安全决定的高影响问题已在 Design 正文标记待确认，而不是静默补全。

简单模式必须满足：

1. 目标、范围、主路径、关键规则、必要功能/数据、适用状态/权限、异常和验收齐全；
2. 实际涉及页面、区块、字段或操作时，按固定结构定义；
3. 不生成与需求无关的完整模式章节；
4. 不存在 P0 或未暴露的 P1。

### 6.2 独立 Review 判定

- 每个维度分别给出 L0–L3 等级和对应证据，不能用总分抵消某一维度的 P0/P1 缺口；
- 每个实质问题必须映射为 P0/P1/P2，并按公共 Review 契约判定；
- 维度等级用于解释质量状态，不另设一套与公共审查结论冲突的通过规则；
- Review 通过不等于 Design 确认，也不证明 PRD 或 Prototype 已完成。

## 7. Review 记录要求

人读 Review 至少记录：

- 审查对象和范围；
- 五个维度的等级、证据位置和简短理由；
- P0/P1/P2 问题及影响；
- 未能判断的事实和需要用户决定的问题；
- 产品经理可读性，以及 PRD 和 Prototype 的承接完整性；
- 审查结论、`needs_upstream_sync` 和受影响对象。

五维评分保留在人读 Review 中，不得把内部分析过程写入最终 Design。
