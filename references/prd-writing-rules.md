# PRD 写作规则

> 本文件是 PRD 的人读规则和交付约束唯一来源。模板只提供骨架，示例用于说明写法；确认版 `output/design/design.md` 是产品事实源。

## 常见错误

| 级别 | 场景 | 为什么错 | 首选修复 |
|---|---|---|---|
| 失败处理 | 按菜单、页面或终端拆成目录 | 同一业务闭环被拆散，研发无法理解前后承接 | 按业务结果重组模块，页面放到真实业务阶段 |
| 失败处理 | 页面正文退化成标签式正文 | 标签不能说明条件、结果和边界 | 改为结构化自然语言和动作标题 |
| 失败处理 | 动作流水账 | 只有点击顺序，没有业务规则、状态和异常 | 合并为独立业务结果，并补充输入、结果和边界 |
| 失败处理 | 字段只集中在一张总表 | 字段与业务阶段脱节，局部使用规则丢失 | 对象级定义一次，使用处补充差异 |
| 失败处理 | 状态、展示状态、过程状态混写 | 页面展示和业务判定会被误解为同一状态 | 分开命名，分别说明来源和作用 |
| 失败处理 | 管理端与移动端被拆成两个模块 | 同一闭环的角色、状态、异常和验收不完整 | 放入同一业务闭环的对应阶段 |
| 失败处理 | 用无依据数字、默认值、提示语补全 | 把推测伪装成产品事实 | 保守表达或列为待确认 |
| 失败处理 | 把 Design 待确认项静默拍板 | 可能改变范围、权限或核心流程 | 原样保留并回到 Design 确认 |
| 反模式 | 用承接矩阵、覆盖率 JSON 或回执证明完整 | 形式证明不能替代语义承接 | 生成后从 Design 回读并直接修正文档 |
| 反模式 | 用 Mermaid 代替交付流程图 | 不符合本项目流程图交付要求 | 需要时提供 draw.io 源文件和 PNG |

## 结构与写作硬规则

### 0. 全量分片写作（所有 PRD 统一流程）

所有 PRD 默认分片写作，不再根据 Design 大小选择“普通 PRD / 超大型 PRD”路径，不设一次性完整写作路径：

1. 分片边界来自业务闭环（Design 的业务边界），不按固定字数、页数或字段数机械切割；小项目产生较少分片。
2. 分片必须直接写入最终 `output/prd/prd.md`；禁止先写临时草稿、最后由主 Agent 整篇重新生成的路径。
3. 最终阶段只做局部整合（模块编号、标题层级、名词统一、页面归属、全局规则引用、跨模块状态和对象名称、待确认事项索引），不得整篇重写，不得把模块正文压缩成摘要。
4. 中断或上下文压缩后，从最终 `prd.md` 的章节骨架判断已完成和未完成模块，只重读当前模块对应的 Design 片段继续写入；不重新读取全部 Design，不重写已完成模块。
5. 流程默认单 Agent 串行分片，不依赖 subagent；subagent 只能并行加速材料读取或模块分析，不是完成条件，也没有最终写入权。
6. 每个功能模块必须包含 `4.x.6 功能详细说明`；有页面或业务动作时不得省略，不能以“无内容”为由跳过。

### 1. 顶层结构

PRD 顶层按以下顺序组织：

1. 文档信息；
2. 产品概述；
3. 总体说明；
4. 功能需求（若干功能模块，按业务闭环组织）；
5. 待确认事项。

模块按业务结果或业务闭环划分，不按菜单、页面清单、管理端/移动端或 Design 章节机械复制。模块数量可随项目变化，不为形式保留空模块。

### 2. 系统级规则与模块规则

只对跨模块共用的事实在“总体说明”中定义一次，例如共用名词、组织层级、数据范围基线、通用角色、共用页面映射和全局限制。仅某个闭环成立的角色、字段、状态、异常、验收和待确认事项必须放回该模块。模块引用全局定义时写明引用关系，不使用“同上”代替关键语义。

### 3. 页面落点

页面是业务承接载体，不是全文唯一组织轴。页面身份可在总体说明的页面映射表中出现，页面正文必须放在其所属功能模块的 `4.x.6 功能详细说明` 中；页面只有名称、没有职责和业务阶段不满足要求。每个 Design 页面必须至少在一个功能模块的 `4.x.6` 中落点，不得只出现在总体页面清单中。管理端和移动端共同完成同一闭环时，放入该闭环；不要建立统一的“移动端模块”。同一共用页面只定义一次，其他模块说明适用范围或引用位置。

### 4. 模块内部结构

每个功能模块必须就近容纳：功能概述、业务对象与关系、角色/权限/数据范围、流程、状态与规则、功能详细说明（`4.x.6`）、字段定义、异常处理、验收标准和待确认事项。有页面或业务动作的模块不得省略 `4.x.6 功能详细说明`；省略其他章节前必须证明该模块没有对应内容。没有页面和业务动作的内容不得创建为功能模块。高影响事实不能藏在文末孤立章节。

### 5. 标题、编号和稳定标识

- 标题表达业务结果或业务阶段，避免“页面一、功能二”式空标题。
- 阶段、页面标题直接写业务名称，不要加“阶段一/二”“页面：”等标签前缀；阶段用 `#####` 级标题表达（如 4.1.6.1），页面用加粗行并标注终端（如 **车辆信息记录（管理端）**），动作用 `######` 级标题或动作锚点。
- 动作使用同层标题或动作锚点；不要为了编号继续堆叠超过四层的数字层级。
- 页面名称在映射和正文中保持一致；如 Design 有稳定 ID，保留并避免重复。
- 业务模块名称可以不同于 Design 菜单模块名称，但必须能从正文看出业务边界和页面落点。

### 6. 表格边界

表格用于对象、字段、枚举、页面映射、权限例外和可比较的规则。不要用表格替代流程、异常、条件和业务解释。字段表不固定七列，列数和列名按信息需要决定；合法的局部字段表不因列数较少而被判错。

### 7. 流程图

流程图只在自然语言难以清楚表达跨角色、跨系统或关键状态闭环时使用。一张图只讲一个闭环，节点写业务动作或结果，泳道只在角色边界有帮助时使用。交付 `.drawio` 源文件和按 2 倍分辨率（X2）导出的 `.png`，图中名称、顺序和正文一致；不使用 Mermaid。

### 8. 验收与待确认

验收标准放在所属功能模块，描述可观察的业务结果、状态、权限和异常结果。待确认事项放在模块末尾；全局待确认事项放在总体说明；文末只保留待确认事项索引，不重复定义或追加结论。

### 9. Design 冲突与高影响未知（写作前识别）

模块写作前识别 Design 事实冲突和高影响未知，记录冲突位置、涉及对象、两方事实、影响范围和受影响模块。至少覆盖：状态及状态转换；角色、权限和数据范围；异常、回退、撤回和恢复；必填、默认值、校验和生效时点；外部系统协作、同步和失败责任。高影响风险未处理前不得进入对应模块写作；PRD 不得用"页面优先""数据字典优先"等通用规则自行选择冲突一方，只能保留冲突事实、列为待确认并回到 Design Fix。低影响展示类未知可保守表达。

### 10. 非页面落点字段回读

每个模块完成前单独回读 Design 的非页面落点字段，以及本模块相关的核心业务对象字段和系统留痕字段。每个字段必须有落点：对象字段定义、页面展示、页面输入、查询或筛选、动作判断、状态转换、系统内部用途、审计/版本/历史记录。不能因为字段没有页面控件就从 PRD 中删除；内部字段写明业务用途并按需分类（主键、内部关联、系统留痕、计算字段、流程状态、权限或数据范围依据、版本或历史记录）。高影响字段原则上一字段一行；合并字段不能掩盖不同对象、不同属性或不同权限，只有字段含义、属性、权限和使用方式完全一致时才允许合并表达。

### 11. 已完成模块变更失效

任何阶段修改已完成模块的功能详细说明、页面、字段、状态、权限、异常和恢复、验收标准、待确认事项或跨模块引用关系，必须使该模块重新进入待验收状态并重新执行模块完成条件。Design 上游变化只使受影响模块失效，共享对象、状态、权限或页面引用的模块同步进入影响评估；不得默认全部模块已验收，不得用旧快照或旧哈希掩盖后续修改。

## 动作与业务自然语言

### 1. 动作标题是阅读锚点

动作标题用“动词 + 业务对象/结果”表达，例如“确认车辆入场记录”“处理滞留告警”“查看组织汇总”。不要把“点击按钮”“进入页面”当成业务动作标题。

### 2. 一个动作写完整因果链

每个动作至少交代：谁在什么前提下发起；使用哪些已确认字段或数据；系统依据什么规则处理；成功后用户看到什么业务结果；业务对象或状态如何变化；失败、无数据、权限不足或外部协作失败时如何表达；已有恢复方式是什么。未确认的超时、重试、补偿、提示逐字文案和数字不要自行添加。

### 3. 结构化自然语言

可以用短段落、列表和局部表格，但必须让读者能定位触发条件、输入、处理、结果、状态、权限和异常。不要用“关键动作：”“状态变化：”等加粗标签拼接伪正文，也不要把三步以上点击顺序当作完整需求。

### 4. 字段的两层表达

业务字段在所属对象处定义名称、含义和已确认属性；页面或动作只补充当前展示、编辑、筛选、校验、来源或是否只读等使用差异。系统内部字段仍需交付，并说明用途；无法从 Design 得出属性时，不写猜测。

### 5. 状态与规则

业务状态描述业务对象是否可继续处理；页面展示状态描述界面如何呈现；操作过程状态描述请求或外部协作的过程。强动作写明允许角色、允许的业务状态和完成后的状态；不要把加载中、空数据、失败提示冒充业务状态。

### 6. 查询、统计、下钻与导出

查询说明筛选字段、查询对象、结果范围和无数据表达；统计说明指标口径、时间/组织范围和数据来源；下钻说明从哪个指标进入哪个明细；导出说明导出对象、权限和数据范围。默认排序、分页数量、导出上限只有在 Design 或明确依据存在时才写。

### 7. 表单与配置

说明已有值及来源，区分保存与提交，区分空值与零值，按动作时点写校验。配置必须说明作用对象、生效范围、生效时点、历史数据影响和失败结果；未知的高影响行为列为待确认。“重置”要说明是清空当前编辑值、恢复已保存值，还是恢复系统默认值。

### 8. 异常与恢复（含外部协作）

明确谁提供数据、谁负责判定、谁接收结果。分别说明成功、失败、无响应、数据不一致和人工处理边界；只有 Design 已确认的重试、补偿、超时和恢复方式才能写成事实。

## 事实边界与最终自检

### 1. 唯一事实源

以确认版 `output/design/design.md` 为准；Design confirmation 若存在，按项目约定作为确认结果读取。Prototype、旧 PRD、示例和常见产品经验只能帮助理解，不能授权新增事实。

### 2. 不得静默新增

不得自行补造页面、字段、角色、权限、状态、流程、接口参数、默认值、排序、分页、超时、重试、补偿、逐字提示文案、历史数据处理方式或外部系统行为。高影响未知必须列为待确认并回到 Design；低影响未知可以采用不承诺具体值的保守表达。

交互细节只能展开 Design 已确认事实：不得自行补造权限、状态、默认值、校验、提示文案、异常恢复或外部系统行为；没有页面和业务动作的内容不得被创建为功能模块。

### 3. 生成后回读

正式展示前直接回读真实 PRD：

1. 按 Design 逐项检查目标、范围、对象、页面、字段、状态、权限、流程和待确认事项是否承接；
2. 检查每个页面是否落在一个真实业务阶段，移动端是否归入所属闭环，共用页面是否只有一个权威定义；
3. 检查模块能否脱离其他模块独立理解，字段、状态、异常、验收是否就近可读；
4. 检查图、源文件、PNG 和正文的名称与流程是否一致；
5. 同时检查遗漏和擅自增加，发现问题直接修正文档；
6. 不生成承接矩阵、覆盖率报告、验证回执或机器签名来替代回读。

### 4. 事实、保守表达和待确认分开

确认事实直接写；无法确认但不影响核心行为的内容用不承诺具体值的表达；影响范围、权限、核心流程、状态、数据边界或系统边界的未知必须进入待确认事项，不得被藏在"按配置"或"按业务规则"中。

### 5. Design 冲突不得由 PRD 拍板

PRD 不得在页面清单、数据字典、状态流转、权限矩阵或其他权威段落存在冲突时自行选择一方作为最终事实。只能保留冲突事实、说明冲突位置和影响对象、列为待确认，并在无法确认前停止对应模块写作，建议回到 Design Fix。

## 机读约束边界

`prd-style-lint.py` 只识别标签式正文、流水账、表格主导、重复稳定标识、模糊跨节引用、机读字段泄漏、明显 AI 痕迹、明确占位符和核心名词问题等确定性坏味道；不以固定章节、固定列数或标题数量判断业务完整性。

`prd-consistency-check.py` 只提取并比较明确的页面、字段和已确认属性冲突。业务闭环是否合理、模块是否自包含、事实是否完整承接，必须由生成时回读和 Review 语义判断负责。

## 规则使用边界

本规则服务 PRD 生成与 Review，不改变 Design、Align、Prototype、Fix 的事实源和主流程；与确认版 Design 冲突时，以 Design 为准，并通过上游修复流程处理 Design 本身的问题。
