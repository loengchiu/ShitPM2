## 最小结构规则（writing pass 装载）

1. PRD 顶层顺序：文档信息 → 产品概述 → 总体说明 → 功能需求 → 待确认事项。
2. 功能需求按业务闭环或业务结果组织，不按菜单、页面清单、管理端/移动端或 Design 章节机械复制。
3. 每个有页面或业务动作的功能模块必须包含 `4.x.6 功能详细说明`，不能以“无内容”为由省略；没有页面和业务动作的内容不得创建为功能模块。
4. 模块角色与权限（`4.x.3 角色与权限`）提供“角色 × 业务能力”矩阵：行是角色，列是业务能力，单元格填写“可、否或条件”，条件复杂时在表下注释展开，表达模块级权限边界。
5. 管理端和移动端放在同一闭环的真实业务阶段；共用页面只定义一次，其他模块说明适用范围。
6. 页面标题、动作标题和终端后缀的格式见 `templates/prd.md`。
7. 模块存在跨页面推进、跨角色协作、跨系统交互、关键业务状态变化，或会改变业务结果的分支、异常与恢复时，`4.x.4 业务流程` 必须包含流程图；简单只读、纯展示或无状态变化和协作分支的配置模块不强制画图。

## 详细需求说明写作规范（module pass 装载）

本节是 `4.x.6` 与业务模块详细需求说明的规范源。交付目标以单业务模块（`4.x`）自包含为基线：研发只读当前业务模块（结合 `4.x.5 状态与业务规则`、`4.x.6 功能详细说明` 及相关章节），不查看 Prototype、Design 或旧 PRD，也不回问产品，即可确定产品行为并独立开发。各章节明确分工：公共数据口径与计算规则入 `4.x.5`，页面交互与规则应用入 `4.x.6`，字段属性入 `4.x.7`（严禁将复杂公式压缩在字段表），验收用例入 `4.x.9`。前端据此确定页面形态、区域、内容、操作和状态；后端据此确定数据来源、处理对象、状态变化和下游结果；测试据此编写主链路与异常用例。视觉风格、像素尺寸、组件技术选型不属于本节职责，除非影响业务判断且 Design 已确认。Design 只作为生成时的事实输入，不能成为交付 PRD 的外部引用。

### 1. 4.x.6 稳定骨架与组织方式

`4.x.6` 采用以下稳定骨架组织：
- 业务阶段：梳理业务闭环所处的阶段流转；
- 页面名称：六级标题（`###### 页面名称`），逐字采用 Design 页面清单名称，不带编号，不擅自改名或造名；
- 页面引入段：交代页面使用背景与任务目标；
- 动作名称：独占一行的无冒号粗体短语（`**动作名称**`），作为小节定位标题；
- 动作正文：高密度自然语言展开，承接业务事实。

页面引入段和动作标题提供稳定落点，动作正文不强制拆成固定小标签。正文按业务复杂度承担适用的信息责任，避免所有页面套用同一种模板。

### 2. 页面引入段责任

页面引入段必须交代四项内容，不规定固定句数或列表形式：
1. 谁在什么业务前提和状态下进入页面；
2. 进入页面要完成什么判断或任务；
3. 结果交给谁，或进入什么后续状态；
4. 页面与上游、下游页面如何衔接。

引入段不提前陈列页面全部字段和规则，也不加入“核心支撑、重要节点、形成闭环”等评价性套话。

### 3. 自然语言硬约束与排版形态

`4.x.6` 正文全部使用自然语言，按内容场景选择三种表达且分工明确：
- 自然段用于业务承接，连续表达业务前提、用户判断、系统处理、结果和下一环节；
- 数字编号列表用于有先后顺序的步骤、状态推进和处理链路，每一项必须是完整业务语句；
- `·` 并列列表用于同层并列的展示项、校验项、限制项、异常项和动作，每一项说明条件、含义或结果。

一个块（自然段或 `·` 列表项）只承载一层事实。禁止将“区域 → 字段清单 → 权限分支 → 版本节点 → 例外提示”等多层事实堆叠在单个块内。长块必须通过分段、短矩阵或子列表分层展开。单块的长度阈值（自然段、`·` 列表项的上限字符数）以 `contracts/prd-writing.profile.json` 的 `paragraph_max_chars`、`dot_item_max_chars` 为唯一落点，本文不重复具体数值。

以下写法不得作为正文：
- 字段表、页面区块表、操作表、状态表或数据流表替代正文叙述；
- “页面职责、使用对象、入口与返回、页面区块、字段来源”等固定元数据块；
- “触发、输入、处理、成功结果、失败结果、后续去向”等行首标签；
- “字段名：说明”“来源：某系统”“结果：已完成”等连续键值对句式；
- 读者跨多个表格、章节或上游文档才能拼出的一条业务链；
- 同一套句式机械替换页面名和字段名。

### 4. 动作正文责任与复杂度分级

Design 操作表是事实输入，不是 PRD 动作目录，动作按业务结果重组：无独立业务结果的浏览动作（查询、筛选、重置、返回、切换、播放控制等）按业务结果合并；动作标题用“动词 + 业务对象/结果”，不得把“点击、打开、切换、返回、播放”直接当标题，不为了证明承接而一对一复刻。

动作按复杂度写，三档复杂度作为生成与审查的责任判定标准，不转写为固定正文小标题：
- **简单动作**（查询、查看、返回、打开详情）：必须写清操作角色、可用条件、页面展示或数据结果；
- **普通动作**（新增、编辑、保存、提交、修改）：必须写清前置条件、输入与校验、系统处理、成功结果、失败保留或恢复路径；
- **复杂动作**（多角色协作、多状态流转、多分支判断、破坏性操作、外部协作）：必须写清允许角色与状态、关键业务分支、状态变化、失败恢复以及下一步衔接。

某项责任不适用时可以不写，但生成和审查必须明确判断过，不能因模型遗漏而静默缺失。简单动作不得扩写伪造复杂交互。合并或精简后不丢失角色、前置条件、状态、数据范围、失败结果和后续去向。

### 5. 模块自包含与章节分工规则

交付目标为单业务模块（`4.x`）自包含。研发和测试只读当前业务模块即可独立评审与开发。模块内公共规则与页面应用明确分工，关键数据口径统一遵循 `references/data-definition-rules.md`：公共数据口径、计算公式与周期规则集中收敛在 `4.x.5`，`4.x.6` 页面动作承接应用，`4.x.7` 仅保留控件属性与来源索引，严禁将数据口径压缩进字段表。

同一事实可以在状态规则、功能详细说明和字段定义中重复出现，但每次出现必须增加新的使用上下文（如角色、状态、条件、对象、输入、校验、计算、结果、异常、恢复方式、展示方式或上下游关系）。

第二处仅换词重述第一处、未增加任何新使用信息的，属于原地重述，审查应予剔除。为满足独立阅读所需的有效重复应当保留，不作为缺陷处理。

### 6. 模块级权限矩阵与正文权限落点

每个业务模块在 `4.x.3 角色与权限` 提供“角色 × 业务能力”矩阵：
- 行是业务角色，列是业务能力，单元格写“可、否或条件”；
- 复杂条件在表格下方注释中逐条展开；
- 能力按业务动作组织，不按界面按钮或图标组织。

矩阵用于表达模块级权限全局边界。`4.x.6` 动作正文在此基础上进一步写清各动作适用的具体业务状态、组织数据范围、例外条件和退回后的处理细节。

### 7. 短矩阵与业务流程图

`4.x.6` 允许使用短矩阵作为快速扫读锚点，适合表达角色权限差异、状态与动作矩阵、固定选项及其流转结果。短矩阵用于辅助理解，不能替代动作正文的规则展开，也不强制所有页面必须配矩阵。

业务流程图：模块存在跨页面推进、跨角色协作、跨系统交互、关键业务状态变化，或会改变业务结果的分支、异常与恢复时，`4.x.4 业务流程` 必须画图；纯查询、纯展示或无状态流转的简单配置无需为了形式画图。每个命中模块至少一张图，复杂闭环拆图。流程图保存为 `output/prd/diagrams/<图名>.drawio`，并按 2 倍分辨率导出同名 `.png` 嵌入正文。流程图只辅助理解，正文必须完整写清规则，图不得新增正文没有的事实。

### 8. 自然中文规则

生成正文时严格遵循以下 10 条自然中文规则：
1. 先写角色和动作，再写条件、处理和结果；
2. 一个句子尽量只承载一个主要动作；
3. 一个自然段只推进一个主要业务判断；
4. 用具体动词替代抽象名词；
5. 用可验证的产品结果替代价值评价；
6. 不在产品正文评价方案是否先进、完整、务实或有效；
7. 不为了修辞制造“不是……而是……”等对比结构；用于排除歧义的否定定义可以保留；
8. 不用“通过……实现……”包住核心事实；
9. 不用“形成闭环、提升效率、强化管理”等总结句代替流程和状态；
10. 未确认事实直接标记待确认，不用概念化表达掩盖未知。

“赋能、抓手、底座、协同、支撑、闭环”等词不能单独作为禁词判断。是否需要修改，取决于它是否替代了具体动作、条件或结果。

### 9. 前端事实承接

页面实际存在的能力必须通过自然语言写清，不能因为 Prototype、Design 其他章节或常见研发经验中可能存在而省略：
- 页面形态与边界：读者能判断是看板、列表、详情、表单，还是多个页面组合；属于同一业务动作的多个页面写清如何进入、返回和衔接。
- 页面构成与信息关系：写清承担业务判断或操作的区域、区域之间共用的查看范围/筛选条件/当前对象，以及切换范围后哪些内容同步变化。
- 展示内容与方式：页面实际展示的字段、指标、状态、图片、视频、趋势、历史记录和提示在正文可读；展示方式影响业务判断或操作时写清是文本、状态标签、图片、播放器、卡片、列表、趋势图、单选、多选、下拉还是多行输入。
- 字段来源与编辑性：动态字段写清业务来源（用户输入、系统计算、当前页面上下文、业务对象关联、外部系统返回或其他角色补录）；写清何时只读、何时可编辑、由哪个角色编辑、已有值如何带出、什么条件下显示或隐藏，以及空值、未知值、超长和异常值如何呈现。
- 操作入口与状态驱动展示：写清用户从哪里发起操作，按钮或入口在什么角色、权限和业务状态下显示、隐藏、可点或不可点；状态变化后相关按钮、字段、列表项、状态标签和页面内容如何刷新或消失。
- 页面过程状态：加载中、空数据、加载失败、无权限、离线、部分数据失败或外部资源不可用时，写清用户看到什么、已成功数据是否保留、能否重试，以及部分失败是否影响其他区域。
- 导航与状态保留：写清页面入口、成功后停留/跳转/返回、返回目标，以及返回后筛选、排序、分页、滚动位置或未提交内容是否保留。
- 多终端与多角色：同一业务在管理端、移动端、小程序等存在不同页面和操作时，分别写清每个终端展示什么、允许修改什么、完成后如何衔接其他角色；不能用“管理端只读、移动端可操作”一句话替代。

### 10. 后端事实承接

业务实际存在的能力必须写清，让后端能确定业务数据从哪里产生、按什么范围和规则查询计算校验、操作后修改哪个业务对象、哪些字段和状态变化、产生哪些记录，以及结果进入哪些后续环节：
- 数据来源与权威来源：每项关键动态数据写清来自哪个业务对象、内部计算、用户录入、组织权限、设备、外部系统或其他角色处理结果；多个来源可能提供同一字段时，写清哪个是当前权威值、人工修改是否覆盖外部值、后续外部更新是否再次覆盖。
- 查询、范围与计算规则：严格执行 `references/data-definition-rules.md` 中的四档数据责任与同名同口径原则。查询和统计写清对象、组织、时间、状态、筛选继承、纳入排除、去重和计算口径（汇总统计必须满足对象、组织、时间起止闭合、分子分母、状态白名单与排除项、去重唯一键、空值零值、刷新时效、下钻导出一致性九项要素；周期结算必须补充账期锚点、取数版本、过程精度、尾差归属、重算锁定规则）；共用范围的指标、列表、趋势、下钻和导出保持一致；刷新失败、切换范围和缓存并存时，写清保留当前范围旧数据还是清空并显示失败，不留展示上一组织数据的歧义。
- 用户输入与业务校验：写清已有值如何带出、哪些字段必填、允许什么取值、字段间联动或互斥关系、在什么时点校验，以及校验失败后页面和已填写内容如何处理。
- 系统处理与写入对象：保存、提交、修改、确认、绑定、领取、撤回、删除、作废或归档时，写清修改哪个业务对象、哪些字段和状态变化、是否更新主信息、当前任务、业务快照、关联对象或历史记录，以及多个对象同时变化时的业务关系和先后结果。
- 新增记录与审计留痕：动作生成任务、台账、告警、处理记录、导出记录、修改历史或审计记录时，写清何时生成、记录哪些产品事实、由谁查看、生成失败是否影响主动作；“记录操作日志”不能替代具体业务用途和下游可见结果。
- 状态变化与重复执行：强动作写清允许发起的角色和状态、成功后的目标状态、状态变化后哪些动作不再允许；同一任务可能被多人处理、重复提交或处理期间被外部事件改变时，写清是否拒绝覆盖、用户看到什么、已填数据是否保留、下一步如何继续。PRD 不规定锁或幂等，但必须规定冲突后的业务结果。
- 下游影响与后续消费者：动作完成后写清结果出现在哪些列表、详情、台账、统计、告警或其他角色待办中，以及数据变化对后续判断、统计口径、权限可见性或外部同步的影响；只写“保存成功”或“返回列表”不构成完整结果。
- 外部系统与失败边界：外部系统提供数据时，写清谁提供、本系统如何使用、失败后业务对象保持什么状态、用户看到什么，以及由系统重试、用户重试、人工处理还是等待外部恢复；只有 Design 已确认的重试次数、超时、补偿和恢复方式才能写成事实。

### 11. 跨前后端的完整业务链

页面和动作最终通过自然语言连续表达：用户在什么业务前提、角色和状态下进入页面，需要完成什么判断或任务；页面向用户提供哪些信息，这些信息来自哪里；用户如何操作，系统依据什么规则处理；成功后哪些对象、字段、状态和页面发生变化；失败后保留什么、用户如何继续；结果由哪个角色、页面或业务环节继续使用。不要求固定段落数量，但不缺少实际适用且影响开发的事实。

按实际适用覆盖：写作前先在内部判断前端和后端各项事实是否适用。适用项必须在正文有明确落点；不适用项直接跳过，不创建空段落，不写“本页不涉及”。无法判断且影响核心流程、权限、数据范围、状态、写入对象或外部协作的事项，必须作为高影响未知回到 Design，不由 PRD 或研发自行拍板。

### 12. 事实边界与信息密度

Design 是唯一事实源，PRD 只承接已确认事实，不静默新增页面、字段、角色、权限、状态、流程、金额口径和外部系统行为；权限、数据范围、状态机、删除传播、外部协作、历史数据、统计口径等未知保留为待确认并回到 Design，不用“按配置”“按业务规则”替代；状态条件、动作分支或权限依据存在多种可能且 Design 未拍板时，禁止用“或”“按业务规则”“按配置”等模糊表达保留不可执行分支，必须回到 Design；不得从“立即生效”等生效描述推导 Design 未确认的时间范围。

正文不写背景原因、价值判断和空泛目标；不重复默认角色和全局规则；不用“支持相关操作”“按常规处理”“用于承载”等模糊句；不为显得完整补造排序、分页、按钮、超时或提示；少用加粗；列表不强行嵌套。

### 13. 统计页与复杂动作逐页验收

含统计、看板、趋势、下钻或导出的模块，必须按页面或子闭环分片生成，不得一次压缩多个统计页。每个 `4.x.6` 页面完成前确认以下四项，任一缺失先回到 Design，不进入下一页面：
- 页面标题与 Design 页面名称完全一致；Design 页面已落正文，或正文明确写出被合并的原页面名称及其承接关系（合并必须写清原页面承接的业务结果去向，不留丢失）；
- 页面形态、区域、关键字段和操作入口可确定；
- 数据来源、组织范围、时间范围和统计/校验口径可确定（统计页必须能读出统计对象、组织范围、时间边界、分子分母、纳入排除、去重、空值零值、下钻继承和导出范围；详细要求统一见 `references/data-definition-rules.md`，八类试读问题作为验收/审查口径，九项要素作为写作口径，二者统一）；
- 状态、权限、异常、成功结果和下一环节可确定。

全部模块生成完成后，从最后一个模块向前回读至少两个模块，专门检查是否出现摘要化和事实密度下降；发现后半段退化为指标、按钮或字段摘要时立即重写该模块并重新回读。

`prd-consistency-check.py` 出现 `deterministic_conflict` 时，不得标记为“全绿”或人工放行；必须修复正文消除冲突，或先修正检查器本身并重新运行。

## 事实边界（writing / module pass 装载）

1. 唯一事实源是设计集清单登记的正式 Design 文件；Prototype、旧 PRD、示例和通用经验只能帮助理解，不能覆盖或补造事实。
2. 高影响未知（权限、数据范围、角色、状态机、流程、删除/作废/归档传播、外部系统、历史数据、统计口径）必须列为待确认并回到 Design；低影响展示细节只能承接 Design confirmation 已拍板的推断值。
3. Design 冲突不得由 PRD 拍板：保留冲突事实、说明冲突位置和影响对象、列为待确认，并在无法确认前停止对应模块写作，建议回到 Design Fix。
4. 生成后直接回读真实 `prd.md` 与 Design：检查承接、遗漏和擅自增加，发现问题直接修正；不生成承接矩阵、覆盖率报告、验证回执或机器签名替代回读。
5. 交付 PRD 必须自包含。不得写 `Design §x.x`、`output/design/设计地图.md`、`按 Design规则` 或其他跨文件指针；确认后的规则直接写入当前 PRD，重复使用时只引用当前 PRD 已存在的章节或页面。未确认事实只写“待确认”及影响，不用外部引用掩盖缺口。
6. 流程图是 PRD 交付包内的辅助资产，不替代正文事实。图中的角色、动作、判断、分支、异常和结果必须能在当前 PRD 正文中定位。
