## 最小结构规则（writing pass 装载）

1. PRD 顶层顺序：文档信息 → 产品概述 → 总体说明 → 功能需求 → 待确认事项。
2. 功能需求按业务闭环或业务结果组织，不按菜单、页面清单、管理端/移动端或 Design 章节机械复制。
3. 模块按需组织：功能概述 → 业务对象与关系 → 角色与权限 → 业务流程 → 业务规则 → 功能说明 → 异常处理 → 验收标准 → 待确认事项；页面说明只在独立页面规格确有需要时单列，界面功能默认在“功能说明”按页面就近写清。页面说明不存在时，后续章节连续编号；页面说明存在时，插入页面说明并顺延后续章节编号。
4. 每个有页面或业务动作的功能模块必须包含“功能说明”；历史 `4.x.6 功能详细说明` 只用于识别旧稿，不写入新稿。
5. 业务流程按具体业务对象连续叙述。租金账单、多缴余额、自然年清算等有独立起点、结果或终态的对象分别成节，不用模块统称合并。
6. 业务规则回答“按什么规则处理”，功能说明回答“谁在什么状态完成什么任务、看到什么、如何处理并得到什么结果”，独立页面说明只补充跨动作共用的页面规格，不重复功能说明。
7. “功能说明”按页面任务和业务结果组织。每个动作在生成前由作者内部核对能否回溯到“业务流程”的事件，以及能否在功能说明的页面任务中找到发起位置。该对应关系只用于生成自检和 Review，不写入 PRD 正文，不新增流程步骤对照、动作追溯表、映射表或固定回执。
8. 模块角色与权限（`4.x.3 角色与权限`）提供“角色 × 业务能力”矩阵：行是角色，列是业务能力，单元格填写“可、否或条件”，条件复杂时在表下注释展开，表达模块级权限边界。
9. 管理端和移动端放在同一闭环的真实业务阶段；共用页面只在功能说明中完整定义一次，其他模块只写差异和适用范围。
10. 页面标题、动作标题和终端后缀的格式见 `templates/prd.md`。
11. 模块存在跨页面推进、跨角色协作、跨系统交互、关键业务状态变化，或会改变业务结果的分支、异常与恢复时，`4.x.4 业务流程` 必须包含流程图；简单只读、纯展示或无状态变化和协作分支的配置模块不强制画图。
12. 不用“业务生命线”“动作与页面承接”等新造词命名章节或小节。并列对象无法形成固定业务名称时拆成两节，不把两个对象硬拼成“XX与XX”标题；既有业务名称按模板保留。

## 详细需求说明写作规范（module pass 装载）

本节是 PRD 模块详细需求说明的唯一规范源。交付目标以单业务模块（`4.x`）自包含为基线：研发只读当前业务模块，不查看 Prototype、Design 或旧 PRD，也不回问产品，即可确定产品行为并独立开发。前端依据功能说明中的页面任务、区块、字段、操作和反馈确定页面行为；后端依据业务流程、业务规则和功能说明确定数据来源、处理对象、状态变化和下游结果；测试依据业务流程、功能说明、异常处理和验收标准编写用例。视觉风格、像素尺寸、组件技术选型不属于本节职责，除非影响业务判断且 Design 已确认。Design 只作为生成时的事实输入，不能成为交付 PRD 的外部引用。

### 1. 模块章节顺序与职责

模块按需组织为：功能概述 → 业务对象与关系 → 角色与权限 → 业务流程 → 业务规则 → 功能说明 → 异常处理 → 验收标准 → 待确认事项。界面功能默认在功能说明中按页面就近写清；只有存在多个动作共用、且放入各动作会明显重复的页面规格时，才在功能说明后增加独立页面说明。不得把页面字段提前塞进业务流程，也不得用页面规格替代业务规则或动作结果。

| 章节 | 只回答 | 不承担 |
|---|---|---|
| 业务流程 | 具体业务对象从起点到终态如何连续推进，退回和失败发生在哪里 | 页面控件清单、公式推导、字段属性 |
| 业务规则 | 状态、计算、口径、快照、重算、刷新范围和金额联动按什么规则成立 | 页面区块、按钮位置、逐字段说明 |
| 功能说明 | 页面或自动任务承担什么业务任务；区块、字段、操作、校验、写入、反馈、失败和下一步如何在任务中衔接 | 流程从头复述、孤立按钮说明、正文追溯说明、与动作无关的字段字典 |
| 页面说明（按需） | 多个动作共用的页面形态、区块、字段属性、状态驱动展示和页面过程状态 | 新业务流程、复杂公式、主链解释、重复动作闭环 |
| 异常处理 | 跨动作的系统异常、并发、重复提交、部分失败和外部失败如何恢复 | 单个动作内已经写清的失败保留 |
| 验收标准 | 从业务流程和功能说明拆出的正常、退回、失败、边界和终态用例 | 只按字段表罗列检查项 |

业务流程按具体业务对象连续叙述。租金账单、多缴余额、自然年清算等有独立起点、结果或终态的对象分别成节，不用模块统称合并。业务流程必须写清起点、推进角色、上一动作结果如何成为下一动作前提、退回或失败发生在哪个动作、最终状态以及终态是否可能被年度清算或合同终止重新打开；流程图放在正文之后，只辅助理解。业务流程说明顺序、责任交接、关键分支和结束条件，表单字段、逐项校验和普通网络失败留在具体操作处。

业务规则必须给状态、计算、口径、快照、重算、刷新范围和金额联动唯一定义。难理解的规则必须配最小数值例子，包括多步计算、状态联动导致金额变化、跨对象金额变化。例子至少写清输入值、计算或状态变化步骤、预期结果和精度；例子不得替代测试用例、验证包或 Design 事实，也不得为了凑例子编造阈值和金额。

功能说明按页面任务和动作闭环写作。Design 页面清单和操作表是事实输入，不是 PRD 目录，动作按业务结果重组：无独立业务结果的浏览动作按业务结果合并。界面功能先写页面承担的任务、进入前提和结果去向，再按区块和操作顺序写清关键字段、输入、校验、系统处理、成功反馈、失败保留和下一步。同一操作的输入、处理、结果、失败和恢复放在同一处，读者不需要跨章拼接。生成前由作者内部核对每个动作能否回溯到 `4.x.4 业务流程` 的事件，以及能否在本页任务中找到发起位置；该对应关系不写入正文。

自动任务、定时触发、跨系统事件和无界面功能按真实触发和业务任务组织，写清触发来源、触发时点或补发条件、输入数据、系统处理、成功结果、失败状态、人工处理和恢复；不虚构页面、按钮或表单。Design 明确存在的系统动作必须在业务流程和功能说明中有可追踪落点，不能因为它没有按钮而省略。简单动作只写实际适用的责任，不虚构确认或异常分支。动作标题用“动词 + 业务对象或业务结果”，不把点击、打开、切换、返回、播放直接当标题，不为了复刻 Design 操作表而一对一拆分。

独立页面说明只在确有跨动作共用规格时使用，页面标题逐字采用 Design 页面名称。页面说明先写页面共同任务、角色和状态差异，再写跨动作共用的区块结构、字段属性、状态驱动展示、加载、空态、异常和无权限。字段表只补充类型、来源、只读或可编辑、显隐和控件属性，不承担复杂公式、统计范围、时间起止或主流程解释。单个页面的操作输入、处理、反馈和失败已经能在功能说明就近读清时，不另建重复页面说明。

### 2. 业务流程写作

每个具体业务对象使用独立的四级或五级小节，先写连续正文，再放流程图。正文按业务发生顺序写清生成、提交、审核、确认、到账、退回、失败恢复和终态，分支在发生点写清，不集中堆到后文。

上一动作的结果必须成为下一动作的前提。例如生成结果进入哪个待办、谁在什么状态接收、审核退回回到哪个节点、失败后哪些数据保留、重新提交是否重新走前级审核。终态写清是否绝对终态，是否可能被年度清算、合同终止或后续调整重新打开。

业务流程不得只写一段摘要加一张图。图中出现的角色、判断、分支、异常出口和结果状态必须能在同一节正文定位；正文不得依赖图才能理解。

### 3. 业务规则写作

每个规则主题使用独立小节，写清状态定义、状态迁移、计算公式、数据口径、快照、重算、刷新范围和金额联动。关键数据口径统一遵循 `references/data-definition-rules.md`，本节只规定 PRD 的叙述位置和例子责任，不复制其四档数据责任定义。只有跨操作或跨页面复用的规则在这里完整定义；某动作特有的规则写在该动作处，读者当下需要的关键条件就近写清，不用模糊引用掩盖缺口。

难理解规则的最小数值例子跟随需要解释的规则。例子只解释规则，不写页面按钮和测试步骤；计算例必须能按正文公式复算，状态或金额联动例必须能看出前后状态、金额来源和最终落点。允许假设输入并明确标为示例，公式、精度和处理结果必须来自已确认事实。

### 4. 功能说明写作

“功能说明”采用以下稳定骨架组织：
- 业务阶段：说明本阶段包含哪些业务任务和结果；
- 页面名称：六级标题（`###### 页面名称`），逐字采用 Design 页面清单名称，不带编号，不擅自改名或造名；
- 页面任务：写谁在什么前提进入、要完成什么判断或任务、结果交给谁或进入什么状态；
- 区块和操作：按任务顺序写区块承担的判断、关键字段和操作；每个操作随后写动作闭环；
- 动作名称：独占一行的无冒号粗体短语（`**动作名称**`），作为动作定位标题；
- 动作正文：写清该操作在该页面中的输入、校验、处理、结果、失败和恢复。

页面名称在功能说明中同时作为页面任务和动作定位锚点。生成前内部核对每个动作能否回溯到业务流程的事件，以及能否在本页任务中找到发起位置。正文只写页面任务和动作闭环，不复述对应关系，不写“对应流程第几步”，不新增流程步骤对照、动作追溯表或映射表。跨动作共用的页面背景、字段属性、状态驱动展示和页面过程状态，才放入按需的独立页面说明。

动作按复杂度写，三档复杂度作为生成与审查的责任判定标准，不转写为固定正文小标题：
- **简单动作**（查询、查看、返回、打开详情）：写清操作角色、可用条件、页面展示或数据结果；
- **普通动作**（新增、编辑、保存、提交、修改）：写清前置条件、输入与校验、系统处理、成功结果、失败保留或恢复路径；
- **复杂动作**（多角色协作、多状态流转、多分支判断、破坏性操作、外部协作）：写清允许角色与状态、关键业务分支、状态变化、失败恢复以及下一步衔接。

复杂动作与高影响操作按实际适用补充以下闭环规则，不适用项不写：
- **逆向与退路**：状态推进、审批或额度扣减动作，写清驳回、撤销与冲销后的落点（退回上一环节还是初始草稿）、已占额度/资源的解扣规则，以及是否允许修改重提；
- **生命周期与解绑**：删除、停用、注销或解绑动作，写清对未完结业务的阻断校验、软删除传播范围，以及历史业务单据中的展示形式（显示占位名还是固化快照）；
- **并发与幂等**：关键资源修改、多角色处理同一任务或重复提交时，写清系统裁决胜出的规则（如先到达者生效、后到达者提示最新状态并刷新）、防重结果与已填内容保留；
- **批量与事务**：批量审批、批量修改或批量导入时，写清部分失败时的事务边界（整单全部回滚还是部分成功）、失败项反馈方式，以及大数据量导出是否走异步任务；
- **时效与快照**：费率、规则或基础信息修改时，写清生效时机（立即、次日还是下一周期），以及下游与历史单据是读取固化快照还是跟随最新主数据。

某项责任不适用时可以不写，但生成和审查必须明确判断过，不能因模型遗漏而静默缺失。简单动作不得扩写伪造复杂交互。合并或精简后不丢失角色、前置条件、状态、数据范围、失败结果和后续去向。

### 5. 页面说明写作

独立页面说明按 Design 页面清单逐页写作，页面标题与功能说明中的页面名称一致。每页先写跨动作共用的页面背景和角色状态差异，不重复功能说明已经写清的任务和动作结果。

页面说明再写以下适用内容：
- 页面形态与边界：读者能判断是看板、列表、详情、表单，还是多个页面组合；属于同一业务动作的多个页面写清如何进入、返回和衔接。
- 页面构成与信息关系：写清承担业务判断或操作的区域、区域之间共用的查看范围、筛选条件或当前对象，以及切换范围后哪些内容同步变化。
- 展示内容与方式：页面实际展示的字段、指标、状态、图片、视频、趋势、历史记录和提示可读；展示方式影响业务判断或操作时写清是文本、状态标签、图片、播放器、卡片、列表、趋势图、单选、多选、下拉还是多行输入。
- 字段来源与编辑性：动态字段写清业务来源、何时只读、何时可编辑、由哪个角色编辑、已有值如何带出、什么条件下显示或隐藏，以及空值、未知值、超长和异常值如何呈现。
- 操作入口与状态驱动展示：写清用户从哪里发起操作，按钮或入口在什么角色、权限和业务状态下显示、隐藏、可点或不可点；状态变化后相关按钮、字段、列表项、状态标签和页面内容如何刷新或消失。
- 页面过程状态：加载中、空数据、加载失败、无权限、离线、部分数据失败或外部资源不可用时，写清用户看到什么、已成功数据是否保留、能否重试，以及部分失败是否影响其他区域。
- 导航与状态保留：写清页面入口、成功后停留/跳转/返回、返回目标，以及返回后筛选、排序、分页、滚动位置或未提交内容是否保留。
- 多终端与多角色：同一业务在管理端、移动端、小程序等存在不同页面和操作时，分别写清每个终端展示什么、允许修改什么、完成后如何衔接其他角色；不能用“管理端只读、移动端可操作”一句话替代。

页面说明不得补造新流程，不得重复功能说明中的动作闭环，不得用字段表承载复杂公式和主流程。只有多个动作共用同一字段、按钮状态或页面过程状态时，才在这里定义；单动作特有内容回到该动作处。

### 6. 自然语言硬约束与排版形态

功能说明和按需页面说明正文全部使用自然语言，按内容场景选择三种表达且分工明确：
- 自然段用于业务承接，连续表达业务前提、用户判断、系统处理、结果和下一环节；
- 数字编号列表用于有先后顺序的步骤、状态推进和处理链路，每一项必须是完整业务语句；
- `·` 并列列表用于同层并列的展示项、校验项、限制项、异常项和动作，每一项说明条件、含义或结果。

一个块（自然段或 `·` 列表项）只承载一层事实。禁止将“区域 → 字段清单 → 权限分支 → 版本节点 → 例外提示”等多层事实堆叠在单个块内。长块必须通过分段、短矩阵或子列表分层展开。单块的长度阈值（自然段、`·` 列表项的上限字符数）以 `contracts/prd-writing.profile.json` 的 `paragraph_max_chars`、`dot_item_max_chars` 为唯一落点，本文不重复具体数值。

**单句只承载一个主要动作和一个条件分支。** 叙述句按 `sentence_max_chars`、操作步骤句按 `step_max_chars` 控制长度，超过即拆成“角色或条件 → 动作 → 结果”多个短句；两个业务事实之间不用分号连接，拆成两句。字段枚举句（连续顿号并列的字段、状态、标签清单）不拆，拆开反而更难读。

以下写法不得作为正文：
- 字段表、页面区块表、操作表、状态表或数据流表替代正文叙述；
- “页面职责、使用对象、入口与返回、页面区块、字段来源”等固定元数据块；
- “触发、输入、处理、成功结果、失败结果、后续去向”等行首标签；
- “字段名：说明”“来源：某系统”“结果：已完成”等连续键值对句式；
- 读者跨多个表格、章节或上游文档才能拼出的一条业务链；
- 同一套句式机械替换页面名和字段名。

### 7. 模块级权限矩阵与正文权限落点

每个业务模块在 `4.x.3 角色与权限` 提供“角色 × 业务能力”矩阵：
- 行是业务角色，列是业务能力，单元格写“可、否或条件”；
- 复杂条件在表格下方注释中逐条展开；
- 能力按业务动作组织，不按界面按钮或图标组织。

矩阵用于表达模块级权限全局边界。“功能说明”在此基础上写清各动作适用的具体业务状态、组织数据范围、例外条件、退回后的处理细节，以及按钮、字段和页面入口的展示结果；独立页面说明只补充多个动作共用的权限展示差异。

### 8. 短矩阵与业务流程图

功能说明和按需页面说明允许使用短矩阵作为快速扫读锚点，适合表达角色权限差异、状态与动作矩阵、固定选项及其流转结果。短矩阵用于辅助理解，不能替代动作正文和页面任务的规则展开，也不强制所有页面必须配矩阵。

业务流程图：模块存在跨页面推进、跨角色协作、跨系统交互、关键业务状态变化，或会改变业务结果的分支、异常与恢复时，“业务流程”必须画图；纯查询、纯展示或无状态流转的简单配置无需为了形式画图。每个命中模块至少一张图，复杂闭环按具体业务对象拆图。流程图保存为 `output/prd/diagrams/<图名>.drawio`，并按 2 倍分辨率导出同名 `.png` 嵌入正文。流程图只辅助理解，正文必须完整写清规则，图不得新增正文没有的事实。

### 9. 自然中文规则

生成正文时严格遵循以下 13 条自然中文规则：
1. 先写角色和动作，再写条件、处理和结果；
2. 一个句子尽量只承载一个主要动作；
3. 一个自然段只推进一个主要业务判断；
4. 用具体动词替代抽象名词；
5. 用可验证的产品结果替代价值评价；
6. 不在产品正文评价方案是否先进、完整、务实或有效；
7. 不为了修辞制造“不是……而是……”等对比结构；用于排除歧义的否定定义可以保留；
8. 不用“通过……实现……”包住核心事实；
9. 不用“形成闭环、提升效率、强化管理”等总结句代替流程和状态；
10. 未确认事实直接标记待确认，不用概念化表达掩盖未知；
11. 用肯定句陈述约束，不用双重否定；“不得、禁止、不允许”用于表达业务约束本身，不算双重否定；
12. “这”“其”“该”只指一个明确对象，一段内出现多个可能对象时把名词重复一遍，不让读者回上文核对指代；
13. 名词前的修饰语不超过两层，超过就拆成两句或改用列表。

“赋能、抓手、底座、协同、支撑、闭环”等词不能单独作为禁词判断。是否需要修改，取决于它是否替代了具体动作、条件或结果。章节和小节标题不得使用“业务生命线”“动作与页面承接”等新造词，也不得把两个并列对象硬拼成“XX与XX”式名称。

### 10. 前端事实承接

页面实际存在的能力必须通过功能说明写清，不能因为 Prototype、Design 其他章节或常见研发经验中可能存在而省略。页面形态、区块、关键字段、展示和编辑条件、操作入口、加载、空态、异常、无权限、导航和状态保留按页面任务就近落位；多个动作共用的页面规格放入按需页面说明。前端只读功能说明和按需页面说明即可确定页面产品行为。

### 11. 后端事实承接

业务实际存在的能力必须写清，让后端能确定业务数据从哪里产生、按什么范围和规则查询计算校验、操作后修改哪个业务对象、哪些字段和状态变化、产生哪些记录，以及结果进入哪些后续环节：
- 数据来源与权威来源：每项关键动态数据写清来自哪个业务对象、内部计算、用户录入、组织权限、设备、外部系统或其他角色处理结果；多个来源可能提供同一字段时，写清哪个是当前权威值、人工修改是否覆盖外部值、后续外部更新是否再次覆盖。
- 查询、范围与计算规则：严格执行 `references/data-definition-rules.md` 中的四档数据责任与同名同口径原则。查询和统计写清对象、组织、时间、状态、筛选继承、纳入排除、去重和计算口径（汇总统计必须满足对象、组织、时间起止闭合、分子分母、状态白名单与排除项、去重唯一键、空值零值、刷新时效、下钻导出一致性九项要素；周期结算必须补充账期锚点、取数版本、过程精度、尾差归属、重算锁定规则）；共用范围的指标、列表、趋势、下钻和导出保持一致；刷新失败、切换范围和缓存并存时，写清保留当前范围旧数据还是清空并显示失败，不留展示上一组织数据的歧义。
- 用户输入与业务校验：写清已有值如何带出、哪些字段必填、允许什么取值、字段间联动或互斥关系、在什么时点校验，以及校验失败后页面和已填写内容如何处理。
- 系统处理与写入对象：保存、提交、修改、确认、绑定、领取、撤回、删除、作废或归档时，写清修改哪个业务对象、哪些字段和状态变化、是否更新主信息、当前任务、业务快照、关联对象或历史记录，以及多个对象同时变化时的业务关系和先后结果。
- 新增记录与审计留痕：动作生成任务、台账、告警、处理记录、导出记录、修改历史或审计记录时，写清何时生成、记录哪些产品事实、由谁查看、生成失败是否影响主动作；“记录操作日志”不能替代具体业务用途和下游可见结果。
- 状态变化与重复执行：强动作写清允许发起的角色和状态、成功后的目标状态、状态变化后哪些动作不再允许；同一任务可能被多人处理、重复提交或处理期间被外部事件改变时，写清是否拒绝覆盖、用户看到什么、已填数据是否保留、下一步如何继续。PRD 不规定锁或幂等，但必须规定冲突后的业务结果。
- 下游影响与后续消费者：动作完成后写清结果出现在哪些列表、详情、台账、统计、告警或其他角色待办中，以及数据变化对后续判断、统计口径、权限可见性或外部同步的影响；只写“保存成功”或“返回列表”不构成完整结果。
- 外部系统与失败边界：外部系统提供数据时，写清谁提供、本系统如何使用、失败后业务对象保持什么状态、用户看到什么，以及由系统重试、用户重试、人工处理还是等待外部恢复；只有 Design 已确认的重试次数、超时、补偿和恢复方式才能写成事实。

### 12. 跨前后端的完整业务链

业务流程、业务规则、功能说明和按需页面说明最终必须能连成一条完整业务链：对象在什么业务前提和状态下开始；用户或系统依据什么规则处理；成功后哪些对象、字段、状态和页面发生变化；失败后保留什么、用户如何继续；结果由哪个角色、页面或业务环节继续使用。不要求固定章节数量、段落数量或字数，但不缺少实际适用且影响开发的事实。

按实际适用覆盖：写作前先在内部判断前端和后端各项事实是否适用。适用项必须在正文有明确落点；不适用项直接跳过，不创建空段落，不写“本页不涉及”。无法判断且影响核心流程、权限、数据范围、状态、写入对象或外部协作的事项，必须作为高影响未知回到 Design，不由 PRD 或研发自行拍板。

### 13. 事实边界与信息密度

Design 是唯一事实源，PRD 只承接已确认事实，不静默新增页面、字段、角色、权限、状态、流程、金额口径和外部系统行为；权限、数据范围、状态机、删除传播、外部协作、历史数据、统计口径等未知保留为待确认并回到 Design，不用“按配置”“按业务规则”替代；状态条件、动作分支或权限依据存在多种可能且 Design 未拍板时，禁止用“或”“按业务规则”“按配置”等模糊表达保留不可执行分支，必须回到 Design；不得从“立即生效”等生效描述推导 Design 未确认的时间范围。

同一事实可以在业务流程、业务规则和功能说明中重复出现，但每次出现必须增加新的使用信息，例如角色、状态、条件、对象、输入、校验、计算、结果、异常、恢复方式、展示方式或上下游关系。第二处仅换词重述第一处、未增加任何新使用信息的，属于原地重述，审查应予剔除。为局部理解保留对象名、关键前置条件和短结论，不作为缺陷处理；不得用“补充上下文”作为整段复写的理由。

正文不写背景原因、价值判断和空泛目标；不重复默认角色和全局规则；不用“支持相关操作”“按常规处理”“用于承载”等模糊句；不为显得完整补造排序、分页、按钮、超时或提示；少用加粗；列表不强行嵌套。

### 14. 统计页与复杂动作逐页验收

含统计、看板、趋势、下钻或导出的模块，必须按页面或子闭环分片生成，不得一次压缩多个统计页。每个页面在功能说明完成前确认以下四项，任一缺失先回到 Design，不进入下一页面：
- 页面标题与 Design 页面名称完全一致；Design 页面已落正文，或正文明确写出被合并的原页面名称及其承接关系（合并必须写清原页面承接的业务结果去向，不留丢失）；
- 页面形态、区域、关键字段和操作入口可确定；
- 数据来源、组织范围、时间范围和统计/校验口径可确定（统计页必须能读出统计对象、组织范围、时间边界、分子分母、纳入排除、去重、空值零值、下钻继承和导出范围；详细要求统一见 `references/data-definition-rules.md`，八类试读问题作为验收/审查口径，九项要素作为写作口径，二者统一）；
- 状态、权限、异常、成功结果和下一环节可确定。

全部模块生成完成后，从最后一个模块向前回读至少两个模块，专门检查是否出现摘要化、事实密度下降或同一操作跨章拼接；发现问题立即重写该模块并重新回读。不以固定目录、字数下降或脚本通过替代业务事实完整。

`prd-consistency-check.py` 出现 `deterministic_conflict` 时，不得标记为“全绿”或人工放行；必须修复正文消除冲突，或先修正检查器本身并重新运行。

## 事实边界（writing / module pass 装载）

1. 唯一事实源是设计集清单登记的正式 Design 文件；Prototype、旧 PRD、示例和通用经验只能帮助理解，不能覆盖或补造事实。
2. 高影响未知（权限、数据范围、角色、状态机、流程、删除/作废/归档传播、外部系统、历史数据、统计口径）必须列为待确认并回到 Design；低影响展示细节只能承接 Design confirmation 已拍板的推断值。
3. Design 冲突不得由 PRD 拍板：保留冲突事实、说明冲突位置和影响对象、列为待确认，并在无法确认前停止对应模块写作，建议回到 Design Fix。
4. 生成后直接回读真实 `prd.md` 与 Design：检查承接、遗漏和擅自增加，发现问题直接修正；不生成承接矩阵、覆盖率报告、验证回执或机器签名替代回读。
5. 交付 PRD 必须自包含。不得写 `Design §x.x`、`output/design/设计地图.md`、`按 Design规则` 或其他跨文件指针；确认后的规则直接写入当前 PRD，重复使用时只引用当前 PRD 已存在的章节或页面。未确认事实只写“待确认”及影响，不用外部引用掩盖缺口。
6. 流程图是 PRD 交付包内的辅助资产，不替代正文事实。图中的角色、动作、判断、分支、异常和结果必须能在当前 PRD 正文中定位。
