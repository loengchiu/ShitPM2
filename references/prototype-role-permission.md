# Prototype 角色与权限表达

> 本文件在页面涉及角色、权限或数据范围差异时读取。它定义原型中角色切换器的形态、权限差异的表达层级、权限事实的来源边界（哪些可推断、哪些必须问用户），以及评审现场最容易被问住的「状态机动作按钮组」模式。
> 产品契约背景：推断值机制见 `output/design/decision-notes.md` 登记约定（低影响直接推断 + 汇总拍板；高影响必须确认）。本文件不改变该契约，只定义原型侧的表达方式。

## 一、定位：原型里的角色是给谁看的

- 原型的角色系统服务于**评审现场**：切一个角色，当场看出"这个角色能做什么、不能做什么、能看到什么范围"。评审核心问题是"不同角色时候的各种问题"，不是演示 RBAC 技术方案。
- 不要只演菜单差异——菜单差异一眼可见、信息量低；**按钮级启停 + 状态迁移**才是评审现场真正会被问住的地方（见 §七）。
- 默认视角是管理员/主管：先给全局，再演"一线看不到某些按钮"的落差。

## 二、角色切换器形态

- 位置：顶栏右上角用户区。
- 形态：`Avatar`（品牌色底 + 白字，取**当前角色首字**）+ **角色名文本**。
- 交互：**点击角色名**展开 `Dropdown`，平铺列出全部角色；选中即切换，**不刷新页面**。
- 默认角色：管理员 / 主管视角。
- 角色数 > 6 时再考虑分组；≤6 一律平铺。
- 模板参考实现：`templates/prototype-vite/src/App.jsx` + `src/shared/role.jsx`。

## 三、权限表达四级表

| 层级 | 表达方式 | 硬规则 |
| :-- | :-- | :-- |
| 菜单可见 | 无权限项**不渲染** | 不得渲染后置灰（菜单灰项会让评审误以为"系统坏了"） |
| 按钮可点 | 无权限 → **不渲染**；有条件可用（状态不满足）→ `disabled` + 悬浮说明 | 禁止用"（无权限）"这类文字标注代替真实控件状态 |
| 字段可见 / 只读 | 不可见 → **整个 label:value 对不渲染**；只读 → 值正常展示、不出现编辑控件 | 禁止渲染成禁用输入框 |
| 数据范围 | **粗粒度示意**：表格顶部一行范围提示（如"以下仅显示本人提交的 3 条"） | **不做部门树、不做范围筛选器** |

补充约束：

- 权限差异必须真实作用于渲染结果，切换角色后页面内容（菜单项数、按钮、字段对、范围提示行）可观察地变化。
- 角色切换是纯前端状态切换，不得触发路由跳转或整页刷新。
- 权限规则只表达 Design 已确认的角色与操作；原型不得发明 Design 之外的角色。

## 四、权限事实来源：推断表与高影响问题

- **可推断的**（菜单可见性 / 按钮级 / 字段级）：按 Design 的角色定义与状态机直接推断，逐条登记推断表（§五），confirmation 前汇总呈报，用户一次拍板（接受 / 修改 / 拒绝）。
- **高影响的**（§六清单）：**必须问用户**，不得由 AI 静默补全，也不得进推断表蒙混。
- 推断依据写不出来（只有"按常识""一般系统都这样"之类套话）的，不写推断——机械重复 N 次相同依据 = 缺陷信号。

## 五、推断表模板

| # | 项 | 角色分层 | 推断结果 | 推断依据（来自 Design 的具体事实） | 用户裁决 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 1 | 菜单：系统管理 / 角色权限 | 仅管理员可见 | 不渲染 | Design 权限矩阵 §x.x（管理员独占系统配置） | 待定 |
| 2 | 按钮：整改单 / 删除 | 管理员+主管可删，一线不可见 | 一线不渲染 | Design 状态机 delete 动作的角色=admin,manager | 待定 |
| 3 | 字段：合同 / 联系电话 | 一线不可见 | 整对不渲染 | Design 字段敏感性标注（联系方式仅管理层） | 待定 |
| 4 | 数据范围：投诉工单列表 | 一线仅本人提交 | 顶部范围提示行 | Design 数据权限：受理人=本人 | 待定 |

填写规则：每行必须有指向 Design 的具体依据；依据列出现空泛套话即视为不可推断，转 §六处理或删除该行。

## 六、高影响问题清单（不得推断）

以下事实涉及权限、数据范围、流程与数据安全，**必须问用户**，合并成少量阻断问题一次问清：

1. **数据范围**：每个角色能看到的数据边界（本人 / 本部门 / 全部；跨组织是否可见）。
2. **审批链**：审批环节的顺序、层级与每个环节的角色。
3. **谁能删谁**：删除类操作的角色与对象范围（含删除后的传播）。
4. **跨组织可见性**：多租户 / 集团内外组织之间的数据隔离边界。
5. 数据层超时与补偿、金额口径、历史数据的迁移与展示口径（涉及权限兜底或资金时同样不推断）。

## 七、状态机动作按钮组（评审最强载体）

详情页底部操作栏里，把该实体的**全部状态迁移动作**一次列全，按「当前状态 + 当前角色」决定每个按钮是**渲染 / `disabled` / 不渲染**：

- 渲染：当前角色在当前状态下有该动作权限且前置状态满足。
- `disabled` + 悬浮说明：动作存在但当前状态不满足（如"未提交，不可审批"）。
- 不渲染：当前角色无该动作权限。

评审时切角色，就能当场看出"这个角色在每种状态下能做什么、不能做什么"。抽取来源：存量审计系统 `rectify/r06`（13 个按钮按角色+状态启停）。

配套要求：

- 动作全集与状态迁移必须来自 Design 状态机，不自造动作、不漏 Design 已定义的迁移动作。
- 每个按钮挂 `data-operation`，与状态机动作名逐字一致。
- 按钮的启停矩阵是权限推断表的重点行，逐条登记（§五）。

## 八、验收清单

- 切换器位置与形态符合 §二；默认管理员/主管视角。
- 切换角色后：菜单项数变化（非置灰）、按钮出现/消失、字段对出现/消失或变只读、有范围限制的列表出现范围提示行，逐项在真实浏览器确认。
- 切换不触发整页刷新。
- 四级表达各自符合 §三的硬规则，无"（无权限）"文字标注、无禁用输入框冒充只读。
- 推断表已登记且每行有具体依据；§六清单内的事实没有以推断形式出现。
