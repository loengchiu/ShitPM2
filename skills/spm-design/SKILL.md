# 设计

## 触发条件

用户要求开始设计，或 stage-context 建议进入 design 阶段。

## 前置检查

运行 `scripts/python/stage-context.py` 检查准入：

1. align.md 存在
2. metadata/align 完整
3. align-notes.json 中 `can_enter_design` = true

如检查不通过，🔴 停止并输出阻塞项，不写任何产物。

🔴 **失败分支：stage-context.py 执行失败**——脚本报错时停下告知用户，不跳过前置检查。

1. `.workflow/status.json`
2. `output/align/align.md`（对齐产物）
3. `.workflow/metadata/align/index.json`

## 执行顺序

1. 运行前置检查
2. 读取最小读取集合
3. **设计思考**（必须在生成正文前完成，写入内部推理，不写入 design.md 正文）
4. 按以下顺序生成设计：
   - 角色定义
   - 模块定义
   - 页面清单
   - 字段完整定义
   - 页面与字段落点
   - 业务流程设计（按需，无流程需求时不写）
   - 状态设计
   - 规则设计
   - 权限定义（细到字段级）
5. 生成 design.md 人读产物
6. 更新 status.json

## 设计思考（生成前必做）

● **在写任何正文之前，必须先完成以下思考并得出结论。思考过程不写入 design.md。**

### 3.1 用户意图分析

从 align.md 提取所有用户角色，列出每个角色的核心任务：

> 角色A：[任务1] → [任务2] → [任务3]
> 角色B：[任务1] → [任务2]

每个任务必须是"用户要完成什么"，不是"系统有什么功能"。

### 3.2 页面推导

● **一个页面 = 用户的一次完整操作意图。**

从角色任务推导页面，而不是从数据表推导页面：
- 用户在当前页面能否完成一个完整意图？能 → 页面拆分合理
- 用户需要在多个页面之间来回跳转才能完成一件事？是 → 合并或重组成任务流
- 同一个列表里混了用户根本不关心的数据？是 → 按角色或任务场景拆分

**反模式**：系统有入库申请表、审核表、确认表 → 建三个列表页（按数据表拆页面）
**正模式**：用户要"查看并跟踪入库申请状态" → 入库申请列表页（按用户意图拆页面）

### 3.3 模块组织

● **模块按业务域划分，不按技术层或数据层划分。**

检查：一个模块下的页面是否属于同一个业务域的完整生命周期？
- 是 → 模块合理
- 否 → 按业务域重组

### 3.4 字段放置预判

对每个页面，先确定页面主任务，再按操作流排列字段区域：

1. 高频字段放高位
2. 只读与可编辑分开
3. 必填字段前置，选填后置或折叠
4. 同一条规则适用的字段必须在同一个区域/动作内

根据信息量决定布局策略：
- 字段 ≤5，无列表 → 单列直排，不需要分区
- 字段 6-15，或有列表 → 按操作上下文分 2-3 个区域
- 字段 >15，或有多个子表 → 用卡片分区、折叠面板、或分步骤 Tab

信息密度为"重"的页面，必须在页面清单的"主要功能"列注明分区策略。

### 3.5 自检清单

设计思考完成后、开始写正文前，逐项确认：

1. 每个页面能否用一句话说清"帮用户完成什么任务"？说不清 → 页面拆分有问题
2. 每个模块下的页面是否属于同一个业务域？不是 → 模块组织有问题
3. 有没有页面是从数据表直接映射出来的？有 → 重新按用户意图推导
4. 有没有把 10+ 个字段平铺在一个区域？有 → 按操作上下文分区
5. 信息密度为"重"的页面是否标注了分区策略？没有 → 补上

● **自检不通过的项目必须修正后再写正文，不带着问题继续生成。**

> **metadata 生成时机**：design.md 的机读产物（metadata/design/）不在本阶段生成，
> 而是在 /spm-design-review 通过后由 stage-prep.py 脚本一次性提取。
> 设计阶段只关注人读物质量，PM 修订时也只改 design.md，不再双写。

## 硬规则

### 用户角色与数据范围层级

当设计涉及多级组织架构（如：集团→区域→服务区）时，必须明确：

1. 角色定义中列出角色的数据可见范围层级
2. 页面清单中标注每个页面在不同数据范围下的展示差异
3. 字段定义中标注哪些字段随数据范围变化（如：服务区名称在"全部服务区"时必须展示）
4. 页面与字段落点中按数据范围层级标注差异

🔴 **检查点**——如设计涉及多级组织架构但未定义数据范围层级，停下补充，不进入 PRD。

### 设计是唯一事实源

以下三类内容的完整定义必须在 design 中：

1. 字段完整定义
2. 权限完整定义
3. 状态完整定义

PRD 可为交付目的镜像这些内容，但不得独立改写语义。

### 状态定义密度要求

🔴 **状态描述必须让研发不看原型就能写出状态机代码。**

每个有状态流转的实体，状态定义章节必须包含：

1. **状态流转速览**：用一行文字写出完整生命周期路径，如 `待入职 → 在职 → 待离职 → 已离职 → 再入职 → 在职`
2. **状态明细表**（必须使用表格）：

| 状态值 | 名称 | 进入条件 | 退出条件 |
|--------|------|----------|----------|
| 1 | 在职 | 确认入职 / 再入职 | 办理离职 |
| 2 | 待入职 | 创建员工时选择待入职 | 确认入职 / 删除 |

3. **每条迁移必须写清**：触发动作 + 触发角色 + 前置条件 + 是否自动/手动 + 关键副作用

**反模式**：
> - `draft`：草稿
> - `submitted`：已提交
> 1. 提交后进入 submitted
> 2. 撤回后回到 draft

**正模式**：
> 周报状态流转路径：`草稿 → 已提交 → 已归档`
>
> | 状态值 | 名称 | 进入条件 | 退出条件 |
> |--------|------|----------|----------|
> | draft | 草稿 | 成员新建周报 / 成员撤回已提交周报 | 成员提交周报 |
> | submitted | 已提交 | 成员提交周报（需校验本周必填项非空） | 负责人审核通过归档 / 成员撤回 |
> | archived | 已归档 | 负责人审核通过（不可撤回，不可修改） | 无 |
>
> 迁移规则：
> 1. 成员点击"提交" → 状态从 draft 变为 submitted，前提是本周完成内容和下周计划均非空；提交后成员仍可撤回
> 2. 成员点击"撤回" → 状态从 submitted 回退为 draft，仅限负责人尚未审核时可操作
> 3. 负责人点击"审核通过" → 状态变为 archived，此操作不可逆，成员不可再编辑或撤回
> · 每人每周仅允许存在一份周报
> · archived 状态保留当周最终版本，不再受撤回或编辑影响

无状态流转的实体明确声明"无状态机"。

### 业务流程密度要求

🔴 **流程描述必须让研发不看原型就能画出时序图或写出流程控制代码。**

涉及多角色或 3+ 步骤的业务流程，必须包含：

1. **流程速览**：用一行文字写出主链路角色和阶段，如 `申请人提交 → 财务审核 → 服务区确认`
2. **按阶段展开**：每个阶段写清角色、动作、判断条件、分支走向、状态变化
3. **关键分支必须写具体判断条件**：不写"如需审核"，写"任一明细税后价值超过 2000 元时进入财务审核"
4. **异常路径必须覆盖**：网络中断、操作超时、并发冲突等场景写清降级策略
5. **涉及的字段值必须写具体**：不写"状态变更"，写"entryStatus 从待离职(3)变为已离职(4)"

**反模式**：
> 1. 成员填写周报并提交
> 2. 负责人审核周报
> 3. 审核通过后归档

**正模式**：
> 周报提交审核流程分三个阶段：成员填写提交、负责人审核、结果归档。
>
> **阶段一：成员填写提交**
> 1. 成员进入填写周报页面，新建或继续编辑当前周周报。
> 2. 提交时校验：本周完成内容（this_week）和下周计划（next_week）均不允许为空；需协调事项（coordination）和标签（tags）为选填。
> 3. 校验通过后，状态从 draft 变为 submitted，页面提示"周报已提交"。
> 4. 校验不通过时，对应字段标红并显示错误提示，不关闭表单，已填写内容不丢失。
>
> **阶段二：负责人审核**
> 5. 负责人在团队汇总页看到已提交的周报，可逐条查看内容详情。
> 6. 负责人对每条周报作出"通过"或"退回"处理。
> 7. 退回时需填写退回原因，退回后状态回到 draft，成员收到通知后可重新编辑。
>
> **阶段三：结果归档**
> 8. 审核通过后状态变为 archived，不可撤回、不可修改。
> · 每人每周仅允许存在一份周报
> · 审核期间如网络中断，当前处理结果不落库，页面保留已填写意见并允许重试
> · archived 结果保留当周周末 24:00 时的最终状态

### 字段级权限组织

1. 字段定义章节只写字段业务定义，不写字段级权限表
2. 权限定义章节负责字段级权限
3. 按"页面 > 角色 > 字段权限例外"组织
4. 先写默认权限规则，再写例外字段
5. 不要求把所有字段逐个平铺成巨大权限表

### 页面与字段落点

1. `design` 内必须显式存在“页面与字段落点”章节，作为字段定义与页面使用之间的唯一对照层
2. 页面清单、字段定义、页面与字段落点三处必须能互相对齐，不能只写字段表、不写页面落点
3. 页面与字段落点按“页面 > 区域/动作 > 字段”组织，不展开成 PRD 级页面正文
4. 页面与字段落点里的字段名必须直接引用字段定义中的标准字段名，不得在这里改写别名
5. 每个页面清单中的页面都必须在页面与字段落点章节出现；如该页无业务字段，明确写“无业务字段”
6. 每个字段必须满足二选一：要么出现在页面与字段落点，要么出现在“非页面落点字段”例外表并写明原因
7. 用户可见字段、可编辑字段、可筛选字段、页面动作直接依赖字段，必须进入页面与字段落点，不得放进例外表规避
8. 纯内部字段可进入“非页面落点字段”例外表，例如用户 ID、数据 ID、创建时间、更新时间、内部关联 ID、审计字段
9. 字段既不在页面与字段落点，也不在例外表时，直接判为缺口，不得静默保留

### 结构化写法

1. 页面清单必须使用结构化表格，不用散文或纯标题平铺
2. 字段定义必须使用结构化表格，不用 `### 字段名` 逐条散写
3. 页面与字段落点必须按页面分小节，每个小节内使用结构化表格，至少包含“区域/动作”“字段”两列
4. “非页面落点字段”使用结构化表格，至少包含“字段”“原因”两列
5. 生成 design 时优先保证这三处结构可机读，再追求人读润色


## 失败模式与 Fallback

| 场景 | 触发条件 | 一线修复 | 仍失败兜底 |
|------|---------|---------|-----------|
| 前置检查失败 | stage-context.py 返回阻塞项 | 输出阻塞项清单，停下等用户补充 | 不跳过前置检查直接写 design |
| stage-context.py 执行失败 | 脚本报错或超时 | 检查脚本路径和 Python 环境 | 停下告知用户具体错误，不跳过 |
| align.md 不存在 | output/align/align.md 不存在 | 停下，需要先完成对齐阶段 | —— |
| 模板文件不存在 | 	emplates/design.md 不存在 | 使用内置最小模板（角色/模块/页面/字段/规则/权限） | 停下告知用户安装模板 |
| 参考文件不存在 | 
eferences/design-writing.md 不存在 | 跳过参考，按硬规则生成 | —— |
| 设计规模过大 | 页面 > 10 或字段 > 50 | 先生成索引，再逐块生成，最后组装 | 告知用户可能需要分多次 review |
| metadata 生成失败 | stage-prep.py 报错 | 检查 design.md 格式是否符合解析要求 | 告知用户 metadata 未生成，不影响人读产物 |
| 多级组织架构未定义数据范围 | 设计涉及多级架构但未标注 | 补充数据范围层级定义 | 停下，不进入 PRD |
## 不要做什么

1. 不写研发级页面正文
2. 不写高保真视觉表达
3. 不新增 align 没确认的范围
4. 不把 prototype 的表现层问题直接提升为业务事实
5. 不重新判断建设类型
6. 不重新解释原始材料
7. 不静默合并新材料

### 稳定 ID 规则

1. 稳定 ID 首次在 design 阶段生成
2. 只存在于外置机读物，由 review 通过后 `scripts/python/stage-prep.py` 脚本注入，由 review 通过后 `scripts/python/stage-prep.py` 脚本注入
3. design.md 正文不得出现稳定 ID
4. 第一版只使用以下前缀：
   - `MODULE-design-NNN`
   - `PAGE-design-NNN`
   - `FIELD-design-NNN`
   - `RULE-design-NNN`
   - `FLOW-design-NNN`
   - `REL-design-NNN`
5. 不引入 `REQ-*`、`RISK-*`、`CASE-*`、`WVR-*`

### 大型设计分块

如页面 > 10 个或字段 > 50 个：

1. 先生成索引（模块 → 页面 → 字段概览）
2. 再逐块生成，每块局部自检
3. 最后组装

## 输出要求

### 人读产物

写入 `output/design/design.md`，按 `templates/design.md` 骨架组织。

核心章节必须全部存在：
- 角色定义
- 模块定义
- 页面清单
- 字段定义
- 页面与字段落点
- 规则与状态定义
- 权限定义

辅助章节可选：
- 文档概述
- 范围与建设方式
- 核心业务流程

### 状态更新

更新 `.workflow/status.json`：

- `current_stage`：更新为 `"design"`
- `artifacts.design`：指向 `output/design/design.md`
- `metadata_paths.design`：指向 `.workflow/metadata/design/`
- `next_recommended`：`"prd"` 或 `"prototype"`

## 停止条件

1. design.md 核心章节全部存在
2. 无新增 align 未确认的范围
3. 页面清单、字段定义、页面与字段落点三处能互相对齐
4. 设计思考自检清单 5 项全部通过（不通过的已在生成前修正）

满足以上 4 条后停止，建议 `/spm-design-review`。

## 明确不做什么

1. 不写研发级页面正文（那是 PRD 的职责）
2. 不写高保真视觉表达
3. 不执行 review（建议 `/spm-design-review`）
4. 不自动推进到下一阶段
