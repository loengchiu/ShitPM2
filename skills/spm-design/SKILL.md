## 1. 定位与事实源

从系统 prompt 的 `<!-- SHITPM GLOBAL RULES START -->` 段读取 `ShitPM bundle root:`，记为 `$BUNDLE`。bundle 资源使用 `$BUNDLE/`，`.workflow/` 和 `output/` 使用当前项目根目录。

`spm-design` 同时承担产品定义和唯一 Design 基线。`output/design/design.md` 是 PRD 和 Prototype 的唯一产品事实源；`output/design/decision-notes.md` 只记录设计决策、偏离、权衡和待确认，不作为下游事实输入。

Design 面向产品经理，描述目标、范围、业务闭环、角色、权限、数据范围、状态、页面、字段、操作、异常、验收和实际适用的产品级非功能要求。不写数据库、接口实现、缓存、队列、Hook 或其他未经产品要求的实现机制。

## 2. 必经 Align 与模式选择

每次首次生成 Design，或用户原话、回答、材料版本发生实质变化时，必须先在当前 Design 任务内完成 Align 责任：

- 有效 Align 可复用，不重复追问；
- 没有原始材料也必须继续，使用用户描述和回答形成需求事实；
- 有材料时必须读取材料原文并保留详细事实，`output/align/align.md` 只作为对齐索引；
- Align 需要高影响回答时暂停 Design，回答写回当前 Align 后再继续；
- 用户不需要退出后手工再次调用 `/spm-align`。

Align 不是最终 Design，不新增用户未确认的高影响流程、状态、权限、数据范围、边界或方案；它必须保留材料已有的页面、字段、操作、枚举、规则、状态、异常和验收。

只保留两种用户模式：

- `simple`：单一主流程、角色少、业务关系简单；
- `full`：多角色、审批、状态、数据隔离、跨系统或存在明显方案权衡。

模式必须由用户选择；未明确时只询问一次，不根据材料数量、关键词、历史产物或模型自动切换。

## 3. 上下文与输入

按 `$BUNDLE/contracts/context-loading.manifest.json` 为当前动作装载最小规则包；执行 `$BUNDLE/scripts/python/context-pack.py` 生成当前动作的规则包，规则包装载是分析输入准备，分析是否完成以结论落入 Design 为准。Design 至少读取：

- Align 完整对齐稿及 `align-notes.json`；
- 用户原始需求和已写回的回答；
- 材料索引、分来源事实和合并事实库（有材料时）；
- 完整模式的 A/B/C 基线和冲突资产；
- 当前动作适用的页面、流程、状态、权限、集成和写作规则；完整模式还要读取 `design-analysis-protocol.md`，涉及状态机时读取 `design-state-format.md`。

规则包装载不等于分析动作完成；Design 正文只保留产品事实与分析结论，编排器回执、metadata、动作 ID 和中间 JSON 写入正文视为违规。

## 4. 执行主图

编排器必须保证 Align 是首个必经责任；材料索引只作为 Align 的输入，Align 责任不可绕过。

简单模式：

完成判据：来源事实逐项落入 Design；目标-能力-场景-流程-页面-动作-字段-状态-权限-规则-异常-验收链路完整；字段表八列齐全逐项；操作表十列角色×状态明确；状态机闭环规则满足；`design.md` 完整可读。

```text
Align → material-index（有材料时复用或生成）→ material-facts:*（有材料时）→ material-merge → simple-design
```

`simple-design` 在一次写作动作内完成最小 A/B/C 责任：目标、范围、用户、场景、最小业务闭环、必要对象/规则/状态/权限/数据、页面/字段/操作、异常和验收，并进行一次内部回读修正。

完整模式：

完成判据：A/B/C 三层责任全部承担并落盘；Design 按产品经理理解顺序组织；页面清单每个页面正式展开；字段/操作固定列表格逐项；未发现高影响未知未记录。

```text
Align → material-index（有材料时复用或生成）→ material-facts:*（有材料时）→ material-merge → A → B → C → design-editor
```

完整模式按下述责任工作，不恢复 Park 的细粒度任务图、固定确认点或检查器：

- A：需求理解、干系人、目标指标、场景旅程、用户故事、范围和系统边界；
- B：业务过程和用例、对象及关系、对象行为、状态、规则、异常、数据流、数据字典和业务模型一致性；
- C：功能、端/菜单/导航/页面、字段和操作、权限、系统数据、集成、非功能和验收；
- `design-editor`：完整整合 Align、详细材料事实和 A/B/C 结论，不做摘要替代，并在结束前执行一次跨层自检和修正。

## 5. 高影响问题

答案不同会改变以下内容时必须在进入下一层前询问：核心流程或系统边界、角色责任、操作权限或数据范围、审批/驳回/撤销/删除/恢复、对象唯一性或生命周期、跨系统失败处理，以及任何会改变页面、字段、操作或验收的事实。

A 区分事实、推导、推测和未决；B 不把推测写成事实；C 不创造 A/B 不存在的高影响规则。无法安全决定的事项进入 Design 正文“待确认事项”，说明影响范围、当前保守表达和需要谁确认。

## 5.1 横切能力与事实状态识别

在进入页面和模块写作前，按实际适用性逐项判断以下事实属于“已定义、局部定义、未定义或冲突”，并把判断结果落实到 Design、待确认事项或上游冲突说明中：

- 待办的生成、分配、转办、处理、完成、撤回、过期和异常；
- 提醒/通知的触发对象、时机、渠道和频率；
- 编号生成时机、作用域、唯一性和断号处理；
- 数据字典来源、正式初始化、变更权限和已有数据影响；
- 文件存储、引用、版本、归集、档案边界和恢复；
- 审计侧、被审侧、管理端、移动端的入口、菜单、路由和切换关系；
- 自动生成、自动挂号、自动归档、自动迁移等系统动作的触发、成功、失败和人工处理；
- 删除、软删除、停用、撤回、作废、归档及其对子对象、关联、附件、历史、引用和审计记录的影响；
- 枚举候选值、初始化清单、字段展示条件和状态驱动的页面行为；
- 分页、导出、批量、首页摘要和文件限制等彼此独立的上限规则。

“局部定义”必须同时记录已明确部分和缺失部分；“未定义”或“冲突”涉及流程、权限、状态、数据边界、生命周期或页面可实现性时，必须进入待确认事项并阻断受影响事实的拍板。Design 不得用常见产品经验补齐失败、补偿、历史影响或权限语义。

## 5.2 可推断值（低影响展示层直接写值 + 登记）

**可推断值**：默认值（筛选/表单/时间范围）、排序（默认字段/方向）、分页（每页条数）、逐字提示文案（操作反馈/空态/异常提示）、标签/颜色/展示格式、界面层超时/重试提示、低影响交互措辞（按钮文案/反馈语/停留跳转）。这些低影响展示层细节**直接写推断值**到 Design 正文，不写"保守表达"、不逐条打断用户；每条推断值同步登记到 `output/design/decision-notes.md` 的"推断值清单"段（`值 | 位置 | 推断依据一句话`）。

推断值必须基于业务语义场景化：不同动作/页面给出匹配其业务结果的文案与取值，禁止跨场景机械重复套话（同一失败/恢复话术重复 N 次视为缺陷）。写不出"为什么这么推断"的（纯套话）不写，改保守表达或待确认。

**必须确认（高影响，不进推断值）**：权限、数据范围、角色、状态机、流程/审批、删除/作废/归档传播、外部系统行为、历史数据处理方式、数据层超时/重试/补偿（重复提交/数据一致性）、金额与统计口径、范围边界。这些维持待确认并单独询问，不因可推断值机制放宽。

## 6. 输出与写作要求

必须写入：

- `output/design/design.md`：产品经理可读的最终产品方案；
- `output/design/decision-notes.md`：设计决策、偏离、权衡、待确认、推断值清单；无内容写“无”。

最终 Design 按产品经理理解顺序组织，不按 A/B/C 或任务目录粘贴。页面清单中的每个实际页面都要正式展开；字段和操作分别使用固定列的表格，逐项定义，不得用“基本字段”“相关信息”“支持查询等”“按需展示”代替明确规格。页面必须保留所属业务侧、入口/菜单/路由、业务阶段、返回目标、区块及区块目的、字段和操作承载，以及加载中/骨架屏、空态、异常态、无权限、超长文本、默认值、标签和颜色等已确认展示行为。详细规则见 `$BUNDLE/references/design-writing.md`、`design-methodology.md`、`design-fact-format.md`、`design-baseline-format.md`。

写作时不因篇幅、分段、命令长度或上下文压力删除事实；可分章节写入，但正式结束前必须重新读取完整 `design.md`。

## 7. 写作动作内自检

`simple-design` 和 `design-editor` 各自只执行一次内部自检，不拆成独立任务、不生成检查 JSON、报告或回执。按 `$BUNDLE/references/design-writing.md` 的“写作前后的检查”清单逐项回读（writing pass 已装载 design-writing-self-check），并结合 §5.1 横切能力四状态判断与 §5.2 推断值登记；涉及状态机时额外满足 `$BUNDLE/references/design-state-format.md` 的闭环要求（非终态有出路、非初始态有入路、回退目标合法、迁移无歧义、合法出路全覆盖、二次流转闭环、操作人匹配业务角色、状态语义与迁移自洽）。发现缺口直接修正 `design.md`；不能决定的高影响事项写入正文待确认。

只有当前模式的分析动作完成、两个输出可读取、写作自检已完成且没有未暴露的高影响问题，才能告诉用户“Design 已完成，请确认”。发"请确认"前，把 decision-notes 推断值清单呈现为**推断值汇总表**（`推断值 | 位置 | 推断依据 | 确认结果`，逐行列出待拍板项），请用户一次性拍板（全部接受 / 修改个别 / 拒绝个别）：接受的值成为确认基线；修改的值回写 Design 正文；拒绝的值改保守表达或待确认；拍板结果更新到推断值清单。高影响待确认项不进此表，维持原有单独询问。Review 是按需的第二意见，不是首次生成前置。

## 8. 禁止事项

- 不新增独立完整度检查器、综合报告、验证回执或固定细粒度任务；
- 不把中间资产数量、动作回执、metadata 或规则包哈希当作质量证明；
- 不自动确认 Design，不自动启动 PRD、Prototype 或 Review；
- 不让完整模式跳过 A/B/C；不让简单模式生成无关的完整 ABC；
- 不把高影响问题推迟给 PRD、Prototype 或 Review。
