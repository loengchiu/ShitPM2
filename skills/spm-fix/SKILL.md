# 同步修复

## 触发条件

用户要求进行同步修复，或 review 结论建议回上游修复。

## 最小读取集合

1. `.workflow/status.json`
2. 用户修改指令
3. 当前阶段稿件
4. 当前机读锚点
5. `contracts/fix-propagation-rules.md`

## 执行顺序（最小判断清单 6 步）

1. 读取用户修改指令
2. 判断修改指向的对象：
   - 目标 / 范围 / 建设方式
   - 模块 / 页面 / 字段 / 规则 / 流程 / 状态 / 权限
   - 表现层布局 / 样式 / 视觉交互
3. 判定问题归属层
4. 判定事实源所在阶段
5. 判定受影响的最深阶段
6. 生成修复顺序并执行

## 硬规则

1. 只改必要内容，不整篇重写
2. 覆盖式更新，不制造多版本并存
3. 不允许逆向定源（PRD 不能直接改 design 的语义）
4. 若无法判断归属层，先停在澄清，不得直接改下游
5. 设计是唯一事实源——字段、权限、状态的完整定义只在 design 中

## 输出要求

### 覆盖产物

按修复顺序逐层覆盖：

1. 更新事实源阶段的稿件和机读物
2. 更新受影响的下游阶段稿件和机读物

### 修复完成后的 review 建议

```
建议进入 [阶段] review，检查对象：[对象列表]
```

不自动执行 review，由 PM 手动确认后触发。

## 明确不做什么

1. 不整篇重写
2. 不制造多版本并存
3. 不回避影响分析直接硬改下游
4. 不允许逆向定源
5. 不自动推进阶段
