# 同步修复

## 触发条件

用户要求进行同步修复，或 review 结论建议回上游修复。

## 最小读取集合

1. .workflow/status.json
2. 用户修改指令
3. 当前阶段人读稿
4. contracts/fix-propagation-rules.md

## 执行顺序

### 步骤 1：接收修改指令

读取用户修改指令，确认修改内容。

🔴 **检查点：指令完整性**——修改指令是否包含「改什么」和「改成什么」？缺少任一项时，停下追问，不猜测。

### 步骤 2：判断修改指向的对象

按以下分类定位修改对象：

| 类别 | 示例 | 归属层 |
|------|------|--------|
| 目标/范围/建设方式 | 一期范围缩减 | 对齐层 |
| 模块/页面/字段/规则 | 新增审批状态字段 | 设计层 |
| 流程/状态/权限 | 审批流程增加回退节点 | 设计层 |
| 表现层布局/样式/视觉 | 卡片间距调整 | 原型层 |

### 步骤 3：判定事实源所在阶段

🔴 **检查点：事实源定位**——修改指向的对象，其完整定义在哪一层？
- 字段、权限、状态的完整定义 → 设计层（design 是唯一事实源）
- 页面结构和交互行为 → 原型层
- 目标和范围 → 对齐层

若无法判断归属层，停下澄清，不得直接改下游。

### 步骤 4：判定受影响的最深阶段

按传播矩阵确定下游影响：

| 修改层 | 直接影响 | 间接影响（需检查） |
|--------|---------|-------------------|
| 对齐层 | design | prd, prototype |
| 设计层 | prd, prototype | design-review 结论 |
| 原型层 | 无 | prototype-review 结论 |

🔴 **检查点：影响范围确认**——列出所有受影响的人读产物文件，逐个检查是否需要更新。

🔴 **失败分支：fix 过程中发现上游产物本身有 bug**——停下，报告给用户：「在修复 X 时发现上游 Y 本身存在问题（具体描述），需要先修 Y 再继续 fix」。不自行决定是否修上游。

### 步骤 5：执行修复

按修复顺序逐层覆盖人读物：

1. 先更新事实源阶段的人读稿
2. 再更新受影响的下游阶段人读稿
3. **不手动修改 metadata**——机读物在下次 review 通过后由 `stage-prep.py` 脚本重新生成

### 步骤 6：修复后建议

输出修复摘要，包含：
- 修改了哪些文件（仅人读稿）
- 影响了哪些下游产物
- 建议重新进入对应阶段 review——review 通过后 metadata 会自动重新生成

不自动执行 review，由 PM 手动确认后触发。

## 硬规则

1. 只改必要内容，不整篇重写
2. 覆盖式更新（当前真相原则），不制造多版本并存
3. 覆盖范围仅限人读物；机读物在下次 review 通过后由脚本重新生成
4. 不允许逆向定源（PRD 不能直接改 design 的语义）
5. 若无法判断归属层，先停在澄清，不得直接改下游
6. 设计是唯一事实源——字段、权限、状态的完整定义只在 design 中
7. 修复后不自动推进阶段
8. fix 不手动修改 metadata，由 review 通过后脚本重生成

## Shell 环境规则

🔴 **Codex 默认 shell 为 PowerShell**——文件编辑操作不要用 Python -c 内联脚本（引号会被 PS 解析破坏），改为写入临时 .py 文件执行。字符串替换不要依赖 \n 匹配（Windows 文件用 \r\n），用 Python 按行号操作。

## 不要做什么

- 不整篇重写——只改受影响的段落
- 不制造多版本并存——覆盖旧内容
- 不回避影响分析直接硬改下游
- 不允许逆向定源
- 不自动推进阶段
- 不在 fix 过程中发现上游有 bug 就顺手修——停下，报告给用户决定
- 不跳过传播矩阵直接改下游
- 不修改 review 结论文件（review 结论是只读的，修正需重新 review）
- 不手动修改 metadata（机读物由 review 通过后脚本自动生成）
