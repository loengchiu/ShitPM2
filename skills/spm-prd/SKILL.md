## 路径解析

从系统 prompt 的 `ShitPM bundle root:` 读取 `$BUNDLE`。

- `scripts/python/`、`references/`、`templates/`、`contracts/`、`schemas/` 使用 `$BUNDLE/` 前缀。
- `.workflow/`、`output/` 使用当前项目根目录。

## 核心职责

PRD 只有两条质量主线：

1. **内容质量**：完整承接已确认 Design 的产品事实，并保持事实一致。
2. **阅读质量**：按业务闭环连续阅读，让产品、研发、测试可以直接评审。

确认版 `output/design/design.md` 是唯一产品事实源；存在 Design confirmation 时，按当前项目约定读取确认结果。Prototype、旧 PRD、示例和通用产品经验只能帮助理解，不能覆盖或补造 Design 事实。`output/prd/prd.md` 是交付物，不是新的事实源。

## 开始前检查

1. 确认 `output/design/design.md` 存在且可读。
2. 运行 Design confirmation 检查：

   ```text
   python $BUNDLE/scripts/python/design-confirmation.py --project-root . check
   ```

3. 检查失败时停止，不生成或覆盖 PRD；用自然语言说明需要用户确认当前 Design。只有用户明确确认后，才运行 `confirm` 记录哈希：

   ```text
   python $BUNDLE/scripts/python/design-confirmation.py --project-root . confirm
   ```

不得在用户未明确确认前运行 `confirm`。不要求 Prototype、Design Review、metadata 或其他历史中间文件作为 PRD 前置条件。

## 模型与上下文

流程开始时根据 Design 的复杂度选择推理深度；执行中不切换模型。

所有 PRD 统一执行同一条全量分片流程，不再根据 Design 大小选择“普通 PRD / 超大型 PRD”路径。小项目只会产生较少分片，不另设一次性写作路径。流程不依赖 subagent；宿主支持 subagent 时，subagent 只能用于并行加速材料读取或模块分析，不是完成条件，也没有最终写入权。

### 阶段 A：全局扫描

只读取并建立以下导航信息，不要求把全部页面正文同时保留在上下文中：

- 产品目标和范围；
- 系统边界；
- 共用角色、权限和数据范围；
- 核心业务对象；
- 非页面落点字段；
- 共用状态和规则；
- 业务闭环；
- 页面清单与页面归属；
- Design 待确认事项。

### 阶段 A-1：Design 风险清单（模块写作前必做）

全局扫描后、进入模块分片写作前，先建立本轮生成任务的临时 Design 风险清单。该清单是当前生成任务的工作材料，不是新的永久交付物或证明文件。

| 类型 | 必须记录的内容 |
|---|---|
| 事实冲突 | 冲突位置、涉及对象、两方事实、影响范围 |
| 高影响未知 | 未定义内容、可能影响的流程/权限/状态/数据边界 |
| 处理结论 | 已确认 / 待确认 / 回 Design Fix / 可保守表达 |
| 模块影响 | 受影响的功能模块和页面 |

识别路径：先读页面清单与业务模块，再读核心对象、数据字典和非页面落点字段、状态流转、权限矩阵，最后对高影响对象做交叉比较。至少识别以下高影响未知：状态及状态转换；角色、权限和数据范围；异常、回退、撤回和恢复；必填、默认值、校验和生效时点；外部系统协作、同步和失败责任。

阻断规则：以下情况不得进入对应模块写作，先保留冲突事实、说明冲突位置和影响对象，列为待确认并回到 Design Fix：

- 核心状态转换冲突；
- 角色或数据范围冲突；
- 强动作的允许角色或允许状态冲突；
- 核心字段必填、默认值或校验规则冲突；
- 异常恢复、外部协作责任或系统边界未定义且会影响业务闭环。

PRD 不得自行选择"页面优先""数据字典优先"或其他通用规则来化解 Design 冲突，也不得替 Design 拍板冲突中的任何一方。低影响、只影响展示表达的未知可以采用不承诺具体值的保守表达。

### 阶段 B：建立最终 PRD 骨架

直接创建或维护最终 `output/prd/prd.md`，先写入：

- 文档信息；
- 产品概述；
- 总体说明；
- 全部业务模块标题；
- 每个模块的固定子章节；
- 待确认事项索引。

每个有业务页面的模块必须预先创建 `4.x.6 功能详细说明`。没有页面和业务动作的内容不得被创建为功能模块。

运行：

```text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass writing
```

`writing` 按 `$BUNDLE/contracts/context-loading.manifest.json` 装载 PRD 边界、结构、动作、名词、版本和写作内自检所需规范，用于阶段 A 全局扫描、阶段 B 骨架建立和阶段 D 有限范围整合。

### 阶段 C：模块分片写入

每次只处理一个业务闭环或一个明确的业务模块。当前模块的输入包括：

- 全局共用事实的精简视图；
- 当前模块的业务闭环；
- 当前模块对应的对象、状态、权限；
- 当前模块对应的页面、区块、字段和操作；
- 当前模块涉及的异常、恢复和验收；
- 当前模块的待确认事项。

只重新读取当前模块对应的 Design 片段，运行：

```text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass module --card scenes
```

`--card scenes` 装载 `references/prd-scene-checklist.md` 的模块写作自检清单。示例不作为装载内容：写作难点需要参考时，直接阅读 `references/prd-writing-examples.md` 对应章节。

模块边界必须来自 Design 的业务边界（业务闭环），不按页数、字段数或字数机械切片。完成当前模块后，直接写入最终 `prd.md`，然后立即按当前 Design 片段回读并修正。

禁止采用以下路径：模块草稿全部完成 → 主 Agent 重新读取全部草稿 → 整篇重新生成 PRD。分片必须直接写入最终 `output/prd/prd.md`；统一整合只做局部修正，不得重新概括、压缩或改写已完成模块正文。

#### 模块完成条件

每个模块完成前必须逐项确认：

1. `4.x.6 功能详细说明`存在且非空；
2. Design 页面均有模块内落点；
3. 页面不只有名称，还写了页面职责和业务阶段；
4. 核心动作写清角色、前置条件、输入、处理、成功结果、状态影响、失败结果和恢复方式；
5. 页面字段的展示、编辑、筛选、只读、来源和校验差异没有丢失；
6. 权限、数据范围和允许状态没有被全局摘要替代；
7. 模块验收和待确认事项已就近写入；
8. 没有新增 Design 未确认的高影响事实。
9. 非页面落点字段已单独回读：每个 Design 非页面字段至少有一个落点（对象字段定义、页面展示、页面输入、查询或筛选、动作判断、状态转换、系统内部用途、审计/版本/历史记录），不能因为字段没有页面控件就从 PRD 中删除；内部字段写明业务用途并按需分类（主键、内部关联、系统留痕、计算字段、流程状态、权限或数据范围依据、版本或历史记录）；高影响字段原则上一字段一行，合并表达只允许字段含义、属性、权限和使用方式完全一致时使用。

任一项不满足时，先修正该模块，再进入下一个分片。

#### 中断恢复

如果发生上下文压缩、中断或宿主重启：

1. 读取当前 `prd.md` 的章节骨架；
2. 找到最后一个未完成模块；
3. 只重新读取该模块对应的 Design 片段；
4. 保留已完成模块，不重新生成；
5. 继续直接写入最终文件。

不得因为中断而重新读取全部 Design 并整篇重写 PRD。

### 阶段 D：有限范围整合

整合阶段只处理：

- 模块编号；
- 标题层级；
- 名词统一；
- 页面归属；
- 全局规则引用关系；
- 跨模块状态和对象名称；
- 待确认事项索引。

禁止重新生成全文，禁止把模块正文压缩成摘要或改写已完成模块。整合修改触达已完成模块的内容（功能详细说明、页面、字段、状态、权限、异常和恢复、验收标准、待确认事项、跨模块引用关系）时，按"已完成模块变更失效"规则重新验收该模块。

## 已完成模块变更失效

任何阶段（含阶段 D 有限整合）修改已完成模块的以下内容，都必须使该模块重新进入待验收状态，并重新执行该模块的全部完成条件：

- 功能详细说明；
- 页面；
- 字段；
- 状态；
- 权限；
- 异常和恢复；
- 验收标准；
- 待确认事项；
- 跨模块引用关系。

重新验收内容包括：`4.x.6` 存在且非空；页面和业务阶段落点正确；页面字段和非页面字段已回读；动作因果链完整；状态、权限、异常和恢复没有冲突；没有新增 Design 未确认事实；模块验收和待确认事项仍然有效。

Design 上游变化时：只使受影响模块失效；与受影响模块存在共享对象、状态、权限或页面引用的模块同步进入影响评估；不得默认把全部模块标记为已验收，不得直接覆盖确认记录。不得用旧快照或旧哈希掩盖后续修改：哈希变化必须说明原因，并以最后一次重新验收的证据为准。

## 正文组织规则

1. 总体说明只放跨模块共用且只需定义一次的内容：名词、角色/组织/数据范围基线、共用状态规则和页面映射。
2. 按业务结果组织业务模块。管理端和移动端放在所属闭环的真实业务阶段；页面是承接载体，不是全文唯一组织轴。共用页面只定义一次，其他模块说明适用范围。
3. 字段按业务对象定义一次，在页面或动作处补充展示、编辑、筛选、只读、来源和校验等使用差异；状态、权限、异常、恢复和验收放在所属模块，不依赖文末总表。
4. 需要表达跨角色、跨系统或关键状态闭环时，生成 `.drawio` 源文件并按 2 倍分辨率（X2）导出 `.png`；不使用 Mermaid。图、源文件和正文使用相同名称和流程。
5. 把跨模块待确认项放在总体说明，把模块待确认项放在对应模块末尾；文末只做索引。

直接写入 `output/prd/prd.md`，同时按既有项目约定维护 `output/prd/decision-notes.md`；不要生成额外的 Design→PRD 对照表、覆盖率 JSON、验证回执或其他证明性中间资产。

## 事实边界

不得从常见产品经验补造页面、字段、角色、权限、状态、流程、接口参数、默认值、排序、分页、超时、重试、补偿、逐字提示文案、历史数据处理方式或外部系统行为。高影响未知必须保留为待确认并回到 Design；低影响未知可以用不承诺具体值的保守表达。

Design 待确认项必须仍标为待确认。若 Prototype 或旧 PRD 与 Design 不一致，以 Design 为准，并在决策记录中说明处理；若 Design 本身需要改变，停止并回到上游 Fix，而不是在 PRD 中自行改写事实。

## 生成内自检与直接修正

展示 PRD 前，在同一写作动作内逐项回读 Design，并发现问题就直接修正：

1. 目标、范围、系统边界和共用规则是否准确承接；
2. 每个业务闭环是否有清楚的起点、业务结果、终点和边界；每个功能模块的 `4.x.6 功能详细说明` 是否完整、非空；
3. 管理端、移动端、页面和动作是否落在 `4.x.6` 的真实业务阶段，共用页面是否只有一个权威定义；
4. 角色、权限、数据范围、敏感动作和职责分离是否就近可读；强动作是否显式写明执行角色和允许状态；
5. 对象、字段、字段属性、状态、状态变化、异常和恢复是否准确且有权威落点；
6. 每个核心动作是否写清前置条件、输入与校验、处理规则、成功/失败结果和数据/状态副作用；
7. 查询、统计、下钻、导出、表单配置和外部协作是否写清适用口径，是否误加无依据数字；
8. 模块是否可以脱离其他模块独立理解，是否存在“同上”或模糊跨节引用掩盖关键内容；
9. 图、`.drawio` 源文件、PNG 与正文的名称、角色和流程是否一致；
10. Design 待确认项是否仍保留，是否出现未授权的新页面、字段、角色、状态、权限或流程；
11. 文风是否存在标签式正文、动作流水账、表格主导、重复稳定标识、机读字段泄漏、AI 痕迹或明确占位符。

不要用额外对照表、覆盖率、脚本退出码或签名类证明文件证明语义完整性。

## 最终检查与结果处理

按顺序运行：

```text
python $BUNDLE/scripts/python/prd-style-lint.py output/prd/prd.md
python $BUNDLE/scripts/python/prd-consistency-check.py --project-root .
```

`prd-style-lint.py` 只识别确定性阅读坏味道：error 返回 `1`，只有 warning/info 返回 `0`，文件不存在或程序无法运行返回 `2`。所有 error 必须修复；warning/info 必须逐项阅读，确认是真问题就修复，确认是误报才保留。不生成永久检查报告或回执。

`prd-consistency-check.py` 保留分类输出：

- `deterministic_conflict`：明确幻觉、字段/枚举/属性冲突、权限反转等，返回 `1`，阻断交付并修复；必要时回到 Design。
- `possible_omission`：可能遗漏或解析不到落点，返回 `0`，由 AI 对照 Design 判断。
- `needs_semantic_judgment`：需要语义判断，返回 `0`；高影响且仍无法判断时停止并询问用户。
- `ok`：返回 `0`，仍需人工阅读最终 `prd.md`。
- 致命运行错误：返回 `2`，停止并修复输入或运行问题。

不得只看退出码 `0` 就宣布 PRD 一致。

## 输出与停止边界

写入：

- `output/prd/prd.md`：最终人读 PRD；
- `output/prd/decision-notes.md`：按项目约定维护的轻量决策记录；
- `.workflow/status.json`：更新 `current_stage` 为 `prd`，登记 `artifacts.prd` 为 `output/prd/prd.md`。

最终交付前必须直接阅读真实 `prd.md`，确认内容完整、事实一致、模块可独立阅读、图文一致。不要自动执行 PRD Review，不自动推进 Prototype，不自动修改 Design 确认。Design 缺失、确认失效、输入不可解析或高影响事实缺失时停止并报告，不用补丁掩盖问题。
