## 事实源与职责

确认版 `output/design/design.md` 是唯一产品事实源；存在 Design confirmation 时按项目约定读取。Prototype、旧 PRD、示例和通用经验只能帮助理解，不能覆盖或补造 Design 事实。`output/prd/prd.md` 是交付物，不是事实源。

PRD 两条质量主线：内容上完整承接 Design 事实并保持一致；阅读上按业务闭环连续可评审。`4.x.6 功能详细说明` 是阅读质量承载章节，写作规范以 `$BUNDLE/references/prd-writing-rules.md` 的详细需求说明写作规范为唯一源。

`4.x.6` 的交付目标：研发只读该章节，不查看 Prototype、Design 或旧 PRD，也不回问产品，即可确定产品行为并独立开发。前端据此确定页面形态、区域、内容、操作和状态；后端据此确定数据来源、处理对象、状态变化和下游结果；测试据此编写主链路与异常用例。模块生成时按实际适用承接前端和后端事实，不适用项不补写，高影响未知回到 Design。

## 开始前检查

1. 确认 `output/design/design.md` 存在且可读。
2. 运行 Design confirmation 检查：

```text
python $BUNDLE/scripts/python/design-confirmation.py --project-root . check
```

3. 检查失败即停止，不生成或覆盖 PRD，并说明需要用户确认；只有用户明确确认后才运行 `confirm`。不要求 Prototype、Design Review、metadata 作为前置条件。

## 执行模式

写作前明确模式，不静默切换：

- 首次生成：目标 PRD 尚不存在，按本 Skill 全量分片生成；
- 重新生成：用户明确要求重跑或整体重写，或质量问题涉及多个页面组织方式时，`4.x.6` 整体重写；旧 PRD 只在初稿完成后用于事实回归，不把整篇重写退化为局部微调；
- 局部修复：只修改用户指定页面、动作或问题，不借机重写无关内容；
- 中断恢复（续写）：执行中断或压缩后，从最后一个未完成模块继续；规则变化时受影响模块重新生成。

所有 PRD 统一分片流程，不再根据 Design 大小选择“普通/大型”路径；不依赖 subagent，subagent 只能并行加速材料读取或模块分析，没有最终写入权。

## 阶段 A：全局扫描

只建立导航信息（目标范围、系统边界、角色权限与数据范围、核心业务对象、共用状态规则、业务闭环、页面归属、流程图适用性、待确认事项），页面正文按需分片装载，不常驻上下文。流程图适用性只做模块级内部判断，不生成清单、回执或中间 JSON。阶段 A 大 Design（约 1000 行以上）不一次性读 design.md 正文，先运行：

```text
python $BUNDLE/scripts/python/design-index.py compile --project-root .
```

读索引 JSON 的页面、状态、字段和操作摘要组成精简导航视图；索引 JSON 全文可能达十几万 token，禁止粘贴进上下文。模块写作前对同一高影响事实做交叉比较（状态表或状态流转、页面操作、字段校验），发现不兼容口径时停止对应模块并回到 Design Fix，不自行裁决。

## 阶段 B：建立最终 PRD 骨架

直接创建或维护最终 `output/prd/prd.md`，写入文档信息、产品概述、总体说明、全部业务模块标题、模块固定子章节和待确认索引；每个有页面或业务动作的模块预建 `4.x.6 功能详细说明`。运行：

```text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass writing
```

`writing` 按 `$BUNDLE/contracts/context-loading.manifest.json` 装载事实边界、最小结构规则、骨架模板、术语和版本规则。

## 阶段 C：模块分片写入

每次只处理一个业务闭环（Design 的业务边界，不按页数、字段数或字数机械切片）。运行：

```text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass module --card scenes --module <模块名>
```

- `--module <模块名>` 确定性提取闭环章节 + 相关页面 + 共用业务对象/权限/页面清单/待确认；匹配不到时命令报错并列出可用标题清单，按清单修正模块名，不静默跳过；片段超阈值时按子闭环或页面拆分。
- `--pages <页面名>` 可显式追加页面；`--example <键>` 按页面类型装载适用正例（dashboard、list-detail-query、form-config、multi-role-state、mobile-cross-terminal、external-auto、simple-readonly 等）。
- 禁止一次性全读 design.md（sed 1,$p、全文粘贴或等效行为视为违反分片流程）；片段不得包含无关模块内容。
- 写作规则和写作示例必须联合装载：module pass 自动装载简单只读、多角色状态示例，分别展示篇幅下限和复杂页面的完整颗粒度；示例只提供颗粒度和表达参考，不提供产品事实。
- 模块名取业务闭环名；页面标题逐字采用 Design 页面名称，合并页面保留原名并说明承接关系。禁止“模块草稿全部完成 → 整篇重新生成”，分片直接写入最终 `prd.md`。
- 按写作规范判断流程图：命中跨页面推进、跨角色协作、跨系统交互、关键业务状态变化或关键分支/异常恢复时必画；简单只读或无协作、无状态变化的配置可不画。每个命中模块至少一张，复杂闭环拆图。
- 正文写清后生成 `output/prd/diagrams/*.drawio` 和 2 倍分辨率 PNG，在 `4.x.4` 嵌入 PNG；流程图只辅助理解，不新增事实。必需图无法生成或导出时停止该模块交付。

模块完成条件（任一项不满足先修正再进入下一模块）：

1. 模块按业务结果组织：开头说明业务对象、起点、推进角色和最终业务结果，不写成页面目录或字段目录。
2. 页面形成业务判断链，且前端可独立开发：能读出“业务前提 → 需要判断或完成什么 → 依据哪些信息 → 用户与系统分别做什么 → 业务结果 → 下一步由谁继续”；页面形态与边界、区域构成与共享范围、展示内容与方式、字段来源与编辑性、操作入口与状态驱动、页面过程状态、导航与状态保留、多终端多角色差异按实际适用写清，前端不查看 Prototype 即可确定页面产品行为；页面职责、使用对象、入口返回、区块和展示事实融入语境、动作前提或结果，不以“页面职责：/使用对象：/入口与返回：/区块清单”为页面主体。
3. 后端业务闭环可独立开发：数据来源与权威来源、查询范围与计算口径、输入与校验、系统处理与写入对象、新增记录与审计留痕、状态变化与重复执行、下游影响与后续消费者、外部系统与失败边界按实际适用写清，后端不查看 Design 即可确定业务数据流和状态结果；不写清写入对象、状态变化和下游去向的动作视为未完成。
4. 动作按业务结果重组：Design 操作表是事实输入，简单浏览动作按业务结果合并，动作标题用“动词 + 业务对象/结果”，不一对一复刻，不把“点击、打开、切换、返回、播放”直接当标题；合并后不丢失角色、前置条件、状态、数据范围、失败结果和后续去向。
5. 动作按复杂度分级写（`$BUNDLE/references/prd-writing-rules.md` 详细需求说明写作规范）：简单动作写触发 + 业务结果；普通表单写前置、输入与校验、处理、成功结果和失败保留；复杂动作写角色与状态、关键分支、状态变化、失败恢复和下一步衔接；禁止“触发：”“处理：”“成功结果：”“失败与恢复：”等行首标签。
6. 字段、区块、状态、权限和异常在真实使用位置表达；数据型功能（指标、统计、下钻、导出）就近写清统计对象、组织范围、时间口径、分子分母、纳入排除、筛选传递、下钻继承、空值零值和刷新失败。
7. 正文符合自然语言硬约束：无字段表、页面区块表、操作表、状态表或数据流表承载详细需求，无页面元数据块、行首标签和键值对句式；按语义使用自然段、数字编号列表和 `·` 并列列表，每一项是完整业务语句。
8. 高影响未知保留待确认，Design 待确认项原样保留，无新增 Design 未确认事实；非页面字段有对象或系统用途落点；自动动作、删除传播、枚举和独立上限按写作规范承接或待确认。
9. 写完直接回读本模块，分别从前端和后端两个视角检查事实承接与歧义，发现页面元数据化、动作清单化、业务链断裂或多种合理理解立即重写；之后修改已完成模块内容时，该模块重新进入回读验收。
10. 含统计、看板、趋势、下钻或导出的模块，必须按页面或子闭环分片生成，不得一次压缩多个统计页。每个 `4.x.6` 页面完成前确认：页面标题与 Design 页面名称完全一致；Design 页面已落正文，或正文明确写出被合并的原页面名称及承接关系；页面形态、区域、关键字段和操作入口可确定；数据来源、组织范围、时间范围和统计/校验口径可确定；状态、权限、异常、成功结果和下一环节可确定。任一确认项缺失先回到 Design，不进入下一页面。
11. 命中流程图条件的模块已在 `4.x.4` 嵌入 PNG，`.drawio` 与 PNG 可打开，图中的角色、动作、判断、分支、异常和结果与正文一致。
12. 全部模块生成完成后，从最后一个模块向前回读至少两个模块，专门检查是否出现摘要化和事实密度下降；发现后半段退化为指标、按钮或字段摘要时立即重写该模块并重新回读。

## 阶段 D：有限范围整合

只处理模块编号、标题层级、名词、页面归属、PRD 内部引用、跨模块状态/对象和待确认索引；触达正文时重新验收模块。页面名保持 Design 原名。PRD 必须自包含：确认规则直接写清，正文只引用当前 `prd.md` 的真实章节或页面；未知写“待确认”及影响。页面引用使用名称，章节编号必须真实存在。

## 最终检查与交付

最终顺序固定：完成最后一次 `prd.md` 和流程图写入 → 回读本次受影响模块并核对图文 → 运行检查 → 处理真实问题 → 再次修改则回到回读 → 内容不再变化后更新 `.workflow/status.json` → 交付前再次直接阅读真实 `prd.md`。状态更新必须在最后一次修改之后，不先用旧检查结论证明新内容。

按顺序运行：

```text
python $BUNDLE/scripts/python/prd-style-lint.py output/prd/prd.md
python $BUNDLE/scripts/python/prd-consistency-check.py --project-root .
```

- lint 只识别确定性阅读坏味道：error 返回 1 必须修复，warning/info 逐项判断，退出码 0 不表示语义通过。
- consistency：`deterministic_conflict` 返回 1，阻断并修复；`possible_omission`、`needs_semantic_judgment` 返回 0，由 AI 对照 Design 判断；`ok` 返回 0，仍需人工阅读；致命错误返回 2。无法提取或无法判断时如实报告，不写“零冲突”。
- 出现 `deterministic_conflict` 时不得标记为“全绿”或人工放行；必须修复正文消除冲突，或先修正检查器本身并重新运行，之后才能更新状态。状态记录只能对应最后一次修改后的检查结果。

## 输出与停止边界

只写入 `output/prd/prd.md`、必需流程图的 `output/prd/diagrams/*.drawio` 与 `*.png`、按项目约定维护 `output/prd/decision-notes.md`、更新 `.workflow/status.json`（`current_stage=prd`、`artifacts.prd=output/prd/prd.md`）。不生成 Design→PRD 对照表、覆盖率 JSON、验证回执或签名类证明资产。

完成后停在 PRD 交付点：PRD Review、Prototype 与 Design 确认由用户显式触发，不自动推进。Design 缺失、确认失效、输入不可解析或高影响事实缺失时停止并报告，不用补丁掩盖问题。
