## 事实源与职责

设计集清单登记的正式 Design 文件（系统级基线、跨模块契约、模块设计）是唯一产品事实体系。Prototype、旧 PRD、示例和通用经验只能帮助理解，不能覆盖或补造 Design 事实。`output/prd/prd.md` 是交付物，不是事实源。PRD 与 Prototype 互不作为前置。

PRD 两条质量主线：内容上完整承接 Design 事实并保持一致；阅读上按业务闭环连续可评审。生成、重新生成或局部修复 `4.x.6 功能详细说明` 时读取 `$BUNDLE/references/prd-writing-rules.md`；页面、动作、字段、状态、权限、异常和流程图规则均以该文件为准。

`4.x.6` 的交付目标：研发只读该章节，不查看 Prototype、Design 或旧 PRD，也不回问产品，即可确定产品行为并独立开发。前端据此确定页面形态、区域、内容、操作和状态；后端据此确定数据来源、处理对象、状态变化和下游结果；测试据此编写主链路与异常用例。模块生成时按实际适用承接前端和后端事实，不适用项不补写，高影响未知回到 Design。

## 开始前检查

1. 确认设计地图和设计集清单存在且可读（`output/design/设计地图.md`、`output/design/设计集清单.json`）。完成条件：两份文件存在、可解析，且清单能定位目标模块。
2. 检查 Design 修改状态：`python $BUNDLE/scripts/python/stage-context.py --project-root .` 输出 `design_change.active`；存在活动事务时停止，先执行 `design-set.py recover`。完成条件：`design_change.active` 为 `false`，或恢复命令已完成且重新检查为 `false`。
3. 读取设计集清单，按目标业务模块运行事实闭包装载：

~~~text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass module --card scenes --module <模块名>
~~~
完成条件：命令成功返回，输出只包含目标模块事实闭包、适用规则和所需示例；目标模块名与设计集清单登记名称一致。

4. 以“无活动事务 + 目标闭包可读”作为 PRD 生成启动条件；PRD 阶段不增加确认动作或确认哈希前置。完成条件：启动条件全部满足。

## 执行模式

写作前明确模式，不静默切换：

- 首次生成：目标 PRD 尚不存在，按本 Skill 全量分片生成；
- 重新生成：用户明确要求重跑或整体重写，或质量问题涉及多个页面组织方式时，`4.x.6` 整体重写；旧 PRD 只在初稿完成后用于事实回归，不把整篇重写退化为局部微调；
- 局部修复：只修改用户指定页面、动作或问题，不借机重写无关内容；
- 中断恢复（续写）：执行中断或压缩后，从最后一个未完成模块继续；规则变化时受影响模块重新生成。

所有 PRD 统一分片流程，不再根据 Design 大小选择普通/大型路径；不依赖 subagent，subagent 只能并行加速材料读取或模块分析，没有最终写入权。
完成条件：已明确本次属于首次生成、重新生成、局部修复或中断恢复之一，并已确定要处理的模块和写入范围。

## 阶段 A：全局扫描

只建立导航信息（目标范围、系统边界、角色权限与数据范围、核心业务对象、共用状态规则、业务闭环、页面归属、流程图适用性、待确认事项），页面正文按需分片装载，不常驻上下文。读取设计地图和设计集清单组成精简导航视图；必要时运行 `python $BUNDLE/scripts/python/design-index.py compile --project-root .` 读索引 JSON 的页面、状态、字段和操作摘要，索引 JSON 全文禁止粘贴进上下文。模块写作前对同一高影响事实做交叉比较（状态表或状态流转、页面操作、字段校验），发现不兼容口径时停止对应模块并回到 Design Fix，不自行裁决。
完成条件：已形成目标范围、业务边界、角色/权限/数据范围、核心对象、页面归属、流程图适用性和待确认事项的导航视图；同一高影响事实没有未处理冲突，或冲突已明确转回 Design Fix。

## 阶段 B：建立最终 PRD 骨架

直接创建或维护最终 `output/prd/prd.md`，写入文档信息、产品概述、总体说明、全部业务模块标题、模块固定子章节和待确认索引；每个有页面或业务动作的模块预建 `4.x.6 功能详细说明`。运行：

~~~text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass writing
~~~

`writing` 按 `$BUNDLE/contracts/context-loading.manifest.json` 装载事实边界、最小结构规则、骨架模板、术语和版本规则。
完成条件：`output/prd/prd.md` 已有最终骨架，所有业务模块和适用的 `4.x.6 功能详细说明` 均有位置，待确认索引已建立，且写作上下文已成功装载。

## 阶段 C：模块分片写入

每次只处理一个业务闭环（Design 的业务边界，不按页数、字段数或字数机械切片）。运行：

~~~text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass module --card scenes --module <模块名>
~~~
完成条件：当前写作上下文只对应一个业务闭环，且其事实闭包、适用写作规则和示例均已装载。

- `--module <模块名>` 将读取范围限定为设计集清单登记的目标模块事实闭包（系统级基线、跨模块契约和目标模块正文）；匹配不到时命令报错并列出已登记模块清单，按清单修正模块名后重跑。
- `--example <键>` 按页面类型装载适用正例（dashboard、list-detail-query、form-config、multi-role-state、mobile-cross-terminal、external-auto、simple-readonly 等）。
- 禁止一次性全读整套 Design（sed 1,$p、全文粘贴或等效行为视为违反事实闭包流程）；片段不得包含无关模块内容。
- 写作规则和写作示例必须联合装载：module pass 自动装载简单只读、多角色状态示例，分别展示篇幅下限和复杂页面的完整颗粒度；示例只提供颗粒度和表达参考，不提供产品事实。
- 模块名取业务闭环名；页面标题逐字采用 Design 页面名称，合并页面保留原名并说明承接关系。模块内容分片直接写入最终 `prd.md`；整体重写只在执行模式明确为重新生成时进行。
- 按写作规范判断流程图：命中跨页面推进、跨角色协作、跨系统交互、关键业务状态变化或关键分支/异常恢复时必画；简单只读或无协作、无状态变化的配置可不画。每个命中模块至少一张，复杂闭环拆图。
- 正文写清后生成 `output/prd/diagrams/*.drawio` 和 2 倍分辨率 PNG，在 `4.x.4` 嵌入 PNG；流程图只辅助理解，不新增事实。必需图无法生成或导出时停止该模块交付。

模块完成条件（任一项不满足先修正再进入下一模块）：

1. 模块按业务结果组织：开头说明业务对象、起点、推进角色和最终业务结果，不写成页面目录或字段目录。
2. 页面形成业务判断链，且前端可独立开发：能读出业务前提、需要判断或完成什么、依据哪些信息、用户与系统分别做什么、业务结果、下一步由谁继续；页面形态与边界、区域构成与共享范围、展示内容与方式、字段来源与编辑性、操作入口与状态驱动、页面过程状态、导航与状态保留、多终端多角色差异按实际适用写清，前端不查看 Prototype 即可确定页面产品行为；页面职责、使用对象、入口返回、区块和展示事实融入语境、动作前提或结果，不以页面职责/使用对象/入口与返回/区块清单为页面主体。
3. 后端业务闭环可独立开发：数据来源与权威来源、查询范围与计算口径、输入与校验、系统处理与写入对象、新增记录与审计留痕、状态变化与重复执行、下游影响与后续消费者、外部系统与失败边界按实际适用写清，后端不查看 Design 即可确定业务数据流和状态结果；不写清写入对象、状态变化和下游去向的动作视为未完成。
4. 动作按业务结果重组：Design 操作表是事实输入，简单浏览动作按业务结果合并，动作标题用动词 + 业务对象/结果，不一对一复刻，不把点击、打开、切换、返回、播放直接当标题；合并后不丢失角色、前置条件、状态、数据范围、失败结果和后续去向。
5. 动作按复杂度分级写（`$BUNDLE/references/prd-writing-rules.md` 详细需求说明写作规范）：简单动作写触发 + 业务结果；普通表单写前置、输入与校验、处理、成功结果和失败保留；复杂动作写角色与状态、关键分支、状态变化、失败恢复和下一步衔接；用自然段、编号列表或 `·` 并列完整表达这些内容。
6. 字段、区块、状态、权限和异常在真实使用位置表达；数据型功能（指标、统计、下钻、导出）就近写清统计对象、组织范围、时间口径、分子分母、纳入排除、筛选传递、下钻继承、空值零值和刷新失败。
7. 正文符合自然语言硬约束：无字段表、页面区块表、操作表、状态表或数据流表承载详细需求，无页面元数据块、行首标签和键值对句式；按语义使用自然段、数字编号列表和 `·` 并列列表，每一项是完整业务语句。
8. 发现 `red` 直接修正；高影响未知作为 Design 的 pending `decision` 原样保留，不新增 Design 未确认事实；非页面字段有对象或系统用途落点；自动动作、删除传播、枚举和独立上限按写作规范承接或待确认。
9. 写完直接回读本模块，分别从前端和后端两个视角检查事实承接与歧义，发现页面元数据化、动作清单化、业务链断裂或多种合理理解立即重写；之后修改已完成模块内容时，该模块重新进入回读验收。
10. 含统计、看板、趋势、下钻或导出的模块，按页面或子闭环分片生成，每次只完成一个统计页。每个 `4.x.6` 页面完成前确认：页面标题与 Design 页面名称完全一致；Design 页面已落正文，或正文明确写出被合并的原页面名称及承接关系；页面形态、区域、关键字段和操作入口可确定；数据来源、组织范围、时间范围和统计/校验口径可确定；状态、权限、异常、成功结果和下一环节可确定。任一确认项缺失先回到 Design，再继续写作。
11. 命中流程图条件的模块已在 `4.x.4` 嵌入 PNG，`.drawio` 与 PNG 可打开，图中的角色、动作、判断、分支、异常和结果与正文一致。
12. 全部模块生成完成后，从最后一个模块向前回读至少两个模块；若已完成模块少于两个，则回读全部已完成模块。专门检查是否出现摘要化和事实密度下降；发现后半段退化为指标、按钮或字段摘要时立即重写该模块并重新回读。
完成条件：当前模块的业务闭环、前端行为、后端结果、页面/动作/字段/状态/权限/异常以及流程图适用项均已完成回读验收；所有适用项有正文落点，所有高影响未知已回到 Design。

## 阶段 D：有限范围整合

只处理模块编号、标题层级、名词、页面归属、PRD 内部引用、跨模块状态/对象和待确认索引；触达正文时重新验收模块。页面名保持 Design 原名。PRD 必须自包含：确认规则直接写清，正文只引用当前 `prd.md` 的真实章节或页面；未知写待确认及影响。页面引用使用名称，章节编号必须真实存在。
完成条件：整合只改变允许的结构和内部引用；所有章节编号、页面名称、跨模块对象/状态和待确认索引均可在最终 `prd.md` 中定位，触达过正文的模块已重新验收。

## 最终检查与交付

最终顺序固定：完成最后一次 `prd.md` 和流程图写入 → 回读本次受影响模块并核对图文 → 运行检查 → 处理真实问题 → 再次修改则回到回读 → 内容不再变化后更新 `.workflow/status.json` → 交付前再次直接阅读真实 `prd.md`。状态更新必须在最后一次修改之后，不先用旧检查结论证明新内容。

按顺序运行：

~~~text
python $BUNDLE/scripts/python/prd-style-lint.py output/prd/prd.md
python $BUNDLE/scripts/python/prd-consistency-check.py --project-root . --module <模块名>
~~~

- lint 只识别确定性阅读坏味道：error 返回 1 必须修复，warning/info 逐项判断，退出码 0 不表示语义通过。
- consistency：按模块运行，`deterministic_conflict` 返回 1，阻断并修复；`possible_omission`、`needs_semantic_judgment` 返回 0，由 AI 对照 Design 判断；`ok` 返回 0，仍需人工阅读；致命错误返回 2。无法提取或无法判断时如实报告，不写零冲突。
- 出现 `deterministic_conflict` 时不得标记为全绿或人工放行；必须修复正文消除冲突，或先修正检查器本身并重新运行，之后才能更新状态。状态记录只能对应最后一次修改后的检查结果。

## 记录模块依据

模块成功生成或同步并通过针对性检查后，写入 PRD 模块依据：

~~~text
python $BUNDLE/scripts/python/design-set.py record-inputs --project-root . --artifact prd --target-id prd:<模块名> --target-name <模块名> --output-path output/prd/prd.md --output-locator <PRD 模块标题> --inputs <本次实际读取的 Design 文件 ID，逗号分隔>
~~~

`--inputs` 使用本次事实闭包实际读取的 Design 文件 ID（如 SYS-001,CON-001,MOD-001），与 provenance 中的指纹一致；语义变化后的模块同步完成后 status 恢复 current、affected_by 清空。
完成条件：依据记录成功写入，`--inputs` 与本次实际读取的 Design 文件一致，且对应模块的 provenance/status 已反映最新内容。

## 输出与停止边界

只写入 `output/prd/prd.md`、必需流程图的 `output/prd/diagrams/*.drawio` 与 `*.png`、`.workflow/provenance/prd.json`、更新 `.workflow/status.json`（`current_stage=prd`、`artifacts.prd=output/prd/prd.md`）。不生成 Design→PRD 对照表、覆盖率 JSON、验证回执或签名类证明资产。

完成后停在 PRD 交付点：PRD Review、Prototype 由用户显式触发，不自动推进。Design 缺失、活动事务未恢复、输入不可解析或高影响事实缺失时停止并报告，不用补丁掩盖问题。
