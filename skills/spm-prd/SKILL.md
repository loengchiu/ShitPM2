## 路径解析

从系统 prompt 的 `ShitPM bundle root:` 读取 `$BUNDLE`。

- `scripts/python/`、`references/`、`templates/`、`contracts/`、`schemas/` 使用 `$BUNDLE/` 前缀。
- `.workflow/`、`output/` 使用当前项目根目录。

## 核心职责

PRD 只有两条质量主线：

1. **内容质量**：完整承接已确认 Design 的产品事实，并保持事实一致。
2. **阅读质量**：按业务闭环连续阅读，让产品、研发、测试可以直接评审。

确认版 `output/design/design.md` 是唯一产品事实源；存在 Design confirmation 时，按当前项目约定读取确认结果。Prototype、旧 PRD、示例和通用产品经验只能帮助理解，不能覆盖或补造 Design 事实。`output/prd/prd.md` 是交付物，不是新的事实源。

## 开始前检查

1. 确认 `output/design/design.md` 存在且可读。
2. 运行 Design confirmation 检查：

   ```text
   python $BUNDLE/scripts/python/design-confirmation.py --project-root . check
   ```

3. 检查失败时停止，不生成或覆盖 PRD；用自然语言说明需要用户确认当前 Design。只有用户明确确认后，才运行 `confirm` 记录哈希：

   ```text
   python $BUNDLE/scripts/python/design-confirmation.py --project-root . confirm
   ```

不得在用户未明确确认前运行 `confirm`。不要求 Prototype、Design Review、metadata 或其他历史中间文件作为 PRD 前置条件。

## 模型与上下文

流程开始时根据 Design 的复杂度选择推理深度；执行中不切换模型。

所有 PRD 统一执行同一条全量分片流程，不再根据 Design 大小选择“普通 PRD / 超大型 PRD”路径。小项目只会产生较少分片，不另设一次性写作路径。流程不依赖 subagent；宿主支持 subagent 时，subagent 只能用于并行加速材料读取或模块分析，不是完成条件，也没有最终写入权。

### 阶段 A：全局扫描

只读取并建立以下导航信息；页面正文按需分片装载，不常驻上下文：

- 产品目标和范围；
- 系统边界；
- 共用角色、权限和数据范围；
- 核心业务对象；
- 非页面落点字段；
- 共用状态和规则；
- 业务闭环；
- 页面清单与页面归属；
- Design 待确认事项。

完成判据：导航信息九项全部建立；未要求保留全部页面正文于上下文。

**大 Design 时先读索引，不读正文**：Design 超过阈值（默认约 1000 行）时，先运行 design-index 生成结构化索引，以索引的页面清单、核心对象、状态、权限精简视图为导航，不一次性读 design.md 正文：

```text
python $BUNDLE/scripts/python/design-index.py compile --project-root .
```

读索引 JSON 的 `pages`（页面名 + 页面属性）、`states`（状态名 + 归属页面）、`fields`/`operations` 摘要即可；索引 JSON 全文可达十几万 token（61 页 + 729 字段时约 17 万 token），**禁止把整个索引 JSON 粘贴进上下文**，只提取页面名 + purpose/roles/states/data_scope/entry_condition 等导航属性组成精简视图。compile 退出码非 0 只表示 design.md 存在非致命结构问题（如缺必填属性），索引文件已生成、导航视图可读，继续使用；只有索引文件缺失或报 `unsupported_format`（design.md 无固定标题结构）时才按停止条件处理，不用 sed/grep 全文自行摸索结构。Design 未超阈值时可读 design.md 正文导航层（方案摘要、闭环清单、页面清单、共用对象/状态/权限、待确认）。

### 阶段 A-1：Design 风险清单（模块写作前必做）

全局扫描后、进入模块分片写作前，先建立本轮生成任务的临时 Design 风险清单。该清单是当前生成任务的工作材料，不是新的永久交付物或证明文件。

| 类型 | 必须记录的内容 |
|---|---|
| 事实冲突 | 冲突位置、涉及对象、两方事实、影响范围 |
| 高影响未知 | 未定义内容、可能影响的流程/权限/状态/数据边界 |
| 处理结论 | 已确认 / 待确认 / 回 Design Fix / 可保守表达 |
| 模块影响 | 受影响的功能模块和页面 |

识别路径：先读页面清单与业务模块，再读核心对象、数据字典和非页面落点字段、状态流转、权限矩阵，最后对高影响对象做交叉比较。至少识别以下高影响未知：状态及状态转换；角色、权限和数据范围；异常、回退、撤回和恢复；必填、默认值、校验和生效时点；外部系统协作、同步和失败责任；待办、提醒、编号、字典、文件/档案、审计侧/被审侧入口；自动动作失败；删除传播；枚举来源；分页、导出、批量、首页和文件上限；页面展示状态和状态驱动操作。

同一事实三处交叉比较是阶段 A-1 的强制动作：状态表或状态流转说明；页面操作、按钮条件和动作结果；字段必填、默认值、校验和提交条件，逐项对照，不只按章节顺序浏览 Design。至少比较：当前状态、目标状态、允许角色、允许状态、必填属性、默认值、校验条件、生效时点、失败和恢复结果。发现同一事实存在不兼容口径时，记录冲突位置、冲突内容、影响对象和受影响模块，停止对应模块写作并回到 Design Fix；不得以“页面优先”“状态表优先”“数据字典优先”等通用规则自行裁决。低影响的纯展示差异可以保守表达；会改变流程、权限、状态、数据边界或提交结果的冲突不能继续写。

完成判据：三处交叉比较已完成；风险清单已建立且记录事实冲突与高影响未知的 4 列内容；识别路径 6 步全部执行；阻断规则无命中或已记录。

阻断规则：以下情况不得进入对应模块写作，先保留冲突事实、说明冲突位置和影响对象，列为待确认并回到 Design Fix：

- 核心状态转换冲突；
- 角色或数据范围冲突；
- 强动作的允许角色或允许状态冲突；
- 核心字段必填、默认值或校验规则冲突；
- 异常恢复、外部协作责任或系统边界未定义且会影响业务闭环。

PRD 不得自行选择"页面优先""数据字典优先"或其他通用规则来化解 Design 冲突，也不得替 Design 拍板冲突中的任何一方。低影响、只影响展示表达的未知可以采用不承诺具体值的保守表达。

### 阶段 B：建立最终 PRD 骨架

直接创建或维护最终 `output/prd/prd.md`，先写入：

- 文档信息；
- 产品概述；
- 总体说明；
- 全部业务模块标题；
- 每个模块的固定子章节；
- 待确认事项索引。

每个有业务页面的模块必须预先创建 `4.x.6 功能详细说明`；只有有页面或业务动作的内容才创建为功能模块。

完成判据：`prd.md` 已创建或维护；文档信息/概述/总体说明/全部模块标题/固定子章节/待确认索引均存在；有页面模块均已预建 `4.x.6`；writing pass 已运行。

运行：

```text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass writing
```

`writing` 按 `$BUNDLE/contracts/context-loading.manifest.json` 装载 PRD 边界、结构、动作、名词、版本和写作内自检所需规范，用于阶段 A 全局扫描、阶段 B 骨架建立和阶段 D 有限范围整合。

### 阶段 C：模块分片写入

每次只处理一个业务闭环或一个明确的业务模块。当前模块的输入包括：

- 全局共用事实的精简视图；
- 当前模块的业务闭环；
- 当前模块对应的对象、状态、权限；
- 当前模块对应的页面、区块、字段和操作；
- 当前模块 Design 页面的页面操作（角色、条件、结果、状态保留和筛选恢复规则）；
- 当前模块 Design 页面的展示行为和状态驱动展示（无权限、加载中/骨架屏、空态、异常态、超长文本、默认值、标签颜色、字段显隐、置灰/隐藏操作和刷新时机）；
- 当前模块涉及的自动动作、删除/归档传播、枚举来源以及分页、导出、批量、首页和文件限制；
- 当前模块涉及的异常、恢复和验收；
- 当前模块的待确认事项。

只重新读取当前模块对应的 Design 片段，运行：

```text
python $BUNDLE/scripts/python/context-pack.py --bundle-root $BUNDLE --project-root . --stage prd --pass module --card scenes --module <模块名>
```

`--module <模块名>` 按标题锚点确定性提取该模块的 Design 片段（闭环章节全文 + 该闭环涉及的页面章节 + 共用业务对象/权限/页面清单/待确认部分），与模块写作规则、场景自检清单一起输出。模块名优先取业务闭环名（如“底稿作业”）；`--pages <页面名>` 可显式追加页面（用于补充标题词关联漏掉的页面，可重复传多个），闭环匹配成功后同样生效。

**禁止一次性全读 design.md**：sed 1,$p、全文粘贴、用编辑器选中全部正文或等效行为视为违反分片流程；必须用 `--module` 命令装载当前模块片段。片段不得包含无关模块内容；模块边界过大（片段超阈值报错）时，先按子闭环或页面拆分模块再分片。模块名匹配不到任何闭环/页面时命令报错并列出可用标题清单，按清单修正模块名后重试，不得静默跳过。

`--card scenes` 装载 `references/prd-scene-checklist.md` 的模块写作自检清单。示例不作为装载内容：写作难点需要参考时，直接阅读 `references/prd-writing-examples.md` 对应章节。

每个模块必须实际运行该模块上下文装载命令，运行成功后才可宣布该模块完成；命令执行失败时报告真实错误，不假装清单已装载。

模块边界必须来自 Design 的业务边界（业务闭环），不按页数、字段数或字数机械切片。完成当前模块后，直接写入最终 `prd.md`，然后立即按当前 Design 片段回读并修正。模块完成条件见下节 12 项，任一项不满足时先修正该模块，再进入下一个分片。

禁止采用以下路径：模块草稿全部完成 → 主 Agent 重新读取全部草稿 → 整篇重新生成 PRD。分片必须直接写入最终 `output/prd/prd.md`；统一整合只做局部修正，不得重新概括、压缩或改写已完成模块正文。

#### 模块完成条件

每个模块完成前必须逐项确认：

1. `4.x.6 功能详细说明`存在且非空；
2. Design 页面均有模块内落点；
3. 页面不只有名称，还写了页面职责和业务阶段；
4. 核心动作按 `$BUNDLE/references/prd-writing-rules.md` §2.1 动作规则分层写清：硬约束（角色、前置条件、输入、处理、成功结果、状态影响、失败结果和恢复方式；状态变更、权限、数据范围、失败后业务影响不得丢失）全部满足；低复杂动作按最低覆盖写，不虚构不存在的表单、确认或异常分支；以上要素以自然语言段落呈现，禁止写成“触发：”“处理：”“成功结果：”“失败与恢复：”等行首标签；高影响交互（二次确认/权限入口/破坏性分支）Design 未定义时列为待确认，低影响交互措辞承接 Design 推断值；
4a. 动作正文按融合规则回读（`$BUNDLE/references/prd-writing-rules.md` §2、§2.1、§6.1、§6.2）：主链路按操作顺序，关键分支单列，状态变化落到结果，下一步衔接角色写在结果处；已确认文案用双引号嵌入正文，动态内容说明来源，超长文本写清处理方式；默认角色不重复、特殊角色限制就近写；无原因腔、重复话术、标签式小节、流水账和模板填空腔；
5. 页面字段的展示、编辑、筛选、只读、来源和校验差异没有丢失；
6. 权限、数据范围和允许状态没有被全局摘要替代；
7. 模块验收和待确认事项已就近写入；
8. 没有新增 Design 未确认的高影响事实。
9. 非页面落点字段已单独回读：每个 Design 非页面字段至少有一个落点（对象字段定义、页面展示、页面输入、查询或筛选、动作判断、状态转换、系统内部用途、审计/版本/历史记录），字段没有页面控件仍保留落点；内部字段写明业务用途并按需分类（主键、内部关联、系统留痕、计算字段、流程状态、权限或数据范围依据、版本或历史记录）；高影响字段原则上一字段一行，合并表达只允许字段含义、属性、权限和使用方式完全一致时使用。
10. 当前模块的 Design 页面操作已逐项回读：每个有业务结果、状态影响、数据影响、筛选恢复或权限差异的操作，均已在对应页面下展开，或明确指向当前 PRD 中唯一且完整的复用定义；没有用“同上”“按常规处理”“支持相关操作”等表达掩盖角色、条件、结果或异常。
11. 页面展示行为和状态驱动展示已逐项回读：无权限入口、加载中/骨架屏、空态、异常态、超长文本、默认值、标签颜色、字段显隐、可见/置灰/隐藏操作、点击跳转和状态变化后的刷新时机均能定位；未确认长度、颜色或刷新时机列为待确认。
12. 自动动作、删除传播、枚举来源和独立上限已逐项回读：自动动作具备触发、成功、失败、状态保留、反馈和人工处理或待确认；删除类动作覆盖主对象、子对象、关联、审批、日志、附件、历史、引用、查询和恢复/审计；枚举具备具体值、正式初始化清单引用或待确认；分页、导出、批量、首页和文件限制分别表达。

任一项不满足时，先修正该模块，再进入下一个分片。

#### 中断恢复

如果发生上下文压缩、中断或宿主重启：

1. 读取当前 `prd.md` 的章节骨架；
2. 找到最后一个未完成模块；
3. 只重新读取该模块对应的 Design 片段；
4. 保留已完成模块，不重新生成；
5. 继续直接写入最终文件。

中断后只重新读取该模块对应的 Design 片段并继续直接写入最终文件，不重新读取全部 Design、不整篇重写 PRD。完成判据：已完成模块原样保留；当前未完成模块已按上述 5 步继续写入。

### 阶段 D：有限范围整合

整合阶段只处理以下七项内容；处理完成后不再改模块正文，不重新生成全文、不把模块正文压缩成摘要或改写已完成模块：

- 模块编号；
- 标题层级；
- 名词统一；
- 页面归属；
- 全局规则引用关系；
- 跨模块状态和对象名称；
- 待确认事项索引。

整合修改触达已完成模块的内容（功能详细说明、页面、字段、状态、权限、异常和恢复、验收标准、待确认事项、跨模块引用关系）时，按"已完成模块变更失效"规则重新验收该模块。

完成判据：7 项整合范围全部处理；引用均指向当前 `prd.md` 真实章节；无"见 6.1"式失效引用；已触达的已完成模块已按变更失效规则重验收。

PRD 内部引用必须指向当前 `prd.md` 中真实存在的章节、页面或规则名称；不得把 Design 原章节编号直接写成 PRD 内部章节编号，不得残留"见 6.1""按第十二章"等无法在当前 PRD 中定位的引用。确实需要引用上游 Design 时，必须明确写成 `Design §6.2` 或"Design 的××规则"，不能伪装成 PRD 自身章节。章节重编号、移动或删除后，所有受影响引用必须同步修正；引用无法定位时，不能以"读者应该知道"为由保留。

## 已完成模块变更失效

任何阶段（含阶段 D 有限整合）修改已完成模块的以下内容，都必须使该模块重新进入待验收状态，并重新执行该模块的全部完成条件：

- 功能详细说明；
- 页面；
- 字段；
- 状态；
- 权限；
- 异常和恢复；
- 验收标准；
- 待确认事项；
- 跨模块引用关系。

重新验收内容包括：`4.x.6` 存在且非空；页面和业务阶段落点正确；页面字段和非页面字段已回读；动作因果链完整；状态、权限、异常和恢复没有冲突；没有新增 Design 未确认事实；模块验收和待确认事项仍然有效。

Design 上游变化时：只使受影响模块失效；与受影响模块存在共享对象、状态、权限或页面引用的模块同步进入影响评估；不得默认把全部模块标记为已验收，不得直接覆盖确认记录。不得用旧快照或旧哈希掩盖后续修改：哈希变化必须说明原因，并以最后一次重新验收的证据为准。

## 正文组织规则

1. 总体说明只放跨模块共用且只需定义一次的内容：名词、角色/组织/数据范围基线、共用状态规则和页面映射。
2. 按业务结果组织业务模块。管理端和移动端放在所属闭环的真实业务阶段；页面是承接载体，不是全文唯一组织轴。共用页面只定义一次，其他模块说明适用范围。
3. 字段按业务对象定义一次，在页面或动作处补充展示、编辑、筛选、只读、来源和校验等使用差异；状态、权限、异常、恢复和验收放在所属模块，不依赖文末总表。
4. 需要表达跨角色、跨系统或关键状态闭环时，生成 `.drawio` 源文件并按 2 倍分辨率（X2）导出 `.png`；不使用 Mermaid。图、源文件和正文使用相同名称和流程。
5. 把跨模块待确认项放在总体说明，把模块待确认项放在对应模块末尾；文末只做索引。

页面、动作和终端命名格式遵循 `$BUNDLE/references/prd-writing-rules.md` §5 与 `templates/prd.md` 示例（页面用 `######`、动作用 `**`、PC 页面无终端后缀、移动端保留终端标识），不在此重复规则明细。

只写入 `output/prd/prd.md`，同时按既有项目约定维护 `output/prd/decision-notes.md`；不生成额外的 Design→PRD 对照表、覆盖率 JSON、验证回执或其他证明性中间资产。

## 事实边界

不得从常见产品经验补造页面、字段、角色、权限、状态、流程、接口参数、金额口径、历史数据处理方式或外部系统行为。默认值、排序、分页、提示文案、标签颜色、界面层超时/重试提示等展示层细节的推断值在 Design 阶段产生并登记（经 confirmation 推断值汇总表拍板），PRD 只承接拍板后的值，不自行新增。高影响未知（权限、数据范围、状态机、删除传播、外部系统、历史数据、数据层超时/重试/补偿、统计口径）必须保留为待确认并回到 Design。

Design 出现"立即生效""修改后生效""启用后生效"等生效描述时，PRD 只能承接已明确写出的事实，不得从生效描述推导时间范围：不得自行写出"只影响后续新建对象""是否影响当前进行中的对象""历史记录不受影响""历史记录需要重算""已产生结果需要追溯更新""当前任务继续使用旧规则""新旧规则并行"或"自动迁移、补偿、回滚"。时间范围会影响业务结果时，必须列为高影响未知并回到 Design，不能把常见产品经验写成确定事实。

Design 待确认项必须仍标为待确认。若 Prototype 或旧 PRD 与 Design 不一致，以 Design 为准，并在决策记录中说明处理；若 Design 本身需要改变，停止并回到上游 Fix，而不是在 PRD 中自行改写事实。

## 生成内自检与直接修正

展示 PRD 前，在同一写作动作内逐项回读 Design，并发现问题就直接修正：

1. 目标、范围、系统边界和共用规则是否准确承接；
2. 每个业务闭环是否有清楚的起点、业务结果、终点和边界；每个功能模块的 `4.x.6 功能详细说明` 是否完整、非空；
3. 管理端、移动端、页面和动作是否落在 `4.x.6` 的真实业务阶段，共用页面是否只有一个权威定义；
4. 角色、权限、数据范围、敏感动作和职责分离是否就近可读；强动作是否显式写明执行角色和允许状态；
5. 对象、字段、字段属性、状态、状态变化、异常和恢复是否准确且有权威落点；
6. 每个核心动作是否按 `$BUNDLE/references/prd-writing-rules.md` §2.1 动作规则分层满足硬约束与最低覆盖（写清前置条件、输入与校验、处理规则、成功/失败结果和数据/状态副作用；低复杂动作不虚构表单、确认或异常分支；高复杂动作逐分支、状态、副作用和恢复）；以上要素是否以自然语言段落呈现，而非“触发：”“处理：”“成功结果：”“失败与恢复：”等行首标签；高影响交互未定义时是否列为待确认、低影响交互措辞是否承接 Design 推断值而非补造；
6a. 是否按融合规则回读（`$BUNDLE/references/prd-writing-rules.md` §2、§2.1、§6.1、§6.2）：主链路是否按操作顺序、关键分支是否单列、状态变化是否落到结果、下一步衔接角色是否写在结果处；已确认文案是否用双引号嵌入正文、动态内容是否说明来源、超长文本是否写清处理方式；默认角色是否不重复、特殊角色限制是否就近；是否存在原因腔、重复话术、标签式小节、流水账和模板填空腔；
7. 查询、统计、下钻、导出、表单配置和外部协作是否写清适用口径，是否误加无依据数字；
8. 模块是否可以脱离其他模块独立理解，是否存在“同上”或模糊跨节引用掩盖关键内容；
9. 图、`.drawio` 源文件、PNG 与正文的名称、角色和流程是否一致；
10. Design 待确认项是否仍保留，是否出现未授权的新页面、字段、角色、状态、权限或流程；
11. 文风是否存在标签式正文（含“触发：”“处理：”“成功结果：”“失败与恢复：”等行首标签）、动作流水账、表格主导、重复稳定标识、机读字段泄漏、AI 痕迹或明确占位符。
12. 页面操作是否逐项承接：Design 明确列出的查询、重置、返回、取消、关闭、导出、下钻、上传、删除等操作是否在对应页面下展开或明确复用；返回操作是否说明筛选条件保留规则，重置是否说明范围和结果；是否存在"同上""按常规处理"掩盖角色、条件、结果或异常。
13. 页面、动作和终端格式是否统一：页面使用 `###### 页面名称`，动作使用 `**动作名称**`，PC 页面不带"（管理端）"等后缀，移动端页面保留"（移动端）"；是否存在 `**页面名称**`、`###### 动作名称`、标题与表格粘连，或 Design 原章节号伪装成的 PRD 内部引用。
14. 页面展示和状态驱动条件是否可回读：无权限、加载中/骨架屏、空态、异常态、超长文本、默认值、标签颜色、字段显隐、可见/置灰/隐藏操作、点击跳转和刷新时机没有被“统一处理”吞掉。
15. 自动动作和删除传播是否闭环：自动生成/挂号/归档/迁移有失败处理或待确认；删除/软删除/停用/撤回/作废/归档有对象、关联、附件、历史、引用、查询和恢复/审计规则或待确认。
16. 枚举、分页和上限是否有来源：枚举有具体值、正式初始化清单引用或待确认；分页、导出、批量、首页和文件限制分别表达，不用一个局部上限替代其他上限。

以直接回读真实 `prd.md` 与 Design 的语义对照作为完整性证明，不用额外对照表、覆盖率、脚本退出码或签名类证明文件证明语义完整性。

## 最终检查与结果处理

最终顺序固定为：完成最后一次 `prd.md` 写入 → 回读本次受影响的模块 → 运行现有 PRD 检查 → 处理检查发现的真实问题 → 如再次修改 `prd.md` 则回到回读步骤 → 确认最终内容不再变化后更新 `.workflow/status.json` → 最终交付前再次直接阅读真实 `prd.md`。任何发生在检查或模块验收之后的正文、字段、状态、权限、异常、引用、标题或格式修改，都会使前次检查和对应模块验收失效。状态更新必须在最后一次修改之后执行，检查结果只能用修改后的 PRD 证明，文件变化后只宣称"上一轮零冲突"视为无效。检查结果无法提取或无法判断时只能报告为无法判断并触发人工回读，不等于通过，也不等于确定存在问题；权限无法提取时写"无法判断"，不写"权限零冲突"。

完成判据：两次脚本均已运行并逐项处理输出；最终 `prd.md` 已直接阅读；`status.json` 已更新且未在检查前更新。

按顺序运行：

```text
python $BUNDLE/scripts/python/prd-style-lint.py output/prd/prd.md
python $BUNDLE/scripts/python/prd-consistency-check.py --project-root .
```

`prd-style-lint.py` 只识别确定性阅读坏味道：error 返回 `1`，只有 warning/info 返回 `0`，文件不存在或程序无法运行返回 `2`。所有 error 必须修复；warning/info 必须逐项阅读，确认是真问题就修复，确认是误报才保留。不生成永久检查报告或回执。

`prd-consistency-check.py` 保留分类输出：

- `deterministic_conflict`：明确幻觉、字段/枚举/属性冲突、权限反转等，返回 `1`，阻断交付并修复；必要时回到 Design。
- `possible_omission`：可能遗漏或解析不到落点，返回 `0`，由 AI 对照 Design 判断。
- `needs_semantic_judgment`：需要语义判断，返回 `0`；高影响且仍无法判断时停止并询问用户。
- `ok`：返回 `0`，仍需人工阅读最终 `prd.md`。
- 致命运行错误：返回 `2`，停止并修复输入或运行问题。

不得只看退出码 `0` 就宣布 PRD 一致。

## 输出与停止边界

写入：

- `output/prd/prd.md`：最终人读 PRD；
- `output/prd/decision-notes.md`：按项目约定维护的轻量决策记录；
- `.workflow/status.json`：更新 `current_stage` 为 `prd`，登记 `artifacts.prd` 为 `output/prd/prd.md`。

最终交付前必须直接阅读真实 `prd.md`，确认内容完整、事实一致、模块可独立阅读、图文一致。完成后停在 PRD 交付点：PRD Review、Prototype 与 Design 确认由用户显式触发，不自动推进。Design 缺失、确认失效、输入不可解析或高影响事实缺失时停止并报告，不用补丁掩盖问题。
