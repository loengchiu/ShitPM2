## 路径与边界

从系统 prompt 的 ShitPM bundle root: 读取 $BUNDLE。规则资源使用 $BUNDLE/scripts/python/、references/、templates/、contracts/；项目文件使用当前项目根目录。

Mark 只处理 output/prototypemark/ 副本：

- 原始 output/prototype/、正式 Design 和 output/prd/prd.md 保持不变。
- 带标注原型是研发和测试的主要日常执行入口；Mark 承载原型无法直接展示、但会影响实现或验收的规格。
- Design 是唯一产品事实源。默认使用 Design；用户明确指定 PRD 时，一条标注只使用 PRD 这一单一来源并标明其为下游材料。同一角标不得拼接 Design 与 PRD，冲突时停止并报告。
- Mark 不是产品事实源，也不是 Review。高影响问题只形成结构化意见，交由 spm-fix 回写 Design。
- 进入测试的页面应完成 Mark；进入研发的页面可提前完成，早期探索原型不强制。

## 任务判定

用户明确说初始化标注或增量更新后执行对应流程；两者都未明确时先询问“需要初始化标注还是增量更新？”。主动发现产品或交互问题属于 Prototype Review，不在 Mark 内处理。

## 初始化标注

1. 检查 output/prototype/ 含 package.json、src/、Design 地图和设计集清单.json；PRD 缺失可继续。运行 `python $BUNDLE/scripts/python/prototype-source-check.py --project-root .`。
   完成条件：源码检查和 Design 输入均可读；失败时停止，不复制、不标注。只有 dist/compiled.js 时报告源码工程缺失。
2. 将 output/prototype/ 复制到 output/prototypemark/，排除 node_modules/ 和旧 dist/，保留源码工程文件。在副本执行 npm ci、npm run build。
   完成条件：副本构建成功，且原始目录没有变化。
3. 建立“不可见规格清单”。优先读取用户已整理的研发/测试关注点；没有时从选定事实源中提取。每条内容必须同时满足：原型无法直接展示或仅看原型无法确认条件、结果和边界；会影响研发实现或测试判断。
   对每条内容记录：页面或区块、适用条件/角色/状态、预期结果、异常或边界、测试如何判断、来源与确认状态。按页面和 UI 区域聚合角标，但不得丢失条目。
   完成条件：所有候选项均完成准入判断；纯可见内容、模块背景和普通流程叙述已剔除；每个保留项均有明确落点和来源。
4. 标注前核对将被作为主规格的可见事实：页面标题、字段名、按钮或操作名、状态名、金额单位和精度。发现与选定事实源的高影响冲突时，停止该页面标注并输出具体冲突。
   完成条件：待标页面的可见高影响事实没有未处理冲突。该检查不替代完整 Prototype Review。
5. 优先使用原型已有的 data-page、data-block、data-field、data-operation、data-state 语义锚点定位目标，再在精确目标上添加唯一的 data-pm-mark="N"；整页规则可使用 data-pm-mark-page="N"。只插入标注属性，不修改现有 class、结构或内容。
   跨页面或后台规则挂在共同触发点或最相关页面容器；找不到可靠承接位时不得硬挂，输出“无承接位”并停止该条挂载。
   完成条件：每条已放入 Mark 的规格均落在正确页面/区块/字段/操作/状态上，且同一区域没有重复角标。
6. 按 $BUNDLE/references/prototype-mark-injection.md 注入 annotations.js、MarkLayer.jsx、pm.css，并在 App.jsx 挂载 MarkLayer。每条标注使用 sections、source 和 status；只展示实际存在的内容分组。
   完成条件：角标和浮窗均由副本源码生成，来源到文件和章节，已确认/待确认状态可辨认。
7. 执行内容自检和交互验证：
   - 删除测试：删除一条标注后，如果研发实现和测试判断都不受影响，删除该标注；
   - 可见性检查：Mark 中没有纯可见字段、按钮或布局复述；
   - 完整性检查：所有影响实现或验收的不可见事实均已有角标或“无承接位”记录；
   - 由另一执行角色仅打开带标注原型，不打开 PRD，回答实现和测试问题；
   - 验证角标点击开合；X、再次点击同一角标可关闭；同一编号只开一个；弹窗或抽屉打开时主页角标隐藏；位置能避让；重新执行 npm run build。
   完成条件：内容达到“不打开 PRD 也能实现和判断”；副本构建通过，交互规则逐项可观察。

## 增量更新

1. 对比现有 Mark、更新后的研发/测试关注点或事实源、以及最新原型，列出不可见规格的新增、修改、删除项。原型源码或页面结构已变化时，先从最新 output/prototype/ 重建副本，再按稳定编号重新挂载，禁止在过期 Mark 上直接叠加。
   完成条件：原型快照、事实来源和差异项均有明确依据。
2. 编号保持稳定，不复用、不重排。新增项使用下一个递增编号；修改项只更新对应 sections、source 和 status；删除项移除属性、角标和备注。
   完成条件：没有无关结构或样式变化。
3. 纯可见字段、按钮、布局或普通交互变化不新增标注；只有原型无法直接展示且影响实现/验收的规格变化进入 Mark。
   完成条件：每个差异项都记录了“进入 Mark / 不进入 Mark”的准入结论。
4. 在副本运行 npm run build，并复验来源、状态、角标、浮窗、无承接位和原始目录保护；再次执行删除测试与“不打开 PRD”试读。
   完成条件：副本可构建、内容自洽，原型和正式事实文件未被修改。

## 高影响意见与无承接位

发现缺失模块、错误状态、权限漏洞、金额口径冲突等高影响问题时，在报告末尾输出六项：归属层、改什么、改成什么、影响范围、来源、建议处理。建议处理使用 spm-fix 回写 Design；不直接修改 Prototype、Design 或 PRD。

发现规格没有可靠 UI 承接位时，输出：事实、影响页面、缺失承接、来源、建议处理。不得用页面标题或不相关容器强行承载。

## 硬规则与最终自检

- 只有“原型不能直接展示且影响实现/验收”的内容进入 Mark；已经可见的字段、按钮、布局和普通交互不重复展示。
- 每条标注必须有页面/区域落点、可执行条件或结果、来源文件与章节，以及“已确认/待确认”状态；无内容的分组不展示。
- 进入测试的页面，最终判据是研发和测试只打开带标注原型、不打开 PRD，也能完成实现和验收判断。
- 同一角标只使用一个事实来源，不混合 Design 与 PRD；待确认内容不得展示为已确认规格。
- 角标使用 position: fixed 并挂载到 document.body；不插入目标元素内部。角标点击而非 hover 打开；浮窗与页面事件隔离。
- 副本 dist/ 只由 npm run build 生成；不使用外部 CDN、不引入 Python 标注脚本、不使用 Unix 专属复制命令或特定 Agent 协议。

最终完成条件：初始化或增量类型明确；可见内容未重复；不可见规格完整且有正确落点或无承接位记录；来源和状态可追溯；带标注原型通过“不打开 PRD”试读；副本构建和关键交互通过；原始 Prototype、PRD、Design 未修改；高影响意见已按结构化格式输出。

- 不能据此宣布的结论：Mark 完成只代表页面具备日常实现/验收所需的不可见规格，不代表原型已与 Design 全量一致，也不能替代 spm-prototype-review。
